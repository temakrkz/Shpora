# 1.11 API Gateway

## Короткий ответ

**API Gateway** — единая точка входа для всех внешних запросов в систему микросервисов: маршрутизация, авторизация, rate limiting (ограничение частоты), агрегация ответов. Клиенту не нужно знать адреса внутренних сервисов.

## Простыми словами

### Как это работает
```
Клиент → API Gateway → Маршрутизация к нужному сервису → Ответ клиенту
```

**Аналогия со стойкой регистрации в здании:**
- Посетитель приходит на один вход (API Gateway)
- Регистратор проверяет пропуск (авторизация)
- Направляет в нужный кабинет (маршрутизация)
- Не нужно знать, где какие кабинеты находятся

### Зачем нужен?
1. **Единый вход** — клиент обращается только к одному адресу
2. **Скрытие внутренней структуры** — клиент не знает о существовании микросервисов
3. **Централизация функций** — авторизация, логирование, rate limiting в одном месте

## Подробно

### Что это?

API Gateway — это **единый фасад** перед множеством микросервисов. Все внешние запросы идут через него, а он перенаправляет их к нужным сервисам.

**Пример:**
- Мобильное приложение банка обращается только к `https://api.bank.com`
- Gateway проверяет JWT-токен
- Направляет запрос в сервис счетов или переводов
- Ограничивает частоту запросов и логирует

### Зачем?

**Для клиента:**
- Не нужно знать адреса всех микросервисов
- Один адрес для всех запросов

**Для системы:**
- Централизованная авторизация
- Централизованное логирование
- Ограничение частоты (rate limiting) в одном месте
- Агрегация ответов из нескольких сервисов

### Как работает?

1. **Клиент отправляет запрос** → `https://api.bank.com/balance`
2. **Gateway принимает запрос:**
   - Проверяет JWT-токен (авторизация)
   - Проверяет лимиты (rate limiting)
   - Логирует запрос
3. **Gateway маршрутизирует к сервису** → `Сервис счетов`
4. **Сервис возвращает ответ** → Gateway передаёт клиенту

### Где используется?

- Микросервисные системы
- Когда есть много внутренних сервисов
- Когда нужно скрыть внутреннюю структуру от клиентов

### Особенности:
- Gateway — **единая точка входа**, но и **единая точка отказа/узкое место**
- Не должен содержать бизнес-логику
- Часто сочетается с BFF (Backend for Frontend)

## Пример из интернет-магазина

**Сценарий:** Мобильное приложение пользователя делает заказ

### Без API Gateway:
```
Приложение → Сервис заказов
Приложение → Сервис платежей
Приложение → Сервис доставки
Приложение → Сервис пользователей
```
**Проблема:** Приложение должно знать адреса всех сервисов

### С API Gateway:
```
Приложение → https://api.shop.com/order
           ↓ (Gateway)
Сервис заказов ← Ответ клиенту
```
**Преимущество:** Приложение знает только один адрес `https://api.shop.com`

## Плюсы/минусы подхода

| Преимущество | Объяснение |
|-------------|------------|
| **Единая точка входа** | Клиент обращается к одному адресу, не нужно знать о микросервисах |
| **Централизованное управление** | Авторизация, логирование, rate limiting в одном месте |
| **Скрытие внутренней структуры** | Внутренние сервисы можно менять без влияния на клиентов |
| **Агрегация ответов** | Gateway может склеивать ответы из нескольких сервисов |

| Недостаток | Объяснение |
|-----------|------------|
| **Единая точка отказа** | Если Gateway упадёт — вся система недоступна |
| **Узкое место** | Весь трафик проходит через один компонент |
| **Не должен содержать бизнес-логику** | Бизнес-логика должна быть в сервисах, а не в Gateway |

## Что важно запомнить аналитику

1. **API Gateway — единый вход**, скрывает внутренние сервисы от клиентов
2. Делает маршрутизацию, авторизацию, rate limiting
3. **Единая точка отказа** — нужна высокая доступность (резервное копирование)
4. Не должен содержать бизнес-логику — только технические функции

## Типичные вопросы и ответы

### Вопрос 1: Зачем нужен API Gateway в микросервисной архитектуре?

**Ответ:**
В микросервисной системе есть много внутренних сервисов (заказы, платежи, доставка). Если клиент будет обращаться к каждому из них напрямую, ему нужно будет знать все адреса. API Gateway решает эту проблему — он становится единым входом для всех клиентов и перенаправляет запросы к нужным сервисам.

**Дополнительно:**
- Централизуется авторизация (проверка JWT)
- Централизуется логирование
- Реализуется rate limiting в одном месте

---

### Вопрос 2: Чем API Gateway отличается от BFF?

**Ответ:**
- **API Gateway** — это общая техническая точка входа для всех клиентов. Он делает маршрутизацию, авторизацию, rate limiting.
- **BFF (Backend for Frontend)** — это специфичный для одного типа клиента слой, который агрегирует и адаптирует данные под конкретного клиента.

**Пример:**
- Gateway: `https://api.shop.com` (для всех клиентов)
- BFF: `https://api.shop.com/mobile`, `https://api.shop.com/web` (специфично для мобильного и веб)

---

### Вопрос 3: Что такое rate limiting?

**Ответ:**
Rate limiting — это ограничение частоты запросов от клиента. Например, "максимум 100 запросов в минуту". Это защищает систему от перегрузки и злоупотреблений.

**Где реализуется:** Часто в API Gateway, потому что удобно централизовать лимиты для всех клиентов.

---

## Практические вопросы для собеседования

### Вопрос 1: Как бы ты поступил, если нужно внедрить API Gateway в существующую систему микросервисов?

**Ответ:**
Я бы сначала уточнил у бизнес-заказчика и команды разработки:
1. Какие клиенты будут обращаться к системе (мобильные приложения, веб, партнёры)?
2. Какие функции нужны в Gateway (авторизация, rate limiting, логирование, агрегация)?
3. Какой стек технологий предпочтителен (Kong, Apigee, AWS API Gateway, самописный)?

**Что я бы предложил:**
- Внедрить API Gateway как единый вход для всех внешних запросов
- Настроить маршрутизацию к существующим сервисам
- Реализовать авторизацию через JWT
- Настроить rate limiting для защиты от перегрузки
- Включить логирование для мониторинга

**Что я бы уточнил:**
- Нужна ли агрегация ответов из нескольких сервисов?
- Требуется ли кэширование в Gateway?
- Как обрабатывать ошибки и таймауты?

---

### Вопрос 2: Как бы ты объяснил бизнесу, почему API Gateway — это единая точка отказа?

**Ответ:**
Я бы объяснил так:

"API Gateway — это как главный вход в здание. Все посетители приходят через него. Если этот вход заблокирован или сломан, никто не может попасть внутрь здания. То же самое с системой микросервисов — если API Gateway упадёт, все клиенты потеряют доступ к системе.

**Как мы это решаем:**
- Резервное копирование (несколько экземпляров Gateway)
- Автоматическое переключение на резервный экземпляр при ошибке
- Мониторинг и быстрое восстановление"

---

### Вопрос 3: Как бы ты поступил, если бизнес хочет добавить сложную логику в API Gateway?

**Ответ:**
Я бы сначала уточнил у бизнеса:
1. Какая именно логика нужна?
2. Насколько она важна для клиента?
3. Можно ли реализовать её в одном из микросервисов вместо Gateway?

**Почему это проблема:**
API Gateway должен делать только технические функции (маршрутизация, авторизация, rate limiting). Если добавить туда бизнес-логику:
- Gateway станет медленным и сложным
- Будет трудно поддерживать
- Нарушится принцип разделения ответственности

**Что я бы предложил:**
"Если логика связана с данными или бизнесом — лучше реализовать её в соответствующем микросервисе. API Gateway должен оставаться лёгким и быстрым, делая только технические функции."

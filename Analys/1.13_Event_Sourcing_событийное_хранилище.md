# 1.13 Event Sourcing (событийное хранилище): что такое, плюсы и минусы

---

## Короткий ответ

**Event Sourcing** — подход к хранению данных, при котором вместо сохранения текущего состояния системы сохраняются все события, которые привели к этому состоянию. Чтобы узнать текущее состояние, нужно "проиграть" все сохранённые события с начала.

---

## Простыми словами

### Аналогия с интернет-магазином

Представьте **журнал регистрации всех действий** в магазине:

| Обычное хранение | Event Sourcing |
|------------------|-----------------|
| Хранится только итоговый результат: "Заказ №123 — статус 'доставлен'" | Хранится вся история: "Заказ создан" → "Оплачен" → "Отправлен на склад" → "Доставлен курьером Ивановым" |

**Пример из интернет-магазина:**

Обычная система хранит в базе данных одну строку для заказа:
```
order_id: 123, status: 'delivered', created_at: '2024-01-15'
```

Event Sourcing хранит события:
```
event_1: OrderCreated(order_id=123, customer_id=456, timestamp='2024-01-15T10:00')
event_2: OrderPaid(order_id=123, amount=5000, timestamp='2024-01-15T10:05')
event_3: OrderShipped(order_id=123, courier='Ivanov', timestamp='2024-01-16T09:00')
event_4: OrderDelivered(order_id=123, delivered_by='Kuznetsov', timestamp='2024-01-17T14:30')
```

Чтобы узнать текущий статус заказа, система "проигрывает" все события от начала до конца.

### Аналогия с дневником

Обычная база данных — это как смотреть на **фотографию**: вы видите только результат (человек стоит в определённом месте).

Event Sourcing — это как читать **дневник**: вы видите всю историю того, что происходило (как человек пришёл, куда пошёл, что делал).

---

## Подробно

### Как работает Event Sourcing?

Вместо того чтобы хранить текущее состояние объекта (например, "статус заказа = 'доставлен'"), система хранит **список событий**, которые привели к этому состоянию.

**Основные компоненты:**

1. **Event Store (хранилище событий)** — база данных, которая хранит все события
2. **Aggregate (агрегат)** — логическая группа связанных событий (например, все события одного заказа)
3. **Command Handler** — обрабатывает команды и создаёт события
4. **Projection (проекция)** — преобразует историю событий в текущее представление для отображения

### Пример работы: изменение статуса заказа

| Шаг | Обычная БД | Event Sourcing |
|-----|------------|-----------------|
| 1. Заказ создан | Вставка строки: `status='created'` | Создание события: `OrderCreated` |
| 2. Заказ оплачен | Обновление: `UPDATE orders SET status='paid'` | Создание события: `OrderPaid` |
| 3. Заказ доставлен | Обновление: `UPDATE orders SET status='delivered'` | Создание события: `OrderDelivered` |

### Зачем используется Event Sourcing?

1. **Полная история изменений** — можно восстановить любое прошлое состояние системы, "проиграв" события до нужной точки
2. **Аудит и отладка** — видно не только что изменилось, но и когда, кем и почему
3. **Временные машины (Time Travel)** — можно посмотреть, как система выглядела в любой момент времени
4. **Создание проекций** — из одних и тех же событий можно строить разные представления: для пользователей, для аналитики, для отчётов

### Типы событий

| Тип события | Пример | Когда создаётся |
|-------------|--------|-----------------|
| **Командные события** | `OrderCreated`, `UserRegistered` | В ответ на действие пользователя или систему |
| **Фактические события** | `PaymentProcessed`, `InventoryUpdated` | Результат обработки команды |
| **Мета-события** | `SystemRebooted`, `DataMigrated` | Технические события о состоянии системы |

### Пример из интернет-магазина: история заказа

События для одного заказа:

```json
[
  { "type": "OrderCreated", "data": {"order_id": 123, "items": ["shirt"], "total": 5000}, "timestamp": "2024-01-15T10:00:00Z" },
  { "type": "PaymentInitiated", "data": {"payment_id": "pay_abc", "amount": 5000}, "timestamp": "2024-01-15T10:01:00Z" },
  { "type": "PaymentConfirmed", "data": {"payment_id": "pay_abc", "status": "success"}, "timestamp": "2024-01-15T10:02:00Z" },
  { "type": "OrderShipped", "data": {"tracking_number": "TRK123", "courier": "Ivanov"}, "timestamp": "2024-01-16T09:00:00Z" },
  { "type": "OrderDelivered", "data": {"delivered_at": "2024-01-17T14:30:00Z"}, "timestamp": "2024-01-17T14:30:00Z" }
]
```

Чтобы узнать текущий статус, система начинает с пустого состояния и последовательно применяет каждое событие.

## Плюсы и минусы Event Sourcing

### ✅ Плюсы

| Преимущество | Объяснение |
|-------------|------------|
| **Полная история** | Можно восстановить любое прошлое состояние системы |
| **Аудит по умолчанию** | Видно все изменения: что, когда и кем |
| **Временные машины** | Возможность посмотреть систему в любой момент времени |
| **Гибкость проекций** | Из одних событий можно строить разные представления для разных задач |
| **Отладка сложных процессов** | Можно проследить весь путь заказа или пользователя |

### ❌ Минусы

| Недостаток | Объяснение |
|-----------|------------|
| **Сложность реализации** | Требует специализированных решений и глубокого понимания |
| **Производительность чтения** | Нужно "проигрывать" события для получения текущего состояния (медленнее, чем чтение из обычной БД) |
| **Объём данных** | Хранится вся история — база может быстро расти |
| **Сложность отладки** | Трудно понять текущее состояние без анализа всей истории событий |
| **Не подходит для всех случаев** | Для простых CRUD-операций избыточно и неэффективно |

---

## Что важно запомнить аналитику

1. **Event Sourcing — это про историю, а не про состояние**. В обычной БД мы храним "что есть сейчас", в Event Sourcing — "как мы пришли к этому".

2. **Не путать с Pub/Sub**! Event Sourcing хранит события для восстановления состояния системы. Pub/Sub рассылает события другим сервисам. Это разные вещи, хотя и связаны.

3. **Проекции — ключевая концепция**. Из событий строятся обычные представления для пользователей (таблицы заказов, профили), чтобы не заставлять их "проигрывать" все события при каждом запросе.

4. **Идеален для доменных объектов** с важной историей: заказы, финансовые операции, настройки пользователей.

5. **Не подходит для простых данных**. Если нужно просто хранить и быстро читать состояние (например, кэш), Event Sourcing избыточен.

6. **Часто используется вместе с CQRS**, где запись идёт через события, а чтение — через проекции.

## ❓ Типичные вопросы и ответы

### Вопрос 1: В чём разница между Event Sourcing и обычным логированием?

**Ответ:**  
Логирование записывает факты о действиях (например, "пользователь вошёл в систему"), но не хранит состояние системы. Event Sourcing — это именно состояния: каждое событие меняет состояние объекта, и из всех событий можно восстановить текущее и прошлое состояние. Лог может быть частью Event Store, но они решают разные задачи.

---

### Вопрос 2: Почему Event Sourcing медленнее обычной БД при чтении?

**Ответ:**  
При обычном чтении мы просто выбираем строку из таблицы — это быстро (O(1)). В Event Sourcing нужно "проиграть" все события от начала до текущего момента, чтобы получить состояние. Это требует обработки множества записей. Поэтому для чтения обычно строят проекции — отдельные представления, которые обновляются при каждом событии и читаются как обычные данные.

---

### Вопрос 3: Когда стоит использовать Event Sourcing?

**Ответ:**  
Event Sourcing подходит когда:
- Важна полная история изменений (финансы, аудит)
- Нужно восстанавливать прошлые состояния системы ("что было в системе вчера в 14:00?")
- Сложные бизнес-процессы с множеством этапов
- Требуется гибкость для создания разных видов отчётов из одних данных

Не подходит для простых CRUD-систем, где важна только скорость чтения и не нужна история.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы ты объяснил бизнесу, почему Event Sourcing может быть медленнее при просмотре статуса заказа?

**Ответ:**  
Я бы сказал так: "Представьте, что вы смотрите на фотографию — она загружается мгновенно. Это как обычная база данных: мы просто показываем вам текущий статус. Event Sourcing работает иначе: чтобы показать статус, система должна 'прожить' всю историю вашего заказа от момента создания до доставки. Это занимает больше времени. Поэтому в системах с Event Sourcing часто строят специальные представления — они обновляются автоматически при каждом изменении и показываются мгновенно".

---

### Вопрос 2: Что делать, если нужно восстановить состояние системы на прошлую дату?

**Ответ:**  
В системе с Event Sourcing это делается так:
1. Находим все события до нужной даты/времени
2. Начинаем с пустого состояния
3. Последовательно применяем каждое событие из списка
4. Получаем точное состояние системы в этот момент

Это называется "временная машина" (Time Travel). В обычных БД для этого нужно делать сложные запросы или хранить полные копии данных на каждый момент времени, что гораздо сложнее и дороже.

---

### Вопрос 3: Как объяснить бизнесу необходимость хранения всей истории событий?

**Ответ:**  
Я бы объяснил так: "Представьте, что вы хотите узнать не только текущий статус заказа, но и весь путь: когда он был создан, когда оплачен, кто его доставил, сколько времени заняла доставка. В обычной системе эта информация разбросана по разным полям и трудно восстанавливается. Event Sourcing хранит всю историю в одном месте — это помогает выявлять проблемы, анализировать процессы и отвечать на вопросы 'что было раньше'".

# 1.14 CQRS (Command Query Responsibility Segregation): что такое, плюсы и минусы

---

## Короткий ответ

**CQRS (Command Query Responsibility Segregation)** — архитектурный паттерн, при котором операции записи (команды) и чтения (запросы) разделены на разные компоненты или модели данных. Это позволяет оптимизировать каждую часть под свои задачи.

---

## Простыми словами

### Аналогия с интернет-магазином

Представьте **административный офис** интернет-магазина:

| Часть офиса | Что делает | Как работает |
|-------------|------------|--------------|
| **Отдел заказов (команды)** | Принимает новые заказы, меняет статусы | Работает быстро, проверяет правила, сохраняет данные в основном хранилище |
| **Отдел отчётов (запросы)** | Генерирует статистику продаж, показывает профили клиентов | Имеет быстрые копии данных для мгновенного отображения |

**Пример из интернет-магазина:**

Когда клиент оформляет заказ:
1. **Команда** "Создать заказ" → отправляется в отдел заказов, данные сохраняются в основной базе
2. **Запрос** "Показать профиль клиента" → отделяется от отдела отчётов, показывает данные из оптимизированной копии

### Аналогия с рестораном

| Архитектура | Как работает в ресторане |
|-------------|-------------------------|
| **Обычная система** | Официант записывает заказ на кухню и одновременно показывает его на экране для клиента — одна таблица, две задачи |
| **CQRS** | Кухня (команды) получает заказ отдельно, а клиентский экран (запросы) показывает данные из отдельной таблицы с быстрой загрузкой |

## Подробно

### Как работает CQRS?

В паттерне CQRS система разделена на две части:

1. **Command side (сторона команд)** — отвечает за запись данных
   - Обрабатывает действия пользователя: "создать заказ", "изменить профиль"
   - Работает с основной моделью данных
   - Может включать валидацию, бизнес-правила, события

2. **Query side (сторона запросов)** — отвечает за чтение данных
   - Обрабатывает запросы: "показать список заказов", "получить профиль клиента"
   - Работает с оптимизированной моделью для быстрого чтения
   - Может использовать кэш, денормализацию, отдельные базы

### Пример из интернет-магазина

**Запись (Command):**
```
Клиент нажимает "Оформить заказ"
↓
Команда: CreateOrder(order_id=123, items=[shirt])
↓
Сохраняется в основную БД заказов
↓
Создаётся событие OrderCreated
```

**Чтение (Query):**
```
Клиент нажимает "Мои заказы"
↓
Запрос: GetOrdersForCustomer(customer_id=456)
↓
Читается из оптимизированной копии данных (денормализованная, с кэшем)
↓
Возвращается список заказов мгновенно
```

### Зачем используется CQRS?

1. **Оптимизация производительности** — запись и чтение имеют разные требования:
   - Запись: важна валидация, бизнес-логика, события
   - Чтение: нужна скорость, часто требуется денормализация

2. **Масштабируемость** — можно масштабировать чтение и запись независимо

3. **Гибкость моделей данных** — для чтения можно использовать денормализованные данные (быстрее), для записи — нормализованные (меньше дублирования)

4. **Разделение ответственности** — команды и запросы обрабатываются разными командами разработчиков

### Пример: профиль пользователя

| Операция | Обычная БД | CQRS |
|----------|------------|------|
| **Запись профиля** | UPDATE users SET name='Ivan', email='ivan@mail.com' | Команда сохраняется в основной БД, создаёт события |
| **Чтение профиля** | SELECT * FROM users WHERE id=123 (быстро) | Запрос читает из денормализованной копии с кэшем (ещё быстрее) |

В CQRS для чтения может существовать отдельная таблица или даже отдельная база данных, которая обновляется при каждом изменении профиля.

## Плюсы и минусы CQRS

### ✅ Плюсы

| Преимущество | Объяснение |
|-------------|------------|
| **Оптимизация производительности** | Чтение может использовать кэш и денормализацию для скорости, запись — валидацию и бизнес-логику |
| **Масштабируемость** | Можно масштабировать чтение и запись независимо друг от друга |
| **Гибкость моделей данных** | Для чтения можно хранить денормализованные данные, для записи — нормализованные |
| **Разделение ответственности** | Команды и запросы могут разрабатываться разными командами |
| **Поддержка событийной архитектуры** | Легко интегрируется с Pub/Sub и Event Sourcing |

### ❌ Минусы

| Недостаток | Объяснение |
|-----------|------------|
| **Сложность реализации** | Нужно поддерживать две модели данных и синхронизировать их |
| **Дополнительные компоненты** | Требуются механизмы обновления проекций при записи |
| **Проблемы согласованности** | Данные в двух моделях могут временно не совпадать ( eventual consistency) |
| **Не подходит для простых систем** | Для небольших приложений избыточно и усложняет архитектуру |
| **Труднее отладить** | Нужно отслеживать две разные модели данных |

## Что важно запомнить аналитику

1. **CQRS — это про разделение чтения и записи**. Не путать с Event Sourcing: CQRS может работать без него, просто разделяя запросы и команды на разные компоненты.

2. **Eventual consistency (согласованность в конечном счёте)** — данные в модели команд и модели запросов могут временно не совпадать. Это нормально для CQRS.

3. **Часто используется вместе с Event Sourcing** — команды создают события, которые обновляют проекции для чтения. Но это разные паттерны: CQRS отвечает на "как разделять", Event Sourcing — на "что хранить".

4. **Идеален для систем с неравномерной нагрузкой** — когда чтение в 10 раз чаще записи (например, дашборды аналитики).

5. **Не подходит для простых CRUD-систем**. Если у вас небольшой магазин или простая CRM, CQRS только усложнит архитектуру без реальной пользы.

6. **Проекции — ключевая концепция**. Для чтения создаются отдельные представления данных, которые обновляются при каждом изменении.

## ❓ Типичные вопросы и ответы

### Вопрос 1: В чём разница между CQRS и Event Sourcing?

**Ответ:**  
Это разные паттерны, которые часто используются вместе, но решают разные задачи:
- **CQRS** отвечает на вопрос "как разделить чтение и запись". Он говорит: "для записи используй одну модель, для чтения — другую".
- **Event Sourcing** отвечает на вопрос "что хранить". Он говорит: "не храни текущее состояние, а сохраняй все события, которые привели к этому состоянию".

Можно использовать CQRS без Event Sourcing (просто две разные БД), можно использовать Event Sourcing без CQRS (одно хранилище событий). Чаще всего их комбинируют.

---

### Вопрос 2: Что такое eventual consistency и почему это нормально в CQRS?

**Ответ:**  
Eventual consistency — это состояние, когда данные в разных частях системы могут временно не совпадать, но со временем придут в соответствие. В CQRS это происходит так: команда записывает данные в основную БД, а проекция для чтения обновляется с небольшой задержкой (через события или очереди). Пользователь может увидеть несоответствие на несколько секунд — это допустимо, если бизнес-процессы не требуют мгновенной согласованности.

---

### Вопрос 3: Когда стоит использовать CQRS?

**Ответ:**  
CQRS подходит когда:
- Чтение происходит в разы чаще записи (дашборды, профили)
- Нужно оптимизировать производительность чтения (кэш, денормализация)
- Система сложная и требует разделения ответственности между командами
- Требуется масштабирование разных частей системы независимо

Не подходит для простых систем с небольшим количеством операций и требованиями к согласованности данных.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы ты поступил, если бизнес просит добавить дашборд аналитики в реальном времени?

**Ответ:**  
Я бы уточнил требования:
- Какие именно метрики нужны (продажи, пользователи, конверсия)
- Насколько важна актуальность данных (секунды, минуты или часы задержки допустимы)
- Как часто обновляются данные в основной системе

Затем я бы предложил использовать CQRS: создать отдельную модель для чтения аналитики, которая будет оптимизирована под быстрые запросы. Данные можно обновлять через события из основной системы или периодически синхронизировать. Если нужна реальная актуальность — рассмотреть потоковую обработку данных.

---

### Вопрос 2: Что делать, если данные в модели чтения не совпадают с данными в модели записи?

**Ответ:**  
Это ожидаемая ситуация в CQRS (eventual consistency). Я бы уточнил у бизнеса:
- Какие данные критичны и требуют мгновенной согласованности
- Какие допустимы задержки

Для некритичных данных можно использовать механизмы автоматического обновления проекций через события. Для важных операций добавить проверку при чтении — если несоответствие обнаружено, предложить пользователю обновить данные или перепроверить в административной панели.

---

### Вопрос 3: Как объяснить бизнесу необходимость двух разных моделей данных?

**Ответ:**  
Я бы объяснил так: "Представьте, что вы ведёте бухгалтерию и одновременно обслуживаете клиентов. Бухгалтерия требует точных записей всех операций с проверками — это как модель записи в CQRS. Клиенты хотят быстро видеть свой баланс и историю — для этого нужна оптимизированная копия данных. Две модели позволяют сделать обе задачи эффективно: бухгалтерия не тормозит от быстрых запросов клиентов, а клиенты получают мгновенные ответы".

# 1.1 Монолит против микросервисов

## Короткий ответ
Монолит — это одна большая программа, где всё работает вместе. Микросервисы — это много маленьких программ, каждая отвечает за свою часть (например, один сервис для корзины, другой для оплаты).

## Простыми словами
Представьте интернет-магазин:

**Монолит** — как старый дом с одной большой комнатой. Всё в одном месте: касса стоит рядом с хранилищем товаров, складом заказов и отделом пользователей. Если что-то сломается — всё останавливается. Но плюс: легко запустить магазин, просто включить один выключатель.

**Микросервисы** — как современный офис с разными отделами в разных комнатах. Отдел оплаты работает отдельно от склада товаров. Если упадёт оплата — товары на складе останутся работать. Минус: нужно управлять многими дверями и коммуникациями между отделами.

## Подробно

### Что такое монолит?
Это **единая программа**, где все функции связаны вместе в одном коде. Когда пользователь делает заказ, система сразу проверяет: есть ли товар → сколько на складе → платит ли он → какой способ доставки. Всё это происходит в одной большой программе.

**Как работает:**
- Пользователь открывает сайт интернет-магазина
- Запрос попадает в одну большую программу
- Программа выполняет все действия по порядку (проверка товара, оплата, доставка)
- Результат возвращается пользователю

**Зачем нужен аналитику знать:**
Вам нужно понимать, что в монолите сложно добавлять новые функции. Если хотите добавить новую систему лояльности клиентов — придётся переписывать часть кода всей программы. Это долго и рискованно.

### Что такое микросервисы?
Это **несколько маленьких программ**, каждая из которых отвечает за одну функцию. Сервис корзины работает отдельно от сервиса оплаты, который работает отдельно от сервиса доставки. Они общаются между собой через специальные сообщения (как почта).

**Как работает:**
- Пользователь добавляет товар в корзину → запрос к сервису "Корзина"
- Пользователь нажимает "Оплатить" → запрос к сервису "Платежи", который сам спрашивает у сервиса "Корзина" сколько товаров
- Сервис "Доставка" узнаёт адрес из сервиса "Пользователи"

**Зачем нужен аналитику знать:**
В микросервисах можно развивать систему независимо. Хотите улучшить оплату? Переделываете только сервис платежей, не трогая остальные. Но нужно хорошо продумывать, как сервисы будут общаться друг с другом.

## Пример из интернет-магазина

### Монолитная система:
```
Пользователь → [Одна большая программа]
                ↓
    Проверка товара → Оплата → Доставка → Результат
```

**Что происходит:**
1. Пользователь добавляет iPhone в корзину
2. Большая программа проверяет, есть ли iPhone на складе
3. Та же программа обрабатывает оплату картой
4. И та же программа рассчитывает доставку
5. Всё это работает как один механизм — если что-то сломается, весь процесс останавливается

### Система на микросервисах:
```
Пользователь → Сервис "Корзина" 
                ↓ (сообщение)
Сервис "Оплата" ←(спрашивает у корзины сколько товаров)
                ↓ (сообщение)
Сервис "Доставка" ←(спрашивает у пользователей адрес)
```

**Что происходит:**
1. Пользователь добавляет iPhone в корзину → Сервис "Корзина" записывает это
2. Пользователь нажимает "Оплатить" → Сервис "Оплата" спрашивает у Сервиса "Корзина": сколько товаров?
3. Сервис "Доставка" спрашивает у Сервиса "Пользователи": какой адрес доставки?
4. Каждый сервис работает независимо — если упадёт оплата, товары в корзине останутся

## Плюсы и минусы

| Аспект | Монолит | Микросервисы |
|--------|---------|--------------|
| **Простота запуска** | ✅ Легко: один сервер | ❌ Сложно: много сервисов нужно настроить |
| **Развитие системы** | ❌ Сложно: всё связано | ✅ Легче: можно менять отдельные части |
| **Надёжность** | ❌ Всё или ничего: если упала оплата — не работает весь магазин | ✅ Устойчивее: падение одного сервиса не ломает другие |
| **Масштабирование** | ❌ Нужно увеличивать всю программу | ✅ Можно усилить только нагруженный сервис (например, оплату во время распродажи) |
| **Команды разработчиков** | ❌ Одна команда на весь проект | ✅ Разные команды могут работать параллельно |
| **Сложность для аналитика** | ⚠️ Проще: меньше точек взаимодействия | ⚠️ Сложнее: нужно понимать, как сервисы общаются |

## Что важно запомнить (для аналитика)

### 1. Как это влияет на ваши требования?
- **В монолите**: проще описать систему целиком, но сложнее вносить изменения
- **В микросервисах**: нужно думать по-другому — не "как работает весь магазин", а "какой сервис отвечает за что и как они общаются"

### 2. Какие вопросы задавать разработчикам?
- "Какие сервисы будут взаимодействовать при этом сценарии?"
- "Что будет, если один из сервисов упадёт во время заказа?"
- "Как данные передаются между сервисами?"

### 3. Пример для анализа:
**Сценарий**: Пользователь добавляет товар в корзину и сразу оплачивает его.

**В монолите вы спросите:**
- "Проверьте, есть ли товар на складе"
- "Обработайте оплату картой"
- "Покажите сообщение об успехе"

**В микросервисах вы спросите:**
- "Какой сервис отвечает за проверку наличия товара?"
- "Какой сервис обрабатывает платежи?"
- "Как они узнают друг о друге — через базу данных или специальные сообщения?"
- "Что будет, если сервис оплаты не ответит вовремя?"

## Практические вопросы для собеседования (junior/junior+)

**Вопрос 1: Что такое монолитная архитектура?**
Это когда все функции системы находятся в одной программе. Например, интернет-магазин с каталогом товаров, корзиной и оплатой — всё это одна программа. Плюсы: просто запускать и поддерживать. Минусы: сложно масштабировать и добавлять новые функции.

**Вопрос 2: Что такое микросервисная архитектура?**
Это когда система состоит из множества небольших независимых программ, каждая отвечает за одну функцию. Например, отдельный сервис для каталога товаров, отдельный для корзины, отдельный для оплаты. Плюсы: можно развивать систему независимо и масштабировать отдельные части. Минусы: сложнее управлять множеством сервисов.

**Вопрос 3: В чём главное отличие монолита от микросервисов?**
Главное отличие — в организации кода и взаимодействия компонентов. В монолите всё в одном коде, а в микросервисах каждая функция — отдельная программа, которая общается с другими через API или сообщения.

**Вопрос 4: Что будет, если упадёт сервис оплаты в микросервисной системе?**
Сервис корзины продолжит работать — товары останутся добавленными. Пользователь сможет позже оплатить их, когда сервис оплаты восстановится. Это называется отказоустойчивость.

**Вопрос 5: Когда стоит использовать монолит?**
- Для небольших проектов (например, сайт-визитка или небольшой магазин)
- Когда команда небольшая (до 10 человек)
- На начальном этапе разработки, когда неясно какие функции будут нужны
- При ограниченном бюджете на инфраструктуру

**Вопрос 6: Когда стоит использовать микросервисы?**
- Для крупных систем с миллионами пользователей
- Когда команда большая (50+ разработчиков) и работает параллельно над разными функциями
- Когда нужно масштабировать отдельные части системы
- Когда разные команды хотят использовать свои технологии

**Вопрос 7: Как аналитику работать с микросервисами?**
1. Понимать границы каждого сервиса — какие функции в нём и как он общается с другими
2. Документировать API между сервисами — чтобы команды понимали, как взаимодействовать
3. Продумывать обработку ошибок — что делать если один сервис не отвечает
4. Работать с командами разработчиков — понимать их архитектуру для написания требований

**Вопрос 8: Какие проблемы возникают при переходе от монолита к микросервисам?**
1. Сложность управления множеством сервисов и зависимостей между ними
2. Нужно настраивать инфраструктуру (серверы, сети, мониторинг)
3. Сервисы должны общаться друг с другом — это создаёт задержки
4. Труднее отлаживать систему из-за распределённости

**Вопрос 9: Какие проблемы возникают при использовании микросервисов?**
1. Сложность разработки — нужно управлять множеством сервисов и их зависимостями
2. Дороже — нужна сложная инфраструктура (серверы, сети, мониторинг)
3. Проблемы с коммуникацией — сервисы должны общаться друг с другом, что может создавать задержки
4. Труднее тестировать из-за распределённости

**Вопрос 10: Что такое отказоустойчивость в контексте микросервисов?**
Это способность системы продолжать работать даже если один из сервисов упал. Например, если упадёт сервис оплаты, каталог товаров и корзина продолжают работать.

## Итог для аналитика

Монолит — это просто, но сложно развивать. Микросервисы — сложнее в настройке, но гибче и надёжнее. Вам важно понимать разницу, чтобы правильно формулировать требования и задавать правильные вопросы разработчикам.

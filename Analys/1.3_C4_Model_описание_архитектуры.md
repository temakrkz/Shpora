# 1.3 C4 Model: описание архитектуры на разных уровнях детализации

## Короткий ответ

C4 Model — это метод описания архитектуры системы на четырёх уровнях детализации: от общего вида до деталей компонентов. Аналитик использует его для документирования и коммуникации с командой, чтобы каждый мог понять нужную ему часть системы.

## Простыми словами

### Аналогия со зданием

Представьте, что вы показываете здание архитектору:
1. **Уровень 0**: Фотография здания со спутника — видно только где оно находится
2. **Уровень 1**: План этажа — видно комнаты и их назначение  
3. **Уровень 2**: Детальный план комнаты — видны мебель и расположение
4. **Уровень 3**: Чертеж конкретной детали мебели

Так же и с архитектурой: от общего к деталям, чтобы каждый мог понять нужную ему часть.

## Подробно

### Четыре уровня C4 Model

#### Level 0: System Context (контекст системы)
**Что показывает:** Система в окружении других систем и пользователей.

**Пример для интернет-магазина:**
```
[Пользователи] → [Сайт магазина] ←→ [Сервис оплаты]
                          ↓
                    [База данных товаров]
```

**Зачем нужно аналитику:** Понимать, с какими внешними системами взаимодействует ваш продукт.

#### Level 1: Container (контейнеры)
**Что показывает:** Высокоуровневые компоненты системы и как они общаются.

**Контейнеры** — это исполняемые единицы: веб-приложение, мобильное приложение, микросервис, API gateway.

**Пример:**
```
[Веб-сайт] → [API Gateway] → [Сервис заказов]
                                    ↓
                          [Сервис пользователей]
                                    ↓
                          [База данных PostgreSQL]
```

#### Level 2: Component (компоненты)
**Что показывает:** Внутренние части контейнера и их взаимодействие.

**Пример для сервиса заказов:**
```
[Сервис заказов]
├─ [Обработка заказа]
├─ [Расчёт стоимости]
├─ [Уведомления]
└─ [Отчётность]
```

#### Level 3: Code (код) — редко используется аналитиками
**Что показывает:** Детали классов и модулей внутри компонентов.

### Пример из интернет-магазина

**Level 0 (Контекст):**
```
Клиенты → Интернет-магазин ←→ Платёжная система
                ↓
          Внутренние сервисы
```

**Level 1 (Контейнеры):**
```
Веб-сайт    Мобильное приложение   API Gateway
     \        /      \               /
      ──────┼─────────┼─────────────┼
            ↓         ↓             ↓
       Сервис заказов  Каталог    Корзина
```

**Level 2 (Компоненты в сервисе заказов):**
```
Сервис заказов:
├─ Обработка заказа
│  ├─ Проверка наличия товара
│  └─ Создание записи в БД
├─ Расчёт стоимости
│  ├─ Применение скидок
│  └─ Добавление доставки
└─ Уведомления
   ├─ Email клиенту
   └─ SMS менеджеру
```

## Плюсы и минусы C4 Model

| Аспект | Плюсы | Минусы |
|--------|-------|--------|
| **Понятность** | Каждый видит систему на уровне, который ему понятен | Нужно поддерживать актуальность диаграмм |
| **Коммуникация** | Упрощает общение с командой и заказчиками | Требует времени на создание и обновление |
| **Документирование** | Показывает эволюцию архитектуры со временем | Может стать громоздким для больших систем |

## Что важно запомнить аналитику

### 1. Начинать всегда с Level 0
Всегда показывайте контекст системы — это помогает понять, где находится ваш сервис в общей картине.

### 2. Не усложняйте
Если уровень 1 понятен заинтересованным сторонам, не переходите к деталям уровня 2.

### 3. Используйте для коммуникации
C4 Model — инструмент общения с командой, а не просто документация. Обновляйте диаграммы при изменениях архитектуры.

## Типичные вопросы и ответы

### Вопрос 1: Что такое C4 model для аналитика?
Это метод документирования архитектуры на четырёх уровнях детализации (Context, Container, Component, Code). Аналитик использует уровни 0-2 для описания системы, уровень 3 редко.

### Вопрос 2: Какие уровни детализации в C4 и когда что использовать?
- **Level 0**: Для общего понимания системы заинтересованными сторонами
- **Level 1**: Для разработчиков, чтобы понять высокоуровневую архитектуру
- **Level 2**: Для понимания внутренней структуры компонентов

### Вопрос 3: Как описывать архитектуру системы с помощью C4?
1. Начните с Level 0 — покажите систему в контексте других систем и пользователей
2. Перейдите к Level 1 — опишите основные контейнеры (сервисы, приложения)
3. При необходимости добавьте Level 2 — детали компонентов внутри контейнеров

## Практические вопросы для собеседования

### Вопрос 1: Как бы ты объяснил заказчику, зачем нужно показывать архитектуру на разных уровнях?

**Ответ:**
Я бы сказал: "Представьте, что вы хотите понять систему. Если я покажу вам все детали сразу — это будет слишком сложно. Но если я начну с общего вида (где находится ваш сервис среди других систем), а потом постепенно перейду к деталям только тех частей, которые вас интересуют — вы поймёте систему быстрее и проще".

---

### Вопрос 2: Как бы ты поступил, если разработчики не хотят обновлять диаграммы C4 после изменений в коде?

**Ответ:**
Я бы объяснил: "Диаграммы C4 помогают всем понимать архитектуру. Если они устаревают, новые сотрудники и даже опытные разработчики будут путаться. Я могу предложить автоматизировать обновление диаграмм из кода или ввести правило: 'обновить диаграмму вместе с релизом'".

---

### Вопрос 3: Как бы ты объяснил бизнесу, почему нужно учитывать внешние системы на уровне контекста?

**Ответ:**
Я бы сказал: "Ваш сервис не работает в вакууме. Платёжная система, служба доставки — всё это влияет на то, как ваш продукт работает для пользователя. Если мы не учтём эти зависимости, возможны проблемы: например, если платёжный шлюз изменит API, нам нужно будет адаптироваться".

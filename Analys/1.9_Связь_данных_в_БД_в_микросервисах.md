# 1.9 Связь данных в БД в микросервисах — как сервисы общаются друг с другом

---

## 📌 Короткий ответ

> В микросервисах каждый сервис имеет свою базу данных, поэтому данные связываются не через JOIN-запросы (как в монолите), а через **события** и **распределённые транзакции**. Это обеспечивает независимость сервисов, но требует понимания новых подходов к согласованности данных.

---

## 💡 Простыми словами

### В монолите:
> Пользователь делает заказ → Один запрос к БД → Всё готово! ✅

**Как это работает:** Все данные в одной базе, можно сразу проверить и обновить всё вместе.

### В микросервисах:
> Пользователь делает заказ → Сервис заказов создаёт заказ → Отправляет событие "Заказ создан" → Сервис платежей бронирует деньги (получает событие) → Сервис доставки создаёт доставку (получает событие)

**Как это работает:** Каждый сервис в своей базе, они общаются через события.

### Аналогия с рестораном:
> **Монолит**: Шеф повар готовит всё на одной кухне и сразу подаёт заказ  
> **Микросервисы**: Разные повара (мясо, овощи, соус) готовят отдельно → передают блюда официанту → официант собирает полный заказ

---

## 🔍 Подробно

### 1. Database per Service — каждый сервис в своей базе

> **Что это?** Каждый микросервис владеет своей собственной базой данных и не может напрямую читать данные других сервисов.

**Почему так?**
- Чтобы сервисы были независимыми (можно менять один без влияния на другие)
- Чтобы можно было использовать разные базы данных для разных сервисов

**Пример:**
- Сервис "Заказы" → своя база с заказами
- Сервис "Платежи" → своя база с транзакциями
- Сервис "Пользователи" → своя база с профилями

### 2. Проблема: как связывать данные между сервисами?

> В монолите мы делаем JOIN (объединяем таблицы), но в микросервисах это невозможно! Сервис заказов не может читать базу платежей — у них разные базы.

### 3. Решение: события как "клей" между сервисами

#### Что такое событие?
> Событие — это сообщение о том, что **что-то произошло**. Например:
- `Заказ создан`
- `Оплата прошла успешно`
- `Товар добавлен в корзину`

#### Как работают события?

**Шаги:**
1. Сервис создаёт данные в своей базе (например, создаёт заказ)
2. Одновременно отправляет событие другим сервисам через "почту" (брокер сообщений)
3. Другие сервисы получают события и реагируют на них

### Аналогия с почтой:
```
Сервис заказов пишет письмо "Заказ создан" → бросает в почтовый ящик
↓
Сервис платежей получает письмо → бронирует деньги
↓
Сервис доставки получает письмо → создаёт доставку
```

### 4. Проблема: как гарантировать, что событие ДОСТАВИТСЯ?

> **Сценарий:** Сервис создал заказ и отправил событие, но "почта" не получила его из-за сбоя. Теперь в базе есть заказ, а платежи не бронированы — **нарушена целостность!**

### 5. Решение: Transactional Outbox (транзакционная почтовая коробка)

> **Что это?** Гарантия, что событие будет отправлено вместе с созданием данных. Если данные не сохранились — событие тоже не отправится.

**Как работает:**
1. Сервис создаёт заказ в базе → сохраняет событие в "почтовый ящик" (таблица outbox)
2. После успешного сохранения → отправляет событие через "почту" (брокер сообщений)
3. Если что-то пошло не так → событие остаётся в ящике и будет отправлено позже

### Аналогия с отправкой письма:
```
1. Пишешь письмо → кладёшь в почтовый ящик ✅
2. Звонишь курьеру → он забирает письмо и отвозит получателю
3. Если курьер не пришёл — письмо остаётся в ящике, ты отправишь его позже
```

### 6. Решение: Паттерн Saga (для распределённых транзакций)

> **Что это?** Паттерн для выполнения **длинных операций**, которые затрагивают несколько сервисов. Вместо одной большой транзакции — последовательность шагов с возможностью отмены каждого шага.

#### Почему нужен?
> В монолите: Начинаем одну большую транзакцию → Создаём заказ → Бронируем деньги → Создаём доставку → Всё или ничего (COMMIT или ROLLBACK)  
> В микросервисах нельзя сделать так, потому что у каждого сервиса своя база. **Saga решает эту проблему!**

#### Как работает Saga?

**Шаги (успешный сценарий):**
1. Сервис заказов создаёт заказ ✅
2. Сервис платежей бронирует деньги ✅
3. Сервис доставки создаёт доставку ✅

**При ошибке (например, банк отказал в оплате):**
1. Отменяем бронирование денег ← компенсирующее действие для шага 2
2. Отменяем заказ ← компенсирующее действие для шага 1

### Аналогия с покупкой билета:
```
Успешно: Купил билет → Оплатил картой → Получил SMS
         ↓ (если оплата не прошла)
Отмена: Не оплатил ← Купить билет отменить нельзя, но можно вернуть деньги
```

### 7. Два подхода к реализации Saga

#### А) Оркестрация — есть дирижёр

> **Что это?** Отдельный сервис управляет всеми шагами и знает, что делать при ошибке.

**Аналогия с оркестром:**
- Дирижёр говорит каждому музыканту, когда играть
- Если один не играет — дирижёр останавливает всех

```
[Дирижёр] → [Сервис А] → [Сервис Б] → [Сервис В]
           ↓(если ошибка)→ [Откат Б] → [Откат А]
```

**Плюсы:** Проще отладка, всё в одном месте  
**Минусы:** Дирижёр может стать "бутылочным горлышком"

#### Б) Хореография — каждый сам по себе

> **Что это?** Сервисы не знают друг о друге. Каждый публикует события, а другие реагируют на них.

**Аналогия с танцами:**
- Нет дирижёра, каждый танцор сам решает, когда двигаться
- Танцор А делает движение → это заставляет Танцора Б сделать следующее

```
[Сервис А] ──(событие)──> [Брокер]
                          ↓
                     [Сервис Б] ──(событие)──> [Брокер]
                                      ↓
                                 [Сервис В]
```

**Плюсы:** Нет центральной точки отказа  
**Минусы:** Сложнее отладка, нужно понимать цепочку событий

### 8. Eventual Consistency (слабая согласованность)

> **Что это?** Данные в разных сервисах **не всегда согласуются мгновенно**, но со временем придут в соответствие.

**Аналогия с доставкой:**
```
12:00 — Сервис заказов видит новый заказ ✅
12:05 — Сервис платежей бронирует деньги (получил событие)
12:10 — Сервис доставки создаёт доставку (получил событие)
```

В промежуток времени 12:00–12:05 данные **не согласованы**:
- В сервисе заказов: заказ создан, но платежи не бронированы ❌
- Через 5 секунд после событий: всё согласовано ✅

**Когда подходит:**
- ✅ Для большинства бизнес-процессов (оформление заказа)
- ✅ Когда можно показать пользователю "заказ в обработке" вместо мгновенного подтверждения

**Когда НЕ подходит:**
- ❌ Финансовые операции, где нужна мгновенная согласованность
- ❌ Критичные системы (банкинг, медицина)

### 9. Event Sourcing (источник событий) — продвинутый паттерн

> **Что это?** Вместо хранения текущего состояния данных в базе, сохраняется **вся история изменений**.

**Обычная база:**
| id | статус    | когда_создан      |
|----|-----------|-------------------|
| 1  | готов     | 2026-09-04 10:00  |

**Event Sourcing:**
| событие_id | заказ_id | что_случилось         | когда          |
|------------|----------|-----------------------|----------------|
| 1          | 1        | Заказ создан          | 2026-09-04 10:00|
| 2          | 1        | Статус изменён на "оплачено" | 2026-09-04 10:05|
| 3          | 1        | Заказ готов           | 2026-09-04 10:10|

**Как узнать текущий статус?** Воспроизводим все события по порядку и применяем их к пустому состоянию.

**Плюсы:** Полная история всех изменений  
**Минусы:** Сложность реализации, нужно хранить всю историю

### 10. CQRS (разделение команд и запросов) — продвинутый паттерн

> **Что это?** Разделение операций **записи** (команды) и **чтения** (запросы).

**Как работает:**
- **Команды** (создать заказ, обновить профиль) → пишут в базу сервиса
- **Запросы** (просмотреть заказы) → читают из отдельной оптимизированной базы

### Аналогия с кухней ресторана:
```
Повар принимает заказ на кухне ← Запись (Command)
↓
Готовит блюдо
↓
Официант подаёт готовое блюдо клиенту ← Чтение (Query)
```

**Плюсы:** Оптимизация, можно использовать разные базы для записи и чтения  
**Минусы:** Сложность реализации, нужно поддерживать синхронизацию

## Пример из интернет-магазина

### Сценарий: Оформление заказа с оплатой и доставкой

**Участники:**
1. Сервис заказов — создаёт заказ
2. Сервис платежей — бронирует деньги
3. Сервис доставки — создаёт доставку

#### Успешный сценарий:

```
Шаг 1: Пользователь делает заказ
→ Сервис заказов создаёт заказ в своей базе ✅
→ Отправляет событие "Заказ создан" через брокер сообщений

Шаг 2: Сервис платежей реагирует на событие
→ Получает событие "Заказ создан"
→ Бронирует деньги пользователя ✅
→ Отправляет событие "Деньги забронированы"

Шаг 3: Сервис доставки реагирует на событие
→ Получает событие "Деньги забронированы"
→ Создаёт доставку заказа ✅
→ Отправляет событие "Доставка создана"

Результат: Заказ оформлен! 🎉
```

---

#### Сценарий с ошибкой (банк отказал в оплате):

```
Шаг 1: Сервис заказов создаёт заказ ✅
→ Отправляет событие "Заказ создан"

Шаг 2: Сервис платежей пытается забронировать деньги ❌
→ Ошибка: банк отказал

Шаг 3: Запускается откат (Saga rollback)
→ Отменяем бронирование денег ← компенсирующее действие
→ Отменяем заказ ← компенсирующее действие

Результат: Заказ отменён, деньги возвращены! 💰
```

---

### Плюсы/минусы подхода

#### ✅ Плюсы:

| Преимущество | Объяснение |
|-------------|------------|
| **Независимость сервисов** | Можно менять один сервис без влияния на другие |
| **Масштабируемость** | Можно масштабировать только перегруженные сервисы |
| **Технологическая свобода** | Разные сервисы могут использовать разные базы данных |
| **Отказоустойчивость** | Сбой одного сервиса не ломает всю систему |

#### ❌ Минусы:

| Недостаток | Объяснение |
|-----------|------------|
| **Сложность реализации** | Нужно понимать события, транзакции, Saga и т.д. |
| **Нет мгновенной согласованности** | Данные согласуются со временем (eventual consistency) |
| **Сложная отладка** | Нужно отслеживать цепочки событий между сервисами |
| **Дублирование данных** | Каждый сервис хранит свои данные, могут быть расхождения |

## 🎯 Что важно запомнить аналитику

### 1. Database per Service — фундамент микросервисов
> Каждый сервис владеет своей базой и не может напрямую читать данные других сервисов. Это обеспечивает независимость, но требует новых подходов к связыванию данных.

### 2. События — это "клей" между сервисами
> Сервисы общаются не напрямую, а через обмен событиями. Если один сервис что-то создаёт или меняет — он отправляет событие другим сервисам.

### 3. Transactional Outbox — гарантия доставки событий
> Паттерн, который гарантирует, что событие будет отправлено вместе с созданием данных. Если данные не сохранились — событие тоже не отправится.

### 4. Saga — решение для распределённых транзакций
> Вместо одной большой транзакции (как в монолите) — последовательность шагов с возможностью отмены каждого шага при ошибке.

### 5. Eventual Consistency (слабая согласованность)
> Данные в разных сервисах не всегда согласуются мгновенно, но со временем придут в соответствие. Это нормально для большинства бизнес-процессов.

### 6. Для junior-аналитика важно понимать:
- ✅ Как данные связаны между сервисами (через события)
- ✅ Что такое eventual consistency и когда она подходит
- ✅ Как работает Saga и компенсирующие действия
- ❌ Не нужно углубляться в технические детали реализации (код брокеров, схемы БД и т.д.)

## ❓ Типичные вопросы и ответы

### Вопрос 1: В чём разница между монолитом и микросервисами с точки зрения работы с данными?

> **Ответ:**  
В монолите все данные хранятся в одной базе данных, поэтому можно использовать JOIN для получения связанных данных из разных таблиц.

В микросервисах каждый сервис имеет свою БД:
- Нельзя делать JOIN между базами разных сервисов
- Данные связываются через события и асинхронную коммуникацию
- Используются паттерны Saga для распределённых транзакций

**Пример:**
```
Монолит: Один запрос к базе → JOIN таблиц → Готово! ✅

Микросервисы: Сервис А создаёт данные → отправляет событие → Сервис Б реагирует на событие ✅
```

---

### Вопрос 2: Что такое паттерн Saga и зачем он нужен?

> **Ответ:**  
Saga — это паттерн для выполнения операций, которые затрагивают несколько сервисов. Вместо одной большой транзакции используется последовательность шагов с возможностью отмены каждого шага при ошибке.

**Как работает (пример оформления заказа):**
```
Успешно: Создать заказ → Бронировать деньги → Создать доставку

При ошибке (например, оплата не прошла):
Отмена бронирования ← Отмена заказа
```

---

### Вопрос 3: Что такое eventual consistency (слабая согласованность)?

> **Ответ:**  
Eventual Consistency — это состояние системы, при котором данные **согласуются со временем**, а не мгновенно.

**Пример из интернет-магазина:**
```
12:00 — Сервис заказов видит новый заказ ✅
12:05 — Сервис платежей бронирует деньги (получил событие)
12:10 — Сервис доставки создаёт доставку (получил событие)
```

В промежуток времени 12:00–12:05 данные **не согласованы**, но через несколько секунд придут в соответствие. Это нормально для большинства бизнес-процессов.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы ты поступил, если нужно реализовать процесс оформления заказа в микросервисах?

**Ответ:**
Я бы разбил процесс на несколько шагов с использованием паттерна Saga:

```
Шаги саги (успешный сценарий):
1. Создать заказ в сервисе заказов → событие "Заказ создан"
2. Бронировать платеж в сервисе платежей → событие "Деньги забронированы"
3. Создать доставку в сервисе доставки → событие "Доставка создана"

При ошибке (например, оплата не прошла):
1. Отменить бронирование платежа ← компенсирующее действие для шага 2
2. Отменить заказ ← компенсирующее действие для шага 1
```

**Что я бы уточнил у бизнес-заказчика:**
- Какие именно шаги обязательны? Можно ли пропустить некоторые?
- Что делать, если несколько шагов идут одновременно (например, оплата и доставка)?
- Как долго ждать ответа от каждого сервиса?
- Какие компенсирующие действия нужны для каждого шага?

---

### Вопрос 2: Как бы ты объяснил разработчику, почему нельзя просто сделать JOIN между базами разных сервисов?

**Ответ:**
Я бы объяснил так:

"В микросервисной архитектуре каждый сервис имеет свою собственную базу данных. Это сделано намеренно для обеспечения независимости сервисов — если мы разрешим один сервис читать БД другого, то они станут зависимыми друг от друга. Это нарушит принцип микросервисов и сделает систему менее гибкой.

Вместо JOIN мы используем события:
1. Сервис создаёт данные в своей БД
2. Одновременно публикует событие о том, что произошло
3. Другие сервисы подписываются на эти события и реагируют на них

Это обеспечивает слабую согласованность (eventual consistency), но сохраняет независимость каждого сервиса."

---

### Вопрос 3: Как бы ты поступил, если данные в разных сервисах расходятся?

**Ответ:**
Я бы сначала уточнил у бизнес-заказчика:
1. Какие именно данные расходятся и как часто это происходит?
2. Насколько критично для бизнеса такое рассогласование?
3. Какой максимальный допустимый интервал рассогласования?

**Варианты решения:**

**Вариант А: Eventual Consistency (для большинства случаев)**
- Объяснить заказчику, что данные согласуются со временем (обычно в течение нескольких секунд)
- Это нормально для большинства бизнес-процессов

**Вариант Б: Reconciliation (примирение данных)**
- Запустить фоновый процесс, который сравнивает данные между сервисами и исправляет расхождения
- Подходит для критичных данных (балансы, остатки)

**Вариант В: Проверить работу событий**
- Убедиться, что все изменения передаются через события

## Итог

Тема **1.9 Связь данных в БД в микросервисах** охватывает ключевые концепции для junior-аналитиков:
- ✅ Database per Service — фундамент микросервисов
- ✅ Eventual Consistency — слабая согласованность вместо мгновенной
- ✅ Событийная модель — события как "клей" между сервисами
- ✅ Transactional Outbox — гарантия доставки событий вместе с транзакцией
- ✅ Saga — паттерн для распределённых транзакций (с возможностью отмены шагов)

Для junior-аналитика важно понимать **концепции** и уметь объяснять их бизнесу, а не углубляться в технические детали реализации.

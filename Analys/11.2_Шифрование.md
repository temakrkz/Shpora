# 11.2 Шифрование — защита данных с помощью математических алгоритмов

---

## 📌 Короткий ответ

> **Шифрование** — процесс преобразования данных в нечитаемый формат (шифртекст) с помощью ключа, чтобы только авторизованные пользователи могли прочитать их обратно. Это **'замок для данных'**: без ключа нельзя открыть и прочитать содержимое.

---

## 💡 Простыми словами

### Аналогия с интернет-магазинам

| Подход | Как работает |
|--------|--------------|
| **Без шифрования** | Данные хранятся в открытом виде: `password = "123456"` — любой, кто получит доступ к базе данных, увидит пароли! |
| **С шифрованием** | Данные преобразуются в нечитаемый формат: `password = "aB7#xK9$mPqR2@nL"` — даже если злоумышленник получит доступ к базе данных, он не сможет прочитать пароли без ключа! |

### Что такое шифрование?

> Это **'замок для данных'**: данные преобразуются в нечитаемый формат с помощью математического алгоритма и ключа. Только у кого есть ключ — может прочитать данные обратно.

**Пример из жизни:**
- **Без шифрования**: пароль `123456` хранится как `123456` → злоумышленник видит его сразу ❌
- **С шифрованием**: пароль `123456` хранится как `aB7#xK9$mPqR2@nL` → злоумышленник не может прочитать ❓

---

## 🔍 Подробно

### Как работает шифрование?

#### 1. **Исходные данные (plaintext)**

> Это **'открытый текст'** — данные в читаемом виде, которые нужно защитить.

**Пример:**
```
Пользователь вводит пароль: "mysecretpassword"
Это plaintext (открытый текст) ❌
```

#### 2. **Шифрование (encryption)**

> Процесс преобразования открытых данных в нечитаемый формат с помощью алгоритма и ключа.

**Пример:**
```
Пароль: "mysecretpassword"
Алгоритм шифрования: AES-256
Ключ: "supersecretkey123"

Результат (шифртекст): "8f7d9e2a1b4c6f8e0d3a5b7c9e1f4g6h8j0k2l4m6n8p0q2r4s6t8u0v2w4x6y8z" ✅✅
```

#### 3. **Шифртекст (ciphertext)**

> Это **'зашифрованные данные'** — нечитаемый формат, который невозможно прочитать без ключа.

**Пример:**
```
Шифртекст: "8f7d9e2a1b4c6f8e0d3a5b7c9e1f4g6h8j0k2l4m6n8p0q2r4s6t8u0v2w4x6y8z" ✅✅
```

#### 4. **Дешифрование (decryption)**

> Процесс преобразования шифртекста обратно в читаемый формат с помощью ключа.

**Пример:**
```
Шифртекст: "8f7d9e2a1b4c6f8e0d3a5b7c9e1f4g6h8j0k2l4m6n8p0q2r4s6t8u0v2w4x6y8z"
Ключ: "supersecretkey123"

Результат (plaintext): "mysecretpassword" ✅✅
```

### Виды шифрования

#### 1. **Симметричное шифрование**

> Используется **один и тот же ключ** для шифрования и дешифрования.

**Как работает:**
```
Ключ: "supersecretkey123"

Шифрование: plaintext + ключ → ciphertext ✅✅
Дешифрование: ciphertext + ключ → plaintext ✅✅
```

**Пример из интернет-магазина:**
- Сервер шифрует данные пользователя с помощью ключа `K`
- При дешифровании используется тот же самый ключ `K`

**Плюсы:**
- Быстро и эффективно
- Простая реализация

**Минусы:**
- Нужно безопасно передавать ключ всем участникам
- Если ключ украден — все данные расшифровываются злоумышленником

#### 2. **Асимметричное шифрование**

> Используется **два разных ключа**: открытый (public) и закрытый (private).

**Как работает:**
```
Открытый ключ: "public_key_123" (можно распространять всем)
Закрытый ключ: "private_key_456" (хранится только у владельца)

Шифрование с открытым ключом → дешифрование закрытым ✅✅
Подпись закрытым ключом → проверка подписи открытым ✅✅
```

**Пример из интернет-магазина:**
- Сервер публикует открытый ключ на сайте
- Браузер пользователя шифрует данные с помощью открытого ключа сервера
- Сервер дешифрует данные с помощью своего закрытого ключа

**Плюсы:**
- Безопасная передача данных (не нужно передавать секретный ключ)
- Возможность цифровой подписи

**Минусы:**
- Медленнее симметричного шифрования
- Сложнее в реализации

### Алгоритмы шифрования

#### 1. **AES (Advanced Encryption Standard)**

> Самый популярный алгоритм симметричного шифрования. Используется для защиты данных при хранении.

**Пример из интернет-магазина:**
```
Задача: "Защитить данные пользователя в базе данных"

Решение:
- Используем AES-256 (самый безопасный вариант)
- Пароль пользователя шифруется перед сохранением в БД
- Даже если злоумышленник получит доступ к БД, он не сможет прочитать пароли без ключа ✅✅
```

#### 2. **RSA**

> Алгоритм асимметричного шифрования. Используется для безопасной передачи данных по сети.

**Пример из интернет-магазина:**
```
Задача: "Передать данные карты платёжному шлюзу безопасно"

Решение:
1. Сервер генерирует пару ключей (открытый + закрытый)
2. Отправляет открытый ключ пользователю
3. Пользователь шифрует данные карты с помощью открытого ключа сервера
4. Сервер дешифрует данные с помощью своего закрытого ключа ✅✅

→ Данные карты передаются по сети в зашифрованном виде! ✅✅
```

#### 3. **SHA (Secure Hash Algorithm)**

> Не является шифрованием, а используется для создания **'цифрового отпечатка'** данных.

**Как работает:**
```
Данные: "mysecretpassword"
Алгоритм: SHA-256

Результат (хеш): "aB7#xK9$mPqR2@nL4cV8eT1fG3hJ5kN7oQ9rS2tU4vW6xY8zA0bC1dE3fG5" ✅✅

Важно: хеш нельзя обратить обратно!
→ Это не шифрование, а 'цифровой отпечаток' данных ✅✅
```

**Пример из интернет-магазина:**
```
Задача: "Проверить, что пароль пользователя верный"

Решение:
1. При регистрации: хешируем пароль и сохраняем в БД
   Пароль: "mysecretpassword" → Хеш: "aB7#xK9$mPqR2@nL4cV8eT1fG3hJ5kN7oQ9rS2tU4vW6xY8zA0bC1dE3fG5" ✅✅

2. При входе: хешируем введенный пароль и сравниваем с сохранённым
   Введён: "mysecretpassword" → Хеш: "aB7#xK9$mPqR2@nL4cV8eT1fG3hJ5kN7oQ9rS2tU4vW6xY8zA0bC1dE3fG5" ✅✅
   → Пароли совпадают! Вход разрешён ✅✅

Важно: мы никогда не храним пароли в открытом виде! ✅✅
```

### Где используется шифрование?

| Место | Что защищается | Какой алгоритм | Пример из интернет-магазина |
|-------|----------------|----------------|----------------------------|
| **База данных** | Пароли пользователей, номера карт | AES-256 | Пароль пользователя хранится зашифрованным ✅✅ |
| **Передача по сети** | Данные при оплате карты | TLS/SSL (RSA + AES) | Данные карты передаются по защищённому каналу ✅✅ |
| **Файлы на диске** | Резервные копии, конфигурации | AES-256 | Резервная копия базы данных зашифрована ✅✅ |
| **Уведомления** | Содержимое email/SMS | Симметричное шифрование | Email с деталями заказа зашифрован ✅✅ |

### Примеры использования в интернет-магазине

#### 1. **Защита паролей пользователей**

```
Сценарий: "Регистрация пользователя"

Шаги:
1. Пользователь вводит пароль: "mysecretpassword"
2. Сервер хеширует пароль с помощью SHA-256
   Пароль → Хеш: "aB7#xK9$mPqR2@nL4cV8eT1fG3hJ5kN7oQ9rS2tU4vW6xY8zA0bC1dE3fG5" ✅✅
3. Хеш сохраняется в базе данных (не сам пароль!) ✅✅

При входе:
1. Пользователь вводит пароль: "mysecretpassword"
2. Сервер хеширует введенный пароль → тот же хеш ✅✅
3. Сравнивает с сохранённым хешем → совпадают! ✅✅
4. Разрешает вход ✅✅

Важно: мы никогда не храним пароли в открытом виде! ✅✅
```

#### 2. **Защита данных карты при оплате**

```
Сценарий: "Оплата картой"

Шаги:
1. Пользователь вводит данные карты на сайте
2. Браузер шифрует данные с помощью TLS/SSL (RSA + AES) ✅✅
3. Данные передаются по защищённому каналу к платёжному шлюзу ✅✅
4. Платёжный шлюз дешифрует данные и обрабатывает оплату ✅✅

Важно: даже если злоумышленник перехватит данные в сети, он не сможет прочитать их без ключа! ✅✅
```

#### 3. **Защита данных в базе данных**

```
Сценарий: "Хранение персональных данных"

Шаги:
1. Пользователь заполняет форму с персональными данными (имя, телефон, адрес)
2. Данные шифруются с помощью AES-256 перед сохранением в БД ✅✅
3. При чтении данные дешифруются с помощью ключа ✅✅

Важно: даже если злоумышленник получит доступ к базе данных, он не сможет прочитать персональные данные без ключа! ✅✅
```

## ⚖️ Плюсы и минусы шифрования

### ✅ Плюсы

| Преимущество | Объяснение | Пример из жизни |
|-------------|------------|-----------------|
| **Защита конфиденциальных данных** | Даже при утечке базы данных злоумышленник не сможет прочитать данные без ключа | Пароли пользователей хранятся в зашифрованном виде — даже если база украдена, пароли недоступны ✅✅ |
| **Соответствие требованиям безопасности** | Многие стандарты (PCI DSS для карт, GDPR для персональных данных) требуют шифрования | Интернет-магазин должен шифровать данные карт по PCI DSS ✅✅ |
| **Защита при передаче по сети** | Данные защищены от перехвата в процессе передачи | Данные карты передаются по защищённому каналу TLS/SSL ✅✅ |

### ❌ Минусы

| Недостаток | Объяснение | Пример из жизни |
|-----------|------------|-----------------|
| **Производительность** | Шифрование требует вычислительных ресурсов | Зашифровать 1 ГБ данных может занять несколько секунд — это медленно ✅✅ |
| **Управление ключами** | Нужно безопасно хранить и передавать ключи | Если ключ украден — все данные расшифровываются злоумышленником ✅✅ |
| **Сложность реализации** | Ошибки в реализации могут сделать шифрование бесполезным | Неправильное хранение ключей → утечка данных ✅✅ |

## 🎯 Что важно запомнить аналитику

### 1. Шифрование — это **'замок для данных'**

> Данные преобразуются в нечитаемый формат с помощью алгоритма и ключа. Только у кого есть ключ — может прочитать данные обратно.

**Что я бы делал:**
- Требую шифрования всех конфиденциальных данных (пароли, номера карт)
- Убеждаюсь, что ключи хранятся безопасно
- Проверяю соответствие требованиям безопасности (PCI DSS, GDPR)

### 2. Разница между шифрованием и хешированием

> **Шифрование** — можно обратить обратно (нужен ключ).  
> **Хеширование** — нельзя обратить обратно (цифровой отпечаток).

| Аспект | Шифрование | Хеширование |
|--------|------------|-------------|
| **Можно ли обратить?** | Да, с помощью ключа | Нет, это 'цифровой отпечаток' |
| **Для чего используется** | Защита данных при хранении и передаче | Проверка целостности паролей |
| **Пример из интернет-магазина** | Пароль пользователя шифруется перед сохранением в БД ✅✅ | Пароль хешируется для проверки при входе ✅✅ |

### 3. AES vs RSA — когда что использовать?

> **AES** — симметричное шифрование, быстро, для защиты данных при хранении.  
> **RSA** — асимметричное шифрование, медленнее, для безопасной передачи данных по сети.

| Аспект | AES (симурическое) | RSA (асимметричное) |
|--------|-------------------|--------------------|
| **Ключи** | Один и тот же для шифрования и дешифрования | Два ключа: открытый + закрытый |
| **Скорость** | Быстро ✅✅ | Медленнее ❌ |
| **Для чего используется** | Защита данных при хранении (БД, файлы) | Безопасная передача по сети (TLS/SSL) |
| **Пример из интернет-магазина** | Пароль пользователя в БД шифруется AES-256 ✅✅ | Данные карты передаются по TLS/SSL (RSA + AES) ✅✅ |

### 4. Хеширование паролей — это не шифрование!

> **Важно:** пароли хешируются, а не шифруются!  
> Хеш нельзя обратить обратно, поэтому даже если злоумышленник получит доступ к БД, он не сможет восстановить пароль.

**Что я бы делал:**
- Требую использования современных алгоритмов хеширования (bcrypt, Argon2)
- Убеждаюсь, что пароли никогда не хранятся в открытом виде
- Проверяю, что хеширование происходит на сервере, а не в браузере

### Вопрос 3: Как работает защита данных карты при оплате?

**Ответ:**

Защита данных карты — это комплекс мер, включающий несколько технологий:

```
Сценарий: "Оплата картой"

1. Передача по сети (TLS/SSL):
   → Браузер шифрует данные с помощью открытого ключа сервера ✅✅
   → Сервер дешифрует с помощью закрытого ключа ✅✅
   → Данные передаются по защищённому каналу ✅✅

2. Хранение в БД (AES-256):
   → Данные карты шифруются перед сохранением ✅✅
   → Даже при утечке БД злоумышленник не сможет прочитать данные без ключа ✅✅

3. Токенизация:
   → Номер карты заменяется на токен (уникальный идентификатор) ✅✅
   → Реальный номер карты хранится только у платёжного шлюза ✅✅
   → Интернет-магазин работает с токенами, а не с реальными данными карт ✅✅

Важно: интернет-магазин часто вообще не хранит данные карт! ✅✅
```

**Что я бы требовал:**
- Соответствие стандарту PCI DSS (для обработки карт) ✅✅
- Использование токенизации вместо хранения реальных данных карт ✅✅
- TLS/SSL для всех соединений по сети ✅✅

### Вопрос 4: Что такое TLS/SSL и как они связаны с шифрованием?

**Ответ:**

> **TLS (Transport Layer Security)** — протокол безопасной передачи данных по сети.  
> **SSL (Secure Sockets Layer)** — предыдущая версия TLS, сейчас используется редко.

**Как работает TLS:**

```
1. Подключение:
   → Браузер и сервер обмениваются сертификатами ✅✅
   → Сервер отправляет свой открытый ключ ✅✅
   → Браузер проверяет сертификат (выдан ли доверенным центром) ✅✅

2. Шифрование канала:
   → Браузер генерирует сессионный ключ ✅✅
   → Сессионный ключ шифруется открытым ключом сервера ✅✅
   → Сервер дешифрует сессионный ключ закрытым ключом ✅✅

3. Передача данных:
   → Все данные шифруются сессионным ключом (AES) ✅✅
   → Данные передаются по защищённому каналу ✅✅

Важно: TLS использует как симметричное (AES), так и асимметричное (RSA) шифрование! ✅✅
```

**Пример из интернет-магазина:**
```
URL сайта: https://shop.example.com/

https — это TLS в действии! ✅✅
→ Все данные, передаваемые между браузером и сайтом, зашифрованы ✅✅
→ Данные карты при оплате защищены ✅✅
→ Персональные данные защищены ✅✅
```

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы ты объяснил разработчику, почему нужно шифровать пароли в БД?

**Ответ:**

Я бы сказал:

> "Представьте, что мы храним пароли пользователей в открытом виде.
>
> **Сценарий 1: Утечка базы данных**
> → Злоумышленник получает доступ к БД ✅✅
> → Видит все пароли в открытом виде: 'password123', 'admin' и т.д. ✅✅
> → Пользователи меняют пароли, но злоумышленники тоже знают их ✅✅
> → Атаки на аккаунты пользователей (фишинг, брутфорс) ✅✅
>
> **Сценарий 2: Пароли зашифрованы**
> → Злоумышленник получает доступ к БД ✅✅
> → Видит только шифртекст: '8f7d9e2a1b4c6f8e0d3a5b7c9e1f4g6h8j0k2l4m6n8p0q2r4s6t8u0v2w4x6y8z' ✅✅
> → Без ключа не может прочитать пароли ✅✅
> → Атаки на аккаунты пользователей невозможны (без ключа) ✅✅

**Важно:** шифрование паролей — это требование безопасности PCI DSS и GDPR! ✅✅"

### Вопрос 2: Как бы ты объяснил заказчику, почему нужно использовать HTTPS?

**Ответ:**

Я бы сказал:

> "HTTPS (HyperText Transfer Protocol Secure) — это защищённая версия HTTP.
>
> **Без HTTPS (HTTP):**
> → Данные передаются в открытом виде по сети ✅✅
> → Злоумышленник может перехватить данные (номер карты, пароль, адрес доставки) ✅✅
> → Пользователь не доверяет сайту (браузер показывает предупреждение 'Небезопасное соединение') ✅✅
>
> **С HTTPS:**
> → Все данные шифруются между браузером и сервером ✅✅
> → Даже если злоумышленник перехватит данные, он не сможет прочитать их без ключа ✅✅
> → Пользователь видит 'Защищённое соединение' (иконка замка в браузере) ✅✅
> → Доверие пользователей к сайту растёт ✅✅

**Пример из интернет-магазина:**
```
URL сайта: https://shop.example.com/

https — это TLS в действии! ✅✅
→ Все данные, передаваемые между браузером и сайтом, зашифрованы ✅✅
→ Данные карты при оплате защищены ✅✅
→ Персональные данные защищены ✅✅
```

### Вопрос 3: Какие требования безопасности нужно учесть при проектировании интернет-магазина?

**Ответ:**

Я бы выделил следующие категории требований:

1. **Шифрование данных**
   - Шифрование персональных данных в БД (AES-256) ✅✅
   - Хеширование паролей (bcrypt, Argon2) ✅✅
   - TLS/SSL для всех соединений по сети ✅✅

2. **Управление доступом**
   - Аутентификация пользователей (пароль + 2FA) ✅✅
   - Авторизация (RBAC — роли и права доступа) ✅✅
   - Логирование действий пользователей ✅✅

3. **Защита от атак**
   - Защита от SQL-инъекций (подготовка запросов) ✅✅
   - Защита от XSS (экранирование вывода) ✅✅
   - Rate limiting (ограничение количества запросов) ✅✅

4. **Соответствие стандартам**
   - PCI DSS для обработки карт ✅✅
   - GDPR для персональных данных ✅✅
   - Локальные требования по защите данных (152-ФЗ в РФ) ✅✅

**Что я бы требовал:**
- Провести аудит безопасности перед релизом ✅✅
- Регулярные обновления зависимостей и библиотек ✅✅
- Тестирование на проникновение (pentest) перед каждым релизом ✅✅

### Вопрос 4: Как бы ты поступил, если разработчик хочет хранить пароли в открытом виде для удобства?

**Ответ:**

Я бы **категорически отказал**:

   ```
   Риск 1: Утечка базы данных

   Риск 2: Атаки на аккаунты пользователей

   ```

2. **Предложил бы альтернативы:**
   - "Можно ли улучшить UX без нарушения безопасности?"

3. **Привлёк бы экспертов по безопасности:**
   - Если разработчик настаивает — подключил security-специалиста
   - Провёл бы оценку рисков и объяснил последствия

4. **Документировал бы решение:**
   - Зафиксировал отказ в письменном виде
   - Объяснил, почему это требование безопасности

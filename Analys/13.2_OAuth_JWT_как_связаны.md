# 13.2 OAuth и JWT: как связаны протокол делегирования доступа и формат токена

---

## 📌 Короткий ответ

> **OAuth 2.0** — это **'протокол'**, который описывает, как выдать права доступа к ресурсам без передачи пароля (например, "войти через Google").  
> **JWT (JSON Web Token)** — это **'формат токена'**, в котором хранятся данные о пользователе и его правах.  
> **OAuth часто использует JWT** как формат токена, но это не одно и то же: OAuth — про выдачу прав, JWT — про формат хранения этих прав.

---

## 💡 Простыми словами

### Аналогия с интернет-магазином

| Подход | Как работает |
|--------|--------------|
| **Без OAuth** | Чтобы купить товар на стороннем сайте, нужно передать пароль от своего аккаунта — небезопасно! ❌ |
| **С OAuth** | Нажимаешь "Войти через Google" → Google выдаёт токен доступа → сторонний сайт использует токен для получения данных (имя, email) без пароля ✅✅ |

### Что такое OAuth?

> Это **'протокол делегирования доступа'**: вы можете разрешить приложению доступ к своим данным без передачи пароля.

**Пример из жизни:**
- Вы хотите купить товар на сайте, который не знаете
- Вместо того чтобы вводить пароль от своего аккаунта Google/Яндекс — нажимаете "Войти через Google" ✅✅
- Google выдаёт токен доступа сайту (не ваш пароль!) ✅✅
- Сайт использует токен для получения ваших данных (имя, email) ✅✅

### Что такое JWT?

> Это **'формат токена'**: подписанная структура с данными о пользователе и его правах.

**Пример из жизни:**
```
Токен доступа:
{
  "user_id": 123,
  "email": "user@example.com",
  "roles": ["buyer"],
  "expires_at": "2025-12-31T23:59:59Z"
}

Этот токен подписан секретным ключом → сайт проверяет подпись и доверяет данным ✅✅
```

## 🔍 Подробно

### OAuth 2.0 — протокол делегирования доступа

#### Что такое делегирование?

> **Делегирование** — передача прав другому лицу или приложению без передачи пароля.

**Пример из жизни:**
- Вы доверяете другу доступ к своей квартире на вечеринку (но не пароль от двери) ✅✅
- Вы доверяете Google доступ к своим контактам для входа в сторонний сервис ✅✅

#### Как работает OAuth 2.0?

**Пошаговый процесс:**

```
1. Пользователь хочет получить доступ к ресурсу
   → Например: "Купить товар на сайте, который не знаю"

2. Пользователь переходит по ссылке авторизации
   → https://shop.example.com/auth?redirect_uri=...&response_type=code&client_id=xyz

3. Пользователь выбирает способ входа (например, Google)
   → Перенаправляется на: https://accounts.google.com/...

4. Пользователь вводит свои данные и разрешает доступ
   → "Разрешить сайту shop.example.com доступ к моим данным?" ✅✅
   → Нажимаем "Разрешить" ✅✅

5. Google возвращает код авторизации (authorization code)
   → https://shop.example.com/callback?code=abc123xyz

6. Сервер shop.example.com обменивает код на токен доступа
   → Отправляет запрос к Google с кодом и client_secret
   → Google возвращает access_token ✅✅

7. Сервер использует токен для получения данных пользователя
   → https://oauth.googleapis.com/tokeninfo?access_token=abc123xyz
   → Получаем: { "user_id": 123, "email": "user@example.com" } ✅✅

8. Сервер создаёт сессию для пользователя и разрешает доступ к ресурсам ✅✅
```

#### Компоненты OAuth 2.0

| Компонент | Что это | Пример из интернет-магазина |
|----------|---------|----------------------------|
| **Resource Owner** (владелец ресурса) | Пользователь, который хочет получить доступ | Вы, пользователь Google аккаунта ✅✅ |
| **Client** (клиент) | Приложение, которое запрашивает доступ | Сайт shop.example.com ✅✅ |
| **Authorization Server** (сервер авторизации) | Сервис, который выдаёт токены | Google OAuth сервер ✅✅ |
| **Resource Server** (сервер ресурсов) | Сервис, у которого есть данные | API Google (имя, email) ✅✅ |

#### Флавы OAuth 2.0

OAuth 2.0 имеет несколько сценариев использования:

1. **Authorization Code Flow** — для веб-приложений
   ```
   Пользователь → Авторизация → Код авторизации → Обмен на токен → Доступ к ресурсам ✅✅
   ```

2. **Implicit Flow** — для SPA (Single Page Applications)
   ```
   Пользователь → Авторизация → Токен сразу в ответе → Использование токена ✅✅
   ```

3. **Client Credentials Flow** — для машин-к-машине взаимодействия
   ```
   Сервер 1 → Запрос токена с client_secret → Токен доступа → Доступ к ресурсам ✅✅
   ```

### JWT (JSON Web Token) — формат токена

#### Что такое JWT?

> **JWT** — это **'подписанная структура данных'**, которая хранит информацию о пользователе и его правах.

**Пример JWT:**
```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

Это один длинный строка, состоящая из трёх частей:

1. **Header** (заголовок) — алгоритм и тип токена
   ```json
   {
     "alg": "HS256",  // Алгоритм подписи
     "typ": "JWT"      // Тип токена
   }
   ```

2. **Payload** (нагрузка) — данные о пользователе и правах
   ```json
   {
     "sub": "1234567890",  // subject (идентификатор пользователя)
     "name": "John Doe",    // имя пользователя
     "iat": 1516239027,     // issued at (время создания)
     "roles": ["buyer"],    // роли пользователя
     "email": "user@example.com"
   }
   ```

3. **Signature** (подпись) — проверка целостности и аутентичности
   ```
   HMACSHA256(
     base64UrlEncode(header) + "." + base64UrlEncode(payload),
     secret_key
   )
   ```

#### Как работает JWT?

**Пошаговый процесс:**

```
1. Сервер авторизации создаёт JWT с данными пользователя
   → { "user_id": 123, "email": "user@example.com", "roles": ["buyer"] } ✅✅
   → Подписывает токен секретным ключом ✅✅
   → Возвращает пользователю в ответе на авторизацию ✅✅

2. Пользователь сохраняет токен (обычно в localStorage или cookie) ✅✅

3. При каждом запросе к защищённому ресурсу пользователь отправляет токен
   → GET /api/orders HTTP/1.1
     Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9... ✅✅

4. Сервер проверяет подпись токена (с помощью секретного ключа)
   → Если подпись верна — данные доверены ✅✅
   → Если подпись неверна — токен поддельный ❌

5. Сервер читает payload и разрешает доступ на основе данных
   → user_id = 123 → найти пользователя в БД ✅✅
   → roles = ["buyer"] → разрешить только просмотр заказов, не удаление ✅✅
```

#### Преимущества JWT

✅ **Stateless** — серверу не нужно хранить сессию, достаточно проверить подпись  
✅ **Быстрый** — проверка подписи быстрее, чем запрос к базе данных  
✅ **Переносимый** — токен можно передать между сервисами  

#### Недостатки JWT

❌ **Нельзя отозвать мгновенно** — пока не истёк срок действия  
❌ **Больше трафика** — токен отправляется с каждым запросом  
❌ **Безопасность зависит от ключа** — если секретный ключ украден, все токены подделываются  

### Связь OAuth и JWT

#### Как они связаны?

> **OAuth 2.0 может использовать JWT как формат токена доступа.**

```
OAuth 2.0 (протокол) → Выдаёт токен доступа
   ↓
JWT (формат) → Формат этого токена
   ↓
Сервер использует токен для проверки прав пользователя ✅✅
```

**Пример из жизни:**
1. Пользователь нажимает "Войти через Google" ✅✅
2. Google выдаёт токен доступа в формате JWT ✅✅
3. Сайт shop.example.com проверяет подпись токена (OAuth + JWT) ✅✅
4. Сервер читает payload токена и разрешает доступ к ресурсам ✅✅

#### Разница между OAuth и JWT

| Аспект | OAuth 2.0 | JWT |
|--------|-----------|-----|
| **Что это такое** | Протокол делегирования доступа | Формат токена с данными о пользователе |
| **Для чего используется** | Выдача прав доступа без пароля | Хранение и передача данных о правах пользователя |
| **Пример из интернет-магазина** | "Войти через Google" → выдаётся токен ✅✅ | Токен содержит: user_id, email, roles ✅✅ |

## ⚖️ Плюсы и минусы OAuth и JWT

### ✅ Плюсы OAuth 2.0

| Преимущество | Объяснение | Пример из жизни |
|-------------|------------|-----------------|
| **Безопасность** | Не нужно передавать пароль сторонним сервисам | Пользователь не вводит пароль на shop.example.com — использует Google аккаунт ✅✅ |
| **Делегирование прав** | Можно дать доступ только к определённым ресурсам | Сайт может получить только email пользователя, но не все данные профиля ✅✅ |
| **Единый вход (SSO)** | Один аккаунт для всех сервисов | Пользователь входит один раз в Google — получает доступ ко всем подключённым сайтам ✅✅ |

### ❌ Минусы OAuth 2.0

| Недостаток | Объяснение | Пример из жизни |
|-----------|------------|-----------------|
| **Сложность реализации** | Нужно правильно реализовать все шаги протокола | Ошибка в реализации может привести к утечке данных ✅✅ |
| **Много шагов** | Процесс авторизации занимает время и требует нескольких запросов | Пользователь проходит 3-4 шага вместо одного входа по паролю ✅✅ |

### ✅ Плюсы JWT

| Преимущество | Объяснение | Пример из жизни |
|-------------|------------|-----------------|
| **Stateless** | Серверу не нужно хранить сессию, достаточно проверить подпись | При каждом запросе сервер проверяет токен — не нужно обращаться к БД ✅✅ |
| **Быстрый** | Проверка подписи быстрее, чем запрос к базе данных | 1 мс на проверку токена vs 50 мс на запрос к БД ✅✅ |
| **Переносимый** | Токен можно передать между сервисами без повторной аутентификации | Сервис заказов передаёт токен сервису уведомлений — пользователь не должен входить заново ✅✅ |

### ❌ Минусы JWT

| Недостаток | Объяснение | Пример из жизни |
|-----------|------------|-----------------|
| **Нельзя отозвать мгновенно** | Пока не истёк срок действия токена — он остаётся валидным | Если украли токен, нужно ждать до его истечения (например, 24 часа) ✅✅ |
| **Больше трафика** | Токен отправляется с каждым запросом | В каждом запросе передаётся ~1-5 КБ данных (токен) ✅✅ |
| **Безопасность зависит от ключа** | Если секретный ключ украден — все токены подделываются | Злоумышленник получил access к secret_key → может создать свои токены ✅✅ |

## 🎯 Что важно запомнить аналитику

### 1. OAuth — это **'протокол', JWT — это 'формат'**

> **OAuth 2.0** описывает, как выдать права доступа без передачи пароля.  
> **JWT** описывает, как хранить и передавать эти права в виде токена.

**Что я бы делал:**
- Требую использования OAuth для входа через сторонние сервисы (Google, Яндекс) ✅✅
- Требую использования JWT для хранения прав пользователя после авторизации ✅✅
- Проверяю, что токен подписан и проверен сервером ✅✅

### 2. OAuth не передаёт пароль!

> **Важно:** при использовании OAuth пользователь НЕ передаёт свой пароль сторонним сервисам.

**Что я бы требовал:**
- Проверять, что OAuth реализация не запрашивает пароль пользователя ❌
- Убеждаться, что токен доступа используется вместо пароля ✅✅
- Требовать HTTPS для всех запросов к OAuth серверу ✅✅

### 3. JWT — это stateless (без состояния)

> Серверу не нужно хранить сессию — достаточно проверить подпись токена.

**Что я бы делал:**
- Требую использования JWT вместо традиционных сессий (cookie + session_id) ✅✅
- Проверяю, что сервер проверяет подпись каждого входящего токена ✅✅
- Убеждаюсь, что срок действия токена ограничен (например, 24 часа) ✅✅

### 4. Токен нужно защищать!

> Если токен украден — злоумышленник получает доступ к ресурсам пользователя.

**Что я бы требовал:**
- Хранение токенов в secure cookie или httpOnly cookie ✅✅
- Использование HTTPS для всех запросов с токеном ✅✅
- Ограничение срока действия токена (например, 24 часа) ✅✅
- Возможность отзыва токена (через blacklist или rotation ключей) ✅✅

   → "Разрешить сайту shop.example.com доступ к вашему email?"

### Вопрос 3: Что такое SSO (Single Sign-On)?

**Ответ:**

> **SSO (Single Sign-On)** — единый вход для всех сервисов. Пользователь входит один раз и получает доступ ко всем подключённым системам без повторной аутентификации.

**Пример из жизни:**
```
Сценарий: "Вход в систему с SSO"

1. Пользователь заходит на сайт shop.example.com ✅✅
2. Нажимает "Войти через Google" ✅✅
3. Вводит свои данные один раз в Google (единый вход) ✅✅
4. Google выдаёт токен доступа всем подключённым сайтам ✅✅
5. Пользователь получает доступ к shop.example.com без повторного ввода пароля ✅✅

Если пользователь позже зайдёт на другой сервис, который использует тот же Google аккаунт:
→ Не нужно вводить пароль снова! ✅✅
→ Достаточно нажать "Войти через Google" и получить токен ✅✅
```

**Что я бы требовал:**
- Поддержку SSO для упрощения входа пользователей ✅✅
- Использование OAuth + JWT для реализации SSO ✅✅
- Безопасное хранение токенов (secure cookie, httpOnly) ✅✅

---

### Вопрос 4: Какие проблемы возникают при неправильной реализации OAuth?

**Ответ:**

1. **Утечка паролей**
   - Ошибка в реализации запрашивает пароль пользователя у стороннего сервиса ❌
   - Пример: сайт shop.example.com просит ввести Google пароль → пользователь передаёт его злоумышленникам ❌

2. **Неправильные права доступа**
   - Сервер получает больше прав, чем нужно
   - Пример: сайт запрашивает доступ ко всем данным профиля, а пользователю нужен только email ❌

3. **Отсутствие HTTPS**
   - Токены передаются по незащищённому каналу
   - Злоумышленник перехватывает токен и получает доступ к ресурсам пользователя ❌

4. **Неограниченный срок действия токенов**
   - Токен действует вечно → если украден, злоумышленник может использовать его годами ❌

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы ты объяснил заказчику, почему нужно использовать OAuth вместо прямого входа по паролю?

**Ответ:**

Я бы сказал:

> "Представьте, что вы хотите купить товар на сайте, который не знаете.
>
> **Без OAuth (прямой вход):**
> → Вам нужно создать аккаунт на этом сайте ✅✅
> → Или ввести пароль от другого сервиса ❌
> → Если введёте пароль — он сохранится на сервере этого сайта ❌
> → Если сайт будет взломан — ваш пароль попадёт к злоумышленникам ❌
>
> **С OAuth:**
> → Вы нажимаете "Войти через Google" ✅✅
> → Не вводите пароль на этом сайте (он остаётся у Google) ✅✅
> → Сайт получает только то, что нужно (имя, email) ✅✅
> → Если сайт будет взломан — злоумышленники не получат ваш Google пароль ✅✅

**Пример из интернет-магазина:**
```
Сценарий: "Вход в систему"

Без OAuth:
→ Пользователь создаёт аккаунт shop.example.com с паролем "mypassword123" ✅✅
→ Сайт сохраняет пароль в БД (или хеш) ✅✅
→ Если сайт взломан — злоумышленники получают пароли всех пользователей ❌

С OAuth:
→ Пользователь нажимает "Войти через Google" ✅✅
→ Не вводит пароль shop.example.com ✅✅
→ Google выдаёт токен доступа сайту (не пароль!) ✅✅
→ Сайт использует токен для получения данных пользователя ✅✅
→ Если сайт взломан — злоумышленники не получают пароли пользователей ✅✅

Важно: OAuth защищает пользователей от утечки паролей! ✅✅"
```

### Вопрос 2: Как бы ты объяснил разработчику, почему JWT лучше традиционных сессий (cookie + session_id)?

**Ответ:**

Я бы сказал:

> "Представьте, что мы храним данные пользователя в двух вариантах.
>
> **Традиционные сессии (cookie + session_id):**
> → Сервер хранит сессию в БД или файле ✅✅
> → При каждом запросе браузер отправляет cookie с session_id ✅✅
> → Сервер проверяет session_id и находит сессию в БД ✅✅
> → Проблема: нужно обращаться к БД при каждом запросе (медленно!) ❌
>
> **JWT:**
> → Токен содержит все данные о пользователе ✅✅
> → При каждом запросе сервер проверяет подпись токена ✅✅
> → Не нужно обращаться к БД (stateless) ✅✅
> → Быстрее: 1 мс на проверку подписи vs 50 мс на запрос к БД ✅✅

**Пример из жизни:**
```
Сценарий: "Пользователь делает 10 заказов"

Традиционные сессии:
→ 10 запросов × 50 мс (запрос к БД) = 500 мс ❌
→ Нужно хранить сессию в БД или файле ✅✅

JWT:
→ 10 запросов × 1 мс (проверка подписи) = 10 мс ✅✅
→ Не нужно хранить сессию на сервере ✅✅

Важно: JWT быстрее и не требует хранения сессий! ✅✅"
```

### Вопрос 3: Какие требования безопасности нужно учесть при проектировании системы с OAuth + JWT?

**Ответ:**

Я бы выделил следующие категории требований:

1. **Безопасность токенов**
   - Хранение в secure cookie или httpOnly cookie ✅✅
   - Использование HTTPS для всех запросов с токеном ✅✅
   - Ограничение срока действия (например, 24 часа) ✅✅
   - Возможность отзыва (через blacklist или rotation ключей) ✅✅

2. **Безопасность подписи JWT**
   - Использование сильного алгоритма (HS256, RS256) ✅✅
   - Хранение секретного ключа в secure месте (не в коде!) ✅✅
   - Регулярная ротация ключей ✅✅

3. **Ограничение прав доступа**
   - Принцип наименьших привилегий (только необходимые права) ✅✅
   - Проверка роли пользователя перед каждым доступом к ресурсу ✅✅
   - Логирование всех действий с токеном ✅✅

4. **Защита от атак**
   - Rate limiting для запросов с токенами ✅✅
   - Проверка на поддельные токены ✅✅
   - Защита от replay-атак (timestamp в токене) ✅✅

**Что я бы требовал:**
- Провести аудит безопасности OAuth реализации перед релизом ✅✅
- Регулярное обновление зависимостей и библиотек ✅✅
- Тестирование на проникновение (pentest) перед каждым релизом ✅✅

### Вопрос 4: Как бы ты поступил, если разработчик хочет хранить JWT в localStorage вместо cookie?

**Ответ:**

Я бы **предупредил о рисках**:

```
Риск: CSRF-атака (Cross-Site Request Forgery)

Сценарий:
1. Пользователь авторизован на shop.example.com ✅✅
2. Злоумышленник создаёт вредоносную страницу ✅✅
3. Пользователь переходит по ссылке злоумышленника ✅✅
4. Браузер автоматически отправляет JWT из localStorage ✅✅
5. Злоумышленник получает доступ к ресурсам пользователя ❌

Решение:
→ Хранить JWT в httpOnly cookie ✅✅
→ httpOnly cookie недоступен для JavaScript → CSRF-атака невозможна ✅✅
```

**Что я бы делал:**
1. Объяснил бы риски CSRF-атаки
2. Предложил бы использовать httpOnly cookie вместо localStorage
3. Убедился бы, что сервер проверяет Origin/Referer заголовки для защиты от CSRF
4. Если разработчик настаивает на localStorage — потребовал бы дополнительных мер защиты (CSP headers)

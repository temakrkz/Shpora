# 14.6. Как устроены соединения с внешними интеграциями

## Короткий ответ

Внешние интеграции — это связи между вашей системой и сторонними сервисами (платёжные шлюзы, доставки, CRM). Реализуются через API (REST/SOAP), используют протоколы HTTP/HTTPS, аутентификацию (API keys, OAuth) и обработку ошибок.

## Простыми словами

Представьте интернет-магазин:
- Чтобы принимать оплату → подключаете платёжный шлюз (например, ЮKassa)
- Чтобы отправлять заказы в доставку → интегрируетесь с СДЭК/Почтой
- Чтобы сохранять клиентов в CRM → синхронизируетесь с Bitrix24

**Как это работает:** Ваша система "говорит" на языке API со сторонними сервисами, обмениваясь данными по HTTP.

## Подробно

### Что такое внешняя интеграция?

Это связь между двумя независимыми системами, которые обмениваются данными через стандартные протоколы (HTTP/REST или SOAP).

**Ключевые компоненты:**

1. **API (Application Programming Interface)** — набор правил и методов для взаимодействия
2. **Протокол передачи данных** — HTTP/HTTPS (самый популярный), иногда FTP/SFTP, TCP
3. **Формат данных** — JSON (стандарт для REST) или XML (для SOAP)
4. **Аутентификация** — проверка прав доступа (API keys, OAuth 2.0, Basic Auth)

### Типы интеграций

| Тип | Описание | Пример |
|-----|----------|--------|
| **Синхронная** | Ожидает ответ сразу | Заказ → платёжный шлюз → подтверждение оплаты |
| **Асинхронная** | Отправляет и не ждёт ответа | Логирование событий в аналитику, отправка уведомлений |

### REST API — основа современных интеграций

**REST (Representational State Transfer)** — архитектурный стиль для веб-сервисов.

**Основные принципы:**
- **Resource-oriented** — всё представлено как ресурс (заказ, товар, пользователь)
- **HTTP methods** — GET (читать), POST (создать), PUT/PATCH (обновить), DELETE (удалить)
- **Stateless** — каждый запрос содержит всю необходимую информацию
- **JSON формат** — лёгкий и универсальный

**Пример REST API:**
```
GET    /api/v1/orders/123        # Получить заказ
POST   /api/v1/orders            # Создать новый заказ
PUT    /api/v1/orders/123        # Обновить заказ
DELETE /api/v1/orders/123        # Отменить заказ
```

### Аутентификация и авторизация

**API Key (ключ API)** — простой способ защиты:
- Сервис выдаёт уникальный ключ
- Ключ передаётся в заголовке запроса
- Простой, но менее безопасный метод

**OAuth 2.0** — современный стандарт делегирования доступа:
- Клиент получает временный токен (access token)
- Токен имеет срок жизни и ограниченные права
- Не требует передачи паролей сторонним сервисам

### Обработка ошибок

Внешние интеграции могут падать по разным причинам:
- Сервис недоступен (503 Service Unavailable)
- Ошибка валидации данных (400 Bad Request)
- Недостаточно прав (401 Unauthorized, 403 Forbidden)

**Что делает аналитик:**
1. Прописывает правила обработки ошибок в требованиях
2. Определяет, что делать при сбое: повторить запрос, показать пользователю ошибку, записать в лог
3. Требует от разработчиков мониторинга и алертов

### Idempotency (идемпотентность)

**Важное понятие:** Операция считается идемпотентной, если её многократное выполнение даёт тот же результат, что и одно выполнение.

**Примеры:**
- **GET /orders/123** — идемпотентно (можно запрашивать сколько угодно раз)
- **POST /orders** — НЕ идемпотентно (каждый POST создаст новый заказ!)

**Зачем это важно:** При повторной отправки запроса из-за сбоя сети не должно создаться дубликатов.

### Webhooks (обратные вызовы)

Механизм, когда сторонний сервис **сам вызывает ваш API** при событии.

**Пример:**
1. Пользователь оплатил заказ в ЮKassa
2. ЮKassa отправляет POST-запрос на ваш webhook: `POST /webhooks/payment`
3. Ваш сервер принимает и обрабатывает событие

**Важно для аналитика:** Указать в требованиях, какие события должны вызывать вебхуки и как они будут выглядеть (payload).

## Пример из интернет-магазина

### Сценарий: Заказ товара с оплатой

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│  Клиент     │────▶│ Интернет-    │────▶│ Платёжный   │
│ (сайт)      │     │ магазин      │     │ шлюз        │
└─────────────┘     └──────────────┘     └─────────────┘
                              │
                              ▼
                        ┌─────────────┐
                        │  Банк       │
                        └─────────────┘
```

**Шаги интеграции:**

1. **Клиент делает заказ** → интернет-магазин создаёт заказ и перенаправляет на платёжный шлюз
2. **Платёжный шлюз (ЮKassa)** → проверяет данные карты, списывает деньги
3. **Шлюз отправляет ответ:** `{"status": "success", "transaction_id": "tx_123"}`
4. **Интернет-магазин** → получает подтверждение, создаёт чек, отправляет уведомление клиенту

**Требования аналитика к интеграции с ЮKassa:**

| Параметр | Значение/Описание |
|----------|-------------------|
| Метод | POST /payments |
| Формат данных | JSON |
| Аутентификация | HMAC-SHA256 подпись |
| Поля запроса | amount, currency, description, customer_email |
| Ожидаемые ответы | success (200), error (400/401/500) |
| Обработка ошибок | Повторить 3 раза с интервалом 1 сек, затем показать пользователю ошибку оплаты |

### SOAP API (устаревший, но встречается)

**SOAP (Simple Object Access Protocol)** — более старый стандарт:
- Использует XML вместо JSON
- Строгая схема данных (WSDL документ описывает все методы)
- Чаще используется в банковских интеграциях и госсекторе

**Пример SOAP запроса:**
```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <CreateOrderResponse>
      <orderId>123</orderId>
    </CreateOrderResponse>
  </soap:Body>
</soap:Envelope>
```

## Плюсы/минусы

### REST API (современный подход)

| Плюсы | Минусы |
|-------|--------|
| Простота и универсальность | Требует хорошего понимания HTTP |
| JSON лёгкий для парсинга | Нужно проектировать контракты заранее |
| Поддержка всех современных языков | Сложно отлаживать без инструментов (Postman) |
| Stateless — легко масштабировать | Нет встроенной транзакционности |

### SOAP API (устаревший, но встречается)

| Плюсы | Минусы |
|-------|--------|
| Строгая типизация и валидация | XML громоздкий и медленный |
| Встроенная безопасность (WS-Security) | Сложно поддерживать |
| Хорошая документация (WSDL) | Устаревший стандарт |

## Что важно запомнить аналитику

1. **Всегда проектируйте контракт заранее** — используйте Swagger/OpenAPI для REST или WSDL для SOAP
2. **Обязательно продумайте обработку ошибок** — что будет, если внешний сервис упадёт?
3. **Идемпотентность критична** — особенно для POST-запросов (создание заказов, оплат)
4. **Webhooks требуют тестирования** — как ваш сервер принимает и обрабатывает обратные вызовы
5. **Аутентификация — не опционально** — даже если кажется, что "внутри компании"
6. **Логирование всех взаимодействий** — для отладки проблем с внешними сервисами

## Типичные вопросы и ответы

### Q: В чём разница между синхронной и асинхронной интеграцией?

**A:** 
- **Синхронная:** Ваш запрос ждёт ответа. Пример: заказ → платёжный шлюз (ждем подтверждения оплаты)
- **Асинхронная:** Отправляете событие и не ждёте. Пример: логирование кликов в аналитику

### Q: Когда использовать REST, а когда SOAP?

**A:** 
- **REST** — для большинства современных интеграций (e-commerce, мобильные приложения)
- **SOAP** — если требуется строгая типизация или работаете с устаревшими банковскими системами

### Q: Что такое API Key и зачем он нужен?

**A:** API Key — это уникальный идентификатор, который сервис выдаёт вам для доступа к своим функциям. Он передаётся в заголовке запроса вместо пароля. Это безопаснее, чем хранить реальные учётные данные.

### Q: Как проверить работу интеграции до разработки?

**A:** 
1. Используйте **Postman** или **Insomnia** — инструменты для тестирования API
2. Запросите **sandbox/test окружение** у провайдера (например, ЮKassa даёт тестовые карты)
3. Проверьте **Swagger/OpenAPI документацию** — там есть примеры запросов

### Q: Что делать, если внешний сервис недоступен?

**A:** 
1. В требованиях указать **правила обработки ошибок** (повторить запрос N раз, затем показать пользователю ошибку)
2. Предусмотреть **fallback-решение** (например, отложить заказ в очередь на повторную отправку)
3. Требовать от разработчиков **мониторинга и алертов**

# 2.14 Виды связей в реляционных БД (1:1, 1:N, M:N)

---

## Короткий ответ

**Виды связей в реляционных БД** — это типы отношений между таблицами: один-к-одному (1:1), один-ко-многим (1:N) и многие-ко-многим (M:N). Они определяют, как данные из разных таблиц связаны друг с другом.

---

## Простыми словами

### Аналогия с семейным деревом

Представьте генеалогическое дерево семьи:

| Тип связи | Пример в семье |
|----------|----------------|
| **1:1 (один-к-одному)** | Один человек — один паспорт |
| **1:N (один-ко-многим)** | Один родитель — много детей |
| **M:N (многие-ко-многим)** | Много студентов — много предметов (студент учится по разным предметам) |

### Что такое связи между таблицами?

Связи показывают, как данные из одной таблицы связаны с данными в другой:
- **1:1** — одна запись в таблице А связана с одной записью в таблице Б
- **1:N** — одна запись в таблице А связана со многими записями в таблице Б
- **M:N** — многие записи в таблице А могут быть связаны с многими записями в таблице Б

---

## Подробно

### 1:1 — Один к одному

**Что это:** Одна запись в одной таблице соответствует ровно одной записи в другой таблице.

**Примеры:**
- Один пользователь — один профиль настроек
- Один сотрудник — одна личная карточка
- Один товар — одна цена (в определённый момент времени)

#### Как реализуется?

Обычно через внешний ключ в обеих таблицах:

```sql
-- Таблица пользователей
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    username VARCHAR(50),
    email VARCHAR(100)
);

-- Таблица профилей (связь 1:1 с пользователями)
CREATE TABLE profiles (
    profile_id INT PRIMARY KEY,
    user_id INT,           -- Внешний ключ на users
    language_preference VARCHAR(10),
    FOREIGN KEY (user_id) REFERENCES users(user_id)
);

-- Можно добавить обратный внешний ключ
ALTER TABLE users ADD COLUMN profile_id INT;
```

**Когда применяется:**
- Когда данные логически разделены, но всегда связаны один к одному
- Для разделения больших таблиц на части по функциональности

---

### 1:N — Один ко многим

**Что это:** Одна запись в одной таблице может быть связана с множеством записей в другой таблице.

**Примеры:**
- Один заказчик — много заказов
- Один товар — много отзывов
- Один учитель — много учеников

#### Как реализуется?

Внешний ключ в таблице "многих":

```sql
-- Таблица клиентов (одна запись)
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100)
);

-- Таблица заказов (много записей на одного клиента)
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,           -- Внешний ключ на customers
    total_amount DECIMAL,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
```

**Как работает:**
- В таблице `customers` — одна запись для клиента "Иван Иванов"
- В таблице `orders` — много записей с одинаковым `customer_id = 123`
- Все эти записи относятся к одному клиенту

**Когда применяется:**
- Самый распространённый тип связи в БД
- Для хранения истории действий (заказы, отзывы, посещения)

---

### M:N — Многие ко многим

**Что это:** Множество записей в одной таблице могут быть связаны с множеством записей в другой таблице.

**Примеры:**
- Много студентов — много предметов (студент учится по разным предметам)
- Много сотрудников — много проектов (сотрудник работает над разными проектами)
- Много товаров — много категорий (товар может относиться к нескольким категориям)

#### Проблема M:N связи

SQL не поддерживает прямые связи "многие ко многим". Нужно использовать **промежуточную таблицу** (junction table).

```sql
-- Таблица студентов
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name VARCHAR(100)
);

-- Таблица предметов
CREATE TABLE subjects (
    subject_id INT PRIMARY KEY,
    name VARCHAR(100)
);

-- Промежуточная таблица "учёба"
CREATE TABLE studies (
    student_id INT,           -- Внешний ключ на students
    subject_id INT,           -- Внешний ключ на subjects
    grade DECIMAL,            -- Оценка студента по предмету
    PRIMARY KEY (student_id, subject_id)  -- Сложный первичный ключ
);
```

**Как работает:**
- Студент "Иван" (student_id = 1) может учиться по разным предметам
- Предмет "Математика" (subject_id = 5) изучают разные студенты
- Каждая пара (студент, предмет) — отдельная запись в таблице `studies`

**Когда применяется:**
- Когда связь между сущностями не является однозначной
- Для хранения отношений "кто что делает" или "что связано с чем"

## Пример из интернет-магазина

### Сценарий: Заказы и товары

#### 1:N — Один заказчик — много заказов

```sql
-- Таблица клиентов (одна запись на клиента)
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(100)
);

-- Таблица заказов (много записей на одного клиента)
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,           -- Внешний ключ на customers
    order_date DATE,
    total_amount DECIMAL,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
```

**Как работает:**
- Клиент "Иван Иванов" — одна запись в `customers`
- У Ивана может быть 10 заказов — 10 записей в `orders` с одинаковым `customer_id = 123`

#### M:N — Много товаров в одном заказе

```sql
-- Таблица товаров (один товар)
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    name VARCHAR(100),
    price DECIMAL
);

-- Таблица заказов (заказ с товарами)
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

-- Промежуточная таблица "позиции заказа"
CREATE TABLE order_items (
    item_id INT PRIMARY KEY,
    order_id INT,              -- Внешний ключ на orders
    product_id INT,            -- Внешний ключ на products
    quantity INT,              -- Количество товара в заказе
    price_at_purchase DECIMAL, -- Цена на момент покупки
    FOREIGN KEY (order_id) REFERENCES orders(order_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);
```

**Как работает:**
- Заказ №123 может содержать 5 товаров — 5 записей в `order_items`
- Товар "Ноутбук" может быть куплен в разных заказах — много записей с одинаковым `product_id`

## Плюсы и минусы различных типов связей

### ✅ Преимущества правильного проектирования связей

| Преимущество | Объяснение |
|-------------|------------|
| **Нормализация данных** | Избегаются дублирования информации |
| **Гибкость системы** | Легко добавлять новые типы отношений между сущностями |
| **Эффективное хранение** | Данные хранятся в одном месте, а не дублируются |

### ❌ Недостатки и проблемы связей

| Недостаток | Объяснение |
|-----------|------------|
| **Сложность JOIN операций** | Запросы с соединениями таблиц могут быть медленными |
| **Риск нарушения целостности** | При удалении записи могут "повиснуть" ссылки на неё |
| **Зависимость таблиц** | Изменение в одной таблице может повлиять на другие |

---

## Что важно запомнить аналитику

1. **1:N — самый распространённый тип связи**  
   Одна сущность имеет историю действий (заказы, отзывы)

2. **M:N требует промежуточной таблицы**  
   SQL не поддерживает прямые связи "многие ко многим" — нужна junction table

3. **Внешний ключ всегда в таблице "многих"**  
   В 1:N связи внешний ключ находится в таблице с множеством записей

4. **Правильное проектирование связей важно для производительности**  
   Неправильные связи могут приводить к медленным запросам и дублированию данных

## ❓ Типичные вопросы и ответы

### Вопрос 1: В чём разница между связями 1:N и M:N?
**Ответ:**  
В связи 1:N одна запись в таблице А связана с множеством записей в таблице Б (например, один клиент — много заказов). В связи M:N многие записи в таблице А связаны со многими записями в таблице Б (например, студенты и предметы), что требует промежуточной таблицы.

---

### Вопрос 2: Где должен находиться внешний ключ при связи 1:N?
**Ответ:**  
Внешний ключ всегда находится в таблице "многих" — той, где одна запись из другой таблицы может повторяться много раз. Например, `customer_id` в таблице заказов (много заказов на одного клиента).

---

### Вопрос 3: Почему нельзя напрямую реализовать связь M:N без промежуточной таблицы?
**Ответ:**  
SQL не поддерживает прямые связи "многие ко многим". Промежуточная таблица нужна для хранения пар связанных записей и дополнительных данных о каждом соединении (например, оценка студента по предмету или количество товара в заказе).

## 🛠 Практические вопросы для собеседования

### Вопрос 1: В интернет-магазине один товар может относиться к нескольким категориям. Как вы спроектируете эту связь?

**Ответ:**  
Это классическая M:N связь — много товаров могут быть в разных категориях, и одна категория может содержать много товаров. Я создам промежуточную таблицу `product_categories` с полями: `product_id`, `category_id`. Это позволит одному товару быть в нескольких категориях без дублирования данных.

---

### Вопрос 2: Нужно ли создавать связь 1:1 между пользователями и их профилями? Почему да или нет?

**Ответ:**  
Создавать отдельную таблицу профилей с связью 1:1 не обязательно — можно хранить данные профиля в той же таблице пользователей. Если данные профиля действительно большие или часто меняются, тогда имеет смысл вынести их в отдельную таблицу для разделения нагрузки и упрощения управления.

---

### Вопрос 3: Как объяснить клиенту необходимость промежуточной таблицы для связи "студенты-предметы"?

**Ответ:**  
Я бы объяснил на примере расписания: если студент учится по разным предметам, а предмет изучают разные студенты — нужно записать каждую пару (студент + предмет). Промежуточная таблица как раз и хранит эти пары. Без неё мы не сможем отследить, какие именно предметы изучает каждый студент.

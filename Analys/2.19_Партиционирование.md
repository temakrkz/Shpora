# 2.19 Партиционирование данных в БД

---

## Короткий ответ

**Партиционирование данных** — это разделение большой таблицы на несколько меньших частей (партиций) для улучшения производительности и упрощения управления данными. Каждая партиция хранится отдельно, но выглядит как одна таблица.

---

## Простыми словами

### Аналогия с архивом документов

Представьте огромный офисный архив:

| Тип хранения | Как работает |
|-------------|--------------|
| **Без партиционирования** | Все документы в одной огромной папке — искать долго, копировать всё сложно |
| **С партиционированием** | Документы разделены по годам и категориям — каждый год в отдельной папке |

### Что такое партиционирование?

**Partitioning (партиционирование)** — это "разбиение" большой таблицы на части:
- Данные делятся по логическим критериям (дата, регион, категория)
- Каждая часть хранится отдельно
- База данных автоматически выбирает нужную партицию при запросе

---

## Подробно

### Зачем нужно партиционирование?

#### 1. Улучшение производительности запросов

**Проблема без партиционирования:**
Таблица `orders` содержит 50 миллионов записей:
- Поиск заказов по дате проверяет все 50 миллионов записей
- Резервное копирование занимает часы

**Решение с партиционированием:**
Таблица разделена на партиции по годам:
- Запросы к заказам 2024 года проверяют только одну партицию (10 млн записей)
- Резервное копирование каждой партиции занимает минуты

#### 2. Упрощение удаления старых данных

**Проблема без партиционирования:**
Удаление заказов старше 2 лет:
```sql
DELETE FROM orders WHERE order_date < '2022-01-01';
-- Нужно проверять и удалять миллионы записей, что занимает часы
```

**Решение с партиционированием:**
Удаление целой партиции:
```sql
DROP PARTITION p_orders_2022;  -- Удаляется сразу вся партиция за секунды
```

#### 3. Распределение данных между серверами

**Проблема без партиционирования:**
Один сервер не справляется с объёмом данных — нужно масштабирование.

**Решение с партиционированием:**
Разные партиции хранятся на разных серверах:
- 2023 год → Сервер 1
- 2024 год → Сервер 2
- 2025 год → Сервер 3

---

### Типы партиционирования

#### 1. Range partitioning (диапазонное)

**Как работает:**
Данные делятся по диапазонам значений:
```sql
CREATE TABLE orders (
    order_id INT,
    customer_id INT,
    order_date DATE,
    total_amount DECIMAL
) PARTITION BY RANGE (YEAR(order_date));

-- Добавляем партиции для каждого года
PARTITION p_2023 VALUES LESS THAN ('2024-01-01'),
PARTITION p_2024 VALUES LESS THAN ('2025-01-01'),
PARTITION p_2025 VALUES LESS THAN ('2026-01-01');
```

**Как распределяются данные:**
- Заказы с `order_date` от '2023-01-01' до '2024-01-01' → партиция p_2023
- Заказы с `order_date` от '2024-01-01' до '2025-01-01' → партиция p_2024

**Когда применяется:**
- По дате (месяц, квартал, год)
- По ценовым диапазонам
- По возрастным группам

#### 2. List partitioning (списокное)

**Как работает:**
Данные делятся по конкретным значениям:
```sql
CREATE TABLE orders (
    order_id INT,
    region_code VARCHAR(10),
    total_amount DECIMAL
) PARTITION BY LIST (region_code);

-- Добавляем партиции для каждого региона
PARTITION p_moscow VALUES IN ('RU-MOW'),
PARTITION p_spb VALUES IN ('RU-SPE'),
PARTITION p_kazan VALUES IN ('RU-KZN');
```

**Как распределяются данные:**
- Заказы с `region_code = 'RU-MOW'` → партиция p_moscow
- Заказы с `region_code = 'RU-SPE'` → партиция p_spb

**Когда применяется:**
- По географическим регионам
- По категориям товаров
- По статусам заказов

#### 3. Hash partitioning (хэшное)

**Как работает:**
Данные распределяются равномерно по хэшу:
```sql
CREATE TABLE orders (
    order_id INT,
    customer_id INT,
    total_amount DECIMAL
) PARTITION BY HASH(customer_id % 4);

-- Добавляем 4 партиции для равномерного распределения
PARTITION p_0 VALUES LESS THAN MAXVALUE,
PARTITION p_1 VALUES LESS THAN MAXVALUE,
PARTITION p_2 VALUES LESS THAN MAXVALUE,
PARTITION p_3 VALUES LESS THAN MAXVALUE;
```

**Как распределяются данные:**
- `customer_id = 1` → партиция p_1 (1 % 4 = 1)
- `customer_id = 2` → партиция p_2 (2 % 4 = 2)
- `customer_id = 3` → партиция p_3 (3 % 4 = 3)

**Когда применяется:**
- Когда не важно, какие именно данные будут на каком сервере
- Нужно равномерное распределение нагрузки между серверами

## Пример из интернет-магазина

### Сценарий: Хранение заказов за несколько лет

Интернет-магазин обрабатывает 10 миллионов заказов в год. Таблица `orders` содержит данные за последние 5 лет (50 млн записей).

**Без партиционирования:**
Все заказы в одной таблице на одном сервере.

Проблемы:
- Поиск заказов по дате проверяет все 50 млн записей — занимает несколько секунд
- Резервное копирование занимает 8 часов
- Удаление старых данных занимает часы

**С партиционированием по годам:**
```sql
CREATE TABLE orders (
    order_id INT,
    customer_id INT,
    order_date DATE,
    total_amount DECIMAL
) PARTITION BY RANGE (YEAR(order_date));

-- Добавляем партиции для каждого года
PARTITION p_2020 VALUES LESS THAN ('2021-01-01'),
PARTITION p_2021 VALUES LESS THAN ('2022-01-01'),
PARTITION p_2022 VALUES LESS THAN ('2023-01-01'),
PARTITION p_2023 VALUES LESS THAN ('2024-01-01'),
PARTITION p_2024 VALUES LESS THAN ('2025-01-01');
```

**Преимущества:**
- Поиск заказов 2024 года проверяет только одну партицию (10 млн записей) — быстрее в 5 раз
- Резервное копирование каждой партиции занимает ~1.6 часа вместо 8 часов для всей таблицы
- Удаление старых данных: `DROP PARTITION p_2020` удаляет всю партицию за секунды

### Сценарий: Географическое распределение

Пользователи интернет-магазина находятся в разных регионах России.

**С партиционированием по регионам:**
```sql
CREATE TABLE orders (
    order_id INT,
    region_code VARCHAR(10),
    total_amount DECIMAL
) PARTITION BY LIST (region_code);

-- Добавляем партиции для каждого региона
PARTITION p_moscow VALUES IN ('RU-MOW'),
PARTITION p_spb VALUES IN ('RU-SPE'),
PARTITION p_kazan VALUES IN ('RU-KZN');
```

**Преимущества:**
- Запросы к заказам Москвы проверяют только одну партицию
- Можно хранить разные партиции на разных серверах в соответствующих регионах
- Упрощается удаление данных по регионам

## Плюсы и минусы партиционирования

### ✅ Преимущества партиционирования

| Преимущество | Объяснение |
|-------------|------------|
| **Ускорение запросов** | База данных проверяет только нужные партиции, а не всю таблицу |
| **Упрощение резервного копирования** | Можно делать бэкапы отдельных партиций независимо |
| **Легкое удаление старых данных** | Удаление целой партиции быстрее, чем очистка таблицы |
| **Распределение нагрузки** | Разные партиции могут храниться на разных серверах |

### ❌ Недостатки и ограничения партиционирования

| Недостаток | Объяснение |
|-----------|------------|
| **Сложность проектирования** | Нужно правильно выбрать ключ партиционирования |
| **Проблемы с перемещением данных** | Если данные не соответствуют ключу, их нужно переносить между партициями |
| **Не все СУБД поддерживают** | Некоторые базы данных имеют ограниченную поддержку партиционирования |
| **Усложнение JOIN операций** | Соединение таблиц из разных партиций может быть медленнее |

---

## Что важно запомнить аналитику

1. **Партиционирование — это логическое разделение таблицы на части**  
   Для пользователя таблица выглядит как одна, но база данных работает с отдельными частями

2. **Ключ партиционирования должен быть селективным**  
   Значения ключа должны быть распределены равномерно, чтобы не было "горячих" и "холодных" партиций

3. **Партиционирование не ускоряет все запросы**  
   Запросы без фильтрации по ключу партиционирования проверяют все партиции — преимущества исчезают

4. **Аналитик должен понимать ограничения партиционирования**  
   Это помогает правильно проектировать структуру БД и предвидеть проблемы с производительностью

## ❓ Типичные вопросы и ответы

### Вопрос 1: Что такое партиционирование данных?
**Ответ:**  
Партиционирование — это разделение большой таблицы на несколько меньших частей (партиций) по определённым критериям. Каждая партиция хранится отдельно, но для пользователя таблица выглядит как одна целая. Это улучшает производительность запросов и упрощает управление данными.

---

### Вопрос 2: Когда стоит использовать партиционирование?
**Ответ:**  
Партиционирование полезно когда таблица очень большая (миллионы+ записей), данные имеют логическую структуру (по дате, региону, категории) и часто к ним применяются фильтры по этим полям. Это ускоряет запросы и упрощает удаление старых данных.

---

### Вопрос 3: Какой ключ партиционирования лучше выбрать для таблицы заказов?
**Ответ:**  
Для таблицы заказов лучше использовать `order_date` — заказы обычно запрашивают по диапазонам дат, а старые данные можно удалять целиком (удаление партиции), что быстрее, чем очистка отдельных записей.

---

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Интернет-магазин хранит 50 миллионов заказов в таблице. Запросы к старым заказам (>2 лет) выполняются очень медленно. Как вы предложите улучшить ситуацию?

**Ответ:**  
Я бы предложил партиционирование таблицы по дате заказа. Создал бы отдельные партиции для каждого года или квартала, и старые данные можно было бы хранить на отдельных серверах или архивировать в отдельную БД. Это ускорило бы запросы к актуальным заказам и упростит удаление старых данных через удаление целых партиций.

---

### Вопрос 2: Заказчик просит партиционирование по ID пользователя. Почему это плохая идея?

**Ответ:**  
Партиционирование по ID пользователя — плохая идея, потому что значения ID распределены случайно. Все пользователи могут попасть в одну партицию, и преимущества партиционирования исчезнут. Лучше использовать Partitioning key с предсказуемым распределением, например, по дате или региону.

---

### Вопрос 3: Как объяснить клиенту, почему партиционирование не ускорит все запросы?

**Ответ:**  
Я бы объяснил на примере поиска в библиотеке: если искать книгу в библиотеке по названию — оглавление (партиция) помогает быстро найти нужную полку. Но если искать любую случайную книгу без указания раздела — оглавление не поможет, нужно будет проверить все полки. Так и с партиционированием — оно ускоряет запросы только когда используется Partitioning key в фильтрах.

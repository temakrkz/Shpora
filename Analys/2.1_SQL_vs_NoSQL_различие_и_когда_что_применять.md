# 2.1 SQL vs NoSQL — различие и когда что применять

---

## 📌 Короткий ответ

> **SQL (реляционные базы данных)** — хранят данные в таблицах с жёсткой структурой, поддерживают транзакции ACID.  
> **NoSQL (нерегуляционные базы данных)** — более гибкие структуры для хранения неструктурированных или быстро меняющихся данных, часто жертвуют частью ACID ради производительности и масштабируемости.

---

## 💡 Простыми словами

### Аналогия с интернет-магазинам

| Тип БД | Как это работает в магазине |
|--------|----------------------------|
| **SQL (реляционная)** | Все данные хранятся в таблицах: клиенты, товары, заказы — каждая запись строго структурирована и связана ключами |
| **NoSQL** | Данные могут быть разной формы: документы JSON для профилей пользователей, графы для рекомендаций товаров, ключ-значение для кэша сессий |

### Пример из интернет-магазина

**SQL база данных:**
> Таблица клиентов с чёткой структурой (id, name, email)  
> Таблица заказов со связью через foreign key на клиента

**NoSQL база данных:**
> Документ профиля пользователя в MongoDB с гибкой структурой JSON: имя, email, предпочтения, история заказов — всё в одном документе

## 🔍 Подробно

### SQL (реляционные базы данных)

> **Основные характеристики:**
- Данные хранятся в **таблицах** с чётко определённой структурой
- Связи между таблицами через **foreign keys**
- Поддерживают **транзакции ACID** (атомарность, согласованность, изоляция, долговечность)
- Жёсткая схема: нужно определять структуру до начала записи

**Примеры:** PostgreSQL, MySQL, SQL Server, Oracle

### NoSQL базы данных

> **Основные типы:**

1. **Документные (Document stores)** — данные в виде JSON/BSON документов  
   - MongoDB, CouchDB  
   - Пример: профили пользователей с гибкой структурой

2. **Ключ-значение (Key-value stores)** — простые пары ключ-значение  
   - Redis, DynamoDB  
   - Пример: кэш сессий, корзина покупок

3. **Колонно-ориентированные (Column-family stores)** — данные в колонках  
   - Cassandra, HBase  
   - Пример: аналитика, отчёты с большими объёмами данных

4. **Графовые (Graph databases)** — связи между данными как главное  
   - Neo4j, Amazon Neptune  
   - Пример: рекомендации товаров, социальные сети

### Когда что применять?

| Ситуация | Рекомендация | Почему |
|----------|--------------|--------|
| **Финансовые операции** | SQL | Требуется строгая согласованность и транзакции ACID |
| **Заказы с чёткой структурой** | SQL | Много связей между таблицами, нужны сложные запросы |
| **Профили пользователей с гибкими данными** | NoSQL (документная) | Структура данных может меняться часто |
| **Кэш и сессии** | NoSQL (key-value) | Нужна максимальная скорость чтения/записи |
| **Аналитика больших объёмов данных** | NoSQL (колоночная) | Быстрые агрегации по колонкам |
| **Рекомендательные системы** | NoSQL (графовая) | Важны связи между сущностями |

### Пример из интернет-магазина: выбор БД

| Сущность | Тип данных | Рекомендация | Почему |
|----------|-----------|--------------|--------|
| Заказы и платежи | Структурированные, много связей | SQL (PostgreSQL) | Требуется ACID для финансовых операций |
| Профиль пользователя | Гибкая структура, редко меняется | NoSQL документная (MongoDB) | Поля могут добавляться/удаляться без миграций |
| Корзина покупок | Быстрые операции чтения/записи | NoSQL key-value (Redis) | Нужна максимальная скорость |
| История просмотров | Большие объёмы, нужны агрегации | NoSQL колоночная (Cassandra) | Эффективные запросы по временным диапазонам |

## ⚖️ Плюсы и минусы SQL vs NoSQL

### ✅ Плюсы SQL

| Преимущество | Объяснение |
|-------------|------------|
| **Транзакции ACID** | Гарантирует точность финансовых операций и целостность данных |
| **Сложные запросы** | Поддержка JOIN, агрегаций, подзапросов для аналитики |
| **Строгая согласованность** | Данные всегда актуальны и непротиворечивы |
| **Зрелые инструменты** | Много готовых решений для бэкапов, репликации, мониторинга |

### ❌ Минусы SQL

| Недостаток | Объяснение |
|-----------|------------|
| **Жёсткая схема** | Изменение структуры требует миграций и простоев |
| **Менее масштабируемая** | Горизонтальное масштабирование сложнее, чем в NoSQL |
| **Ограниченная гибкость** | Трудно хранить данные с неструктурированной или быстро меняющейся схемой |

### ✅ Плюсы NoSQL

| Преимущество | Объяснение |
|-------------|------------|
| **Гибкая схема** | Можно добавлять поля без миграций базы данных |
| **Масштабируемость** | Легко добавлять новые узлы для горизонтального масштабирования |
| **Высокая производительность** | Оптимизированы для простых операций чтения/записи |
| **Разные модели данных** | Можно выбрать подходящую модель под задачу (документы, графы и т.д.) |

### ❌ Минусы NoSQL

| Недостаток | Объяснение |
|-----------|------------|
| **Отсутствие ACID в некоторых случаях** | Многие системы жертвуют согласованностью ради доступности и скорости |
| **Ограниченная поддержка сложных запросов** | JOIN, агрегации часто работают медленнее или не поддерживаются |
| **Сложность управления данными** | Меньше инструментов для бэкапов, репликации, мониторинга |

## 🎯 Что важно запомнить аналитику

1. **Не существует "лучшей" БД**. Выбор зависит от требований: нужна ли строгая согласованность (SQL) или скорость и масштабируемость (NoSQL).

2. **Часто используются вместе** — в одной системе могут быть разные типы БД для разных задач (например, PostgreSQL для заказов + MongoDB для профилей + Redis для кэша).

3. **ACID vs BASE** — SQL следует принципам ACID (Atomicity, Consistency, Isolation, Durability), многие NoSQL системы используют BASE (Basically Available, Soft state, Eventual consistency) — согласованность не мгновенная, а в конечном счёте.

4. **Микросервисы и полиглотное хранение** — каждый сервис может использовать свою БД, подходящую под его задачи. Это называется polyglot persistence.

5. **Для junior-аналитика важно понимать требования бизнеса**: нужна ли мгновенная согласованность данных или допустима задержка в несколько секунд? Сколько операций чтения/записи будет? Как часто меняется структура данных?

6. **SQL — стандарт дефолта**. Если неясно, что нужно, чаще выбирают SQL из-за зрелости и предсказуемости. NoSQL выбирают только когда есть конкретные требования, которые он решает лучше.

## ❓ Типичные вопросы и ответы

### Вопрос 1: Почему в микросервисах часто используют разные типы баз данных?

> **Ответ:**  
Каждый сервис имеет свои задачи и требования к данным. Например, сервис заказов требует строгой согласованности (SQL), а сервис рекомендаций — высокой скорости чтения графов связей (графовая БД). Использование подходящей БД под каждую задачу называется polyglot persistence и позволяет оптимизировать производительность и упростить архитектуру.

---

### Вопрос 2: Что будет, если в NoSQL системе данные не будут согласованы?

> **Ответ:**  
Это зависит от типа системы и настроек. В системах с eventual consistency (согласованностью в конечном счёте) данные могут временно отличаться на разных узлах. Это нормально для высоконагруженных систем — пользователь может увидеть устаревшие данные на несколько секунд, но система продолжит работать. Для критичных данных нужно настроить механизмы синхронизации или использовать гибридный подход (SQL для важных операций + NoSQL для остальных).

---

### Вопрос 3: Когда стоит отказаться от SQL в пользу NoSQL?

> **Ответ:**  
Стоит переходить на NoSQL когда:
- Требуется горизонтальное масштабирование на десятки/сотни узлов
- Структура данных часто меняется и не может быть определена заранее
- Нужна максимальная скорость простых операций чтения/записи (кэш, сессии)
- Работаем с данными, которые естественно описываются графами или документами

Не стоит переходить на NoSQL только потому что "это модно" — если требования не требуют его преимуществ, SQL будет проще и надёжнее.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы ты поступил, если заказчик просит добавить в систему хранения профилей пользователей поддержку произвольных полей (например, "любимый цвет", "хобби")?

**Ответ:**  
Я бы оценил требования к данным и нагрузке:
- Если профили читаются часто и структура меняется редко — можно использовать SQL с ALTER TABLE для добавления новых колонок или JSON-колоночные типы в современных СУБД (PostgreSQL 10+ поддерживает JSONB)
- Если структура данных очень гибкая и часто меняется, а чтение происходит нечасто — предложить NoSQL документную базу (MongoDB), где каждый профиль может быть отдельным документом с произвольными полями

В техническом задании я бы явно указал требования к согласованности данных и частоте изменений структуры.

---

### Вопрос 2: Что делать, если система должна поддерживать миллионы пользователей с высокой нагрузкой на чтение?

**Ответ:**  
Я бы предложил гибридный подход:
- **SQL база** для критичных операций (регистрация, платежи) — требуется строгая согласованность
- **NoSQL key-value (Redis)** для кэша профилей и сессий — максимальная скорость чтения
- **Поиск по Elasticsearch** для быстрого поиска пользователей

Также нужно предусмотреть механизмы синхронизации данных между базами и стратегии обработки ошибок при сбоях.

---

### Вопрос 3: Как объяснить бизнесу разницу между SQL и NoSQL?

**Ответ:**  
Я бы объяснил так: "Представьте, что вы ведёте бухгалтерию (финансовые операции) и одновременно управляете складом (товары). Бухгалтерия требует точных записей с проверками — это как SQL база данных. Склад может хранить товары в разных форматах, добавлять новые категории без перестройки всей системы — это как NoSQL. В современной системе часто используют оба подхода: для важных операций нужна строгая согласованность (SQL), а для гибких данных и высокой скорости чтения — более простые структуры (NoSQL)".

# 2.23 Процесс проектирования БД: что такое и как проходит

---

## 📌 Короткий ответ

> **Процесс проектирования БД** — это последовательность шагов, которые аналитик или архитектор выполняет для создания базы данных: от понимания бизнес-требований до финальной схемы с таблицами, полями и связями.

---

## 💡 Простыми словами

### Аналогия с интернет-магазином

Представьте, что вы открываете **новый склад** для интернет-магазина. Процесс проектирования БД — это как планировка склада:

| Этап | Что делаем на складе | Что делаем в БД |
|------|---------------------|-----------------|
| **Понимание требований** | Определяем, какие товары будем хранить и сколько места нужно | Определяем, какие данные нам нужны (клиенты, заказы, товары) |
| **Создание зон хранения** | Разделяем склад на зоны: одежда, электроника, бытовая техника | Создаём таблицы: `users`, `products`, `orders` |
| **Размещение полок** | Решаем, где хранить каждый товар и как его называть | Добавляем поля в таблицы: `product_id`, `name`, `price` |
| **Создание маршрутов** | Прокладываем пути между зонами для эффективной работы | Создаём связи между таблицами (foreign keys) |
| **Тестирование** | Пробуем перемещать товары и находить их | Проверяем, что данные сохраняются и извлекаются корректно |

### Пример из интернет-магазина

**Бизнес-требования:**
- Нужно хранить информацию о клиентах (имя, email, телефон)
- Нужно хранить информацию о товарах (название, цена, категория)
- Нужно хранить заказы с информацией о том, что купил каждый клиент

**Результат проектирования БД:**
```
Таблица users:
  - user_id (уникальный номер клиента)
  - name (имя)
  - email (почта)
  - phone (телефон)

Таблица products:
  - product_id (уникальный номер товара)
  - name (название)
  - price (цена)
  - category_id (категория)

Таблица orders:
  - order_id (уникальный номер заказа)
  - user_id (кому заказ, связь с таблицей users)
  - total_amount (сумма заказа)
  - created_at (дата создания)

Таблица order_items (что в заказе):
  - item_id
  - order_id (какой заказ)
  - product_id (какой товар)
  - quantity (сколько штук)
```

## 🔍 Подробно

### Этапы процесса проектирования БД

#### Этап 1: Сбор требований (Requirements Gathering)

**Что делаем:**
- Определяем, какие данные нужны системе
- Понимаем бизнес-процессы
- Собираем информацию от заказчиков и стейкхолдеров

**Пример из интернет-магазина:**
> "Нам нужно хранить информацию о клиентах: имя, email, телефон. Также нужна история заказов."

#### Этап 2: Концептуальное моделирование (Conceptual Design)

**Что делаем:**
- Создаём высокоуровневую схему данных
- Определяем основные сущности и их связи
- Не думаем о технических деталях на этом этапе

**Пример из интернет-магазина:**
```
[Клиент] ──(создаёт)──> [Заказ]
                          │
                        (содержит)
                          ↓
                      [Товары в заказе]
```

#### Этап 3: Логическое моделирование (Logical Design)

**Что делаем:**
- Превращаем концептуальную схему в таблицы и поля
- Определяем типы данных для каждого поля
- Создаём первичные и внешние ключи
- Нормализуем данные (убираем дублирование)

**Пример из интернет-магазина:**
```
Таблица users:
  - user_id (INT, PRIMARY KEY)
  - name (VARCHAR(100))
  - email (VARCHAR(255), UNIQUE)
  - phone (VARCHAR(20))

Таблица products:
  - product_id (INT, PRIMARY KEY)
  - name (VARCHAR(200))
  - price (DECIMAL(10, 2))
```

#### Этап 4: Физическое моделирование (Physical Design)

**Что делаем:**
- Определяем технические детали реализации
- Выбираем типы данных для конкретной СУБД
- Добавляем индексы для ускорения запросов
- Решаем вопросы партиционирования и репликации

**Пример из интернет-магазина:**
```sql
-- Индекс для быстрого поиска по email
CREATE INDEX idx_users_email ON users(email);

-- Индекс для фильтрации заказов по дате
CREATE INDEX idx_orders_created_at ON orders(created_at);

-- Партиционирование таблицы заказов по месяцам
PARTITION BY RANGE (YEAR(created_at)) ...
```

#### Этап 5: Тестирование и валидация

**Что делаем:**
- Проверяем, что схема работает корректно
- Тестируем на реальных данных
- Ищем узкие места и проблемы производительности

**Пример из интернет-магазина:**
```sql
-- Вставляем тестовые данные
INSERT INTO users (user_id, name, email) VALUES 
(1, 'Иван', 'ivan@example.com'),
(2, 'Мария', 'maria@example.com');

-- Проверяем запросы
SELECT * FROM orders WHERE user_id = 1; -- Должен работать быстро
```

### Типичные инструменты проектирования БД

#### 1. ER-диаграммы (Entity-Relationship)

Визуальное представление сущностей и связей:
- **Сущности** — прямоугольники (например, "Клиент", "Заказ")
- **Атрибуты** — овалы (имя, email, цена)
- **Связи** — линии между сущностями

#### 2. SQL-скрипты

Текстовое описание базы данных:
```sql
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255) UNIQUE
);

CREATE INDEX idx_users_email ON users(email);
```

#### 3. Специализированные инструменты

- **dbdiagram.io** — визуальное проектирование через код
- **MySQL Workbench** — для MySQL серверов
- **pgModeler** — для PostgreSQL
- **ER/Studio** — профессиональный инструмент

## ✅ Плюсы и минусы процесса проектирования БД

### ✅ Преимущества структурированного подхода

| Преимущество | Объяснение |
|--------------|------------|
| **Понятность требований** | Чёткое понимание того, какие данные нужны системе |
| **Избежание дублирования** | Нормализация помогает убрать избыточные данные |
| **Масштабируемость** | Хорошо спроектированная БД легче расширяется в будущем |
| **Снижение ошибок** | Тестирование на ранних этапах выявляет проблемы до реализации |

### ❌ Недостатки и риски

| Недостаток | Объяснение |
|------------|------------|
| **Время разработки** | Процесс проектирования занимает время, особенно для сложных систем |
| **Сложность изменений** | Изменить хорошо спроектированную БД сложнее, чем плохо спроектированную |
| **Непредвиденные требования** | Бизнес может изменить требования в процессе разработки |

---

## 📌 Что важно запомнить аналитику

1. **Проектирование БД — это итеративный процесс**, который проходит несколько этапов от требований до реализации
2. **Аналитик участвует на всех этапах** — от сбора требований до валидации схемы
3. **Хорошо спроектированная БД экономит время разработчиков** и снижает количество ошибок
4. **Важно балансировать между нормализацией и производительностью**

## ❓ Типичные вопросы и ответы

### Вопрос 1: Что такое процесс проектирования БД для аналитика?
**Ответ:** Процесс проектирования БД — это последовательность шагов, которые выполняются для создания базы данных. Начинается с понимания бизнес-требований ("нам нужны данные о клиентах"), затем создаётся концептуальная схема (сущности и связи), потом логическая модель (таблицы и поля), и наконец физическая реализация (индексы, типы данных). Аналитик участвует на всех этапах — от сбора требований до валидации результата.

### Вопрос 2: Почему важно тестировать спроектированную БД?
**Ответ:** Тестирование помогает выявить проблемы до того, как разработчики начнут писать код. Например, можно проверить, что запросы работают быстро, а данные сохраняются корректно. Это экономит время и снижает количество багов в продакшене.

### Вопрос 3: Кто отвечает за проектирование БД — аналитик или разработчик?
**Ответ:** Ответственность может быть разделена. Аналитик собирает требования и участвует в концептуальном моделировании, но часто именно разработчики (или DBA) создают финальную физическую схему с индексами и оптимизацией. Важно, чтобы аналитик понимал процесс и мог объяснить бизнес-требования.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Вам нужно спроектировать БД для интернет-магазина. Какие данные вы бы собрали на этапе требований?

**Ответ:**  
Я бы собрал информацию по следующим категориям:
1. **Клиенты**: имя, email, телефон, адрес доставки, история заказов
2. **Товары**: название, цена, описание, изображения, категория, поставщик
3. **Заказы**: номер заказа, дата создания, статус, сумма, способ оплаты
4. **Платежи**: номер транзакции, статус, валюта, время обработки

Также уточнил бы:
- Сколько примерно клиентов и заказов в день? (для оценки производительности)
- Какие отчёты нужно генерировать? (для определения индексов)
- Нужно ли хранить историю изменений данных? (аудит)

---

### Вопрос 2: Вы видите, что после проектирования БД запросы работают медленно. Ваши действия?

**Ответ:**  
Я бы проверил следующие моменты:
1. **Анализировал логи запросов** — какие именно запросы медленные и почему
2. **Проверил индексы** — возможно, не хватает индексов для часто используемых полей фильтрации
3. **Оценил нормализацию** — слишком сильно нормализованная БД может требовать много JOIN-запросов
4. **Подумал о партиционировании** — если таблица очень большая (например, заказы за несколько лет), возможно, нужно разбить её по месяцам

---

### Вопрос 3: Как вы объясните процесс проектирования БД бизнесу?

**Ответ:**  
Я бы использовал аналогию с планировкой магазина:
"Представьте, что мы открываем новый магазин. Сначала мы определяем, какие товары будем продавать и сколько места нужно (требования). Потом разбиваем помещение на зоны: кассы, склад, примерочные (таблицы). Затем размещаем полки и решаем, где хранить каждый товар (поля и связи). И в конце проверяем, удобно ли всё работает — можно ли быстро найти нужный товар (тестирование)."

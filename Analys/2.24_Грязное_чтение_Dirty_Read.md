# 2.24 Грязное чтение (Dirty Read): что такое и как избежать

---

## 📌 Короткий ответ

> **Грязное чтение** — это ситуация, когда одна транзакция читает данные, которые были изменены другой транзакцией, но ещё не подтверждены. Если вторая транзакция отменится, первая транзакция получит неверные данные.

---

## 💡 Простыми словами

### Аналогия с интернет-магазином

Представьте ситуацию на складе:

**Сценарий грязного чтения:**
1. **Клиент А** делает заказ на телефон за 30 000 ₽
2. **Менеджер Б** видит этот заказ и проверяет, есть ли в наличии телефоны по цене до 35 000 ₽
3. Менеджер видит: "Да, есть!" (потому что заказ Клиента А уже записан в систему)
4. Но вдруг **Клиент А отменяет заказ** перед подтверждением
5. Теперь менеджер Б принял решение на основе данных, которые больше не актуальны

**Проблема:** Менеджер принял решение о том, что телефон есть в наличии, хотя на самом деле его нет (потому что заказ был отменён).

### Пример из интернет-магазина (технический)

**Транзакция 1 (Клиент А):**
```sql
-- Клиент меняет статус заказа с "new" на "confirmed"
UPDATE orders SET status = 'confirmed' WHERE order_id = 123;

-- Но транзакция не подтверждена ещё!
-- Она находится в состоянии ожидания подтверждения
```

**Транзакция 2 (Клиент Б — грязное чтение):**
```sql
-- Клиент Б читает статус заказа, который только что изменил Клиент А
SELECT status FROM orders WHERE order_id = 123;
-- Результат: 'confirmed' (но это ещё не подтверждено!)

-- Клиент Б принимает решение на основе этого статуса
UPDATE notifications SET sent = true WHERE order_id = 123 AND status = 'confirmed';
```

**Проблема:** Если транзакция Клиента А отменится, то уведомление для Клиента Б будет отправлено ошибочно.

### Как это выглядит в коде (концептуально)

```sql
-- Транзакция 1: Обновляет данные
BEGIN TRANSACTION;
UPDATE products SET price = 2500 WHERE product_id = 100; -- Цена снижена
COMMIT; -- Или ROLLBACK!
```

```sql
-- Транзакция 2: Читает данные (грязное чтение)
SELECT price FROM products WHERE product_id = 100;
-- Видит цену 2500, но если транзакция 1 отменится — это неверно
```

## 🔍 Подробно

### Что такое транзакция?

**Транзакция** — это набор операций с данными, которые выполняются как единое целое. Либо все операции выполнятся успешно (COMMIT), либо ни одна не выполнится (ROLLBACK).

**Пример из интернет-магазина:**
```sql
-- Транзакция при оформлении заказа:
BEGIN TRANSACTION;

-- 1. Создаём заказ
INSERT INTO orders (user_id, total_amount) VALUES (5, 3000);

-- 2. Уменьшаем остаток товара
UPDATE products SET stock = stock - 1 WHERE product_id = 100;

-- 3. Записываем в историю изменений
INSERT INTO order_history (order_id, action) VALUES (123, 'created');

COMMIT; -- Всё выполнено успешно
```

Если на любом этапе возникнет ошибка — всё откатится:
```sql
ROLLBACK; -- Отменяем все изменения
```

### Что такое изоляция транзакций?

**Изоляция транзакций** — это свойство БД, которое гарантирует, что несколько одновременных транзакций не будут мешать друг другу. Это одна из 4 свойств ACID.

Без изоляции:
- Транзакция А может прочитать данные транзакции Б до её подтверждения (грязное чтение)
- Две транзакции могут одновременно изменить одно и то же поле, и одно изменение потеряется

### Типы проблем с изоляцией (аномалии)

#### 1. Грязное чтение (Dirty Read)

**Что происходит:** Транзакция читает данные, которые были изменены другой транзацией, но ещё не подтверждены. Если вторая транзация отменится — первая получит неверные данные.

**Пример из интернет-магазина:**
```sql
-- Транзакция 1: Менеджер меняет цену товара
BEGIN TRANSACTION;
UPDATE products SET price = 200 WHERE product_id = 50; -- Цена снижена с 300 до 200

-- Транзакция 2: Клиент читает новую цену (грязное чтение!)
SELECT price FROM products WHERE product_id = 50;
-- Видит 200, но если менеджер отменит изменение — это неверно
```

**Когда возникает:** Уровень изоляции `READ UNCOMMITTED`

#### 2. Чтение несостоянных данных (Non-repeatable Read)

**Что происходит:** Одна и та же транзакция читает одни и те же данные дважды, но между чтениями другая транзакция изменила эти данные.

**Пример из интернет-магазина:**
```sql
-- Транзакция 1: Клиент проверяет остаток товара
BEGIN TRANSACTION;
SELECT stock FROM products WHERE product_id = 100; -- Результат: 5 штук

-- Другая транзакция уменьшает остаток
UPDATE products SET stock = stock - 3 WHERE product_id = 100;

-- Транзакция 1 читает снова (несостоянные данные!)
SELECT stock FROM products WHERE product_id = 100; -- Результат: 2 штуки!
```

**Когда возникает:** Уровень изоляции `READ COMMITTED`

#### 3. Потерянное обновление (Lost Update)

**Что происходит:** Две транзакции одновременно читают одно и то же значение, изменяют его и записывают обратно. Одно изменение теряется.

**Пример из интернет-магазина:**
```sql
-- Транзакция 1: Клиент А хочет купить 2 товара
BEGIN TRANSACTION;
SELECT stock FROM products WHERE product_id = 100; -- Результат: 5 штук

-- Транзакция 2: Клиент Б тоже хочет купить 2 товара (одновременно!)
BEGIN TRANSACTION;
SELECT stock FROM products WHERE product_id = 100; -- Результат: 5 штук

-- Обе транзакции уменьшают остаток на 2
UPDATE products SET stock = stock - 2 WHERE product_id = 100 AND id = 123;
UPDATE products SET stock = stock - 2 WHERE product_id = 100 AND id = 456;

-- Итог: остаток уменьшился только на 2, хотя должен был уменьшиться на 4!
```

**Когда возникает:** Уровень изоляции `READ COMMITTED` и выше

### Уровни изоляции транзакций (от самого низкого к самому высокому)

#### 1. READ UNCOMMITTED — Грязное чтение разрешено

**Что разрешено:** Транзакции могут читать данные, которые ещё не подтверждены другими транзакциями.

**Проблемы:**
- ✅ Нет блокировок (высокая производительность)
- ❌ Грязное чтение возможно

**Когда использовать:** Редко! Только когда грязные данные не критичны (например, аналитика).

#### 2. READ COMMITTED — Стандартный уровень

**Что разрешено:** Транзакции читают только подтверждённые данные других транзакций.

**Проблемы:**
- ✅ Нет грязного чтения
- ❌ Чтение несостоянных данных возможно
- ❌ Потерянное обновление возможно

**Когда использовать:** Часто используется по умолчанию в PostgreSQL, SQL Server.

#### 3. REPEATABLE READ — Повторяемое чтение

**Что разрешено:** Транзакция видит одни и те же данные при каждом чтении (в рамках одной транзакции).

**Проблемы:**
- ✅ Нет грязного чтения
- ✅ Нет чтения несостоянных данных
- ❌ Потерянное обновление возможно

**Когда использовать:** Когда важно, чтобы данные не менялись в рамках одной транзакции.

#### 4. SERIALIZABLE — Полная изоляция (самый строгий)

**Что разрешено:** Транзакции выполняются как будто последовательно, одна за другой. Никаких параллельных изменений.

**Проблемы:**
- ✅ Нет никаких аномалий изоляции
- ❌ Много блокировок (низкая производительность при высокой нагрузке)

**Когда использовать:** Для критически важных операций с данными.

### Пример из интернет-магазина: разные уровни изоляции

#### Сценарий: Проверка наличия товара перед покупкой

**Уровень READ UNCOMMITTED (грязное чтение):**
```sql
-- Клиент проверяет наличие товара
SELECT stock FROM products WHERE product_id = 100; -- Результат: 5 штук

-- Другой клиент уже купил 3 штуки, но ещё не подтвердил заказ
UPDATE products SET stock = stock - 3 WHERE product_id = 100;

-- Первый клиент покупает товар (думая, что есть 5 штук)
INSERT INTO orders ... -- Ошибка! Не хватает товара
```

**Уровень READ COMMITTED (стандартный):**
```sql
-- Клиент проверяет наличие товара
SELECT stock FROM products WHERE product_id = 100; -- Результат: 5 штук

-- Другой клиент подтверждает заказ на 3 штуки
UPDATE products SET stock = stock - 3 WHERE product_id = 100;

-- Первый клиент покупает товар (видит актуальные данные)
INSERT INTO orders ... -- Успешно! Осталось 2 штуки
```

**Уровень SERIALIZABLE (полная изоляция):**
```sql
-- Обе транзакции выполняются последовательно, одна за другой
-- Нет риска конфликтов, но производительность ниже
```

## ✅ Плюсы и минусы уровней изоляции

### ✅ Преимущества разных уровней изоляции

| Уровень | Преимущество | Объяснение |
|---------|--------------|------------|
| **READ UNCOMMITTED** | Высокая производительность | Нет блокировок, транзакции не ждут друг друга |
| **READ COMMITTED** | Баланс между производительностью и корректностью | Нет грязного чтения, но меньше блокировок чем в SERIALIZABLE |
| **REPEATABLE READ** | Гарантирует стабильные данные в рамках транзакции | Подходит для сложных отчётов и аналитики |
| **SERIALIZABLE** | Полная защита от всех аномалий | Гарантирует корректность данных ценой производительности |

### ❌ Недостатки разных уровней изоляции

| Уровень | Недостаток | Объяснение |
|---------|------------|------------|
| **READ UNCOMMITTED** | Грязное чтение | Данные могут быть неверными, если транзакция отменится |
| **READ COMMITTED** | Чтение несостоянных данных и потерянное обновление | Требует дополнительных механизмов для защиты |
| **REPEATABLE READ** | Потерянное обновление возможно | Нужно использовать дополнительные блокировки |
| **SERIALIZABLE** | Низкая производительность | Много блокировок, транзакции ждут друг друга |

---

## 📌 Что важно запомнить аналитику

1. **Грязное чтение — это когда вы читаете данные, которые ещё не подтверждены другой транзакцией**
2. **Безопаснее использовать уровни изоляции READ COMMITTED или выше**
3. **Выбор уровня изоляции зависит от бизнес-требований:** если неверные данные критичны — используйте более строгий уровень
4. **Аналитик должен понимать, какие операции с данными могут привести к проблемам изоляции**

## ❓ Типичные вопросы и ответы

### Вопрос 1: Что такое грязное чтение для аналитика?
**Ответ:** Грязное чтение — это ситуация, когда одна транзакция читает данные, которые были изменены другой транзакцией, но ещё не подтверждены. Если вторая транзакция отменится, первая транзакция получит неверные данные. Например, менеджер видит новую цену товара, которую менеджер по продажам временно снизил, а потом отменил.

### Вопрос 2: Какой уровень изоляции защищает от грязного чтения?
**Ответ:** Уровень READ COMMITTED и выше (REPEATABLE READ, SERIALIZABLE) защищают от грязного чтения. На уровне READ UNCOMMITTED грязное чтение возможно — это самый низкий уровень изоляции.

### Вопрос 3: Когда нужно использовать высокий уровень изоляции?
**Ответ:** Высокий уровень изоляции нужен, когда корректность данных критически важна и последствия неверных данных серьёзны. Например, при финансовых операциях или обработке заказов. Но высокая изоляция снижает производительность из-за блокировок.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: В интернет-магазине клиент покупает товар, а система показывает ошибку "недостаточно товара", хотя в системе есть нужный остаток. Ваши действия?

**Ответ:**  
Я бы проверил следующие моменты:
1. **Проверил уровень изоляции транзакций** — возможно, используется READ UNCOMMITTED и происходит грязное чтение
2. **Проанализировал логи транзакций** — возможно, другая транзакция уже уменьшила остаток, но ещё не подтвердилась
3. **Убедился в корректности блокировок** — возможно, есть конфликт между двумя транзакциями

---

### Вопрос 2: Вам нужно спроектировать систему учёта склада с высокой нагрузкой. Как вы подойдёте к выбору уровня изоляции?

**Ответ:**  
Я бы начал с анализа бизнес-требований:
1. **Оценил критичность ошибок** — если неверный остаток критичен, нужен высокий уровень изоляции (SERIALIZABLE)
2. **Проанализировал нагрузку** — при высокой нагрузке SERIALIZABLE может снизить производительность
3. **Выбрал компромисс** — возможно, READ COMMITTED для большинства операций и SERIALIZABLE только для критических

---

### Вопрос 3: Как вы объясните уровень изоляции транзакций бизнесу?

**Ответ:**  
Я бы использовал аналогию с кассой в магазине:
"Представьте, что два клиента одновременно пытаются купить последний товар. Если касса не блокирует их (низкий уровень изоляции), один из клиентов может получить товар, хотя он уже продан другому. Уровень изоляции — это как очередь у кассы: чем строже правила, тем медленнее обслуживание, но меньше ошибок".

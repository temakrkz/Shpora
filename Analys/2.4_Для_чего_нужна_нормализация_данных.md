# 2.4 Для чего нужна нормализация данных: что такое, плюсы и минусы

---

## Короткий ответ

**Нормализация данных** — это процесс организации структуры базы данных для уменьшения дублирования информации и повышения целостности данных. Данные разбиваются на логические таблицы с чёткими связями между ними.

---

## Простыми словами

### Аналогия с интернет-магазином

Представьте таблицу заказов в магазине:

**Без нормализации (плохо):**
```
Заказы:
ID | Клиент    | Товар       | Цена  | Адрес доставки
1  | Иванов И. | Футболка    | 500   | ул. Ленина, д. 1
2  | Петров П. | Рубашка     | 800   | пр. Мира, д. 5
3  | Иванов И. | Джинсы      | 1200  | ул. Ленина, д. 1
4  | Сидоров С.| Футболка    | 500   | наб. Реки, д. 10
```

**Проблема:** адрес клиента "Иванов И." записан дважды — если он изменится, нужно обновлять в двух местах. Риск ошибки и несогласованности данных.

**С нормализацией (хорошо):**
```
Клиенты:
ID | ФИО        | Адрес доставки
1  | Иванов И.  | ул. Ленина, д. 1
2  | Петров П.  | пр. Мира, д. 5
3  | Сидоров С. | наб. Реки, д. 10

Заказы:
ID | Клиент_ID | Товар    | Цена
1  | 1         | Футболка | 500
2  | 2         | Рубашка  | 800
3  | 1         | Джинсы   | 1200
4  | 3         | Футболка | 500
```

**Преимущество:** адрес хранится только один раз в таблице клиентов. Если он изменится — обновляем в одном месте, и все заказы автоматически актуальны.

### Таблица сравнения подходов

| Подход | Дублирование данных | Риск ошибок | Удобство чтения |
|--------|---------------------|-------------|-----------------|
| **Без нормализации** | Много (адреса, имена повторяются) | Высокий (нужно обновлять в нескольких местах) | Простой (всё в одной таблице) |
| **С нормализацией** | Минимум (каждое поле хранится один раз) | Низкий (обновление в одном месте) | Сложнее (нужны JOIN между таблицами) |

## Подробно

### Что такое нормализация?

Нормализация — это процесс проектирования базы данных таким образом, чтобы:
1. **Уменьшить дублирование данных** — каждое значение хранится только в одном месте
2. **Повысить целостность данных** — изменения в одном месте автоматически отражаются везде
3. **Создать чёткие связи между данными** — через первичные и внешние ключи

### Нормализация по уровням (нормальным формам)

**1NF (Первая нормальная форма):**
- Каждая ячейка содержит только одно значение
- Нет повторяющихся групп колонок

**2NF (Вторая нормальная форма):**
- Все данные зависят от всего первичного ключа
- Нет частичных зависимостей

**3NF (Третья нормальная форма):**
- Нет транзитивных зависимостей
- Данные не зависят от других данных, кроме первичного ключа

### Пример из интернет-магазина: нормализация заказа

**До нормализации:**
```sql
-- Одна таблица с дублированием
CREATE TABLE orders (
    id INT PRIMARY KEY,
    customer_name VARCHAR(100),
    customer_email VARCHAR(255),
    customer_address TEXT,
    product_name VARCHAR(100),
    product_price DECIMAL(10, 2),
    quantity INT
);
```

**Проблемы:**
- Если клиент меняет email — нужно обновлять во всех заказах
- Если цена товара меняется — нужно обновлять в каждом заказе
- Много дублирования данных

**После нормализации:**
```sql
-- Таблица клиентов (хранится один раз)
CREATE TABLE customers (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255),
    address TEXT
);

-- Таблица товаров (цена хранится один раз)
CREATE TABLE products (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    price DECIMAL(10, 2)
);

-- Таблица заказов (ссылается на клиенты и товары через foreign key)
CREATE TABLE orders (
    id INT PRIMARY KEY,
    customer_id INT REFERENCES customers(id),
    product_id INT REFERENCES products(id),
    quantity INT,
    order_date TIMESTAMP
);
```

**Преимущества:**
- Email клиента хранится один раз — если он изменится, обновляем в таблице клиентов
- Цена товара хранится один раз — при изменении применяется ко всем заказам автоматически
- Минимум дублирования данных

## Плюсы и минусы нормализации

### ✅ Плюсы нормализации

| Преимущество | Объяснение |
|-------------|------------|
| **Минимальное дублирование** | Каждое значение хранится только в одном месте |
| **Целостность данных** | Изменения применяются автоматически ко всем связанным записям |
| **Экономия места** | Меньше повторяющихся данных = меньше объём базы |
| **Предсказуемость** | Структура данных чётко определена и документирована |

### ❌ Минусы нормализации

| Недостаток | Объяснение |
|-----------|------------|
| **Сложные запросы** | Нужно использовать JOIN для получения полной информации из нескольких таблиц |
| **Производительность чтения** | Много табличных соединений замедляют чтение данных |
| **Сложность разработки** | Требует тщательного проектирования структуры базы данных |

---

## Что важно запомнить аналитику

1. **Нормализация — это про запись данных**. Она оптимизирует хранение и целостность, но может замедлить чтение из-за необходимости JOIN между таблицами.

2. **Часто используется вместе с денормализацией** — для записи данные нормализованы (минимум дублирования), а для чтения созданы денормализованные копии (быстрые запросы). Это основа CQRS.

3. **Идеальна для финансовых систем**. Банки, платежи и заказы требуют строгой целостности данных — нормализация здесь критична.

4. **Не подходит для высоконагруженных систем чтения**. Если чтение происходит в разы чаще записи (дашборды, профили), нормализованная структура может стать узким местом.

5. **Для junior-аналитика важно понимать**, что нормализация — это не всегда хорошо. Нужно балансировать между целостностью данных и производительностью чтения в зависимости от требований бизнеса.

## ❓ Типичные вопросы и ответы

### Вопрос 1: В чём разница между нормализацией и денормализацией?

**Ответ:**  
Нормализация уменьшает дублирование данных, разбивая их на логические таблицы с чёткими связями. Денормализация намеренно дублирует данные для ускорения чтения — например, хранит имя клиента прямо в таблице заказов вместо ссылки на таблицу клиентов. Нормализация оптимизирует запись и целостность данных, денормализация — чтение и производительность.

---

### Вопрос 2: Почему нормализованная база может работать медленнее при чтении?

**Ответ:**  
При нормализации данные разбиты на несколько таблиц. Чтобы получить полную информацию (например, список заказов с именами клиентов), нужно выполнять JOIN между таблицами — это дополнительные операции для базы данных. При денормализации все нужные поля хранятся в одной таблице, и запрос выполняется быстрее. Поэтому для систем с высокой нагрузкой на чтение часто создают отдельные денормализованные копии данных.

---

### Вопрос 3: Когда стоит отказаться от нормализации?

**Ответ:**  
Нормализацию можно не использовать когда:
- Требуется максимальная скорость чтения (дашборды, профили пользователей)
- Структура данных часто меняется и сложно поддерживать чёткие связи
- Данные временные или кэшируемые (просмотры товаров, рекомендации)

В таких случаях можно намеренно дублировать данные для ускорения чтения — это называется денормализация. Важно явно указать это в техническом задании и предусмотреть механизмы синхронизации данных между нормализованной и денормализованными таблицами.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы ты поступил, если бизнес просит добавить дашборд аналитики с мгновенным отображением продаж?

**Ответ:**  
Я бы предложил гибридный подход:
- **Основная база данных нормализована** — хранятся заказы, клиенты и товары с чёткими связями для целостности данных
- **Отдельная денормализованная копия** — таблицы со статистикой продаж, которая обновляется при каждом изменении в основной базе

Для мгновенного отображения дашборд читает данные из денормализованной копии (быстро), а не из нормализованной базы с JOIN-запросами. Это основа CQRS: команды записывают данные в нормализованную структуру, а проекции создают оптимизированные представления для чтения.

---

### Вопрос 2: Что делать, если нужно часто менять структуру данных (добавлять новые поля)?

**Ответ:**  
В строго нормализованной базе добавление новых полей требует ALTER TABLE и миграций, что может привести к простоям. Я бы предложил использовать NoSQL документную базу для таких случаев — каждый документ может иметь произвольные поля без необходимости менять структуру всей таблицы. Для критичных операций (платежи) можно оставить нормализованную реляционную БД, а для гибких данных (профили пользователей) — NoSQL.

---

### Вопрос 3: Как объяснить бизнесу необходимость нормализации данных?

**Ответ:**  
Я бы объяснил так: "Представьте, что вы ведёте бухгалтерию и храните данные о клиентах в одном месте. Если клиент меняет адрес, вам нужно обновить его только один раз — это как нормализация. Если же вы записываете адрес в каждой записи о заказе, то при изменении адреса нужно обновлять сотни или тысячи записей вручную, что приводит к ошибкам. Нормализация гарантирует, что данные всегда актуальны и непротиворечивы".

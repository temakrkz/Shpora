# 2.5 Что такое денормализация и в каких случаях используется: что такое, плюсы и минусы

---

## Короткий ответ

**Денормализация данных** — это намеренное дублирование данных в базе данных для ускорения чтения. Вместо JOIN между таблицами все нужные поля хранятся в одной таблице или создаются отдельные копии данных.

---

## Простыми словами

### Аналогия с интернет-магазином

Представьте **таблицу заказов** в магазине:

| Сценарий | Как работает |
|----------|--------------|
| **Нормализация** (медленно) | Запрос читает таблицу заказов, делает JOIN с таблицей клиентов для получения имени и адреса клиента — несколько операций |
| **Денормализация** (быстро) | Таблица заказов уже содержит имя и адрес клиента — всё в одной таблице, один запрос, мгновенное отображение |

### Пример из интернет-магазина

**Нормализованная структура:**
```sql
-- Таблица заказов (только ID клиента)
orders: { id: 123, customer_id: 456 }

-- Таблица клиентов
customers: { id: 456, name: "Иван Иванов", address: "ул. Ленина, д. 1" }

-- Запрос: показать заказ с именем клиента
SELECT orders.*, customers.name FROM orders JOIN customers ON orders.customer_id = customers.id;
```

**Денормализованная структура:**
```sql
-- Таблица заказов (уже содержит имя и адрес)
orders: { 
  id: 123, 
  customer_name: "Иван Иванов", 
  customer_address: "ул. Ленина, д. 1",
  product: "Футболка" 
}

-- Запрос: показать заказ с именем клиента
SELECT * FROM orders WHERE id = 123;
```

**Преимущество:** один запрос вместо JOIN — быстрее при чтении!

### Таблица сравнения подходов

| Подход | Скорость чтения | Скорость записи | Объём данных | Риск ошибок |
|--------|-----------------|-----------------|--------------|-------------|
| **Нормализация** | Медленнее (нужны JOIN) | Быстрее (меньше дублирования) | Меньший | Низкий |
| **Денормализация** | Быстрее (всё в одной таблице) | Медленнее (нужно обновлять в нескольких местах) | Больше | Средний (нужна синхронизация) |

## Подробно

### Что такое денормализация?

Денормализация — это процесс намеренного дублирования данных для ускорения чтения:
1. **Поля из разных таблиц копируются в одну** — вместо JOIN все данные сразу доступны
2. **Создаются отдельные копии данных** — для чтения используются денормализованные представления, а запись идёт в нормализованную базу

### Примеры денормализации из интернет-магазина

**Пример 1: Профиль пользователя с историей заказов**

| Таблица | Данные |
|---------|--------|
| **Денормализованный профиль (для быстрого чтения)** | id, name, email, total_orders, last_order_date, favorite_category |
| **Нормализованная история заказов** | order_id, customer_id, product_name, amount, date |

Когда пользователь заходит в свой профиль — система показывает данные из денормализованной таблицы (мгновенно). При создании нового заказа — обновляется счётчик total_orders и last_order_date.

**Пример 2: Страница товара с информацией о продавце**

| Таблица | Данные |
|---------|--------|
| **Денормализованный товар** | id, name, price, description, seller_name, seller_rating, seller_location |
| **Нормализованная информация о продавце** | seller_id, name, rating, location |

На странице товара сразу показывается имя и рейтинг продавца без JOIN-запроса. При изменении данных продавца — обновляется денормализованная копия через события или триггеры.

### Как работает синхронизация?

Денормализованные данные должны быть актуальными, поэтому используются механизмы синхронизации:

1. **При записи в нормализованную БД** — автоматически обновляются денормализованные копии
2. **Через события и очереди** — при изменении данных создаётся событие, которое обрабатывается проекцией для обновления денормализованных таблиц
3. **Периодическая синхронизация** — денормализованные данные обновляются раз в минуту/час (для аналитики)

### Пример из интернет-магазина: CQRS с денормализацией

| Операция | Что происходит |
|----------|----------------|
| **Запись (Command)** | Клиент создаёт заказ → данные сохраняются в нормализованную БД заказов → создаётся событие OrderCreated |
| **Обновление проекции** | Событие OrderCreated обрабатывается сервисом, который обновляет денормализованные таблицы: счётчик продаж, профиль клиента с total_orders |
| **Чтение (Query)** | Пользователь смотрит дашборд → данные читаются из денормализованных таблиц мгновенно без JOIN |

## Плюсы и минусы денормализации

### ✅ Плюсы денормализации

| Преимущество | Объяснение |
|-------------|------------|
| **Высокая скорость чтения** | Все данные в одной таблице — нет необходимости выполнять JOIN |
| **Меньше запросов к БД** | Один SELECT вместо нескольких JOIN-запросов |
| **Идеально для дашбордов и отчётов** | Аналитика работает быстро на денормализованных данных |
| **Упрощение сложных запросов** | Не нужно думать о структуре связей при чтении |

### ❌ Минусы денормализации

| Недостаток | Объяснение |
|-----------|------------|
| **Дублирование данных** | Одно и то же значение хранится в нескольких местах |
| **Сложность записи** | При изменении нужно обновлять данные во всех дублируемых местах |
| **Риск несогласованности** | Если обновление не дошло до всех копий — данные могут отличаться |
| **Больший объём базы данных** | Хранится больше информации, чем необходимо |

---

## Что важно запомнить аналитику

1. **Денормализация — это про чтение**. Она оптимизирует скорость чтения, но усложняет запись и требует механизмов синхронизации.

2. **Часто используется вместе с нормализацией** — для записи данные нормализованы (целостность), а для чтения созданы денормализованные копии (скорость). Это основа CQRS.

3. **Идеальна для систем с высокой нагрузкой на чтение**. Если чтение происходит в 10-100 раз чаще записи (дашборды, профили пользователей), денормализация критична для производительности.

4. **Не подходит для финансовых операций**. Платежи и заказы требуют строгой целостности данных — здесь нормализация важнее скорости чтения.

5. **Для junior-аналитика важно понимать**, что денормализация не всегда плохо. Нужно балансировать между целостностью данных и производительностью в зависимости от требований бизнеса.

## ❓ Типичные вопросы и ответы

### Вопрос 1: В чём разница между нормализацией и денормализацией?

**Ответ:**  
Нормализация уменьшает дублирование данных, разбивая их на логические таблицы с чёткими связями — это оптимизирует запись и целостность. Денормализация намеренно дублирует данные для ускорения чтения — все нужные поля хранятся в одной таблице или создаются отдельные копии. Нормализация подходит для финансовых систем, денормализация — для высоконагруженных систем с высокой нагрузкой на чтение.

---

### Вопрос 2: Что будет, если денормализованные данные не будут актуальными?

**Ответ:**  
Это проблема несогласованности данных. Если обновление в нормализованной базе дошло, а в денормализованную копию не — пользователь увидит устаревшие данные. В техническом задании нужно предусмотреть механизмы синхронизации: автоматическое обновление при записи через триггеры или события, периодическую синхронизацию для аналитики, и явно указать допустимую задержку в данных (например, "данные обновляются с задержкой не более 5 секунд").

---

### Вопрос 3: Когда стоит отказаться от денормализации?

**Ответ:**  
Денормализацию можно не использовать когда:
- Требуется строгая целостность финансовых данных (платежи, заказы)
- Нагрузка на чтение небольшая или сопоставима с записью
- Структура данных часто меняется и сложно поддерживать дублирование
- Система простая и нормализованная база справляется с нагрузкой

В таких случаях лучше использовать нормализованную структуру без искусственного дублирования данных.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы ты поступил, если бизнес просит добавить дашборд аналитики с мгновенным отображением продаж?

**Ответ:**  
Я бы предложил гибридный подход:
- **Основная база данных нормализована** — хранятся заказы, клиенты и товары с чёткими связями для целостности данных
- **Отдельные денормализованные таблицы** — статистика продаж (количество заказов, сумма выручки), которая обновляется при каждом изменении в основной базе

Для мгновенного отображения дашборд читает данные из денормализованных таблиц (быстро), а не из нормализованной базы с JOIN-запросами. Это основа CQRS: команды записывают данные в нормализованную структуру, а проекции создают оптимизированные представления для чтения.

---

### Вопрос 2: Что делать, если нужно часто менять структуру данных (добавлять новые поля)?

**Ответ:**  
В строго денормализованной базе добавление новых полей требует обновления всех дублируемых таблиц, что сложно поддерживать. Я бы предложил использовать NoSQL документную базу для таких случаев — каждый документ может иметь произвольные поля без необходимости менять структуру всей таблицы. Для критичных операций (платежи) можно оставить нормализованную реляционную БД, а для гибких данных (профили пользователей, настройки) — NoSQL с возможностью добавлять новые поля без миграций.

---

### Вопрос 3: Как объяснить бизнесу необходимость денормализации?

**Ответ:**  
Я бы объяснил так: "Представьте, что вы смотрите на страницу профиля пользователя с историей заказов. Если данные хранятся в разных таблицах (клиенты и заказы), системе нужно выполнить несколько запросов для получения всей информации — это как ждать ответа от нескольких коллег по телефону. Денормализация работает иначе: все нужные данные уже собраны в одном месте, как если бы коллега заранее подготовил полный ответ. Страница загружается мгновенно, но при изменении данных нужно обновлять их во всех местах".

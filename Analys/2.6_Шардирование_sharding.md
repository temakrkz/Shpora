# 2.6 Шардирование (sharding): что такое, плюсы и минусы

---

## Короткий ответ

**Шардирование (Sharding)** — это способ горизонтального масштабирования базы данных: данные разбиваются на части (шарды) и распределяются по нескольким серверам. Это позволяет обрабатывать большие объёмы данных и высокую нагрузку, добавляя новые серверы вместо замены старого оборудования.

---

## Простыми словами

### Аналогия с интернет-магазином

Представьте **большой склад** интернет-магазина:

| Ситуация | Без шардирования | С шардированием |
|----------|------------------|-----------------|
| **Малый магазин** | Один большой склад хранит все товары — достаточно одного менеджера | Не нужно шардирование, один сервер справляется |
| **Большой магазин (миллионы товаров)** | Один менеджер не успевает работать с миллионами товаров — система тормозит | Склад разбит на 10 отделов (шардов), каждый работает со своими товарами |

**Пример из интернет-магазина:**

У магазина миллионы заказов. Если хранить все в одной таблице на одном сервере:
- Запросы становятся медленными
- Добавление новых товаров требует перестройки всей базы
- Сервер не справляется с нагрузкой

С шардированием:
- **Шард 1**: заказы клиентов с ID от 1 до 100,000
- **Шард 2**: заказы клиентов с ID от 100,001 до 200,000
- ...
- **Шард N**: заказы клиентов с ID > (N-1)×100,000

Каждый шард — это отдельная база данных на своём сервере. Запросы распределяются по нужному шарду автоматически.

### Таблица сравнения подходов

| Подход | Когда работает хорошо | Проблемы при росте |
|--------|----------------------|--------------------|
| **Вертикальное масштабирование** (больший сервер) | Малый/средний объём данных | Ограничено мощностью одного сервера, дорого |
| **Горизонтальное масштабирование / шардирование** | Большие объёмы данных, высокая нагрузка | Сложность распределения данных, миграция между шардами |

## Подробно

### Как работает шардирование?

Шардирование разбивает одну большую базу данных на несколько меньших (шардов), которые распределяются по разным серверам.

**Основные стратегии шардирования:**

1. **По диапазону ID** — данные делятся по числовому диапазону
   ```
   Шард 1: user_id от 1 до 10,000
   Шард 2: user_id от 10,001 до 20,000
   Шард 3: user_id от 20,001 до 30,000
   ```

2. **По хешу** — ID преобразуется в хеш-код для распределения
   ```
   user_id = 12345 → hash(12345) % 3 = 1 → Шард 1
   user_id = 67890 → hash(67890) % 3 = 2 → Шард 2
   ```

3. **По географии** — данные делятся по регионам
   ```
   Шард 1: пользователи из Москвы и области
   Шард 2: пользователи из Санкт-Петербурга и области
   Шард 3: пользователи из других регионов
   ```

4. **Комбинированная стратегия** — комбинация нескольких подходов для равномерного распределения

### Пример из интернет-магазина: шардирование заказов

**Ситуация:** Магазин обрабатывает миллионы заказов в месяц. Одна база данных не справляется с нагрузкой.

**Решение через шардирование по ID заказа:**
```
Шард 1 (PostgreSQL на сервере А):
- Заказы с order_id от 1 до 500,000

Шард 2 (PostgreSQL на сервере Б):
- Заказы с order_id от 500,001 до 1,000,000

Шард 3 (PostgreSQL на сервере В):
- Заказы с order_id от 1,000,001 до 1,500,000
```

**Как работает запрос:**
```sql
-- Клиент ищет заказ по ID
SELECT * FROM orders WHERE id = 456789;

-- Система:
1. Вычисляет, что 456789 попадает в диапазон Шард 1
2. Отправляет запрос только на сервер А (не нужно искать на всех)
3. Получает результат мгновенно
```

### Зачем используется шардирование?

1. **Горизонтальное масштабирование** — можно добавлять новые серверы вместо замены старого оборудования
2. **Обработка больших объёмов данных** — каждый шард хранит только часть данных, что ускоряет работу
3. **Высокая нагрузка** — запросы распределяются по нескольким серверам параллельно

### Пример из интернет-магазина: рост базы данных

| Время | Объём данных | Решение |
|-------|--------------|---------|
| 1 год | 10 млн заказов | Один сервер, одна база данных |
| 2 года | 50 млн заказов | Добавлен второй шард (разбивка по ID) |
| 3 года | 200 млн заказов | Добавлены ещё два шарда (всего 4 сервера) |

Без шардирования пришлось бы постоянно заменять серверы на более мощные — это дорого и требует простоя системы.

## Плюсы и минусы шардирования

### ✅ Плюсы шардирования

| Преимущество | Объяснение |
|-------------|------------|
| **Горизонтальное масштабирование** | Можно добавлять новые серверы вместо замены старого оборудования |
| **Обработка больших объёмов данных** | Каждый шард хранит только часть данных, что ускоряет работу с запросами |
| **Высокая нагрузка** | Запросы распределяются по нескольким серверам параллельно |
| **Стоимость** | Дешевле масштабирование: можно добавлять бюджетные серверы вместо дорогих мощных |

### ❌ Минусы шардирования

| Недостаток | Объяснение |
|-----------|------------|
| **Сложность распределения данных** | Нужно правильно выбрать стратегию шардирования, чтобы данные распределялись равномерно |
| **Проблемы с JOIN между шардами** | Запросы, объединяющие данные из разных шардов, работают медленно или не поддерживаются |
| **Миграция данных сложная** | Перенос данных между шардами требует остановки системы или сложных механизмов миграции |
| **Увеличение сложности архитектуры** | Нужно управлять несколькими базами данных вместо одной |

---

## Что важно запомнить аналитику

1. **Шардирование — это про горизонтальное масштабирование**. В отличие от вертикального (больший сервер), шардирование добавляет новые серверы для распределения нагрузки.

2. **Не все запросы поддерживаются**. JOIN между данными из разных шардов часто не работает или очень медленный. Нужно проектировать систему так, чтобы минимизировать такие запросы.

3. **Выбор стратегии критичен**. Если данные распределяются неравномерно (например, некоторые ID используются чаще), некоторые шарды будут перегружены, а другие простаивать.

4. **Миграция сложная**. Добавление нового шарда требует перераспределения данных из старых шардов — это может потребовать остановки системы или сложных механизмов миграции в реальном времени.

5. **Идеален для определённых сценариев**:
   - Системы с предсказуемым ростом (например, по ID)
   - Когда данные можно логически разделить на независимые части
   - Высокая нагрузка и большие объёмы данных

6. **Для junior-аналитика важно понимать**, что шардирование — это не панацея. Оно усложняет архитектуру и подходит только для определённых сценариев. Нужно тщательно оценивать требования бизнеса перед внедрением.

## ❓ Типичные вопросы и ответы

### Вопрос 1: В чём разница между вертикальным и горизонтальным масштабированием?

**Ответ:**  
Вертикальное масштабирование (scale-up) — это замена сервера на более мощный (больше CPU, RAM, диск). Горизонтальное масштабирование (scale-out) — добавление новых серверов для распределения нагрузки. Вертикальное проще в реализации, но ограничено мощностью одного сервера и дорого при росте. Горизонтальное позволяет практически неограниченно добавлять ресурсы, но усложняет архитектуру (например, шардирование БД).

---

### Вопрос 2: Что будет, если JOIN нужно сделать между данными из разных шардов?

**Ответ:**  
Это одна из главных проблем шардирования. Стандартные СУБД не поддерживают эффективный JOIN между разными базами данных. Возможные решения:
- **Консолидация запросов**: объединять данные на уровне приложения перед отправкой в БД
- **Шардирование по ключу**: проектировать систему так, чтобы часто используемые JOIN были внутри одного шарда
- **Отказ от шардирования** для таких сценариев и использование вертикального масштабирования

В техническом задании нужно явно указать, какие запросы требуют JOIN между разными сущностями — это влияет на выбор стратегии шардирования.

---

### Вопрос 3: Когда стоит отказаться от шардирования?

**Ответ:**  
Шардирование можно не использовать когда:
- Объём данных небольшой и предсказуемый (вертикальное масштабирование дешевле)
- Часто нужны JOIN между разными сущностями
- Система простая и шардирование усложнит архитектуру без реальной пользы
- Нет технической команды, способной поддерживать распределённую систему

В таких случаях лучше использовать вертикальное масштабирование или NoSQL базы данных, которые проще масштабировать горизонтально.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы ты поступил, если бизнес просит добавить поддержку миллионов пользователей с историей заказов?

**Ответ:**  
Я бы оценил требования к данным и нагрузке:
- Если история заказов важна (нужно хранить все действия пользователя) — шардирование обязательно из-за объёма данных
- Если нужна только актуальная информация о пользователе — можно использовать денормализацию и кэширование без шардирования

Затем я бы предложил стратегию шардирования по ID пользователя: каждый шард отвечает за диапазон пользователей. Для JOIN между заказами и историей действий одного пользователя нужно проектировать систему так, чтобы все данные о пользователе находились в одном шарде (шардирование по ключу пользователя).

---

### Вопрос 2: Что делать, если данные распределяются неравномерно по шардам?

**Ответ:**  
Это проблема "горячих" и "холодных" шардов. Решения:
- **Пересмотреть стратегию шардирования**: вместо диапазона использовать хеширование для равномерного распределения
- **Ребалансировка**: периодически перераспределять данные между шардами (требует остановки или сложных механизмов)
- **Разные стратегии для разных данных**: критичные данные шардировать по хешу, остальные — по диапазону

В техническом задании нужно явно указать требования к равномерности распределения нагрузки и допустимые задержки при перераспределении.

---

### Вопрос 3: Как объяснить бизнесу необходимость шардирования?

**Ответ:**  
Я бы объяснил так: "Представьте, что вы ведёте бухгалтерию с миллионами записей. Если все записи хранятся в одной книге — поиск нужной информации занимает много времени, а добавление новых записей замедляет работу. Шардирование работает иначе: книга разбита на несколько thinner-томов, каждый из которых хранит часть записей. Поиск становится быстрее, потому что нужно искать только в одном томе, а не во всей книге. При этом если одного тома недостаточно — можно добавить ещё один".

# 2.7 Как происходит кэширование: что такое, плюсы и минусы

---

## Короткий ответ

**Кэширование** — это сохранение часто запрашиваемых данных во временном хранилище (кэше) для ускорения доступа. Вместо чтения из медленной базы данных система сначала проверяет кэш, где данные хранятся быстрее.

---

## Простыми словами

### Аналогия с интернет-магазином

Представьте **административный офис** интернет-магазина:

| Ситуация | Без кэша | С кэшем |
|----------|----------|---------|
| **Клиент заходит на страницу товара** | Система каждый раз читает данные о товаре из базы данных — медленно | Данные о популярном товаре уже в кэше — мгновенно |
| **Администратор смотрит статистику продаж** | Каждый запрос считывает данные из БД и считает заново | Статистика уже посчитана и сохранена в кэше — быстро |

**Пример из интернет-магазина:**

**Без кэша:**
```
Клиент нажимает "Показать товар №123"
↓
Система читает данные о товаре из PostgreSQL (медленно: 50-200 мс)
↓
Возвращает информацию клиенту
```

**С кэшем:**
```
Клиент нажимает "Показать товар №123"
↓
Система проверяет Redis кэш (быстро: 1-5 мс)
↓
Данные уже в кэше → возвращаются мгновенно
↓
Если данных нет в кэше → читаем из БД и сохраняем в кэш для следующих запросов
```

### Таблица сравнения подходов

| Подход | Скорость чтения | Нагрузка на БД | Объём памяти |
|--------|-----------------|----------------|--------------|
| **Без кэша** | Медленнее (50-200 мс) | Высокая (каждый запрос читает из БД) | Нет |
| **С кэшем** | Быстрее (1-5 мс) | Низкая (часто данные берут из кэша) | Занимает память для хранения данных |

## Подробно

### Как работает кэширование?

Кэширование использует принцип LRU (Least Recently Used — наименее недавно используемое):
1. **Первый запрос** → данные читаются из базы данных и сохраняются в кэш
2. **Следующие запросы** → данные берутся из кэша мгновенно
3. **Если кэш переполнен** → старые данные удаляются, чтобы освободить место

### Типы кэширования

1. **Кэш на стороне приложения** — данные хранятся в памяти сервера приложения
2. **Кэш на стороне базы данных** — БД сама хранит часто запрашиваемые данные
3. **Распределённый кэш (Redis, Memcached)** — кэш хранится на отдельном сервере и доступен всем приложениям

### Пример из интернет-магазина: кэширование товаров

**Сценарий:** Популярный товар №123 читают 1000 пользователей в минуту.

| Время | Без кэша | С кэшем (Redis) |
|-------|----------|-----------------|
| T1 | Пользователь 1 читает товар → чтение из БД (50 мс), сохранение в кэш | Пользователь 1 читает товар → чтение из БД (50 мс), сохранение в кэш |
| T2 | Пользователь 2 читает товар → чтение из БД (50 мс) | Пользователь 2 читает товар → данные уже в кэше (1 мс) |
| ... | ... | ... |
| T1000 | Пользователь 1000 читает товар → чтение из БД (50 мс) | Пользователь 1000 читает товар → данные уже в кэше (1 мс) |

**Итог:** с кэшем система работает в 50 раз быстрее для повторных запросов!

### Стратегии инвалидации кэша

Когда данные в базе меняются, нужно обновлять или удалять их из кэша:

| Стратегия | Как работает | Когда использовать |
|-----------|--------------|-------------------|
| **Write-through** | При записи в БД сразу обновляется и кэш | Критичные данные, нужна мгновенная согласованность |
| **Write-behind (write-back)** | Сначала запись в БД, потом асинхронное обновление кэша | Не критичные данные, допустима задержка |
| **Time-based** | Кэш обновляется по таймеру (например, раз в минуту) | Данные редко меняются (прайс-лист, информация о товарах) |
| **Cache-aside** | Приложение само управляет кэшем: проверяет кэш → если нет → читает из БД и сохраняет в кэш | Самый популярный подход для большинства сценариев |

### Пример из интернет-магазина: стратегии инвалидации

**Сценарий:** Изменилась цена товара.

| Стратегия | Что происходит |
|-----------|----------------|
| **Write-through** | Обновление цены в БД → мгновенное обновление кэша → все пользователи видят новую цену сразу |
| **Time-based** | Обновление цены в БД → кэш обновляется через 5 минут → до этого пользователи могут видеть старую цену |
| **Cache-aside** | Обновление цены в БД → приложение удаляет товар из кэша → следующий запрос прочитает новую цену из БД и сохранит в кэш |

## Плюсы и минусы кэширования

### ✅ Плюсы кэширования

| Преимущество | Объяснение |
|-------------|------------|
| **Высокая скорость чтения** | Данные берутся из памяти (кэша), а не с диска базы данных |
| **Снижение нагрузки на БД** | Часто запрашиваемые данные читаются из кэша, а не из БД |
| **Масштабируемость** | Можно добавить больше кэш-серверов без замены БД |
| **Улучшение пользовательского опыта** | Страницы загружаются быстрее, меньше задержек |

### ❌ Минусы кэширования

| Недостаток | Объяснение |
|-----------|------------|
| **Несогласованность данных** | Кэш может содержать устаревшие данные до обновления |
| **Дополнительная сложность** | Нужно управлять жизненным циклом кэша (инвалидация, очистка) |
| **Занимает память** | Кэш требует ресурсов сервера для хранения данных |
| **Проблемы с согласованностью** | В распределённых системах сложно синхронизировать данные между кэшем и БД |

---

## Что важно запомнить аналитику

1. **Кэширование — это про скорость чтения**. Оно не ускоряет запись, но снижает нагрузку на базу данных за счёт повторных чтений.

2. **Нужно балансировать согласованность и скорость**. Если данные критичны (цены, остатки), кэш должен обновляться мгновенно при изменении в БД. Если допустима задержка — можно использовать time-based инвалидацию.

3. **Кэш не заменяет базу данных**. Кэш хранит только часто запрашиваемые данные, а полная информация остаётся в БД для записи и сложных запросов.

4. **Идеален для определённых сценариев**:
   - Часто читаемые данные (прайс-лист, информация о товарах)
   - Сессии пользователей
   - Результаты вычислений или агрегаций

5. **Для junior-аналитика важно понимать**, что кэширование — это компромисс между скоростью чтения и согласованностью данных. Нужно явно указывать в ТЗ допустимую задержку (например, "данные в кэше могут отличаться от БД не более чем на 5 секунд").

## ❓ Типичные вопросы и ответы

### Вопрос 1: В чём разница между кэшированием и шардированием?

**Ответ:**  
Кэширование ускоряет чтение часто запрашиваемых данных, храня их во временном хранилище (Redis, Memcached). Шардирование разбивает большие объёмы данных на части для распределения по нескольким серверам. Кэширование работает внутри одного сервера и ускоряет доступ к данным, шардирование масштабирует систему горизонтально за счёт добавления новых серверов. Часто используются вместе: шардированная БД + Redis-кэш для часто читаемых данных.

---

### Вопрос 2: Что будет, если данные в кэше устареют?

**Ответ:**  
Это проблема несогласованности (stale data). Решения:
- **Write-through**: при записи в БД сразу обновляется и кэш — мгновенная согласованность, но выше нагрузка на кэш
- **Time-based**: кэш обновляется по таймеру (например, раз в минуту) — простая реализация, но возможна задержка до 1 минуты
- **Cache-aside с инвалидацией**: при изменении данных в БД удаляются или обновляются соответствующие записи в кэше — баланс между скоростью и согласованностью

В техническом задании нужно явно указать допустимую задержку обновления кэша (например, "цены должны быть актуальны не более чем на 5 секунд").

---

### Вопрос 3: Когда стоит отказаться от кэширования?

**Ответ:**  
Кэширование можно не использовать когда:
- Данные редко читаются и часто меняются (каждое изменение требует инвалидации)
- Объём данных слишком большой для памяти сервера
- Система простая и БД справляется с нагрузкой без кэша
- Требуется мгновенная согласованность данных, а механизмы инвалидации сложны в реализации

В таких случаях лучше использовать оптимизацию запросов или вертикальное масштабирование вместо кэширования.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы ты поступил, если бизнес просит добавить дашборд аналитики с мгновенным отображением продаж?

**Ответ:**  
Я бы предложил гибридный подход:
- **Основная база данных** — хранит все заказы и транзакции для целостности данных (нормализованная структура)
- **Кэш для часто читаемых метрик** — статистика продаж (количество заказов, сумма выручки за день/неделю), которая обновляется при каждом изменении в БД

Для мгновенного отображения дашборд читает данные из кэша (Redis), а не из нормализованной базы с JOIN-запросами. Если цена товара меняется — соответствующая метрика инвалидируется и пересчитывается при следующем запросе. Это основа CQRS: команды записывают данные в БД, а проекции создают оптимизированные представления для чтения через кэш.

---

### Вопрос 2: Что делать, если нужно часто менять структуру данных (добавлять новые поля)?

**Ответ:**  
В строго нормализованной базе добавление новых полей требует ALTER TABLE и миграций, что может привести к простоям. Я бы предложил использовать NoSQL документную базу для таких случаев — каждый документ может иметь произвольные поля без необходимости менять структуру всей таблицы. Для критичных операций (платежи) можно оставить нормализованную реляционную БД с кэшированием часто читаемых данных, а для гибких данных (профили пользователей, настройки) — NoSQL с возможностью добавлять новые поля без миграций.

---

### Вопрос 3: Как объяснить бизнесу необходимость кэширования?

**Ответ:**  
Я бы объяснил так: "Представьте, что вы смотрите на страницу профиля пользователя с историей заказов. Если данные хранятся в разных таблицах (клиенты и заказы), системе нужно выполнить несколько запросов для получения всей информации — это как ждать ответа от нескольких коллег по телефону. Кэширование работает иначе: часто запрашиваемые данные сохраняются во временном хранилище, как если бы коллега заранее подготовил полный ответ. Страница загружается мгновенно, но при изменении данных нужно обновлять кэш".

# 3.10 Security в OpenAPI: как работает

📌 **Короткий ответ**  
Security в OpenAPI — это механизм описания правил безопасности для API, который позволяет разработчикам и системам понять, как авторизоваться и аутентифицироваться при использовании API. OpenAPI не хранит сами секреты (пароли, ключи), а лишь описывает, **где** и **как** их нужно передать.

> **Security в OpenAPI описывает правила безопасности, но не хранит сами секретные данные.**

---

💡 **Простыми словами**  
Представьте, что вы приходите в интернет-магазин с товаром на продажу. У входа стоит охранник (сервер API). Охранник спрашивает: "Кто вы и есть ли у вас разрешение?"  

В OpenAPI прописано:
- **Где** нужно показать разрешение (в заголовке запроса, в URL или в теле)
- **Как** выглядит это разрешение (тип токена, формат подписи)
- **Какой** тип проверки нужен (JWT, базовая авторизация и т.д.)

Но сами пароли и ключи хранятся отдельно — их не видно ни в OpenAPI, ни в документации.

🔍 **Подробно**  

## Что такое OpenAPI?  
OpenAPI (ранее Swagger) — это стандарт для описания REST API. Он позволяет:
- Автоматически генерировать документацию
- Генерировать клиентский код на разных языках
- Тестировать API через UI

В OpenAPI есть раздел `security`, который описывает **правила доступа** к операциям API.

## Основные механизмы безопасности в OpenAPI  

### 1. Типы аутентификации (Authentication)  
Ответ на вопрос: "Как система узнаёт, кто вы?"

- **ApiKeyAuth** — ключ передаётся в заголовке или URL
- **OAuth2** — обмен токенами для получения доступа к ресурсам
- **HttpBasicAuth** — логин и пароль в Base64
- **OpenIdConnect** — стандарт для аутентификации (часто поверх OAuth2)

### 2. Типы авторизации (Authorization)  
Ответ на вопрос: "Что вы имеете права делать?"

После того как система узнала, кто вы, она проверяет ваши права доступа к конкретным ресурсам. В OpenAPI это описывается через `securitySchemes` и привязкой к операциям API.

### 3. Где указываются правила безопасности  

```yaml
# Пример секции security в OpenAPI
components:
  securitySchemes:
    apiKeyAuth:
      type: apiKey
      name: X-API-Key
      in: header
  
    oauth2:
      type: OAuth2
      flows:
        clientCredentials:
          tokenUrl: https://auth.example.com/oauth/token
          scopes:
            read: доступ к чтению данных
            write: доступ к записи данных

security:
  - apiKeyAuth: []  # Все операции требуют API ключ
  
paths:
  /api/orders:
    get:
      security:
        - oauth2: [read]  # Эта операция требует OAuth с scope read
```

### 4. Как это работает на практике  

1. **Клиент** (например, мобильное приложение интернет-магазина) запрашивает токен авторизации у сервиса аутентификации
2. Сервер API проверяет наличие и правильность токена в запросе
3. Если токен верный — клиент получает доступ к ресурсам согласно своим правам
4. OpenAPI описывает, **какой** тип токена нужен и **где** его передать

🛠 **Пример из интернет-магазина**  

### Сценарий: Заказ товара через API  

**Без безопасности:**  
Любой человек может отправить запрос `GET /api/orders` и увидеть все заказы всех пользователей.

**С Security в OpenAPI:**  
OpenAPI описывает, что для доступа к `/api/orders` нужен токен OAuth2 с scope `orders:read`.

**Как это выглядит для разработчика:**
1. Пользователь входит на сайт интернет-магазина
2. Система создаёт для него JWT-токен (например, на 24 часа)
3. При каждом запросе к API клиент добавляет заголовок `Authorization: Bearer <token>`
4. Сервер проверяет токен и разрешает доступ только если он валиден

**Что описывает OpenAPI:**  
```yaml
paths:
  /api/orders/{orderId}:
    get:
      summary: Получить информацию о заказе
      security:
        - bearerAuth: []  # Требуется JWT-токен
      responses:
        '200':
          description: Успешный ответ с данными заказа
```

⚖️ **Плюсы/минусы**  

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Единое описание правил безопасности для всех разработчиков | Не хранит сами секреты — нужно подключать внешние системы аутентификации |
| Автоматическая генерация документации с инструкциями по авторизации | Требует настройки инфраструктуры (серверы OAuth, выдача токенов) |
| Поддержка нескольких типов аутентификации в одном API | Сложность для новичков — нужно понимать разницу между auth и authorization |
| Возможность ограничивать доступ к разным операциям разным способом | Не защищает от уязвимостей вне самого OpenAPI (например, SQL-инъекций) |

---

🎯 **Что важно запомнить аналитику**  

1. **OpenAPI описывает правила безопасности, но не реализует их.** Сами секреты хранятся в системах аутентификации.
2. **Разница между Authentication и Authorization:**  
   - Authentication = "Кто вы?" (проверка токенa/пароля)  
   - Authorization = "Что вы можете делать?" (проверка прав доступа)
3. **API ключи не должны храниться в коде клиента.** Они передаются динамически через заголовки или URL.
4. **Всегда указывайте требования к безопасности для каждой операции API**, даже если они одинаковые — это упрощает поддержку документации.

---

❓ **Типичные вопросы и ответы**  

**Вопрос: Чем аутентификация отличается от авторизации?**  
Ответ: Аутентификация проверяет, кто вы (логин/пароль, токен). Авторизация проверяет, что вы имеете права делать (доступ к конкретным ресурсам или операциям).

**Вопрос: Где в OpenAPI описываются правила безопасности?**  
Ответ: В секции `components.securitySchemes` определяются типы аутентификации, а в секции `security` привязываются требования к операциям API.

**Вопрос: Можно ли использовать разные методы авторизации для разных операций одного API?**  
Ответ: Да, это поддерживается. В OpenAPI можно указать разные схемы безопасности для разных эндпоинтов или даже для разных методов внутри одного эндпоинта.

**Вопрос: Что такое OAuth2 и когда его применять?**  
Ответ: OAuth2 — это стандарт для делегирования доступа (например, "позвольте приложению прочитать мои заказы"). Применяется, когда нужно предоставить доступ к ресурсам без передачи пароля.

🛠 **Практические вопросы для собеседования**  

1. **Как описать в OpenAPI требование, что операция требует JWT-токен?**  
   → Создать securityScheme типа `httpBearerAuth` и указать его в секции `security` операции API.

2. **Что будет, если клиент не передаст токен авторизации?**  
   → Сервер вернёт ошибку 401 Unauthorized. OpenAPI лишь описывает это требование, но проверка происходит на уровне сервера.

3. **Можно ли в одном API использовать и OAuth2, и API ключи?**  
   → Да, для разных операций можно указать разные методы авторизации. Например, публичные эндпоинты — без авторизации, личные заказы — через OAuth2.

4. **Где хранить API-ключи клиента?**  
   → В безопасном хранилище (например, Keycloak, Vault), а не в коде приложения. Ключ передаётся динамически при каждом запросе.

5. **Как защитить чувствительные данные в теле запроса?**  
   → Использовать HTTPS (TLS/SSL) для шифрования трафика между клиентом и сервером. OpenAPI сам по себе не шифрует данные — это задача инфраструктуры.

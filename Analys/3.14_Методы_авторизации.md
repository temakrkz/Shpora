# 3.14 Методы авторизации

> **Короткий ответ**  
> Авторизация — это проверка прав доступа пользователя к ресурсам. Основные методы: Basic Auth, Bearer Token (OAuth2), API Key, Session-based, mTLS и SAML/OIDC для Enterprise.

> **Простыми словами**  
> Представьте вход в интернет-магазин:
> - **Basic Auth:** Вы пишете логин/пароль на каждой странице входа
> - **Bearer Token:** Вы получаете пропуск один раз, он действует до истечения срока
> - **API Key:** Это как ключ от склада — передаётся отдельно от пользователя

> **Подробно**  
> **Авторизация** (authentication) — это проверка «Кто ты?» (логин/пароль, токен).  
> **Авторизация доступа** (authorization) — это проверка «Что тебе разрешено?» (права доступа по ролям/scopes).

## Основные методы авторизации

### 1. Basic Auth (Базовая авторизация)

**Как работает:**
- Клиент передаёт логин и пароль в заголовке `Authorization: Basic <base64(login:password)>`
- Сервер декодирует и проверяет credentials в базе данных/сервисе аутентификации

**Пример:**
```
Authorization: Basic YWRtaW46cGFzc3dvcmQ=  # base64("admin:password")
```

**Плюсы:**
- Простота реализации
- Работает везде (HTTP поддерживает)

**Минусы:**
- ⚠️ **Нужен HTTPS!** Без него пароль передаётся в открытом виде
- Пароль нужно передавать на каждом запросе
- Не подходит для мобильных приложений

### 2. Bearer Token (OAuth2 / JWT)

**Как работает:**
1. Пользователь входит один раз → получает токен
2. Токен сохраняется и передаётся в заголовке `Authorization: Bearer <token>`
3. Сервер проверяет токен у сервиса аутентификации

**Пример:**
```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

**Плюсы:**
- Не нужно передавать пароль на каждом запросе
- Поддержка гранулярных прав (scopes)
- Подходит для мобильных приложений и SPA

**Минусы:**
- Токены нужно хранить безопасно
- Риск утечки (если токен украдут — злоумышленник получит доступ)

### 3. API Key

**Как работает:**
- Сервис получает уникальный ключ при регистрации
- Ключ передаётся в заголовке `X-API-Key: <key>` или в URL-параметре (не рекомендуется!)

**Пример:**
```
X-API-Key: sk_live_51HxYz...
```

**Плюсы:**
- Простота для машинных клиентов
- Можно выдавать разные ключи разным сервисам

**Минусы:**
- ⚠️ **Нельзя использовать в URL!** (параметры сохраняются в истории)
- Нет гранулярной авторизации по scopes
- Ключ нужно хранить на стороне клиента (риск утечки)

### 4. Session-based (Сессии)

**Как работает:**
1. Пользователь входит → сервер создаёт сессию и cookie `session_id`
2. Сервер хранит данные сессии в Redis/базе данных
3. Каждый запрос содержит cookie, сервер проверяет её

**Пример:**
```
Cookie: session_id=abc123xyz789
```

**Плюсы:**
- Простота для веб-приложений
- Не нужно хранить секреты на клиенте

**Минусы:**
- Не подходит для мобильных приложений (cookies сложно управлять)
- Требует центрального хранилища сессий (Redis/DB)
- Сессии нужно инвалидировать при выходе

### 5. mTLS (Mutual TLS)

**Как работает:**
- Сервер и клиент обмениваются сертификатами
- Оба стороны проверяют сертификат другой стороны
- Аутентификация происходит на уровне SSL/TLS

**Пример:**
```
# Клиент отправляет запрос с сертификатом
# Сервер проверяет сертификат клиента → разрешает доступ
```

**Плюсы:**
- Максимальная безопасность (сертификаты сложнее украсть)
- Не нужно передавать токены/пароли

**Минусы:**
- Сложность реализации и управления сертификатами
- Требует инфраструктуры PKI (Certificate Authority)
- Не подходит для браузерных приложений

### 6. SAML / OIDC (Enterprise)

**Как работает:**
- Интеграция с корпоративным Identity Provider (Okta, Azure AD)
- Пользователь входит один раз в корпоративную систему → получает доступ ко всем сервисам

**Пример:**
```
# Single Sign-On: вход в Google → автоматический вход во все сервисы компании
```

**Плюсы:**
- Единый вход для всех сервисов
- Централизованное управление пользователями
- Соответствие корпоративным политикам безопасности

**Минусы:**
- Сложность интеграции
- Требует Enterprise-решений (Okta, Azure AD)

## Сравнение методов

| Метод | Безопасность | Простота | Для чего подходит |
|-------|--------------|----------|-------------------|
| Basic Auth | ⭐⭐ | ⭐⭐⭐⭐⭐ | Внутренние сервисы (HTTPS обязателен!) |
| Bearer Token | ⭐⭐⭐⭐ | ⭐⭐⭐ | Мобильные приложения, SPA, API |
| API Key | ⭐⭐ | ⭐⭐⭐⭐ | Сервис-сервис интеграции |
| Session-based | ⭐⭐⭐ | ⭐⭐⭐⭐ | Веб-приложения |
| mTLS | ⭐⭐⭐⭐⭐ | ⭐⭐ | Внутренние микросервисы, платежные системы |
| SAML/OIDC | ⭐⭐⭐⭐⭐ | ⭐⭐ | Enterprise, корпоративные системы |

## Пример из интернет-магазина

**Сценарий:** Разные клиенты используют разные методы авторизации.

| Клиент | Метод | Почему |
|--------|-------|--------|
| **Мобильное приложение** | Bearer Token (JWT) | Токены легко хранить в secure storage, не нужно передавать пароль |
| **Веб-сайт** | Session-based + OAuth2 | Удобный вход через соцсети, сессии управляются браузером |
| **Сервис доставки** | API Key | Простая интеграция без входа пользователей |
| **Платёжный шлюз** | mTLS | Максимальная безопасность для финансовых данных |
| **Корпоративный клиент** | SAML/OIDC | Единый вход через корпоративную систему |

## Что важно запомнить аналитику

1. **Authentication ≠ Authorization**  
   - Authentication = «Кто ты?» (логин/пароль → токен)
   - Authorization = «Что тебе разрешено?» (проверка прав по ролям/scopes)

2. **Никогда не передавайте credentials в URL!**  
   URL-парсер может сохранить их в истории браузера или логах сервера.

3. **Выбор метода зависит от контекста:**
   - Мобильные приложения → Bearer Token (JWT)
   - Веб-приложения → Session-based + OAuth2
   - Сервис-сервис → API Key или mTLS
   - Enterprise → SAML/OIDC

4. **Безопасность токенов:**  
   Токены нужно хранить в защищённом хранилище (HttpOnly cookie, secure storage), НЕ в localStorage.

## Типичные вопросы и ответы

**Q: В чём разница между аутентификацией и авторизацией?**  
A: Аутентификация — это проверка личности («Кто ты?»). Авторизация — это проверка прав доступа («Что тебе разрешено?»).

**Q: Почему API Key нельзя передавать в URL?**  
A: URL-парсер может сохранить ключ в истории браузера, и он будет виден всем, кто имеет доступ к истории.

**Q: Когда использовать mTLS вместо OAuth2?**  
A: mTLS подходит для внутренних микросервисов или высоконагруженных систем, где важна максимальная безопасность без передачи токенов.

# 3.15 Авторизация через сертификаты (mTLS)

> **Короткий ответ**  
> mTLS (Mutual TLS) — это взаимная аутентификация, где сервер и клиент обмениваются сертификатами для проверки подлинности друг друга на уровне SSL/TLS.

> **Простыми словами**  
> Представьте, что вы входите в банк:
> - Обычный HTTPS: Банк проверяет ваш паспорт (сертификат банка)
> - mTLS: И вы показываете свой пропуск (клиентский сертификат), и банк проверяет ваш пропуск

> **Подробно**  
> **mTLS (Mutual TLS)** — это расширение стандартного TLS, где обе стороны (сервер и клиент) предъявляют цифровые сертификаты для взаимной аутентификации. Это обеспечивает максимальный уровень безопасности на уровне транспорта.

> **Как это работает:**
> 1. Клиент подключается к серверу по HTTPS
> 2. Сервер просит у клиента сертификат (`Certificate Request`)
> 3. Клиент отправляет свой клиентский сертификат (подписан Certificate Authority)
> 4. Сервер проверяет подпись сертификата и разрешает доступ

## Пример из интернет-магазина

**Сценарий:** Платёжный шлюз подключается к интернет-магазину для обработки платежей.

### Обычный HTTPS:
```
# Магазин → Шлюз: "Я магазин, вот мой сертификат"
# Шлюз проверяет сертификат магазина → разрешает соединение
# Данные передаются в зашифрованном виде
```

**Проблема:** Сервер знает, что подключается шлюз, но не может проверить подлинность шлюза. Злоумышленник мог бы создать свой "фейковый" шлюз.

### mTLS:
```
# Магазин → Шлюз: "Я магазин, вот мой сертификат"
# Шлюз → Магазин: "Покажите ваш сертификат!"
# Шлюз → Магазин: "Вот мой сертификат платежной системы"
# Магазин проверяет сертификат шлюза (подписан CA)
# Сервер разрешает доступ только после проверки обоих сертификатов
```

**Преимущество:** Обе стороны гарантированно аутентифицированы. Злоумышленник не сможет создать свой "фейковый" шлюз, потому что у него нет валидного сертификата.

## Плюсы/минусы

| Плюсы | Минусы |
|-------|--------|
| **Максимальная безопасность** — аутентификация на уровне транспорта | **Сложность управления** — нужно хранить и обновлять сертификаты |
| **Не нужны токены/пароли** — нет риска их утечки | **Требуется инфраструктура PKI** (Certificate Authority) |
| **Идеально для сервис-сервис интеграций** | **Сложность отладки** — трудно воспроизвести ошибки |
| **Автоматическое шифрование** — не нужно передавать credentials | **Производительность** — проверка сертификатов требует вычислений |

## Что важно запомнить аналитику

1. **mTLS работает на уровне SSL/TLS**, ниже уровня HTTP. Сервер и клиент обмениваются сертификатами ДО того, как начинается обмен данными по HTTP.

2. **Сертификаты должны быть подписаны Certificate Authority** (или внутренним CA). Браузеры/системы проверяют цепочку доверия.

3. **Клиентский сертификат содержит идентификатор сервиса**, а не пользователя. Это позволяет различать разные сервисы без использования токенов.

4. **mTLS подходит для:**
   - Внутренних микросервисов
   - Платёжных шлюзов
   - Систем, где важна максимальная безопасность

5. **Для mTLS нужна инфраструктура PKI:**
   - Certificate Authority (выдаёт сертификаты)
   - Система хранения и ротации ключей
   - Автоматическое обновление сертификатов

## Типичные вопросы и ответы

**Q: В чём разница между обычным HTTPS и mTLS?**  
A: Обычный HTTPS проверяет только сертификат сервера. mTLS проверяет сертификаты обеих сторон (сервера и клиента).

**Q: Почему mTLS сложнее обычного OAuth2?**  
A: mTLS требует инфраструктуры PKI, управления сертификатами и их ротации. OAuth2 проще — достаточно настроить Auth0/Keycloak.

**Q: Когда использовать mTLS вместо JWT/OAuth2?**  
A: Для внутренних микросервисов или высоконагруженных систем, где важна максимальная безопасность без передачи токенов.

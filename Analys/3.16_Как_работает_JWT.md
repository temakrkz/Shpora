# 3.16 Как работает JWT

> **Короткий ответ**  
> JWT (JSON Web Token) — это стандарт для передачи данных между системами в виде зашифрованного токена, состоящего из трёх частей: header, payload, signature.

> **Простыми словами**  
> Представьте, что вы покупаете товар в интернет-магазине:
> - **Без JWT:** Каждый раз вводите логин/пароль → сервер проверяет их → разрешает покупку
> - **С JWT:** Вы получаете «пропуск» (токен) после входа → показываете его на каждой странице → магазин проверяет пропуск

> **Подробно**  
> **JWT (JSON Web Token)** — это стандарт для создания токенов аутентификации. Токен представляет собой строку из трёх частей, разделённых точками: `header.payload.signature`.

## Структура JWT

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9  .  eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ  .  abc123xyz789
     ↑                                    ↑                          ↑
   Header (заголовок)                  Payload (нагрузка)    Signature (подпись)
```

### 1. Header (Заголовок)

**Что внутри:**
- Алгоритм подписи (`alg`): `HS256`, `RS256` и т.д.
- Тип токена (`typ`): обычно `"JWT"`

**Пример:**
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

### 2. Payload (Нагрузка)

**Что внутри:**
- **Claims** — данные о пользователе/сессии:
  - `sub` — идентификатор пользователя (`userId`)
  - `name` — имя пользователя
  - `email` — email
  - `roles` — роли пользователя (`["admin", "user"]`)
  - `scopes` — разрешения (`["order:create", "profile:read"]`)

- **Standard claims** (стандартные):
  - `iat` — время создания токена (`issued at`)
  - `exp` — время истечения токена (`expiration time`)
  - `nbf` — время начала действия токена (`not before`)

### 3. Signature (Подпись)

**Что внутри:**
- Хэш всех частей токена + секретный ключ сервера
- Гарантирует, что токен не был изменён после создания

**Пример расчёта:**
```
header + "." + payload + "=" + HMACSHA256(
  header + "." + payload,
  secret_or_private_key
)
```

## Как работает JWT в интернет-магазине

### Сценарий: Пользователь делает заказ

#### Шаг 1: Вход (Login)
```
# Клиент → Сервер: логин/пароль
POST /login
{ "email": "user@example.com", "password": "***" }

# Сервер проверяет credentials → создаёт JWT токен
Response: {
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "expires_in": 3600,  # Токен живёт 1 час
  "refresh_token": "dGhpcyBpcyBhIHJlZnJlc2ggdG9rZW4..."
}
```

#### Шаг 2: Просмотр профиля
```
# Клиент → Сервер: токен в заголовке
GET /user/profile
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

# Сервер проверяет подпись токена (не подделан ли он)
# Проверяет exp — не истёк ли токен
# Извлекает userId из payload → показывает профиль пользователя
```

#### Шаг 3: Создание заказа
```
# Клиент → Сервер: токен в заголовке + данные заказа
POST /orders
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
{ "items": [...] }

# Сервер проверяет токен → извлекает userId и roles из payload
# Проверяет, что у пользователя есть scope order:create
# Создаёт заказ
```

## Плюсы/минусы JWT

| Плюсы | Минусы |
|-------|--------|
| **Stateless** — серверу не нужно хранить сессию (токен самодостаточен) | **Токены нельзя отозвать мгновенно** (нужно ждать истечения exp) |
| **Маленький размер** (~1-2 KB) → быстро передаётся по сети | **Нельзя изменить данные токена** (подпись проверяется на целостность) |
| **Кроссплатформенность** — работает везде (веб, мобильные, десктоп) | **Риск утечки** — если токен украдут, злоумышленник получит доступ до exp |
| **Гибкость** — можно добавлять любые claims в payload | **Безопасность зависит от секретного ключа** (если его украдут — все токены подделываются) |

## Типичные вопросы и ответы

**Q: В чём разница между access token и refresh token?**  
A: Access token — это токен доступа с коротким сроком жизни (1-2 часа). Refresh token — токен для получения нового access token, живёт дольше (7-30 дней), но используется реже.

**Q: Почему JWT нельзя изменить после создания?**  
A: Потому что подпись проверяет целостность всех частей токена. Любое изменение payload сделает подпись невалидной.

**Q: Как отозвать JWT токен, если пользователь вышел из системы?**  
A: Есть два способа:
1. **Blacklist/Whitelist:** Сохраняйте использованные токены в Redis и проверяйте их при каждом запросе (не stateless больше)
2. **Short expiration + refresh tokens:** Делайте access token коротким (5-15 мин), а refresh token используйте для получения нового

**Q: Что такое RS256 и HS256?**  
A: Это алгоритмы подписи:
- `HS256` — HMAC с SHA-256 (секретный ключ хранится на сервере)
- `RS256` — RSA с SHA-256 (использует пару ключей: public для проверки, private для подписи)

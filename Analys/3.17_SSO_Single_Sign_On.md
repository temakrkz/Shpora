# 3.17 SSO (Single Sign-On)

> **Короткий ответ**  
> SSO (Single Sign-On) — это система единого входа, позволяющая пользователю войти один раз и получить доступ ко всем связанным сервисам без повторной аутентификации.

> **Простыми словами**  
> Представьте корпоративный портал:
> - **Без SSO:** Чтобы зайти в почту → вводите логин/пароль<br>Чтобы зайти в CRM → снова вводите логин/пароль<br>Чтобы зайти в чат → ещё раз вводите логин/пароль
> - **С SSO:** Вы входите один раз в корпоративную систему → автоматически получаете доступ ко всем сервисам

> **Подробно**  
> **SSO (Single Sign-On)** — это аутентификационная система, позволяющая пользователю войти один раз и получить доступ к нескольким независимым приложениям/сервисам без повторной аутентификации.

## Типы SSO

### 1. Федерированная авторизация (Federated Identity)

**Как работает:**
- Есть центральный Identity Provider (IdP) — хранит данные пользователей
- Несколько сервисов (Service Providers, SP) доверяют IdP для аутентификации
- Пользователь входит один раз в IdP → получает доступ ко всем SP

**Примеры IdP:** Okta, Azure AD, Google Workspace, Auth0

### 2. Enterprise SSO

**Как работает:**
- Компания использует единый корпоративный IdP (например, Azure AD)
- Все сервисы компании подключены к IdP через SAML или OIDC
- Сотрудники входят один раз → получают доступ ко всем внутренним системам

## Пример из интернет-магазина

### Сценарий: Корпоративный клиент использует несколько сервисов

**Сервисы:**
1. **Корпоративная почта** (Okta)
2. **CRM система** (Salesforce)
3. **Интернет-магазин** (Shopify)
4. **Система учёта затрат** (Expensify)

### Без SSO:
```
# Сотрудник хочет проверить заказ в интернет-магазине
1. Открывает почту → вводит корпоративный логин/пароль
2. Переходит в CRM → снова вводит логин/пароль
3. Заходит в магазин → ещё раз вводит логин/пароль
4. Открывает систему учёта →第四次 ввод логин/пароль

# Итого: 4 входа, неудобно и медленно
```

### Со SSO (через Okta):
```
# Сотрудник входит один раз в корпоративную почту через Okta
1. Вводит корпоративный логин/пароль → Okta проверяет
2. Okta говорит: "Вы авторизованы"

# Теперь сотрудник переходит к другим сервисам
3. Открывает CRM → Okta автоматически аутентифицирует (SSO)
4. Заходит в магазин → ещё раз SSO через Okta
5. Открывает систему учёта → снова SSO через Okta

# Итого: 1 вход, все сервисы доступны автоматически
```

## Как работает SSO технически

### Сценарий: OAuth2/OIDC (современный подход)

#### Шаг 1: Переход к IdP
```
# Клиент → Магазин: "Я хочу войти"
GET https://shop.example.com/login?redirect_uri=https://shop.example.com/dashboard&response_type=code&client_id=abc123

# Магазин перенаправляет пользователя к Okta (IdP)
Redirect to: https://okta.example.com/oauth/authorize?client_id=abc123&redirect_uri=https://shop.example.com/callback&scope=email+profile
```

#### Шаг 2: Вход в IdP
```
# Пользователь вводит корпоративный логин/пароль в Okta
# Okta проверяет credentials → создаёт access token
Response: {
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refresh_token": "...",
  "expires_in": 3600,
  "id_token": "eyJhbGciOiJSUzI1NiIs..."  # содержит claims о пользователе
}
```

#### Шаг 3: Возврат в магазин с кодом
```
# Okta перенаправляет пользователя обратно в магазин с авторизационным кодом
Redirect to: https://shop.example.com/callback?code=authorization_code_xyz789
```

#### Шаг 4: Обмен кода на токен
```
# Магазин → Okta: "Обменяй код на токен"
POST https://okta.example.com/oauth/token
{
  "grant_type": "authorization_code",
  "code": "authorization_code_xyz789",
  "client_id": "abc123",
  "client_secret": "***"
}

# Okta возвращает access token и id_token
Response: {
  "access_token": "...",
  "id_token": "...",
  "expires_in": 3600
}
```

#### Шаг 5: Магазин использует токен
```
# Магазин → Сервер: авторизованный запрос с токеном
GET /user/profile
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

# Сервер проверяет токен → показывает профиль пользователя
```

## Плюсы/минусы SSO

| Плюсы | Минусы |
|-------|--------|
| **Удобство** — один вход ко всем сервисам | **Единая точка отказа** — если IdP упадёт, все сервисы недоступны |
| **Безопасность** — меньше паролей для запомнить → меньше фишинга | **Сложность настройки** — нужно интегрировать каждый сервис с IdP |
| **Управление доступом** — централизованное управление пользователями в IdP | **Проблемы с синхронизацией** — данные из разных источников могут конфликтовать |
| **Соответствие политикам безопасности** — корпоративные политики легко применять | **Зависимость от стороннего IdP** (если используется Okta/Azure AD) |

## Что важно запомнить аналитику

1. **SSO ≠ OAuth2**, но SSO часто использует OAuth2/OIDC как механизм.
2. **IdP (Identity Provider)** — это центральный сервис, который хранит данные пользователей и проверяет их.
3. **SP (Service Provider)** — это приложение, которое доверяет IdP для аутентификации.
4. **SSO работает через токены:** Пользователь входит один раз в IdP → получает токен → показывает его всем SP.

## Типичные вопросы и ответы

**Q: В чём разница между SSO и OAuth2?**  
A: OAuth2 — это протокол для делегирования доступа (получения токенов). SSO — это паттерн использования OAuth2/OIDC для единого входа в несколько сервисов.

**Q: Что такое IdP и SP в контексте SSO?**  
A: IdP (Identity Provider) — это центральный сервис, который хранит данные пользователей и проверяет их (Okta, Azure AD). SP (Service Provider) — это приложение, которое доверяет IdP для аутентификации.

**Q: Почему SSO повышает безопасность?**  
A: Потому что пользователи запоминают один пароль вместо нескольких → меньше риска фишинга. Также корпоративные политики безопасности легче применять централизованно.

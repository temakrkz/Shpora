# 3.18 RESTful

> **Короткий ответ**  
> RESTful — это подход к проектированию API, который следует принципам архитектурного стиля REST (Representational State Transfer): ресурсоориентированность, работа с HTTP-методами, statelessness и другие принципы.

> **Простыми словами**  
> Представьте интернет-магазин:
> - **RESTful:** `/products/123` — это конкретный товар с ID 123<br>`GET /products/123` — посмотреть этот товар<br>`PUT /products/123` — обновить этот товар
> - **Не RESTful:** `getProduct.php?id=123` — просто скрипт, который что-то делает

> **Подробно**  
> **REST (Representational State Transfer)** — это архитектурный стиль для создания распределённых систем. **RESTful API** — это API, которое следует принципам REST.

## 6 принципов REST (Roy Fielding)

### 1. Client-Server (Клиент-Сервер)
**Что это:** Клиент и сервер разделены по функциям:
- Клиент отвечает за интерфейс пользователя
- Сервер отвечает за хранение данных и бизнес-логику

**Пример из интернет-магазина:**
```
# Клиент (браузер/приложение): отображает товары, кнопки "Купить"
# Сервер: хранит каталог товаров, обрабатывает заказы
```

### 2. Stateless (Без состояния)
**Что это:** Каждый запрос содержит всю информацию для его обработки — сервер не запоминает предыдущие запросы.

**Пример из интернет-магазина:**
```
# Запрос 1: GET /products → список товаров (сервер не помнит, что вы смотрели раньше)
# Запрос 2: POST /orders → создание заказа (сервер проверяет токен в заголовке, а не историю)

# Каждый запрос независим — серверу не нужно хранить сессию между запросами
```

### 3. Cacheable (Кэшируемость)
**Что это:** Ответы должны явно указывать, можно ли их кэшировать или нет.

**Пример из интернет-магазина:**
```
# GET /products — ответ с заголовком: Cache-Control: public, max-age=3600
# Браузер может кэшировать список товаров 1 час → быстрее для пользователя

# POST /orders — ответ с заголовком: Cache-Control: no-cache
# Ответ нельзя кэшировать (каждый заказ уникален)
```

### 4. Layered System (Слоистая архитектура)
**Что это:** Сервер не должен знать, кто клиент — могут быть прокси-серверы, балансировщики нагрузки между ними.

**Пример из интернет-магазина:**
```
# Пользователь → CDN (кэширует статику) → Load Balancer → API Gateway → Микросервисы
# Каждый слой работает независимо и не знает о других
```

### 5. Code on Demand (Код по требованию) — опциональный
**Что это:** Сервер может отправлять JavaScript код клиенту для выполнения на стороне клиента.

**Пример из интернет-магазина:**
```
# GET /app/checkout.js → браузер скачивает и запускает скрипт оформления заказа
# Скрипт работает в браузере, не нагружает сервер
```

### 6. Uniform Interface (Единый интерфейс) — обязательный
**Что это:** Клиент и сервер взаимодействуют через стандартизированный интерфейс:
- **Ресурсоориентированность** — всё представлено как ресурсы (товары, заказы, пользователи)
- **Манипуляции через идентификаторы** — операции выполняются по ID ресурса
- **Self-descriptive messages** — каждый запрос/ответ содержит всю информацию для его обработки
- **Hypertext as the engine of application state** — клиент получает ссылки на возможные действия

## Пример из интернет-магазина

### RESTful API:

| Ресурс | URL | HTTP метод | Описание |
|--------|-----|------------|----------|
| Товары | `/products` | GET | Список товаров |
| Товар (по ID) | `/products/123` | GET | Один товар с ID 123 |
| Создать товар | `/products` | POST | Добавить новый товар |
| Обновить товар | `/products/123` | PUT | Полное обновление товара |
| Частично обновить | `/products/123` | PATCH | Изменить только некоторые поля |
| Удалить товар | `/products/123` | DELETE | Удалить товар |
| Заказы пользователя | `/users/me/orders` | GET | Список заказов текущего пользователя |

### Не RESTful API:

```
# Плохо — не ресурсоориентировано
GET /getProducts.php?category=electronics&page=1&limit=20

# Плохо — нет единого интерфейса
POST /createOrder.php
POST /updateProduct.php?id=123
DELETE /removeUser.php?id=456
```

## Плюсы/минусы RESTful

| Плюсы | Минусы |
|-------|--------|
| **Простота** — использует стандартные HTTP методы и коды ответов | **Не подходит для всех сценариев** (например, чаты требуют WebSocket) |
| **Кроссплатформенность** — работает везде (веб, мобильные, десктоп) | **Ограниченная функциональность** — сложно реализовать сложные операции |
| **Кэшируемость** — ответы можно кэшировать для ускорения | **Проблемы с версиями API** — нужно поддерживать старые версии |
| **Масштабируемость** — легко добавить новые сервисы/прокси | **Сложность валидации данных** — сложно проверить структуру запроса на клиенте |

## Что важно запомнить аналитику

1. **REST ≠ RESTful**  
   REST — это архитектурный стиль. RESTful API — это API, который следует принципам REST.

2. **HTTP методы имеют семантику:**
   - `GET` — получить ресурс (безопасно, идиempotent)
   - `POST` — создать ресурс (не безопасно, не idempotent)
   - `PUT` — полностью обновить ресурс (безопасно, idempotent)
   - `PATCH` — частично обновить ресурс (безопасно, обычно не idempotent)
   - `DELETE` — удалить ресурс (безопасно, idempotent)

3. **RESTful API должен быть ресурсоориентированным:**
   - URL должны представлять ресурсы (`/products`, `/users`)
   - HTTP методы должны соответствовать операциям над ресурсами
   - Ответы должны содержать ссылки на возможные действия (self-descriptive messages)

## Типичные вопросы и ответы

**Q: В чём разница между REST и RESTful?**  
A: REST — это архитектурный стиль. RESTful API — это API, который следует принципам REST.

**Q: Почему HTTP PUT считается idempotent, а POST — нет?**  
A: `PUT /resource` с одним и тем же телом всегда даёт один и тот же результат (ресурс обновлён). `POST /resource` создаёт новый ресурс каждый раз.

**Q: Когда RESTful подход не подходит?**  
A: Для чатов в реальном времени, интерактивных игр или когда нужна двусторонняя связь без ожидания ответа.

# 3.19 Stateless (без сохранения состояния)

> **Короткий ответ**  
> Stateless — это принцип, при котором каждый запрос содержит всю информацию для его обработки, и сервер не запоминает предыдущие запросы клиента.

> **Простыми словами**  
> Представьте, что вы делаете заказ в интернет-магазине:
> - **Stateless:** Каждый раз вы показываете пропуск (токен) → магазин проверяет его → разрешает действие<br>**Не Stateless:** Вы входите один раз → магазин запоминает вас и хранит сессию до выхода

> **Подробно**  
> **Statelessness** — это принцип архитектуры REST, при котором сервер не сохраняет состояние между запросами. Каждый запрос должен содержать всю необходимую информацию для его обработки.

## Как работает Stateless в интернет-магазине

### Сценарий: Пользователь просматривает товары и делает заказ

#### Без stateless (с сохранением состояния):
```
# Шаг 1: Вход
POST /login { "email": "user@example.com", "password": "***" }
Response: { "session_id": "abc123", "expires_in": 3600 }

# Сервер сохраняет сессию в Redis/базе данных:
# Redis: session_id=abc123 → userId=456, roles=["user"]

# Шаг 2: Просмотр профиля (сервер проверяет session_id)
GET /profile?session_id=abc123
Response: { "name": "Иван", "email": "user@example.com" }

# Шаг 3: Создание заказа (сервер проверяет session_id)
POST /orders { "items": [...] }
Response: { "order_id": "ORD-001" }

# Проблема: если сервер упадёт, сессия потеряется → нужно восстанавливать Redis/базу данных
```

#### Со stateless (с токенами):
```
# Шаг 1: Вход
POST /login { "email": "user@example.com", "password": "***" }
Response: { 
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",  # содержит userId, roles
  "expires_in": 3600
}

# Сервер НЕ сохраняет сессию! Токен самодостаточный (JWT)

# Шаг 2: Просмотр профиля (сервер проверяет токен)
GET /profile
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Response: { "name": "Иван", "email": "user@example.com" }

# Сервер извлекает userId и roles из токена → не нужно проверять Redis/базу данных

# Шаг 3: Создание заказа (сервер проверяет токен)
POST /orders { "items": [...] }
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Response: { "order_id": "ORD-001" }

# Преимущество: сервер не зависит от Redis/базы данных для сессий → легче масштабировать
```

## Плюсы/минусы Stateless

| Плюсы | Минусы |
|-------|--------|
| **Масштабируемость** — любой сервер может обработать запрос (не нужно синхронизировать сессию) | **Больше данных в заголовках** — токен передаётся на каждом запросе |
| **Отказоустойчивость** — при перезапуске сервера сессия не теряется (токен самодостаточный) | **Токены нельзя отозвать мгновенно** (нужно ждать истечения exp) |
| **Простота** — не нужно хранить и синхронизировать сессии в Redis/базе данных | **Безопасность зависит от токена** — если токен украдут, злоумышленник получит доступ до exp |

## Что важно запомнить аналитику

1. **Stateless ≠ Stateful**  
   - Stateless: каждый запрос содержит всю информацию (токен в заголовке)
   - Stateful: сервер хранит состояние между запросами (сессия в Redis/базе данных)

2. **JWT — это stateless**  
   JWT-токены содержат все необходимые данные внутри себя, поэтому серверу не нужно проверять внешнее хранилище сессий.

3. **Statelessness помогает масштабировать:**
   - Можно добавить любой новый сервер без синхронизации сессий
   - Не нужно использовать Redis/базу данных для хранения сессий
   - Легче обрабатывать нагрузку (каждый запрос независим)

4. **Trade-off: Stateless проще масштабировать, но сложнее управлять токенами**  
   При stateless нельзя мгновенно отозвать токен (нужно ждать exp). При stateful можно удалить сессию из Redis и пользователь сразу выйдет из системы.

## Типичные вопросы и ответы

**Q: В чём разница между Stateless и Stateful API?**  
A: Stateless — каждый запрос содержит всю информацию, сервер не хранит состояние. Stateful — сервер запоминает предыдущие запросы и хранит сессию между ними.

**Q: Почему JWT считается stateless?**  
A: Потому что токен содержит все необходимые данные внутри себя (userId, roles, scopes), и серверу не нужно проверять внешнее хранилище для аутентификации.

**Q: Какие минусы у Stateless подхода?**  
A: Токены нельзя отозвать мгновенно (нужно ждать истечения exp), больше данных в заголовках запросов, сложнее управлять безопасностью токенов.

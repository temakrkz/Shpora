# 3.23 POST vs PUT

> **Короткий ответ**  
> POST создаёт новый ресурс (не idempotent), а PUT полностью обновляет существующий ресурс или создаёт его, если не существует (idempotent).

> **Простыми словами**  
> Представьте интернет-магазин:
> - **POST:** «Создай мне новый товар» → сервер присваивает ID и добавляет в каталог<br>**PUT:** «Обнови товар с ID 123» → сервер находит товар по ID и обновляет его (или создаёт, если не существует)

> **Подробно**  
> **POST** и **PUT** — это HTTP-методы для работы с ресурсами. Они оба могут создавать ресурсы, но имеют фундаментальные различия в семантике.

## Ключевые отличия

| Характеристика | POST | PUT |
|----------------|------|-----|
| **Создание ресурса** | Да (новый уникальный ресурс) | Да (ресурс должен иметь ID заранее) |
| **Обновление ресурса** | Нет (создаёт новый) | Да (полное обновление по ID) |
| **Idempotent?** | ❌ Нет (каждый POST создаёт новый ресурс) | ✅ Да (один и тот же PUT даёт один результат) |
| **Безопасный?** | ❌ Нет (изменяет состояние сервера) | ✅ Безопасен (не изменяет данные, только обновляет) |
| **ID присваивает** | Сервер сам присваивает ID | Клиент должен указать ID в URL |

## Idempotency — что это и почему важно?

### Что такое idempotent операция?

**Idempotent (идемпотентная)** операция — это операция, которую можно выполнить много раз с одним и тем же результатом.

**Примеры:**
- **PUT /products/123 { "name": "iPhone" }** → выполняется 10 раз → результат: один товар с ID 123 называется «iPhone» ✅ idempotent
- **POST /orders { "items": [...] }** → выполняется 10 раз → результат: 10 разных заказов ❌ не idempotent

### Почему это важно?

**Сценарий:** Пользователь нажал кнопку «Оплатить», но интернет медленный. Он нажимает ещё раз, пока грузится страница.

```
# POST (не idempotent):
POST /orders { "items": [...] }  # Заказ создан
POST /orders { "items": [...] }  # Второй заказ создан! ❌ Дубликат заказа

# PUT (idempotent):
PUT /orders/123 { "status": "paid" }  # Статус обновлён
PUT /orders/123 { "status": "paid" }  # Статус не изменился (уже paid) ✅ idempotent
```

## Пример из интернет-магазина

### POST — создание нового заказа:

```http
# Клиент отправляет данные заказа (без ID)
POST /orders
{
  "items": [
    { "product_id": 123, "quantity": 2 }
  ],
  "customer_email": "user@example.com"
}

# Сервер создаёт новый заказ и присваивает уникальный ID
Response: 201 Created
Location: https://shop.example.com/orders/ORD-001
{
  "order_id": "ORD-001",
  "status": "created",
  "total_amount": 5000
}

# Если клиент отправит тот же запрос ещё раз — будет второй заказ!
POST /orders { ... } → ORD-002 (новый заказ) ❌ Не idempotent
```

### PUT — полное обновление заказа:

```http
# Клиент указывает ID в URL и обновляет все поля
PUT /orders/ORD-001
{
  "items": [
    { "product_id": 123, "quantity": 5 }  # Изменили quantity с 2 на 5
  ],
  "status": "shipped"
}

# Сервер находит заказ по ID и обновляет его полностью
Response: 200 OK
{
  "order_id": "ORD-001",
  "items": [
    { "product_id": 123, "quantity": 5 }
  ],
  "status": "shipped"
}

# Если клиент отправит тот же запрос ещё раз — результат будет один и тот же ✅ idempotent
PUT /orders/ORD-001 { ... } → тот же результат
```

## PATCH vs PUT (кратко)

| Характеристика | PATCH | PUT |
|----------------|------|-----|
| **Обновление** | Частичное (только изменённые поля) | Полное (все поля в теле запроса) |
| **Idempotent?** | Обычно нет | Да |
| **Пример** | `PATCH /orders/123 { "status": "shipped" }` | `PUT /orders/123 { "items": [...], "status": "shipped" }` |

## Когда использовать POST vs PUT

### Используйте POST, когда:
- ✅ Создаётся новый ресурс с уникальным ID (заказ, комментарий, отзыв)
- ✅ Клиент не знает ID нового ресурса заранее
- ✅ Нужно создать несколько ресурсов в одном запросе (batch creation)

**Примеры из интернет-магазина:**
```http
POST /orders → создаёт новый заказ (сервер присваивает ID)
POST /products/comments → создаёт комментарий к товару
POST /cart/items → добавляет товар в корзину
```

### Используйте PUT, когда:
- ✅ Обновляется существующий ресурс по известному ID
- ✅ Нужно полностью обновить все поля ресурса
- ✅ Клиент знает ID ресурса заранее

**Примеры из интернет-магазина:**
```http
PUT /products/123 → обновляет товар с ID 123 (все поля)
PUT /orders/ORD-001 → обновляет заказ ORD-001 полностью
PUT /users/me/profile → обновляет профиль пользователя
```

## Что важно запомнить аналитику

1. **POST не idempotent, PUT idempotent**  
   POST создаёт новый ресурс каждый раз. PUT с одним и тем же телом всегда даёт один результат.

2. **ID в URL:**
   - POST: `/orders` (без ID) — сервер присваивает ID
   - PUT: `/orders/ORD-001` (с ID) — клиент указывает ID заранее

3. **Полное vs частичное обновление:**
   - PUT обновляет все поля ресурса
   - PATCH обновляет только изменённые поля

4. **RESTful API должен быть предсказуемым:**  
   Клиент должен знать, что POST создаст новый ресурс, а PUT обновит существующий.

## Типичные вопросы и ответы

**Q: В чём разница между POST и PUT?**  
A: POST создаёт новый ресурс (сервер присваивает ID), не idempotent. PUT полностью обновляет существующий ресурс по известному ID, idempotent.

**Q: Почему POST не считается idempotent?**  
A: Потому что каждый POST создаёт новый уникальный ресурс. Один и тот же запрос 10 раз даст 10 разных ресурсов.

**Q: Когда использовать PATCH вместо PUT?**  
A: PATCH используется для частичного обновления (только изменённые поля). PUT обновляет все поля ресурса.

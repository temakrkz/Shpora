# 3.24 Обратная совместимость API — breaking vs non-breaking changes

---

## 📌 Короткий ответ

> **Обратная совместимость** — старые клиенты продолжают работать после изменений API.
> - ✅ **Non-breaking (обратно совместимое)**: добавление новых необязательных полей, новые методы/ресурсы
> - ❌ **Breaking (ломает совместимость)**: удаление полей, изменение типов данных, изменение смысла эндпоинтов

---

## 💡 Простыми словами

### Аналогия с розеткой

| Изменение | Совместимо? | Почему |
|-----------|-------------|--------|
| Добавить новую розетку в стену | ✅ Да | Старые приборы продолжают работать |
| Убрать существующую розетку | ❌ Нет | Приборы, подключённые к ней, перестанут работать |
| Изменить напряжение с 220В на 110В | ❌ Нет | Все старые приборы сломаются |

### Когда что использовать

- **Non-breaking**: когда можно добавить новое без удаления старого
- **Breaking**: когда нужно удалить/изменить существующее — требует новой версии API

---

## 🔍 Подробно

### Виды изменений API

#### ✅ Non-breaking (обратно совместимые)

**Что можно:**
1. **Добавить новые поля в ответе** (лучше сделать их необязательными)
2. **Добавить новый эндпоинт/ресурс**
3. **Добавить новые параметры запроса** (не удалять старые)
4. **Изменить тип с более узкого на более широкий** (например, `string` → `any`)

**Пример из интернет-магазина:**
```json
// Старый ответ товара:
{
  "id": 123,
  "name": "Телефон"
}

// Новый ответ (добавили поле):
{
  "id": 123,
  "name": "Телефон",
  "rating": 4.5  // новое необязательное поле
}
```
Старые клиенты просто игнорируют неизвестные поля — всё работает!

#### ❌ Breaking (ломает совместимость)

**Что нельзя:**
1. **Удалить существующее поле из ответа**
2. **Изменить тип данных поля** (`string` → `number`)
3. **Изменить смысл/поведение эндпоинта**
4. **Сделать обязательным необязательное поле**

**Пример из интернет-магазина:**
```json
// Старый ответ:
{
  "id": 123,
  "name": "Телефон",
  "price": 9990
}

// Новый ответ (удалили price):
{
  "id": 123,
  "name": "Телефон"
}
```
Старый клиент, который использовал `price`, сломается!

---

### Как управлять обратной совместимостью

#### Версионирование API

Когда нужно breaking change:
1. Создать новую версию API (v2, v3)
2. Поддерживать старую версию некоторое время
3. Мигрировать клиентов на новую версию
4. Удалить старую версию

**Пример:**
- `GET /api/v1/products` — старый эндпоинт без поля `rating`
- `GET /api/v2/products` — новый эндпоинт с полем `rating`
- Через 6 месяцев удаляют v1

#### Стратегии управления изменениями

| Стратегия | Когда использовать |
|-----------|-------------------|
| **Добавлять новые поля** | Большинство случаев (наиболее безопасно) |
| **Новая версия API** | Breaking changes, когда нельзя изменить контракт |
| **Feature flags** | Поле добавлять с флагом отключения для старых клиентов |

---

## ⚖️ Плюсы/минусы

### Non-breaking изменения

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Не нужно версионировать | Могут накапливаться лишние поля |
| Клиенты продолжают работать | Нужно документировать новые поля |
| Проще внедрять | Старые клиенты могут игнорировать новые данные |

### Breaking изменения

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Чистый контракт без мусора | Требует версионирования |
| Можно удалить ненужные поля | Нужно поддерживать старые версии |
| Явное разделение версий | Клиенты должны обновляться |

---

## 🎯 Что важно запомнить аналитику

1. **Правило 80/20**: 80% изменений обратно совместимы (добавление полей), 20% ломают (удаление/изменение)
2. **Никогда не удаляйте поля** — это самое простое правило обратной совместимости
3. **Новые поля делайте необязательными** — старые клиенты просто их проигнорируют
4. **Breaking change = новая версия API** — если нужно удалить/изменить, создавайте v2
5. **Документируйте контракт** (OpenAPI/Swagger) — чтобы все видели изменения заранее

## ❓ Типичные вопросы и ответы

### Q: Что такое breaking change в API?
**A:** Изменение, которое ломает работу старых клиентов: удаление полей, изменение типов, изменение поведения эндпоинтов.

### Q: Как сделать изменение обратно совместимым?
**A:** Добавлять новые необязательные поля, не удалять существующие, не менять типы данных.

### Q: Когда нужно создавать новую версию API?
**A:** Когда требуется breaking change (удаление/изменение полей) и нельзя сделать иначе.

### Q: Можно ли удалить поле из ответа API?
**A:** Нет, это ломает совместимость. Лучше оставить поле пустым или добавить новое вместо него.

### Q: Как мигрировать клиентов на новую версию API?
**A:** Поддерживать старую версию некоторое время (обычно 3-6 месяцев), постепенно направлять трафик на новую.

# 3.26 GraphQL — запрос данных по необходимости

---

## 📌 Короткий ответ

> **GraphQL** — язык запросов к API, где клиент сам говорит серверу: "дай мне именно эти поля в таком порядке". В отличие от REST (где получаете фиксированный набор полей), GraphQL позволяет получить ровно то, что нужно.

---

## 💡 Простыми словами

### Аналогия с заказом в ресторане

| Подход | Как работает |
|--------|--------------|
| **REST** | Вы берёте готовое меню: "Салат Цезарь" — всегда с теми же ингредиентами, без вариантов. |
| **GraphQL** | Вы говорите официанту: "Беру салат, но без орехов и добавьте больше пармезана". Готовят именно так как вы просили. |

### Когда что использовать

- **REST**: когда структура ответа предсказуема и не меняется часто
- **GraphQL**: когда разным клиентам нужны разные наборы полей из одного ресурса

---

## 🔍 Подробно

### Как работает GraphQL

**Клиент отправляет запрос:**
```graphql
query {
  product(id: "123") {
    name
    price
    reviews {
      author
      rating
    }
  }
}
```

**Сервер возвращает ТОЛЬКО запрошенные поля:**
```json
{
  "product": {
    "name": "Телефон",
    "price": 9990,
    "reviews": [
      {"author": "Иван", "rating": 5},
      {"author": "Мария", "rating": 4}
    ]
  }
}
```

---

### Преимущества GraphQL перед REST

#### ✅ Переизбыток данных (Over-fetching) в REST

**Пример REST:**
```json
// Запрос: только название товара
GET /api/products/123

// Ответ (всегда тот же, даже если нужно только 1 поле):
{
  "id": 123,
  "name": "Телефон",
  "description": "Длинное описание...",
  "price": 9990,
  "category": "Электроника",
  "manufacturer": "Samsung",
  "warranty": "1 год",
  "createdAt": "2024-01-01"
}
```
Клиенту нужно только `name`, но он получает всё!

#### ✅ Недостаток данных (Under-fetching) в REST

**Пример REST:**
```json
// Запрос: список товаров с отзывами
GET /api/products?withReviews=true

// Ответ:
[
  {
    "id": 123,
    "name": "Телефон",
    // Нет отзывов! Нужно делать второй запрос
  },
  {
    "id": 124,
    "name": "Ноутбук",
    // Нет отзывов! Второй запрос
  }
]
```
Нужно делать несколько запросов для получения всех данных.

#### ✅ GraphQL решает обе проблемы

**Пример GraphQL:**
```graphql
// Клиент сам выбирает, что ему нужно:
query {
  products {
    id
    name
    price  # только цена, без скидки
  }
  
  product(id: "123") {
    name
    reviews {
      author
      rating  # только рейтинг, без текста отзыва
    }
  }
}

// Ответ содержит ровно эти поля:
{
  "products": [
    {"id": 123, "name": "Телефон", "price": 9990},
    {"id": 124, "name": "Ноутбук", "price": 55000}
  ],
  "product": {
    "name": "Телефон",
    "reviews": [
      {"author": "Иван", "rating": 5},
      {"author": "Мария", "rating": 4}
    ]
  }
}
```

---

### Типы запросов в GraphQL

#### Query — чтение данных
```graphql
# Получить список товаров
query {
  products {
    id
    name
    price
  }
}
```

#### Mutation — изменение данных
```graphql
# Добавить товар в корзину
mutation {
  addToCart(productId: "123", quantity: 2) {
    cartId
    totalItems
  }
}
```

#### Subscription — подписка на события (асинхронно)
```graphql
# Уведомления о новых заказах
subscription {
  newOrder {
    orderId
    customerName
    totalAmount
  }
}
```

---

### Schema — описание API в GraphQL

**Пример schema для интернет-магазина:**
```graphql
type Product {
  id: ID!
  name: String!
  description: String
  price: Float!
  category: Category!
  reviews: [Review!]!
}

type Review {
  author: String!
  rating: Int!
  text: String
  createdAt: DateTime!
}

enum Category {
  ELECTRONICS
  CLOTHING
  FOOD
}

# ! означает обязательное поле
```

**Что это даёт:**
- Чёткое описание всех доступных полей и типов
- Автогенерация документации (GraphiQL Playground)
- Клиент знает, какие поля можно запросить

## ⚖️ Плюсы/минусы

### GraphQL

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Точные данные — только то, что нужно | Сложность реализации на сервере |
| Один endpoint для всех запросов | Может быть сложным для отладки |
| Клиент контролирует структуру ответа | Непредсказуемая нагрузка на БД |
| Идемпотентные queries (безопасно повторять) | Нет автоматического документирования как в OpenAPI |

### REST

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Простота реализации | Переизбыток или недостаток данных |
| Предсказуемая структура | Много endpoints для разных комбинаций |
| Широкая поддержка и стандарты | Сложное версионирование при изменениях |

---

## 🎯 Что важно запомнить аналитику

1. **GraphQL — это язык запросов**, а не просто формат данных (как JSON)
2. **Один endpoint** для всех операций (queries, mutations, subscriptions)
3. **Клиент выбирает поля** — решает проблемы over/under-fetching
4. **Schema определяет API** — документация и контракт одновременно
5. **GraphQL может быть медленнее REST** при неправильной реализации (N+1 проблема)

## ❓ Типичные вопросы и ответы

### Q: В чём главное отличие GraphQL от REST?
**A:** В REST сервер решает, какие поля вернуть (фиксированная структура). В GraphQL клиент сам выбирает, какие поля запросить.

### Q: Что такое N+1 проблема в GraphQL?
**A:** Когда для каждого объекта из списка делается отдельный запрос к БД. Например, 1 запрос на список товаров + N запросов на отзывы для каждого товара.

### Q: Какие типы операций есть в GraphQL?
**A:** Query (чтение), Mutation (изменение), Subscription (подписка на события).

### Q: Что означает `!` после поля в GraphQL?
**A:** Поле обязательное — сервер должен вернуть его, иначе ошибка.

### Q: Когда лучше использовать REST вместо GraphQL?
**A:** Для простых CRUD-операций, когда структура ответа предсказуема и не меняется часто (например, мобильные API с ограниченным трафиком).

## 🛠 Практические вопросы для собеседования

1. Объясните разницу между REST и GraphQL простыми словами.
2. Приведите пример проблемы over-fetching в REST и как GraphQL её решает.
3. Что такое N+1 проблема в GraphQL? Как её решить?
4. Какие типы операций есть в GraphQL?
5. Когда лучше использовать REST, а когда GraphQL?

**Ответы на практические вопросы:**

1. **REST — это как меню в ресторане**: вы берёте готовое блюдо с фиксированным набором ингредиентов. **GraphQL — как заказ по-собственному**: вы говорите "хочу салат без орехов и больше пармезана", и готовят именно так как просили.

2. **Over-fetching в REST**: клиент запрашивает `/api/products/123` и получает 20 полей, а ему нужно только 1 (например, `name`). В GraphQL клиент пишет запрос: `{ product(id: "123") { name } }` — сервер возвращает ровно это.

3. **N+1 проблема**: при загрузке списка товаров с отзывами делается 1 запрос на список + N запросов по одному для отзывов каждого товара. Решение: DataLoader (кэширование запросов), batch loading, или предварительная агрегация данных.

4. **Три типа операций:**
   - `Query` — чтение данных (`products { name }`)
   - `Mutation` — изменение данных (`addToCart(productId: "123")`)
   - `Subscription` — подписка на события (уведомления о новых заказах)

5. **REST лучше**: для простых CRUD, мобильных приложений с ограниченным трафиком, когда структура ответа предсказуема. **GraphQL лучше**: когда разным клиентам нужны разные комбинации полей из одного ресурса, или нужно минимизировать количество запросов (например, в SPA).

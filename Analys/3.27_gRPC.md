# 3.27 gRPC — высокопроизводительный RPC для микросервисов

---

## 📌 Короткий ответ

> **gRPC** — это протокол для общения между сервисами (RPC), который использует HTTP/2 и Protocol Buffers (Protobuf) вместо JSON. Быстрее REST, работает по сети как вызов функции: `getUser(123)` → получаешь объект пользователя.

---

## 💡 Простыми словами

### Аналогия с доставкой еды

| Подход | Как работает |
|--------|--------------|
| **REST/JSON** | Вы звоните в ресторан, заказываете через меню: "Хочу пиццу". Официант пишет на бумаге, передаёт повару. Повар готовит и отдаёт. Медленнее, больше шагов. |
| **gRPC** | Вы говорите напрямую с кухней через внутреннюю систему: "Пицца №123". Кухня сразу готовит и отдаёт. Быстрее, меньше шагов. |

### Когда что использовать

- **REST/JSON**: общение с внешними клиентами (браузеры, мобильные приложения)
- **gRPC**: общение между микросервисами внутри системы

---

## 🔍 Подробно

### Как работает gRPC

**1. Определение контракта (Protobuf)**

```protobuf
// file: user.proto

syntax = "proto3";

message User {
  string id = 1;        // номер пользователя
  string name = 2;      // имя
  int32 age = 3;        // возраст
}

service UserService {
  // Метод получения пользователя по ID
  rpc GetUser(GetUserRequest) returns (User);
  
  // Метод создания нового пользователя
  rpc CreateUser(CreateUserRequest) returns (CreateUserResponse);
}

message GetUserRequest {
  string user_id = 1;
}

message CreateUserRequest {
  string name = 1;
  int32 age = 2;
}

message CreateUserResponse {
  User user = 1;
}
```

**2. Генерация кода**

Из `.proto` файлов генерируется код для разных языков:
- `User.java`, `UserService.java` — для Java
- `user_pb2.py` — для Python
- `user.ts` — для TypeScript

**3. Вызов RPC**

```java
// Клиент вызывает метод как функцию:
UserService client = new UserServiceClient(...);
User user = client.getUser(new GetUserRequest("123"));
```

### Преимущества gRPC перед REST

#### ⚡ Скорость и эффективность

| Характеристика | REST/JSON | gRPC/Protobuf |
|----------------|-----------|---------------|
| **Формат данных** | JSON (текст) | Protobuf (бинарный) |
| **Размер сообщения** | 2-5x больше | Компактный бинарный формат |
| **Протокол** | HTTP/1.1 или HTTP/2 | HTTP/2 (многопоточность, сжатие) |
| **Сериализация** | Парсинг JSON | Быстрая сериализация Protobuf |

**Пример:**
```json
// REST/JSON: 500 байт
{
  "userId": "123",
  "userName": "Иван Иванов",
  "userEmail": "ivan@example.com",
  "userAge": 25,
  "isActive": true,
  "createdAt": "2024-01-01T10:00:00Z"
}

// gRPC/Protobuf: ~150 байт (бинарный формат)
```

#### 🔧 Типобезопасность

**REST:**
```json
// Клиент отправляет:
{"userId": "abc"}  // строка вместо числа!

// Сервер должен проверять и преобразовывать
```

**gRPC:**
```protobuf
message User {
  string id = 1;        // строка
}

// Если отправить число вместо строки — компиляция не пройдёт
```

### Сравнение REST vs gRPC

| Характеристика | REST/JSON | gRPC/Protobuf |
|----------------|-----------|---------------|
| **Контракт** | OpenAPI/Swagger (YAML/JSON) | .proto файлы |
| **Формат данных** | JSON (текст, читаемый человеком) | Protobuf (бинарный, нечитаемый) |
| **Протокол** | HTTP/1.1 или HTTP/2 | HTTP/2 |
| **Скорость** | Медленнее (парсинг JSON) | Быстрее (бинарный формат) |
| **Размер сообщения** | Большой | Компактный |
| **Клиенты** | Любые браузеры, мобильные | Только с поддержкой Protobuf |
| **Идемпотентность** | GET идемпотентен | Не гарантируется |
| **Аутентификация** | Bearer token в заголовке | mTLS или токены |

### Пример из интернет-магазина

**REST (общение с браузером):**
```http
GET /api/v1/products/123 HTTP/1.1
Authorization: Bearer eyJhbGc...

// Ответ:
{
  "id": 123,
  "name": "Телефон",
  "price": 9990,
  "category": "Электроника"
}
```

**gRPC (общение между сервисами):**
```protobuf
// Сервис Catalog общается с сервисом Inventory:
rpc GetStock(GetStockRequest) returns (GetStockResponse);

message GetStockRequest {
  string product_id = 1;
}

message GetStockResponse {
  int32 available_quantity = 1;
}

// Вызов из кода:
InventoryService client = new InventoryServiceClient(...);
int stock = client.getStock(new GetStockRequest("123"));
```

## ⚖️ Плюсы/минусы

### gRPC

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Очень быстро (бинарный формат) | Не работает в браузере напрямую |
| Компактные сообщения | Сложнее отладить (не читаемый формат) |
| Типобезопасность | Требует генерации кода из .proto |
| HTTP/2 (многопоточность) | Меньше инструментов и библиотек |

### REST/JSON

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Работает в любом браузере | Большие сообщения |
| Простота отладки | Медленнее (парсинг JSON) |
| Широкая поддержка | Нет типобезопасности |

---

## 🎯 Что важно запомнить аналитику

1. **gRPC — для общения между микросервисами**, REST — для внешних клиентов
2. **Protobuf — это контракт** как OpenAPI, но в бинарном формате
3. **gRPC быстрее REST** из-за бинарного формата и HTTP/2
4. **gRPC не работает напрямую в браузере** (нужен прокси)
5. **Типобезопасность**: ошибки компилируются заранее, а не во время выполнения

## ❓ Типичные вопросы и ответы

### Q: В чём разница между REST и gRPC?
**A:** REST — это архитектурный стиль с HTTP и JSON для внешних клиентов. gRPC — протокол RPC на HTTP/2 с Protobuf для общения между сервисами.

### Q: Почему gRPC быстрее REST?
**A:** 1) Бинарный формат Protobuf (меньше данных), 2) HTTP/2 (многопоточность, сжатие заголовков), 3) Быстрая сериализация без парсинга JSON.

### Q: Можно ли использовать gRPC в браузере?
**A:** Нет напрямую. Нужно использовать прокси (например, grpc-web), который конвертирует gRPC в HTTP/JSON.

### Q: Что такое Protobuf?
**A:** Protocol Buffers — формат сериализации данных от Google. Аналог JSON, но бинарный и более компактный.

### Q: Когда использовать REST вместо gRPC?
**A:** Для общения с браузерами и мобильными приложениями (REST), между микросервисами внутри системы (gRPC).

## 🛠 Практические вопросы для собеседования

1. Объясните разницу между REST и gRPC простыми словами.
2. Почему gRPC быстрее REST? В чём причины?
3. Можно ли использовать gRPC в браузере? Как?
4. Что такое Protobuf и зачем он нужен?
5. Приведите пример, когда лучше REST, а когда gRPC из интернет-магазина.

**Ответы на практические вопросы:**

1. **REST — это как меню в ресторане**: вы делаете HTTP-запрос (GET/POST), получаете JSON с данными. Подходит для любых клиентов (браузеры, мобильные). **gRPC — как вызов функции**: вы говорите `getUser(123)`, а не отправляете HTTP-запрос. Работает только между сервисами внутри системы.

2. **Три причины:**
   - Бинарный формат Protobuf (меньше данных в 2-5 раз)
   - HTTP/2 вместо HTTP/1.1 (многопоточность, сжатие заголовков)
   - Быстрая сериализация без парсинга JSON

3. **Не напрямую**. gRPC использует HTTP/2, а браузеры поддерживают только HTTP/1.1. Решение: grpc-web — прокси-сервер, который конвертирует gRPC в HTTP/JSON для браузера.

4. **Protocol Buffers (Protobuf)** — это формат сериализации данных от Google. Как JSON, но бинарный и более компактный. Из `.proto` файлов генерируется код для разных языков.

5. **REST**: общение с браузером (`/api/products`), мобильными приложениями, внешними системами. **gRPC**: микросервисы общаются между собой (Catalog → Inventory), внутри одного домена. Например: сервис заказов вызывает gRPC-метод сервиса инвентаря для проверки наличия товара.

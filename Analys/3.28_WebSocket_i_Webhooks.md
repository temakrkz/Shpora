# 3.28 WebSocket и Webhooks — постоянное соединение vs обратные вызовы

---

## 📌 Короткий ответ

> **WebSocket** — это постоянное соединение, где сервер может отправлять данные клиенту в любой момент без запроса. **Webhooks** — это когда клиент подписывается на события, а сервер сам отправляет данные при их появлении. Оба подхода делают REST асинхронным, но по-разному.

---

## 💡 Простыми словами

### Аналогия с доставкой еды

| Подход | Как работает |
|--------|--------------|
| **WebSocket** | Вы звоните в ресторан и говорите: "Я буду ждать, как только еда готова". Шеф держит трубку до тех пор, пока не приготовит. Вы продолжаете ждать на линии. |
| **Webhooks** | Вы оставляете заявку: "Как только еда готова, позвоните мне". Шеф звонит вам сам, когда заказ готов. Вам не нужно держать трубку. |

### Когда что использовать

- **WebSocket**: когда клиент должен быть онлайн и события происходят часто (чат, live-обновления)
- **Webhooks**: когда события редкие или клиент может отсутствовать (уведомления о заказах, статусы платежей)

---

## 🔍 Подробно

### WebSocket — постоянное соединение

**Как работает:**
1. Клиент устанавливает постоянное соединение с сервером
2. Канал остаётся открытым в обе стороны
3. Сервер может отправить данные клиенту в любой момент без запроса
4. Соединение держится до тех пор, пока не разорвано

**Пример из интернет-магазина — чат поддержки:**
```
Клиент подключается к WebSocket → канал открыт
├─ Клиент отправляет: "Здравствуйте"
├─ Сервер рассылает всем клиентам в чате новое сообщение
├─ Клиент отправляет: "Мой заказ не приходит!"
└─ Сервер мгновенно показывает сообщение оператору

Соединение остаётся открытым пока клиент не отключится
```

**Типичные сценарии WebSocket:**
- Чат поддержки в реальном времени
- Уведомления о новых заказах (мгновенная доставка)
- Live-обновление курсов валют при оплате
- Совместное редактирование документов

---

### Webhooks — обратные вызовы

**Как работает:**
1. Клиент подписывается на определённые события: "Пришли мне уведомление, когда появится новый заказ"
2. Сервер сохраняет эту подписку (URL клиента + тип событий)
3. Когда событие происходит, сервер **сам отправляет запрос** клиенту с данными
4. Если клиент недоступен — сервер может сохранить сообщение в очередь и отправить позже

**Пример из интернет-магазина — уведомления о заказах:**
```
Магазин → Клиент подписывается на webhook: "Пришли статусы заказов"
├─ Появился новый заказ №123 → Сервер отправляет POST /webhooks/shop/orders
│   └─ Тело: {"orderId": 123, "status": "created"}
├─ Статус заказа изменился на "shipped" → Сервер отправляет
│   └─ Тело: {"orderId": 123, "status": "shipped", "trackingNumber": "TRK123456"}
└─ Клиент обрабатывает уведомления и показывает их пользователю
```

**Типичные сценарии Webhooks:**
- Уведомления о новых заказах в CRM/ERP системах
- Статусы платежей (платёжный шлюз → магазин)
- Синхронизация данных между сервисами
- Триггеры для автоматических действий

---

### Сравнение WebSocket и Webhooks

| Характеристика | WebSocket | Webhooks |
|----------------|-----------|----------|
| **Инициатива** | Клиент подключается, сервер отправляет в любой момент | Сервер сам инициирует отправку при событии |
| **Соединение** | Постоянное (удерживает ресурсы) | Только при наличии данных |
| **Задержки** | Мгновенные | Зависят от доступности клиента |
| **Трафик** | Только при изменениях | При каждом событии |
| **Подключение** | Одно постоянное соединение | Каждый раз новый HTTP-запрос |
| **Клиент должен быть онлайн** | Да (или нужна логика reconnect) | Нет (можно использовать очереди) |
| **Идеально для** | Чатов, live-обновлений | Уведомлений, синхронизации данных |

---

### Проблемы и решения

#### WebSocket проблемы:
1. **Клиент может отключиться** → Реализовать логику повторного подключения (reconnect) с экспоненциальной задержкой
2. **Мобильные сети могут разрывать соединения** → Отключать при потере сети, использовать только для важных уведомлений
3. **Батарея тратится на поддержание соединения** → Автоматически отключать в фоне

#### Webhooks проблемы:
1. **Клиент недоступен** → Сохранять сообщения в очередь (Kafka, RabbitMQ) и отправлять позже
2. **Спам/нагрузка** → Ограничивать частоту вызовов, использовать секретные ключи для проверки
3. **Повторные попытки** → Реализовать retry logic с экспоненциальной задержкой

## ⚖️ Плюсы/минусы

### WebSocket

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Мгновенная доставка данных без запросов | Сложнее реализовать чем REST |
| Экономия трафика (только при изменениях) | Нужно управлять состоянием соединения |
| Двусторонняя связь в реальном времени | Проблемы с перезагрузкой страницы и мобильными сетями |

### Webhooks

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Сервер сам отправляет данные при событии | Клиент должен быть доступен (или нужна очередь) |
| Экономия ресурсов сервера (нет постоянных соединений) | Сложность реализации retry logic и обработки ошибок |
| Не требует, чтобы клиент был онлайн постоянно | Риск спама/нагрузки на эндпоинты клиента |

---

## 🎯 Что важно запомнить аналитику

1. **WebSocket — для постоянного общения** (чат, live-обновления), когда клиент должен быть онлайн
2. **Webhooks — для событийных уведомлений**, когда сервер сам инициирует отправку при появлении данных
3. **WebSocket держит соединение открытым** → удерживает ресурсы, требует reconnect логики
4. **Webhooks создают новый запрос при каждом событии** → проще масштабировать, но нужна обработка недоступности клиента
5. **Используются вместе**: REST для CRUD + WebSocket для чатов + Webhooks для уведомлений

## ❓ Типичные вопросы и ответы

### Q: В чём разница между WebSocket и Webhooks?
**A:** WebSocket — это постоянное соединение, где клиент держит канал открытым и сервер может отправить данные в любой момент. Webhooks — это когда клиент подписывается на события, а сервер сам отправляет запрос при их появлении.

### Q: Когда использовать WebSocket вместо Webhooks?
**A:** Когда нужна мгновенная двусторонняя связь в реальном времени (чат поддержки, совместное редактирование) и клиент должен быть онлайн.

### Q: Когда использовать Webhooks вместо WebSocket?
**A:** Когда события редкие или клиент может отсутствовать (уведомления о заказах, статусы платежей). Сервер сам инициирует отправку при появлении данных.

### Q: Что делать, если клиент недоступен для Webhooks?
**A:** Сохранять сообщения в очередь сообщений (Kafka, RabbitMQ) и отправлять позже, когда клиент станет доступен.

### Q: Какие проблемы могут возникнуть с WebSocket на мобильных устройствах?
**A:** Мобильные сети могут разрывать соединения для экономии трафика или батареи. Решение: автоматически отключать WebSocket при потере сети или в фоне, использовать только для важных уведомлений.

## 🛠 Практические вопросы для собеседования

1. Объясните разницу между WebSocket и Webhooks простыми словами.
2. В каком сценарии из интернет-магазина лучше использовать WebSocket? А Webhooks?
3. Какие проблемы могут возникнуть при использовании WebSocket на мобильных устройствах?
4. Что делать, если клиент недоступен для получения Webhook уведомления?
5. Как защитить Webhook-эндпоинты от спама и злоупотреблений?

**Ответы на практические вопросы:**

1. **WebSocket — это как разговор по телефону**: берёте трубку один раз и общаетесь до тех пор, пока не повесите. Сервер может говорить в любой момент без новых звонков от клиента. **Webhooks — это как автоответчик**: вы оставляете номер телефона, а когда у вас что-то происходит (появился заказ), сервер сам вам звонит с уведомлением.

2. **WebSocket лучше для чата поддержки**: мгновенная доставка сообщений между клиентом и оператором в реальном времени. **Webhooks лучше для уведомлений о заказах**: магазин отправляет CRM системе "появился новый заказ №123", когда склад обновит статус.

3. **Проблемы на мобильных:**
   - Мобильные сети могут разрывать соединения для экономии трафика
   - Батарея тратится на поддержание постоянного соединения
   - Решение: автоматически отключать WebSocket при потере сети или в фоне, использовать только для важных уведомлений

4. **Если клиент недоступен:** Сервер должен сохранять сообщения в очередь сообщений (Kafka, RabbitMQ) и отправлять позже, когда клиент станет доступен. Можно реализовать retry logic с экспоненциальной задержкой между попытками.

5. **Защита Webhook-эндпоинтов:**
   - Использовать секретные ключи для проверки подписей запросов
   - Ограничивать частоту вызовов (rate limiting)
   - Проверять IP-адреса отправителей (белый список)
   - Валидировать структуру и содержимое входящих данных

# 3.29 Выбор интеграции — когда что использовать (SOAP, REST, GraphQL, gRPC, брокеры, вебхуки, вебсокеты)

---

## 📌 Короткий ответ

> **Выбор технологии зависит от задачи:**
> - **REST/JSON** — для внешних клиентов (браузеры, мобильные приложения)
> - **gRPC/Protobuf** — для общения между микросервисами внутри системы
> - **GraphQL** — когда разным клиентам нужны разные наборы полей из одного ресурса
> - **WebSocket** — для чатов и live-обновлений в реальном времени
> - **Webhooks** — для уведомлений о событиях (появился заказ, изменился статус)
> - **Брокеры сообщений (Kafka/RabbitMQ)** — для асинхронного взаимодействия между сервисами

---

## 💡 Простыми словами

### Аналогия с доставкой еды в торговом центре

| Технология | Как работает | Когда использовать |
|------------|--------------|-------------------|
| **REST/JSON** | Вы берёте готовое меню и заказываете по номеру блюда | Когда структура ответа предсказуема (статус заказа, список товаров) |
| **GraphQL** | Вы говорите официанту: "Хочу салат без орехов и больше пармезана" | Когда разным клиентам нужны разные комбинации данных |
| **gRPC** | Вы звоните напрямую на кухню через внутреннюю систему | Когда сервисы общаются внутри одного здания (микросервисы) |
| **WebSocket** | Вы берёте трубку и ждёте, пока официант не подойдёт с готовым заказом | Когда нужно мгновенное уведомление о статусе заказа |
| **Webhooks** | Официант сам звонит вам, когда ваш заказ готов | Когда вы хотите получать уведомления о событиях |
| **Брокеры (Kafka/RabbitMQ)** | Вы оставляете заявку в системе заказов, а кухня сама её выполняет | Когда сервисы должны работать независимо друг от друга |

## 🔍 Подробно

### REST/JSON — универсальный стандарт

**Когда использовать:**
- Общение с браузерами и мобильными приложениями
- Простые CRUD-операции (создать, прочитать, обновить, удалить)
- Когда структура ответа предсказуема и не меняется часто
- Внешние интеграции с другими системами

**Пример из интернет-магазина:**
```
Клиент → GET /api/v1/products/123 → Сервер возвращает JSON со списком товаров
```

**Детальный пример использования:**
1. **Пользователь заходит на сайт** и видит список товаров категории "Смартфоны"
2. **Мобильное приложение** делает запрос: `GET /api/v1/products?category=smartphones&limit=20`
3. **Сервер возвращает JSON:**
   ```json
   {
     "products": [
       {"id": 1, "name": "iPhone 15", "price": 999},
       {"id": 2, "name": "Samsung Galaxy S24", "price": 899}
     ]
   }
   ```

**Плюсы:**
- Работает в любом браузере и мобильном приложении
- Простота реализации и отладки
- Широкая поддержка инструментов (Postman, Swagger)

**Минусы:**
- Переизбыток или недостаток данных (нужно делать несколько запросов)
- Медленнее GraphQL/gRPC из-за парсинга JSON

---

### gRPC/Protobuf — для микросервисов

**Когда использовать:**
- Общение между микросервисами внутри одной системы
- Когда важна скорость и эффективность передачи данных
- Высоконагруженные внутренние сервисы

**Пример из интернет-магазина:**
```
Сервис заказов → gRPC вызов сервиса инвентаря: getStock(productId: "123") → Сервер возвращает количество товара
```

**Детальный пример использования:**
1. **Пользователь добавляет товар в корзину** (сервис корзины)
2. **Перед оформлением заказа**, сервис корзины проверяет наличие товара через gRPC-вызов:
   ```
   Сервис корзины → gRPC call → Сервис инвентаря: CheckStock(productId="iPhone15", quantity=1)
   ← Ответ: {"available": true, "stock": 50}
   ```
3. **Если товара нет**, сервис возвращает ошибку пользователю

**Плюсы:**
- Очень быстро (бинарный формат Protobuf)
- Компактные сообщения (меньше данных в 2-5 раз чем JSON)
- Типобезопасность (ошибки компилируются заранее)

**Минусы:**
- Не работает напрямую в браузере (нужен прокси)
- Сложнее отладить (не читаемый формат)
- Требует генерации кода из .proto файлов

---

### GraphQL — гибкость запросов

**Когда использовать:**
- Когда разным клиентам нужны разные наборы полей из одного ресурса
- Мобильные приложения с ограниченным трафиком
- Когда нужно минимизировать количество запросов (получить всё за один вызов)

**Пример из интернет-магазина:**
```
Мобильное приложение запрашивает: { products { id name price } }
→ Сервер возвращает только эти поля, без лишних данных
```

**Детальный пример использования:**
1. **Мобильное приложение** (ограниченный трафик) запрашивает:
   ```graphql
   query {
     product(id: "123") {
       id
       name
       price
     }
   }
   ```
   → Сервер возвращает только эти 3 поля

2. **Десктопное приложение** (полные данные) запрашивает:
   ```graphql
   query {
     product(id: "123") {
       id
       name
       price
       description
       reviews { author rating text }
       relatedProducts { id name }
     }
   }
   ```
   → Сервер возвращает все запрошенные поля

**Плюсы:**
- Клиент выбирает, какие поля получить (нет переизбытка данных)
- Один endpoint для всех операций (queries, mutations, subscriptions)
- Идемпотентные queries (безопасно повторять запросы)

**Минусы:**
- Сложность реализации на сервере (нужен GraphQL server)
- Может быть сложным для отладки
- Непредсказуемая нагрузка на БД (N+1 проблема)

---

### WebSocket — постоянное соединение

**Когда использовать:**
- Чат поддержки в реальном времени
- Уведомления о новых заказах, статусах платежей
- Live-обновление курсов валют при оплате
- Совместное редактирование документов

**Пример из интернет-магазина:**
```
Клиент подключается к WebSocket → канал открыт
├─ Клиент отправляет: "Здравствуйте"
├─ Сервер мгновенно показывает сообщение оператору
└─ Оператор отвечает: "Ваш заказ №123 уже в обработке"
```

**Детальный пример использования:**
1. **Пользователь открывает чат с поддержкой** на сайте интернет-магазина
2. **Клиент подключается к WebSocket**, получает уникальное соединение
3. **Общение в реальном времени:**
   - Пользователь: "Где мой заказ №456?"
   - Сервер передаёт сообщение оператору мгновенно (без задержки)
   - Оператор: "Ваш заказ находится на складе, ожидается доставка завтра"
   - Клиент видит ответ моментально

**Плюсы:**
- Мгновенная доставка данных без запросов от клиента
- Экономия трафика (только при изменениях)
- Двусторонняя связь в реальном времени

**Минусы:**
- Сложнее реализовать чем REST
- Нужно управлять состоянием соединения и повторным подключением
- Проблемы с мобильными сетями (могут разрывать соединения)

---

### Webhooks — обратные вызовы

**Когда использовать:**
- Уведомления о новых заказах в CRM/ERP системах
- Статусы платежей от платёжного шлюза
- Синхронизация данных между сервисами
- Триггеры для автоматических действий (отправка email, создание задачи)

**Пример из интернет-магазина:**
```
Магазин → Клиент подписывается на webhook: "Пришли статусы заказов"
├─ Появился новый заказ №123 → Сервер отправляет POST /webhooks/shop/orders
│   └─ Тело: {"orderId": 123, "status": "created"}
└─ CRM получает уведомление и показывает его менеджеру
```

**Детальные примеры использования:**

**Пример 1: Уведомление о новом заказе в CRM**
1. **Магазин создаёт webhook-эндпоинт** в своей системе: `POST /webhooks/shop/orders`
2. **Когда клиент делает заказ**, сервер магазина отправляет HTTP POST запрос:
   ```
   POST https://crm.example.com/webhook/orders
   Body: {
     "orderId": 123,
     "customerName": "Иван Иванов",
     "totalAmount": 9990,
     "items": [{"productId": 456, "quantity": 2}]
   }
   ```
3. **CRM получает уведомление** и показывает заказ менеджеру

**Пример 2: Статусы платежей от платёжного шлюза**
1. **Магазин подключается к платёжному шлюзу (например, Stripe)** через webhook
2. **Когда клиент оплачивает заказ**, шлюз отправляет уведомление:
   ```
   POST https://shop.example.com/webhooks/stripe/payment
   Body: {
     "paymentId": "pay_123",
     "status": "succeeded",
     "amount": 9990,
     "currency": "RUB"
   }
   ```
3. **Магазин получает подтверждение оплаты** и обновляет статус заказа

**Пример 3: Уведомление о доставке от логистической компании**
1. **Сервис доставки подписывается на webhook** магазина
2. **Когда курьер доставляет заказ**, логистическая компания отправляет уведомление:
   ```
   POST https://shop.example.com/webhooks/delivery/status
   Body: {
     "orderId": 123,
     "status": "delivered",
     "deliveryTime": "2024-01-15T14:30:00Z"
   }
   ```
3. **Магазин обновляет статус заказа** и уведомляет клиента

**Плюсы:**
- Сервер сам отправляет данные при событии (не нужно polling)
- Экономия ресурсов сервера (нет постоянных соединений)
- Не требует, чтобы клиент был онлайн постоянно (можно использовать очереди)

**Минусы:**
- Клиент должен быть доступен (или нужна очередь для отложенной доставки)
- Сложность реализации retry logic и обработки ошибок
- Риск спама/нагрузки на эндпоинты клиента

### Брокеры сообщений (Kafka, RabbitMQ) — асинхронное взаимодействие

**Когда использовать:**
- Когда сервисы должны работать независимо друг от друга
- Высоконагруженные системы с большим количеством событий
- Когда нужна гарантия доставки сообщений (at-least-once, exactly-once)
- Когда события нужно хранить для повторной обработки (replay)

**Пример из интернет-магазина:**
```
Сервис заказов → публикует событие в Kafka: "order.created" → 
├─ Сервис уведомлений подписан на это событие → отправляет email клиенту
├─ Сервис аналитики подписан → сохраняет данные для отчётов
└─ Сервис склада подписан → обновляет остатки товаров

Все сервисы работают независимо, каждый обрабатывает события по-своему
```

**Детальные примеры использования:**

**Пример 1: Обработка заказа (Kafka)**
1. **Клиент оформляет заказ** на сайте интернет-магазина
2. **Сервис заказов публикует событие в Kafka:**
   ```
   Topic: orders.events
   Message: {
     "eventType": "order.created",
     "orderId": 123,
     "customerId": 456,
     "totalAmount": 9990,
     "timestamp": "2024-01-15T10:30:00Z"
   }
   ```
3. **Сервис уведомлений** подписан на этот топик → отправляет email клиенту
4. **Сервис аналитики** подписан → сохраняет данные для отчётов
5. **Сервис склада** подписан → обновляет остатки товаров

Каждый сервис работает независимо, не ожидая ответа от других.

**Пример 2: Обработка платежей (RabbitMQ)**
1. **Клиент оплачивает заказ**, сервис заказов отправляет сообщение в RabbitMQ:
   ```
   Exchange: payment.events
   Routing Key: order.payment.pending
   Message: {
     "orderId": 123,
     "amount": 9990,
     "paymentMethod": "card"
   }
   ```
2. **Сервис оплаты** подписан на этот exchange → обрабатывает платеж
3. **После успешной оплаты**, сервис отправляет сообщение:
   ```
   Routing Key: order.payment.success
   Message: {
     "orderId": 123,
     "status": "paid"
   }
   ```
4. **Сервис заказов** подписан → обновляет статус заказа

**Плюсы:**
- Асинхронное взаимодействие (сервисы не ждут друг друга)
- Высокая производительность (особенно Kafka)
- Гарантия доставки сообщений
- Возможность повторной обработки событий (replay)

**Минусы:**
- Сложность реализации и отладки
- Требует инфраструктуры брокеров (Kafka, RabbitMQ)
- Нужно управлять подписками на события

|----------------|-----------|---------|---------------|-----------|----------|--------------------------|
| **Для кого** | Внешние клиенты | Внешние клиенты | Внутренние сервисы | Чаты, live-обновления | Уведомления | Асинхронное взаимодействие |
| **Скорость** | Средняя | Средняя | Очень быстро | Мгновенно | Быстро (при событии) | Очень быстро |
| **Формат данных** | JSON (текст) | JSON (текст) | Protobuf (бинарный) | JSON/protobuf | JSON | JSON/protobuf |
| **Клиент выбирает данные** | Нет | Да | Нет | Нет | Нет | Нет |
| **Постоянное соединение** | Нет | Нет | Нет | Да | Нет | Нет |

| **Сложность реализации** | Простая | Средняя | Средняя | Сложная | Средняя | Сложная |

## 🛠 Когда что применять на примере интернет-магазина

### REST/JSON — для внешних клиентов
**Применять, когда:**
- Клиент — браузер или мобильное приложение
- Нужно получить/отправить данные по предсказуемой структуре
- Примеры:
  - `GET /api/v1/products` — список товаров
  - `POST /api/v1/orders` — создать заказ
  - `GET /api/v1/users/profile` — профиль пользователя

### GraphQL — для гибких запросов
**Применять, когда:**
- Разным клиентам нужны разные наборы данных
- Нужно минимизировать количество запросов
- Примеры:
  - Мобильное приложение запрашивает только id и name товара
  - Десктопное приложение запрашивает все данные с отзывами и рейтингом

### gRPC — для внутренних сервисов
**Применять, когда:**
- Сервисы общаются внутри одной системы
- Важна скорость и эффективность передачи данных
- Примеры:
  - Сервис корзины проверяет наличие товара у сервиса инвентаря
  - Сервис заказов получает данные о клиенте у сервиса пользователей

### WebSocket — для чатов и live-обновлений
**Применять, когда:**
- Нужна мгновенная двусторонняя связь в реальном времени
- Примеры:
  - Чат поддержки с оператором
  - Live-уведомления о статусе заказа ("Ваш заказ доставлен!")
  - Совместное редактирование документов

### Webhooks — для уведомлений о событиях
**Применять, когда:**
- Сервер должен сам инициировать отправку при появлении данных
- Примеры:
  - Платёжный шлюз → магазин (статус платежа)
  - Магазин → CRM (новый заказ)
  - Логистическая компания → магазин (статус доставки)

### Брокеры сообщений — для асинхронного взаимодействия
**Применять, когда:**
- Сервисы должны работать независимо друг от друга
- Нужно обрабатывать большое количество событий параллельно
- Примеры:
  - Обработка заказов (уведомления, аналитика, склад)
  - Синхронизация данных между сервисами
  - Асинхронная обработка платежей

4. **WebSocket — для чатов и live-обновлений**, когда нужна мгновенная двусторонняя связь

## ❓ Типичные вопросы и ответы

### Q: Когда использовать REST вместо GraphQL?
**A:** Для простых CRUD-операций, мобильных приложений с ограниченным трафиком, когда структура ответа предсказуема и не меняется часто. Например, `GET /api/v1/products` — список товаров всегда имеет одинаковую структуру.

### Q: Почему gRPC быстрее REST?
**A:** 1) Бинарный формат Protobuf (меньше данных в 2-5 раз), 2) HTTP/2 вместо HTTP/1.1 (многопоточность, сжатие заголовков), 3) Быстрая сериализация без парсинга JSON.

### Q: Можно ли использовать WebSocket для простых запросов типа "получить список товаров"?
**A:** Нет, WebSocket — только для постоянного соединения и push-данных. Для получения данных используйте REST или GraphQL.

### Q: В чём разница между Webhooks и брокерами сообщений?
**A:** Webhooks — это когда сервер сам отправляет HTTP-запрос клиенту при событии (синхронно). Брокеры — это когда сервис публикует сообщение в очередь, а другие сервисы подписаны на эти события и берут их оттуда (асинхронно).

### Q: Когда использовать Kafka вместо RabbitMQ?
**A:** Kafka лучше для высоконагруженных систем с большим количеством событий, где важна скорость и возможность хранить сообщения для повторной обработки. RabbitMQ лучше для простых очередей с гарантированной доставкой и маршрутизацией по exchange.

## 🛠 Практические вопросы для собеседования

### 1. Объясните разницу между REST, GraphQL и gRPC простыми словами.
**Ответ:** 
- **REST — это как меню в ресторане**: вы делаете HTTP-запрос (GET/POST), получаете JSON с данными. Подходит для любых клиентов (браузеры, мобильные).
- **GraphQL — это как заказ по-собственному**: вы говорите "хочу салат без орехов и больше пармезана", и готовят именно так как просили. Клиент сам выбирает, какие поля запросить.
- **gRPC — это вызов функции**: вы говорите `getUser(123)`, а не отправляете HTTP-запрос. Работает только между сервисами внутри системы через бинарный формат Protobuf.

### 2. В каком сценарии из интернет-магазина лучше использовать WebSocket? А Webhooks?
**Ответ:** 
- **WebSocket лучше для чата поддержки**: мгновенная доставка сообщений между клиентом и оператором в реальном времени, двусторонняя связь.
- **Webhooks лучше для уведомлений о заказах**: магазин отправляет CRM системе "появился новый заказ №123", когда склад обновит статус. Сервер сам инициирует отправку при появлении данных.

### 3. Когда использовать брокеры сообщений вместо прямых HTTP-вызовов между сервисами?
**Ответ:** Брокеры нужны, когда:
- Сервисы должны работать независимо друг от друга (не ждать ответа)
- Нужно обрабатывать большое количество событий параллельно
- События нужно хранить для повторной обработки (replay)
- Требуется гарантия доставки сообщений (at-least-once, exactly-once)

### 4. Как защитить Webhook-эндпоинты от спама и злоупотреблений?
**Ответ:** 
- Использовать секретные ключи для проверки подписей запросов
- Ограничивать частоту вызовов (rate limiting)
- Проверять IP-адреса отправителей (белый список)
- Валидировать структуру и содержимое входящих данных

### 5. Приведите пример, когда REST подходит, а GraphQL нет (и наоборот).
**Ответ:** 
- **REST подходит**, когда структура ответа предсказуема (статус заказа, список товаров). Например, `GET /api/v1/orders` всегда возвращает одинаковую структуру данных.
- **GraphQL нужен**, когда разным клиентам нужны разные комбинации полей из одного ресурса. Например, мобильное приложение запрашивает только id и name товара, а десктоп — всё с отзывами и рейтингом. REST не может адаптировать ответ под нужды клиента.

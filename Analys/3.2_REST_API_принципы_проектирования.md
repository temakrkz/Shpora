# 3.2 REST API — принципы проектирования

---

## 📌 Короткий ответ

> **REST (Representational State Transfer)** — это стиль проектирования API, который использует HTTP-методы и ресурсы для взаимодействия с клиентом.  
> **6 принципов** (по Roy Fielding): 5 обязательных + 1 опциональный:
> 1. **Client-Server** — разделение клиента и сервера
> 2. **Statelessness** — без состояния
> 3. **Cacheability** — кэшируемость
> 4. **Layered Architecture** — многоуровневая архитектура
> 5. **Uniform Interface** — единый интерфейс (ресурсы, манипуляции через URI, самоопределение, гиперmedia)
> 6. **Code on Demand** — загрузка кода на клиент (необязательно)

---

## 💡 Простыми словами

### Что такое REST?

Представь интернет-магазин:
- Товары → `/api/products`
- Заказчики → `/api/customers`
- Заказы → `/api/orders`

**REST API** — это правила, как общаться с этими ресурсами через HTTP.

### 6 принципов REST (по Roy Fielding)

| Принцип | Обязательный? | Что значит | Пример |
|---------|---------------|------------|--------|
| **Client-Server** | ✅ Да | Клиент и сервер независимы | Мобильное приложение работает отдельно от сервера |
| **Statelessness** | ✅ Да | Каждый запрос самодостаточен | Сервер не помнит историю, проверяет токен в каждом запросе |
| **Cacheability** | ✅ Да | Запросы можно кэшировать | Браузер сохраняет список товаров для быстрого доступа |
| **Layered Architecture** | ✅ Да | Система состоит из слоёв | API Gateway → Сервис заказов → База данных |
| **Uniform Interface** | ✅ Да | Единый интерфейс для всех клиентов | Все клиенты используют одни и те же URL и методы |
| **Code on Demand** | ❌ Нет | Загрузка кода на клиент (опционально) | JS-скрипт загружается через API для интерактивности |

## 🔍 Подробно

### 1. Client-Server (Клиент-Сервер) — обязательный принцип

**Что это:** Клиент и сервер независимы друг от друга. Можно менять один без изменения другого.

**Как работает:**
```
Клиент (мобильное приложение) → [API] → Сервер (база данных)
         ↓                          ↓
   Может измениться           Может измениться
   независимо                  независимо
```

**Пример из интернет-магазина:**
- Мобильное приложение обновляется до версии 2.0
- Сервер остаётся прежним — всё работает!
- Или сервер обновляет логику, не меняя мобильное приложение

**Почему это важно:** Позволяет независимо развивать клиент и сервер.

---

### 2. Statelessness (Без состояния) — обязательный принцип

**Что это:** Каждый запрос содержит всю необходимую информацию для обработки. Сервер не "помнит" предыдущие запросы.

**Как работает:**
```
Запрос 1: POST /api/login → ответ: {token: "abc123"}
Запрос 2: GET /api/products, header: Authorization: abc123
         ↓
Сервер не помнит, что вы только что вошли — он проверяет токен в каждом запросе
```

**Пример из интернет-магазина:**
```http
# Заход в систему
POST /api/login
{ "username": "admin", "password": "secret" }
→ ответ: { "token": "abc123" }

# Получение списка товаров (токен передаётся с каждым запросом)
GET /api/products
Authorization: Bearer abc123
```

**Почему это важно:** 
- Можно масштабировать (каждый сервер обрабатывает запросы независимо)
- Надёжно (если один сервер упадёт — другие продолжат работать)

---

### 3. Cacheability (Кэшируемость) — обязательный принцип

**Что это:** Запросы можно кэшировать для ускорения работы. GET-запросы должны явно указывать, могут ли они быть кэшированы.

**Как работает:**
```http
# Сервер указывает: этот ответ можно кэшировать 1 час
GET /api/products
Cache-Control: max-age=3600

# Браузер сохраняет список товаров на 1 час
# При повторном запросе — берёт из кэша, не обращается к серверу
```

**Пример из интернет-магазина:**
- Список товаров → можно кэшировать (не меняется часто)
- Статус заказа → нельзя кэшировать (меняется постоянно)

**Почему это важно:** Ускоряет работу при повторных запросах.

---

### 4. Layered Architecture (Многоуровневая архитектура) — обязательный принцип

**Что это:** Система состоит из нескольких слоёв, каждый выполняет свою функцию. Клиент не знает, с каким именно сервером работает.

**Как работает:**
```
Клиент → [API Gateway] → [Сервис заказов] → [База данных]
         ↓              ↓               ↓
    Шлюз          Бизнес-логика     Хранение
   (аутентификация)  (обработка)    (данные)
```

**Пример из интернет-магазина:**
1. **API Gateway** — проверяет авторизацию, ограничивает скорость запросов
2. **Сервис заказов** — обрабатывает логику создания заказа
3. **База данных** — хранит данные о заказах

**Почему это важно:** Позволяет добавлять промежуточные слои (кэширование, логирование) без изменения клиента.

---

### 5. Uniform Interface (Единый интерфейс) — обязательный принцип

Это самый важный принцип REST! Он состоит из 4 подпринципов:

#### a) Ресурсы (Resources)
Всё представлено в виде ресурсов с уникальными идентификаторами.

**Пример:**
```
/api/products          # Все товары
/api/products/123      # Товар с ID 123
/api/orders            # Все заказы
```

#### b) Манипуляции через URI (Manipulations through URI)
Изменение состояния происходит через ссылки на ресурсы.

**Пример:**
```http
GET /api/orders/123 → получить данные заказа
PUT /api/orders/123?status=pending → обновить статус
DELETE /api/orders/123 → удалить заказ
```

#### c) Самоопределение (Self-descriptive messages)
Каждый запрос содержит всю информацию для его обработки.

**Пример:**
```http
POST /api/orders
Content-Type: application/json      # Формат данных указан в заголовке
Authorization: Bearer abc123        # Авторизация указана в заголовке
```

#### d) Гиперmedia (HATEOAS — Hypermedia as the Engine of Application State)
(Опционально, но рекомендуется) Ответы содержат ссылки на возможные действия.

**Пример:**
```json
{
  "id": 12345,
  "status": "created",
  "_links": {
    "self": "/api/orders/12345",
    "cancel": "/api/orders/12345/cancel",
    "track": "/api/orders/12345/track"
  }
}
```

**Почему это важно:** Клиент может автоматически определять, какие действия возможны.

---

### 6. Code on Demand (Загрузка кода на клиент) — необязательный принцип

**Что это:** Сервер может отправлять код (например, JavaScript), который выполняется на стороне клиента.

**Как работает:**
```http
GET /api/products
→ ответ включает <script src="/js/product-view.js"></script>
→ браузер загружает и исполняет скрипт для интерактивности
```

**Пример из интернет-магазина:**
- Сервер возвращает список товаров в HTML + JavaScript
- Клиент получает интерактивный интерфейс без отдельного фронтенда

**Почему это необязательно:** Большинство современных API отделяют бэкенд и фронтенд полностью. Этот принцип используется редко.

## 🛠 Пример из интернет-магазина

### Полный пример REST API с соблюдением всех принципов

#### 1. Client-Server
Мобильное приложение обновляется независимо от сервера.

#### 2. Statelessness
```http
# Каждый запрос содержит токен авторизации

Authorization: Bearer abc123
```

#### 3. Cacheability
```http
# Список товаров можно кэшировать
GET /api/products?category=electronics

```

#### 4. Layered Architecture
```
Клиент → API Gateway (аутентификация) → Сервис заказов → База данных
```

#### 5. Uniform Interface
```http
# Ресурсы с ID
GET /api/orders/123

# Манипуляции через URI
PUT /api/orders/123?status=pending
DELETE /api/orders/123

# Самоопределение в заголовках
Content-Type: application/json
Authorization: Bearer abc123
```

#### 6. Code on Demand (опционально)
```http
GET /api/products
→ ответ включает <script> для интерактивности
```

## ⚖️ Плюсы и минусы REST API

### ✅ Плюсы

| Преимущество | Объяснение | Пример из жизни |
|-------------|------------|-----------------|
| **Простота** | Легко понять и использовать | Разработчик может начать работать за 1 час |
| **Универсальность** | Работает с любым клиентом (веб, мобильное приложение) | Одно API для сайта и приложения |
| **Масштабируемость** | Можно добавлять серверы без изменений кода | При росте трафика просто добавляем мощности |
| **Кэширование** | GET-запросы можно кэшировать | Ускоряет работу при повторных запросах |

### ❌ Минусы

| Недостаток | Объяснение | Пример из жизни |
|-----------|------------|-----------------|
| **Неэффективность для сложных операций** | Каждый запрос — отдельный HTTP-запрос | Чтобы получить данные заказа и его товаров — 2 запроса вместо 1 |
| **Проблемы с безопасностью** | Токены могут быть перехвачены в URL | Нужно использовать HTTPS и хранить токены правильно |
| **Не подходит для real-time** | Каждый запрос требует соединения | Не подходит для чатов или уведомлений в реальном времени |

## 🎯 Что важно запомнить аналитику

1. **REST — это 6 принципов, не просто "используй GET/POST"**  
   > Нужно понимать каждый принцип и уметь объяснить его бизнесу.

2. **5 обязательных + 1 опциональный**  
   > Code on Demand — это необязательно, остальные 5 должны соблюдаться всегда.

3. **Uniform Interface — самый важный принцип**  
   > Именно он делает API "RESTful" (соответствующим REST).

4. **Statelessness — ключ к масштабированию**  
   > Без состояния можно добавлять серверы без изменений в коде.

## ❓ Типичные вопросы и ответы

### Вопрос 1: Какие принципы REST обязательны?

> **Ответ:**
> - **Обязательные (5):** Client-Server, Statelessness, Cacheability, Layered Architecture, Uniform Interface
> - **Необязательный (1):** Code on Demand
> 
> Все 5 обязательных должны соблюдаться для настоящего REST API.

### Вопрос 2: В чём разница между REST и SOAP?

> **Ответ:**
> - **REST** — стиль проектирования с JSON, проще и быстрее для веб-приложений
> - **SOAP** — строгий протокол с XML, встроенной безопасностью, используется в корпоративных системах
> 
> **Пример:**
> - Интернет-магазин → REST (простота важнее)
> - Банковская система → SOAP (надёжность важнее)

### Вопрос 3: Почему Statelessness важен?

> **Ответ:** Statelessness позволяет масштабировать систему. Каждый сервер может обрабатывать запросы независимо, не зная истории предыдущих запросов. Если один сервер упадёт — другие продолжат работать.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы вы спроектировали API для интернет-магазина?

**Ответ:**
Я бы использовал RESTful подход с соблюдением всех 5 обязательных принципов.

**Пример структуры API:**
```
/api/products          # GET — список товаров, POST — создать товар (Client-Server)
/api/products/123      # GET — данные товара, PUT/PATCH — обновить (Statelessness)

                     → API Gateway → Сервис заказов → База данных (Layered Architecture)
```

**Что я бы уточнил:**
- Какие поля обязательны при создании ресурса?
- Нужна ли пагинация для списков?
- Как обрабатывать ошибки (какие коды HTTP)?

---

### Вопрос 2: Объясните принцип Statelessness бизнесу.

**Ответ:**
Я бы сказал:
> "Statelessness — это как разовая покупка в магазине. Каждый раз вы показываете карту лояльности, и кассир проверяет её заново. Магазин не помнит ваши прошлые покупки — каждый визит независим."

**Почему это важно:** Позволяет добавлять новые кассы (серверы) без изменений в работе магазина.

---

### Вопрос 3: Что такое HATEOAS и нужно ли его использовать?

**Ответ:**
HATEOAS — это когда API возвращает не только данные, но и ссылки на возможные действия.

**Пример:**
```json
{
  "id": 12345,
  "_links": {
    "cancel": "/api/orders/12345/cancel",
    "track": "/api/orders/12345/track"
  }
}
```

**Нужно ли использовать?** Опционально. Для простых API не обязательно, но для сложных — полезно, так как клиент автоматически понимает возможные действия.

# 3.35 Шина (ESB) vs ETL: когда что использовать

---

## 📌 Короткий ответ

| Аспект | **ESB** (Enterprise Service Bus) | **ETL** (Extract-Transform-Load) |
|--------|----------------------------------|----------------------------------|
| **Основная задача** | Интеграция и маршрутизация сообщений между системами в реальном времени | Перенос и трансформация данных из источника в хранилище |
| **Когда данные нужны** | Сразу, по требованию (real-time или near real-time) | Периодически (по расписанию: раз в час/день/неделю) |
| **Направление** | Точка-точка, точка-множество, множество-множество | Источник → Хранилище данных (однонаправленно) |
| **Пример** | Заказ из интернет-магазина сразу отправляется в систему лояльности | Ежедневный экспорт всех заказов в дата-центр для аналитики |

> **ESB** — это "почтовое отделение", которое передаёт сообщения между системами почти мгновенно.  
> **ETL** — это "архивариус", который собирает данные, обрабатывает их и кладёт на полку для отчётов.

---

## 💡 Простыми словами

Представьте интернет-магазин:

### 📬 ESB (как курьерская служба)
Когда клиент делает заказ:
1. Заказ создаётся в системе магазина
2. **ESB мгновенно передаёт** его в систему оплаты, склад и службу доставки
3. Все системы работают **одновременно**, данные синхронизируются в реальном времени

> ESB — это "живая" интеграция. Данные летят сразу, как только что-то произошло.

### 📊 ETL (как архивариус)
В конце дня:
1. ETL-процесс **собирает** все заказы за день из системы магазина
2. **Трансформирует**: объединяет в один файл, форматирует, добавляет метки "дата", "час"
3. **Загружает** в дата-центр для отчётов: "сколько всего продано", "какие товары популярны"

> ETL — это "пакетная" обработка. Данные собираются, обрабатываются и кладутся на хранение для аналитики.

---

## 🔍 Подробно

### Что такое **ESB** (Enterprise Service Bus)

**Что это:**
- Центральный "маршрутизатор" между системами в организации
- Принимает сообщения от одной системы, решает куда их отправить, передаёт получателю

**Как работает:**
```
Система А → ESB → Система Б
              ↓
            Система В
```

**Зачем нужен:**
- **Маршрутизация**: решает, кому отправить сообщение
- **Трансформация форматов**: конвертирует JSON в XML или наоборот
- **Протоколы**: переводит HTTP в JMS (очередь) и обратно
- **Мониторинг**: видит все сообщения, которые проходят через него

**Когда используется:**
- Системы должны работать **одновременно**
- Нужно мгновенное уведомление о событии
- Разные системы используют разные форматы данных

---

### Что такое **ETL** (Extract-Transform-Load)

**Что это:**
- Процесс переноса данных из источников в хранилище для аналитики
- Три этапа: Извлечь → Трансформировать → Загрузить

**Как работает:**
```
Источники (системы магазина, склад, CRM) 
         ↓ [Extract]
Сбор всех данных за период
         ↓ [Transform]
Обработка: объединение, очистка, агрегация
         ↓ [Load]
Загрузка в Data Warehouse / Data Lake
```

**Зачем нужен:**
- **Аналитика**: строить отчёты "сколько продали", "кто лучшие клиенты"
- **История**: сохранять данные для анализа за прошлые периоды
- **Объединение**: собрать разрозненные данные в один источник правды

**Когда используется:**
- Нужно построить **отчёт** или дашборд
- Анализ исторических данных (за месяц/квартал/год)
- Данные не нужны мгновенно, можно подождать 15 минут/час/день

---

### Сравнение подходов

| Аспект | ESB | ETL |
|--------|-----|-----|
| **Скорость** | Мгновенно (миллисекунды) | Периодически (минуты/часы/дни) |
| **Направление** | Двустороннее, многонаправленное | Однонаправленно: источники → хранилище |
| **Данные** | Текущие транзакции | Агрегированные данные для отчётов |
| **Пример времени** | "Заказ создан" — сразу отправляется | "Отчёт за день" — собирается к 18:00 |

---

## 🛠 Пример из интернет-магазина

### Сценарий: Клиент сделал заказ на iPhone

#### 🔹 ESB в действии (реальное время)
```
18:42:05 — Клиент делает заказ на сайте
         ↓ [мгновенно]
ESB получает сообщение "Заказ создан"
         ↓
     ┌────┬─────────┬──────────┐
     ↓    ↓          ↓          ↓
Система  Система   Склад      SMS-сервис
оплаты    лояльности (забронировать)
         ↓
Уведомление клиенту: "Ваш заказ принят!"
```

**Что происходит:**
- Заказ сразу проверяется на оплату
- На складе резервируется iPhone под этот заказ
- Клиенту приходит SMS с номером заказа
- Всё за **1-2 секунды**

#### 🔹 ETL в действии (пакетно)
```
Конец рабочего дня (18:00)
         ↓ [сбор данных]
ETL собирает все заказы за день из системы магазина
         ↓ [трансформация]
Объединяет с данными о клиентах, товарах, ценах
         ↓ [загрузка]
Загружает в Data Warehouse
```

**Что происходит:**
- К 18:30 данные готовы для аналитики
- Менеджер видит отчёт "Сегодня продано на 5 млн руб."
- Маркетолог анализирует "какие категории популярны"
- Все данные **за день**, не по одному заказу

---

### Когда что использовать — таблица

| Ситуация | Решение | Почему |
|----------|---------|--------|
| Клиент оплатил — нужно сразу отправить чек | **ESB** | Чек нужен мгновенно |
| Нужно построить отчёт "продажи за месяц" | **ETL** | Данные не нужны срочно |
| Система склада должна узнать о новом заказе | **ESB** | Товар нужно забронировать сейчас |
| Анализ поведения клиентов для маркетинга | **ETL** | Нужна история, можно подождать |
| Синхронизация цен между сайтами | **ESB** | Цены должны быть актуальными |
| Еженедельный отчёт о продажах по регионам | **ETL** | Отчитываемся раз в неделю |

## ⚖️ Плюсы и минусы

### ESB (Enterprise Service Bus)

#### ✅ Плюсы:
- **Мгновенная реакция**: данные передаются сразу после события
- **Гибкость**: можно добавлять новые системы без изменения старых
- **Централизованный контроль**: все интеграции в одном месте
- **Трансформация форматов**: конвертирует JSON ↔ XML, HTTP ↔ JMS

#### ❌ Минусы:
- **Одно место отказа**: если ESB падает — всё останавливается
- **Сложность**: нужно настраивать маршруты, трансформации, мониторинг
- **Производительность**: добавляет задержку (хотя и небольшую)
- **Цена**: дорогие решения (MuleSoft, IBM Integration Bus)

---

### ETL (Extract-Transform-Load)

#### ✅ Плюсы:
- **Надёжность**: можно перепроверять данные перед загрузкой
- **История**: сохраняются все данные для анализа
- **Масштабируемость**: легко обрабатывать миллионы строк
- **Гибкость расписания**: можно настроить на любое время

#### ❌ Минусы:
- **Задержка данных**: не подходит для real-time задач
- **Ресурсоёмкость**: требует мощных серверов для обработки больших объёмов
- **Сложность отладки**: трудно понять, почему данные не совпадают
- **Устаревание**: если источник изменился, нужно обновлять ETL-процесс

---

## 🎯 Что важно запомнить аналитику

### ✅ Ключевые моменты:

1. **ESB = интеграция в реальном времени**  
   → Когда системы должны "знать" о событии сразу

2. **ETL = пакетная обработка для аналитики**  
   → Когда нужно построить отчёт или дашборд

3. **Они не исключают друг друга!**  
   → В одной системе могут быть и ESB, и ETL:
     - ESB передаёт заказ в реальном времени
     - ETL собирает заказы для еженедельного отчёта

4. **Выбор зависит от вопроса:**
   - "Что происходит прямо сейчас?" → ESB
   - "Что происходило за период?" → ETL

## ❓ Типичные вопросы и ответы

### Q: В чём главное отличие ESB и ETL?  
**A:** Главное — **когда данные нужны**. ESB передаёт мгновенно, когда что-то произошло. ETL собирает данные по расписанию для отчётов.

---

### Q: Можно ли использовать ETL вместо ESB?  
**A:** Нет, это разные задачи. ETL не подойдёт, если нужно мгновенное уведомление (например, "заказ создан"). Но можно использовать оба вместе: ESB для реального времени + ETL для аналитики.

---

### Q: Когда данные в системе могут отличаться?  
**A:** Если используются разные подходы! ESB передаёт сразу, ETL — с задержкой. Пока ETL не соберёт данные, они могут быть неполными или устаревшими.

---

### Q: Что такое "data warehouse" и зачем он нужен?  
**A:** Data Warehouse (склад данных) — это централизованное хранилище для аналитики. Сюда загружают ETL-процессы данные из разных систем, чтобы строить отчёты.

---

### Q: Можно ли сделать ETL в реальном времени?  
**A:** Да, это называется **streaming ETL**. Но классический ETL — пакетный процесс с задержкой.

---

## 🛠 Практические вопросы для собеседования

### 1. В интернет-магазине нужно синхронизировать цены между сайтом и мобильным приложением. Что использовать: ESB или ETL?  
**→ Ответ:** **ESB**. Цены должны быть актуальными в реальном времени. Когда цена меняется на сайте, она должна мгновенно обновиться в приложении.

---

### 2. Нужно построить еженедельный отчёт о продажах по регионам. Что использовать: ESB или ETL?  
**→ Ответ:** **ETL**. Отчитываемся раз в неделю, данные не нужны срочно. Можно собирать и обрабатывать всю ночь перед отчетом.

---

### 3. Клиент сделал заказ — нужно сразу забронировать товар на складе. Что использовать: ESB или ETL?  
**→ Ответ:** **ESB**. Товар нужно резервировать мгновенно, иначе другой клиент может его купить.

---

### 4. Нужно собрать данные о всех заказах за последний месяц для анализа. Что использовать: ESB или ETL?  
**→ Ответ:** **ETL**. Анализ исторических данных не требует мгновенности. Можно собирать данные по расписанию (например, раз в день).

---

### 5. Система лояльности должна начислять баллы сразу после покупки. Что использовать: ESB или ETL?  
**→ Ответ:** **ESB**. Клиент должен увидеть начисленные баллы мгновенно, чтобы их потратить на следующую покупку.

---

### 6. Нужно сохранить историю всех заказов для аудита и анализа. Что использовать: ESB или ETL?  
**→ Ответ:** **ETL**. История нужна для отчётов, можно собирать данные периодически.

---

### 7. Можно ли в одном проекте использовать и ESB, и ETL?  
**→ Ответ:** Да! Это распространённая практика:
- **ESB**: передаёт заказы в реальном времени (оплата, склад, уведомления)
- **ETL**: собирает данные для аналитики (ежедневные отчёты, дашборды)

---

### 8. Что произойдёт, если использовать ETL вместо ESB для уведомлений о заказах?  
**→ Ответ:** Клиент получит уведомление с задержкой (минуты/часы). Это плохо для пользовательского опыта — клиент может подумать, что заказ не принят.

---

### 9. Какие технологии можно использовать для ESB?  
**→ Ответ:** MuleSoft, Apache Camel, IBM Integration Bus, Oracle Service Bus, или самописные решения на Java/Python.

---

### 10. Какие инструменты подходят для ETL?  
**→ Ответ:** Informatica, Talend, Apache NiFi, Kettle (Pentaho), или облачные решения: AWS Glue, Azure Data Factory, Google Cloud Dataflow.

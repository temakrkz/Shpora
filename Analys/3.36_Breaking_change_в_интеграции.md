# 3.36 Breaking change в интеграции: как избежать и исправить

---

## 📌 Короткий ответ

**Breaking change (разрушающее изменение)** — это изменение в API или интеграции, которое **ломает работу** существующих потребителей.

| Тип изменения | Breaking? | Пример |
|---------------|-----------|--------|
| Удаление поля из ответа | ✅ Да | Раньше возвращали `user.name`, теперь нет |
| Изменение типа данных | ✅ Да | Поле было строкой, стало числом |
| Добавление нового поля | ❌ Нет | Можно игнорировать лишние поля |
| Изменение кода ответа (200 → 401) | ✅ Да | Теперь доступ запрещён без авторизации |
| Удаление эндпоинта | ✅ Да | `/api/users` больше не существует |

> **Breaking change** — это когда вы меняете API так, что старые клиенты перестают работать.  
> **Non-breaking change** — изменения, которые старые клиенты могут игнорировать или обрабатывать корректно.

---

## 💡 Простыми словами

Представьте интернет-магазин:

### 📱 Старое приложение (клиент)
```
Запрос: GET /api/products?category=phones
Ответ от сервера:
{
  "products": [
    {
      "id": 1,
      "name": "iPhone",
      "price": 79900,
      "stock": 5
    }
  ]
}
```

Приложение показывает: "iPhone — 79 900 руб., в наличии 5 шт."

---

### 🔥 Breaking change (плохой вариант)
Разработчик сервера решает изменить API:

**Изменения:**
1. Удалил поле `stock` (не нужно, есть на складе)
2. Изменил цену с числа на строку (чтобы добавить валюту)

```json
{
  "products": [
    {
      "id": 1,
      "name": "iPhone",
      "price": "79900"  // ❌ стало строкой!
    }
  ]
}
```

**Что происходит:**
- Старое приложение пытается разделить цену на 100: `79900 / 100 = 799`
- Но `"79900"` — это строка, деление не работает!
- Приложение **падает с ошибкой**: "Cannot convert string to number"

> Пользователь видит белый экран. Заказ не оформлен. Клиент злится.

---

### ✅ Non-breaking change (хороший вариант)
Тот же разработчик делает изменения аккуратно:

**Изменения:**
1. Добавил новое поле `discount` (скидка 5%)
2. Поле `stock` оставил, но сделал опциональным

```json
{
  "products": [
    {
      "id": 1,
      "name": "iPhone",
      "price": 79900,
      "discount": 5,        // ✅ новое поле
      "stock": 5            // ✅ старое поле осталось
    }
  ]
}
```

**Что происходит:**
- Старое приложение работает как раньше (игнорирует `discount`)
- Новое приложение использует скидку для расчёта цены
- **Никто не сломался!**

## 🔍 Подробно

### Что такое Breaking Change?

**Определение:**  
Изменение в API или интеграции, которое заставляет существующих потребителей (клиентов) работать неправильно или падать.

**Примеры breaking changes:**
1. **Удаление поля**: поле `user.email` больше не возвращается
2. **Изменение типа**: поле было числом, стало строкой
3. **Изменение формата даты**: `"2024-01-15"` → `"15/01/2024"`
4. **Удаление эндпоинта**: `/api/orders` больше не существует
5. **Изменение кода ответа**: 200 OK → 404 Not Found
6. **Требование авторизации**: раньше работал без токена, теперь нужен

---

### Что такое Non-Breaking Change?

**Определение:**  
Изменение в API, которое не ломает работу существующих потребителей.

**Примеры non-breaking changes:**
1. **Добавление нового поля**: `discount` — можно игнорировать
2. **Новый эндпоинт**: `/api/v2/users` — старый продолжает работать
3. **Изменение опционального поля**: добавили описание к полю, которое и так было пустым
4. **Добавление заголовка ответа**: `X-Request-ID` — клиент может его игнорировать

---

### Типы изменений в API

#### 1. **Breaking changes** (ломает работу)

| Изменение | Почему ломает |
|-----------|---------------|
| Удаление поля из ответа | Клиент не найдёт нужные данные |
| Изменение типа данных | Ошибка конвертации (строка → число) |
| Удаление эндпоинта | Запрос падает с 404 |
| Изменение кода ответа | Логика обработки меняется |
| Добавление обязательного поля в запросе | Старый клиент не передаёт новое поле |

#### 2. **Non-breaking changes** (не ломает)

| Изменение | Почему безопасно |
|-----------|------------------|
| Добавление нового поля в ответе | Клиент может игнорировать лишнее |
| Новый эндпоинт | Старый продолжает работать |
| Опциональное поле стало пустым по умолчанию | Не влияет на логику |
| Изменение формата заголовка | Клиент может его не читать |

## 🛠 Пример из интернет-магазина

### Сценарий: API для мобильного приложения

#### 🔴 Breaking change (плохо)

**Было (старое API):**
```json
GET /api/orders/123
{
  "order_id": 123,
  "total_price": 79900,
  "status": "pending",
  "customer_name": "Иван"
}
```

Приложение показывает: "Ваш заказ №123 на сумму 79 900 руб."

---

**Стало (разработчик изменил API):**
```json
GET /api/orders/123
{
  "order_id": 123,
  "total_price": "79900",  // ❌ стало строкой!
  "status": "pending"       // ✅ поле customer_name убрал
}
```

**Что ломается:**
- Приложение пытается отобразить сумму: `79900 / 100 = 799`
- Но `"79900"` — строка, деление не работает!
- **Ошибка**: "Cannot convert string to number"
- Пользователь видит белый экран

---

#### 🟢 Non-breaking change (хорошо)

**Стало (безопасное изменение):**
```json
GET /api/orders/123
{
  "order_id": 123,
  "total_price": 79900,
  "status": "pending",
  "customer_name": "Иван",      // ✅ поле осталось
  "delivery_address": "ул. Ленина 1"  // ✅ новое поле
}
```

**Что работает:**
- Старое приложение показывает заказ как раньше (игнорирует `delivery_address`)
- Новое приложение использует адрес доставки
- **Никто не сломался!**

## ⚖️ Плюсы и минусы breaking changes

### Почему breaking changes — это плохо?

#### ❌ Минусы:
1. **Сломанные клиенты**: все приложения, которые используют API, перестают работать
2. **Недовольные пользователи**: видят ошибки вместо данных
3. **Дорого исправлять**: нужно обновлять всех клиентов одновременно
4. **Потеря доверия**: разработчики боятся вносить изменения

#### ✅ Плюсы (редко):
1. **Упрощение API**: можно убрать лишние поля и сделать проще
2. **Безопасность**: можно добавить обязательную авторизацию
3. **Производительность**: меньше данных = быстрее

---

## 🎯 Что важно запомнить аналитику

### ✅ Ключевые моменты:

1. **Breaking change — это плохо для пользователей**  
   → Старые приложения перестают работать, пользователи видят ошибки

2. **Нужно избегать breaking changes**  
   → Использовать стратегии версионирования API (v1, v2)

3. **Добавление нового поля — безопасно**  
   → Клиенты могут игнорировать лишние данные

4. **Удаление поля — опасно**  
   → Нужно предупреждать клиентов заранее и давать время на обновление

5. **Важно документировать изменения**  
   → OpenAPI/Swagger должен обновляться при каждом изменении API

## ❓ Типичные вопросы и ответы

### Q: Что такое breaking change простыми словами?  
**A:** Это изменение в API, которое ломает работу старых клиентов. Например, если вы удалили поле из ответа, приложение не сможет его прочитать и упадёт с ошибкой.

---

### Q: Почему breaking changes — это плохо?  
**A:** Потому что все приложения, которые используют ваш API, перестают работать одновременно. Пользователи видят ошибки вместо данных, а разработчикам нужно срочно исправлять проблему.

---

### Q: Как избежать breaking changes?  
**A:** 
1. **Версионирование**: `/api/v1/` и `/api/v2/` — старый API продолжает работать
2. **Добавление новых полей**, а не удаление старых
3. **Предупреждение клиентов**: за 1-2 месяца до изменений
4. **Обновление документации** (OpenAPI/Swagger)

---

### Q: Что такое non-breaking change?  
**A:** Изменение, которое не ломает старые клиенты. Например, добавление нового поля в ответе — старые приложения могут его игнорировать и работать как раньше.

---

### Q: Можно ли удалить поле из API без breaking changes?  
**A:** Нет, удаление поля всегда breaking change. Но можно сделать так:
- Поле становится **опциональным** (может быть пустым)
- Даваете клиентам время на обновление (1-2 месяца)
- Потом удаляете через новую версию API (`/api/v2/`)

---

### Q: Что делать, если breaking change уже произошёл и клиенты сломались?  
**A:** 
1. **Срочно откатите изменения** к старой версии
2. **Уведомите всех клиентов** о проблеме
3. **Планируйте изменения правильно**: версионирование + предупреждение

---

### Q: Как документировать breaking changes для клиентов?  
**A:** 
- Обновить OpenAPI/Swagger спецификацию
- Создать changelog (список изменений)
- Отправить уведомление через email или в блоге разработчика
- Дать время на обновление (обычно 1-2 месяца)

## 🛠 Практические вопросы для собеседования

### 1. API возвращает поле `price` как число, а вы хотите сделать его строкой с валютой. Это breaking change? Как избежать проблем?  
**→ Ответ:** Да, это breaking change — приложение может пытаться делить число на 100 и упасть. Чтобы избежать:
- Версионируйте API: `/api/v1/` (число), `/api/v2/` (строка)
- Или добавьте валюту в отдельное поле: `"price": 79900, "currency": "RUB"`

---

### 2. Вы удалили поле `customer_name` из ответа заказа. Что произойдёт? Как исправить?  
**→ Ответ:** 
- **Что произойдёт**: приложения, которые используют это поле, упадут с ошибкой
- **Как исправить**: срочно откатите изменения или создайте новую версию API `/api/v2/`, где поле удалено

---

### 3. Можно ли добавить новое обязательное поле в запросе без breaking changes?  
**→ Ответ:** Нет, это breaking change — старые клиенты не будут передавать новое поле и сервер вернёт ошибку. Нужно:
- Сделать поле опциональным с дефолтным значением
- Или использовать новую версию API

---

### 4. Как предупредить клиентов о breaking changes?  
**→ Ответ:** 
1. Обновите OpenAPI/Swagger спецификацию
2. Создайте changelog со списком изменений
3. Отправьте уведомление за 1-2 месяца до изменений
4. Предложите миграционный период

---

### 5. API сломался у клиентов после обновления. Что делать?  
**→ Ответ:** 
1. Срочно откатите изменения к старой версии
2. Уведомите всех клиентов о проблеме
3. Проанализируйте, какие изменения были breaking
4. В будущем используйте версионирование API

---

### 6. Разработчик добавил новое поле `discount` в ответ товара. Это breaking change?  
**→ Ответ:** Нет, это non-breaking change — старые приложения могут игнорировать лишнее поле и работать как раньше.

---

### 7. Вы хотите изменить формат даты с `"2024-01-15"` на `"15/01/2024"`. Это breaking change?  
**→ Ответ:** Да, это breaking change — приложения могут парсить дату в одном формате и упасть при другом. Нужно использовать новую версию API или добавлять оба формата временно.

---

### 8. Как сделать так, чтобы удаление поля не было breaking change?  
**→ Ответ:** 
- Поле становится опциональным (может быть пустым)
- Даваете клиентам время на обновление (1-2 месяца)
- Через новую версию API (`/api/v2/`) удаляете поле окончательно

---

### 9. Что такое OpenAPI/Swagger и зачем он нужен?  
**→ Ответ:** Это документация API в формате JSON/YAML, которая описывает все эндпоинты, поля, типы данных. Помогает разработчикам понять, как работает API, и автоматически генерирует клиентский код.

---

### 10. Какое изменение считается самым безопасным для API?  
**→ Ответ:** Добавление нового опционального поля в ответе — старые клиенты могут его игнорировать и работать как раньше.

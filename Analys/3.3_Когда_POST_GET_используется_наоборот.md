# 3.3 Когда POST и GET используется 'наоборот'

---

## 📌 Короткий ответ

> **Правило:** GET — только чтение, POST — создание/изменение.  
> **Исключения бывают**, когда: нужно передать данные в URL (GET) или создать ресурс без ID (POST).

---

## 💡 Простыми словами

### Стандартное правило

| Метод | Для чего | Пример |
|-------|----------|--------|
| **GET** | Чтение данных | `GET /api/products` — получить список товаров |
| **POST** | Создание/изменение | `POST /api/orders` — создать новый заказ |

### Но бывают исключения!

Иногда разработчики используют POST вместо GET или наоборот. Почему?

---

## 🔍 Подробно

### 1. Когда POST используется вместо GET (создание с параметрами в URL)

**Ситуация:** Нужно создать ресурс, но ID ещё не известен.

**Пример:**
```http
# Неправильно: мы не знаем ID нового заказа
POST /api/orders/99999  # Какой это заказ? Мы же его только создаём!

# Правильно: создаём без ID в URL
POST /api/orders         # Сервер сам назначит ID и вернёт его
```

**Почему так?**
- POST позволяет передать данные в теле запроса (не в URL)
- GET не должен менять состояние сервера, а создание заказа — это изменение

### 2. Когда GET используется вместо POST (фильтрация через параметры)

**Ситуация:** Нужно получить данные с фильтрацией по параметрам.

**Пример:**
```http
# Правильно: фильтруем через параметры запроса
GET /api/products?category=electronics&min_price=1000

# Неправильно: пытаемся создать фильтр через POST
POST /api/products/filter  # Зачем создавать, если можно просто получить?
```

**Почему так?**
- GET предназначен для чтения с фильтрацией
- Параметры в URL — это стандартный способ фильтрации

### 3. Когда POST используется вместо GET (крупные данные)

**Ситуация:** Нужно передать много данных или чувствительную информацию.

**Пример:**
```http
# Неправильно: передаём пароль в URL (видно в истории браузера!)
GET /api/login?username=admin&password=123456  # ОПАСНО!

# Правильно: передаём данные в теле запроса
POST /api/login
Content-Type: application/json

{
  "username": "admin",
  "password": "123456"
}
```

**Почему так?**
- URL виден в истории браузера, логах сервера
- POST позволяет шифровать данные в теле запроса

### 4. Когда GET используется вместо POST (получение данных с пагинацией)

**Ситуация:** Нужно получить часть данных из большого списка.

**Пример:**
```http
# Правильно: пагинация через параметры
GET /api/orders?page=2&limit=10

# Неправильно: пытаемся создать страницу через POST
POST /api/orders/page  # Зачем создавать, если можно просто получить?
```

## 🛠 Пример из интернет-магазина

### Сценарий 1: Поиск товаров (GET)

**Пользователь вводит:** "iPhone" с ценой от 50000 рублей.

```http
# Правильно: поиск через GET
GET /api/products?search=iphone&min_price=50000
```

**Почему GET?** Мы читаем данные, не создаём ничего нового.

---

### Сценарий 2: Создание заказа (POST)

**Пользователь добавил товары в корзину и нажал "Оплатить".**

```http
# Правильно: создание через POST
POST /api/orders
Content-Type: application/json

{
  "customer_id": 456,
  "items": [
    {"product_id": 789, "quantity": 2},
    {"product_id": 101, "quantity": 1}
  ],
  "delivery_address": {
    "street": "ул. Ленина",
    "city": "Москва"
  }
}
```

**Почему POST?** Мы создаём новый заказ (изменяем состояние сервера).

---

### Сценарий 3: Обновление статуса заказа (PATCH)

**Менеджер изменил статус заказа с "Новый" на "В обработке".**

```http
# Правильно: частичное обновление через PATCH
PATCH /api/orders/12345
Content-Type: application/json

{
  "status": "processing"
}
```

**Почему PATCH?** Мы меняем только одно поле, а не весь заказ целиком.

## ⚖️ Когда можно нарушать правила?

### ✅ Допустимые исключения

| Ситуация | Почему допустимо | Пример |
|----------|------------------|--------|
| **Параметры в URL слишком длинные** | GET имеет лимит на длину URL (обычно 2000 символов) | Поиск по тексту с большим количеством фильтров |
| **Чувствительные данные** | Нельзя передавать пароли/карты в URL | Логин, пароль, номер карты |
| **Создание без ID** | POST позволяет создать ресурс и получить новый ID от сервера | Создание заказа, пользователя |

### ❌ Недопустимые нарушения

| Ситуация | Почему опасно | Пример |
|----------|---------------|--------|
| **GET для изменения данных** | Нарушает принцип "без состояния" | GET /api/orders/123 → увеличивает счётчик просмотров (изменяет данные) |
| **POST для чтения** | Неэффективно, создаёт лишние соединения | POST /api/products → получить список товаров |

---

## 🎯 Что важно запомнить аналитику

1. **GET — только чтение, не изменение**  
   > Если запрос меняет данные (даже косвенно), используйте POST/PATCH/PUT.

2. **POST для создания, PUT/PATCH для обновления**  
   > POST — создать новый ресурс, PUT — заменить целиком, PATCH — изменить часть полей.

3. **URL не должен содержать чувствительные данные**  
   > Пароли, номера карт, персональные данные — только в теле запроса (POST).

4. **Исключения бывают, но должны быть обоснованы**  
   > Если используете POST вместо GET — объясните почему (крупные данные, безопасность и т.д.).

## ❓ Типичные вопросы и ответы

### Вопрос 1: Почему нельзя использовать GET для создания заказа?

> **Ответ:** GET предназначен только для чтения. Если мы используем GET для создания, это нарушает принцип "без состояния" — сервер должен помнить, что запрос изменил данные.  
> Кроме того, GET-запросы кэшируются браузером и прокси-серверами, что может привести к отображению устаревших данных.

### Вопрос 2: Когда допустимо использовать POST вместо GET?

> **Ответ:**
> 1. Когда нужно передать чувствительные данные (пароли, номера карт)
> 2. Когда параметры запроса слишком длинные для URL
> 3. Когда нужно создать ресурс и получить новый ID от сервера

### Вопрос 3: В чём разница между PUT и PATCH?

> **Ответ:**
> - **PUT** заменяет ресурс целиком. Если не передать поле `email`, оно станет `null`.
> - **PATCH** обновляет только указанные поля. Остальные остаются без изменений.
> 
> **Пример:**
> ```http
> PUT /api/users/123 → { "email": "new@example.com" }  # email изменён, phone удалён (стал null)
> PATCH /api/users/123 → { "phone": "+79001234567" }   # только телефон изменён
> ```

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы вы спроектировали API для поиска товаров?

**Ответ:**
Я бы использовал **GET**, потому что это чтение данных с фильтрацией.

```http
GET /api/products?search=iphone&category=electronics&min_price=50000&max_price=100000&page=1&limit=20
```

**Что я бы уточнил:**
- Какие параметры поиска нужны (цена, категория, бренд)?
- Нужна ли пагинация?
- Как обрабатывать ошибки поиска?

---

### Вопрос 2: Почему нельзя передавать номер карты в URL?

**Ответ:**
URL виден:
1. В истории браузера пользователя
2. В логах сервера
3. В реферере при переходе на другую страницу

Это нарушает конфиденциальность и может привести к утечке данных.  
**Правильно:** передавать в теле запроса через POST с шифрованием (HTTPS).

---

### Вопрос 3: Как бы вы спроектировали API для обновления профиля пользователя?

**Ответ:**
Я бы использовал **PATCH**, потому что пользователь обычно меняет только одно или несколько полей.

```http
PATCH /api/users/123
Content-Type: application/json

{
  "phone": "+79001234567",
  "address": {
    "city": "Москва"
  }
}
```

**Что я бы уточнил:**
- Какие поля можно менять?
- Нужна ли валидация данных?
- Как обрабатывать ошибки обновления?

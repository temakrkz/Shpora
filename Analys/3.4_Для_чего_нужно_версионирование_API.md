# 3.4 Для чего нужно версионирование API

---

## 📌 Короткий ответ

> **Версионирование** — это способ управлять изменениями в API без поломки старых клиентов.  
> Когда меняем API → создаём новую версию (v1, v2) → старые клиенты продолжают работать со старой версией.

---

## 💡 Простыми словами

### Проблема без версионирования

Представь интернет-магазин:
- **Версия 1.0**: заказ выглядит так — `{id, customer_id, items}`
- Через месяц добавили поле `status` → `{id, customer_id, items, status}`

**Что происходит?**
- Старое мобильное приложение (которое не знает про `status`) ломается!
- Оно пытается прочитать новое поле и получает ошибку.

### Решение: версионирование

```
v1.0 — старый формат (без status)
v2.0 — новый формат (с status)
```

Старые клиенты работают с v1, новые — с v2. Всё работает!

---

## 🔍 Подробно

### Почему нужно версионирование?

API со временем меняется:
- Добавляются новые поля
- Убираются устаревшие поля
- Меняется структура данных
- Изменяется логика работы

**Без версионирования:** одно изменение API → все клиенты ломаются.  
**С версионированием:** изменения не ломают старых клиентов.

### Когда нужно версионирование?

| Ситуация | Почему нужна новая версия |
|----------|---------------------------|
| Добавление обязательного поля | Старые клиенты его не знают и ломается |
| Удаление поля | Старые клиенты продолжают отправлять устаревшее поле |
| Изменение формата данных | `{id: 123}` → `{"id": "abc"}` (число → строка) |
| Изменение логики работы | Раньше заказы создавались автоматически, теперь нужно подтверждение |

## 🛠 Пример из интернет-магазина

### Сценарий: Добавление поля `status` в заказ

#### Версия 1.0 (старая):
```json
{
  "id": 12345,
  "customer_id": 456,
  "items": [
    {"product_id": 789, "quantity": 2}
  ]
}
```

#### Версия 2.0 (новая):
```json
{
  "id": 12345,
  "customer_id": 456,
  "items": [
    {"product_id": 789, "quantity": 2}
  ],
  "status": "created"  # новое поле!
}
```

**Проблема:** Старое мобильное приложение (v1) не знает про `status` и ломается.  
**Решение:** Поддерживаем обе версии одновременно.

---

## ⚖️ Способы версионирования

### 1. В URL (самый популярный)

Добавляем версию в путь к ресурсу:
```http
GET /api/v1/orders/123         # Старая версия
GET /api/v2/orders/123         # Новая версия
```

**Плюсы:**
- Простота и понятность
- Легко отслеживать, какая версия используется

**Минусы:**
- URL становится длиннее

---

### 2. В заголовке HTTP (Header)

Добавляем версию в заголовок:
```http
GET /api/orders/123
Accept-Version: v2
```

**Плюсы:**
- URL остаётся чистым
- Можно менять версию без изменения пути

**Минусы:**
- Менее распространён, сложнее отладить

---

### 3. В параметрах запроса (Query string)

Добавляем версию как параметр:
```http
GET /api/orders/123?version=2
```

**Плюсы:**
- Простота реализации
- Можно использовать без изменений в коде клиента

**Минусы:**
- Менее стандартный подход, может конфликтовать с другими параметрами

---

## 🎯 Что важно запомнить аналитику

1. **Версионирование — это про совместимость**  
   > Новые изменения не должны ломать старых клиентов.

2. **Поддерживайте несколько версий одновременно**  
   > Не удаляйте старую версию сразу, дайте время на миграцию.

3. **Документируйте изменения между версиями**  
   > Клиенты должны знать, что изменилось в новой версии.

4. **Планируйте жизненный цикл версий**  
   > Укажите дату окончания поддержки старой версии.

## ❓ Типичные вопросы и ответы

### Вопрос 1: Когда нужно создавать новую версию API?

> **Ответ:**
> 1. Когда добавляется обязательное поле, которого не было раньше
> 2. Когда меняется структура данных (формат JSON)
> 3. Когда изменяется логика работы (например, порядок полей в ответе)
> 4. Когда удаляются поля или меняются их значения

### Вопрос 2: Как долго поддерживать старую версию?

> **Ответ:** Обычно 6-12 месяцев.  
> Нужно дать время разработчикам клиентов обновить свои приложения.

### Вопрос 3: Что делать, если нужно удалить поле в API?

> **Ответ:**
> 1. Создайте новую версию с удалённым полем
> 2. Укажите дату окончания поддержки старой версии
> 3. Предупредите клиентов за месяц до удаления

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы вы версионировали API интернет-магазина?

**Ответ:**
Я бы использовал **версию в URL**, потому что это самый понятный и распространённый подход.

```http
GET /api/v1/products          # Старая версия (без новых полей)
GET /api/v2/products          # Новая версия (с новыми полями)
```

**Что я бы уточнил:**
- Какие изменения планируются в новой версии?
- Когда планируется завершение поддержки старой версии?
- Нужно ли документировать различия между версиями?

---

### Вопрос 2: Клиент использует старую версию API, но вы хотите добавить обязательное поле. Что делать?

**Ответ:**
Я бы создал **новую версию API**, потому что добавление обязательного поля ломает старых клиентов.

```http
v1.0 — без нового поля (поддержка до 31 декабря)
v2.0 — с новым обязательным полем (новая версия)
```

**Что я бы уточнил:**
- Когда клиент сможет обновиться на новую версию?
- Нужно ли предоставить миграционный период?

---

### Вопрос 3: Как документировать изменения между версиями API?

**Ответ:**
Я бы использовал **OpenAPI/Swagger**, где для каждой версии есть отдельная спецификация.

**Пример документации:**
```yaml
# v1.0 — старый формат
paths:
  /api/v1/orders:
    get:
      responses:
        '200':
          description: Список заказов
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/OrderV1'

# v2.0 — новый формат с полем status
paths:
  /api/v2/orders:
    get:
      responses:
        '200':
          description: Список заказов
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/OrderV2'
```

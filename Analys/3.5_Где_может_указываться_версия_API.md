# 3.5 Где может указываться версия API и чем отличаются версии HTTP

---

## 📌 Короткий ответ

> **Версию API можно указать в:** URL, заголовке (Header), параметре запроса.  
> **HTTP-версии** (1.0/1.1/2) — это протокол передачи данных, а не версия самого API.

---

## 💡 Простыми словами

### Версия API vs Версия HTTP

| Что | Что такое | Пример |
|-----|-----------|--------|
| **Версия API** | Формат данных и логика работы сервиса | `/api/v1/orders` — старый формат заказа |
| **HTTP-версия** | Протокол передачи данных между клиентом и сервером | `HTTP/1.1` vs `HTTP/2` — как передаются данные |

### Где указывать версию API?

Есть 3 основных места:

```
1. В URL: /api/v1/orders
2. В заголовке: Accept-Version: v2
3. В параметре: /api/orders?version=2
```

---

## 🔍 Подробно

### 1. Версия в URL (самый популярный способ)

**Пример:**
```http
GET /api/v1/products          # Старая версия API
GET /api/v2/products          # Новая версия API
POST /api/v1/orders           # Создание заказа в старой версии
```

**Плюсы:**
- ✅ Самый понятный и распространённый способ
- ✅ Легко отладить (видно в браузере)
- ✅ Простота реализации

**Минусы:**
- ❌ URL становится длиннее
- ❌ Нужно поддерживать несколько эндпоинтов

---

### 2. Версия в заголовке HTTP (Header)

**Пример:**
```http
GET /api/products
Accept-Version: v1            # Указываем версию в заголовке

POST /api/orders
X-API-Version: 2              # Другой формат заголовка
```

**Плюсы:**
- ✅ URL остаётся чистым и коротким
- ✅ Можно менять версию без изменения пути

**Минусы:**
- ❌ Менее распространён, сложнее отладить
- ❌ Не все клиенты поддерживают этот подход

---

### 3. Версия в параметре запроса (Query string)

**Пример:**
```http
GET /api/products?version=1   # Старая версия
GET /api/products?version=2   # Новая версия
POST /api/orders?ver=v2       # Короткая версия
```

**Плюсы:**
- ✅ Простота реализации
- ✅ Можно использовать без изменений в коде клиента

**Минусы:**
- ❌ Менее стандартный подход
- ❌ Может конфликтовать с другими параметрами

---

## 🛠 Пример из интернет-магазина

### Сценарий: Разные версии API для разных клиентов

#### Клиент 1 (старое мобильное приложение):
```http
GET /api/v1/products?category=electronics&limit=20
```

**Ответ:**
```json
[
  {"id": 1, "name": "iPhone", "price": 99990}
]
```

#### Клиент 2 (новое веб-приложение):
```http
GET /api/v2/products?category=electronics&limit=20
```

**Ответ:**
```json
[
  {
    "id": 1,
    "name": "iPhone",
    "price": 99990,
    "rating": 4.5,          # новое поле в v2
    "in_stock": true        # новое поле в v2
  }
]
```

**Важно:** Оба клиента работают одновременно без конфликтов!

## ⚖️ HTTP-версии (1.0/1.1/2) — это другое!

### Что такое HTTP?

HTTP — это протокол передачи данных между клиентом и сервером. Он отвечает за то, **как** передаются данные, а не **что** передаётся.

### Различия версий HTTP

| Версия | Когда используется | Особенности |
|--------|-------------------|-------------|
| **HTTP/1.0** | Устарело (2000-е) | Один запрос — одно соединение |
| **HTTP/1.1** | Стандарт сейчас | Поддержка keep-alive, pipelining |
| **HTTP/2** | Современный стандарт | Мультиплексирование (несколько запросов по одному соединению), сжатие заголовков |

### Пример: HTTP-версия не влияет на версию API

```http
# Оба запроса используют HTTP/1.1, но разные версии API
GET /api/v1/orders HTTP/1.1      # Старая версия API
Host: shop.example.com

GET /api/v2/orders HTTP/1.1      # Новая версия API
Host: shop.example.com
```

**Важно:** HTTP-версия — это про то, **как** передаются данные (быстро или медленно).  
Версия API — это про то, **что** передаётся (формат данных и логика работы).

---

## 🎯 Что важно запомнить аналитику

1. **Версия API ≠ Версия HTTP**  
   > `/api/v1/orders` — версия API. `HTTP/1.1` — протокол передачи. Это разные вещи!

2. **URL — лучший способ версионирования**  
   > Самый понятный и распространённый подход для большинства клиентов.

3. **Поддерживайте несколько версий одновременно**  
   > Не удаляйте старую версию сразу, дайте время на миграцию.

4. **Документируйте различия между версиями**  
   > Клиенты должны знать, что изменилось в новой версии.

## ❓ Типичные вопросы и ответы

### Вопрос 1: В чём разница между версией API и HTTP-версией?

> **Ответ:**
> - **Версия API** — это формат данных и логика работы сервиса (например, `/api/v1/orders`).
> - **HTTP-версия** — это протокол передачи данных (например, `HTTP/1.1` vs `HTTP/2`).
> 
> HTTP-версия отвечает за то, **как быстро** передаются данные. Версия API — за то, **что именно** передаётся.

### Вопрос 2: Почему версия в URL лучше, чем в заголовке?

> **Ответ:**
> - В URL видно сразу, какая версия используется (не нужно смотреть заголовки)
> - Легче отладить и документировать
> - Большинство клиентов используют этот подход по умолчанию

### Вопрос 3: Можно ли использовать HTTP/2 для API?

> **Ответ:** Да! HTTP/2 — это современный стандарт, который быстрее передаёт данные.  
> Но версия API (v1/v2) указывается независимо от HTTP-версии.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы вы версионировали API для мобильного приложения?

**Ответ:**
Я бы использовал **версию в URL**, потому что это самый понятный подход для мобильных разработчиков.

```http
GET /api/v1/products          # Старая версия (минимум полей)
GET /api/v2/products          # Новая версия (больше данных, новые поля)
```

**Что я бы уточнил:**
- Какие изменения планируются в новой версии?
- Когда планируется завершение поддержки старой версии?
- Нужно ли документировать различия между версиями?

---

### Вопрос 2: Что такое HTTP/2 и зачем он нужен?

**Ответ:**
HTTP/2 — это улучшенная версия протокола HTTP, которая быстрее передаёт данные благодаря:
1. **Мультиплексированию** — несколько запросов по одному соединению
2. **Сжатию заголовков** — меньше данных для передачи
3. **Пушингу (push)** — сервер может отправить данные до того, как клиент их запросит

**Пример:** Раньше для загрузки страницы с 10 изображениями нужно было открыть 10 соединений.  
Теперь всё по одному соединению → быстрее!

---

### Вопрос 3: Как документировать версии API?

**Ответ:**
Я бы использовал **OpenAPI/Swagger**, где для каждой версии есть отдельная спецификация.

```yaml
# v1.0 — старый формат
paths:
  /api/v1/orders:
    get:
      responses:
        '200':
          description: Список заказов
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/OrderV1'

# v2.0 — новый формат с новыми полями
paths:
  /api/v2/orders:
    get:
      responses:
        '200':
          description: Список заказов
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/OrderV2'
```

# 3.8 Idempotency-key — как сделать POST идемпотентным

---

## 📌 Короткий ответ

> **Idempotency-key** — это уникальный идентификатор запроса, который гарантирует: если отправить один и тот же запрос несколько раз → результат будет одинаковым.  
> Полезно для повторных попыток при сбоях сети.

---

## 💡 Простыми словами

### Проблема без Idempotency-key

Представь интернет-магазин:
1. Пользователь нажимает "Оплатить заказ"
2. Запрос доходит до сервера → оплата прошла успешно ✅
3. Сеть упала, пользователь не получил ответ
4. Пользователь нажимает "Оплатить" ещё раз (думая что ничего не произошло)

**Без Idempotency-key:** Заказ оплачивается **дважды**! ❌  
→ Две транзакции в банке → проблема!

### Решение: Idempotency-key

Пользователь отправляет с каждым запросом уникальный ID:
```http
POST /api/orders
Idempotency-Key: abc123xyz
{ "items": [...] }
```

**Что происходит:**
- Первый запрос с `abc123xyz` → оплата прошла ✅
- Второй запрос с тем же `abc123xyz` → сервер видит что это повтор, отклоняет ❌

**Итого:** Заказ оплачивается **один раз**! ✅

## 🔍 Подробно

### Что такое идемпотентность?

**Идемпотентность** — свойство запроса, при котором многократное выполнение даёт тот же результат, что и одно выполнение.

| Метод | Идемпотентный? | Почему |
|-------|----------------|--------|
| **GET** | ✅ Да | Чтение данных не меняет их |
| **DELETE** | ✅ Да | Удалить уже удалённое — ничего не происходит |
| **PUT** | ✅ Да (частично) | Обновление ресурса с теми же данными → тот же результат |
| **POST** | ❌ Нет | Создание нового ресурса каждый раз создаёт новый! |

### Почему POST не идемпотентен?

```http
# Первый запрос — создаётся заказ 12345
POST /api/orders
→ ответ: { "id": 12345, ... }

# Второй запрос с теми же данными — создаётся заказ 12346! ❌
POST /api/orders
→ ответ: { "id": 12346, ... }
```

**Проблема:** При повторной попытке после сбоя → дубликаты заказов.

### Как сделать POST идемпотентным?

Добавляем **Idempotency-key** — уникальный идентификатор запроса:

```http
POST /api/orders
Idempotency-Key: abc123xyz  ← уникальный ID этого запроса
Content-Type: application/json

{ "items": [...] }
```

**Логика сервера:**
1. Получаем запрос с `Idempotency-Key: abc123xyz`
2. Проверяем в памяти/базе данных: был ли уже такой ключ?
3. Если **был** → возвращаем тот же результат (не создаём новый заказ)
4. Если **нет** → обрабатываем запрос, сохраняем ключ и результат

## 🛠 Пример из интернет-магазина

### Сценарий: Оплата заказа с повторной попыткой

#### 1. Первый запрос (успешный):
```http
POST /api/payments
Idempotency-Key: pay_2024_01_15_abc123xyz
Content-Type: application/json

{
  "order_id": 12345,
  "amount": 99990
}
```

**Ответ сервера:**
```json
{
  "status": "success",
  "transaction_id": "TXN789456"
}
```

Сервер сохраняет: `pay_2024_01_15_abc123xyz → TXN789456`

---

#### 2. Сеть упала, пользователь нажимает ещё раз (повторная попытка):
```http
POST /api/payments
Idempotency-Key: pay_2024_01_15_abc123xyz  ← тот же ID!
Content-Type: application/json

{
  "order_id": 12345,
  "amount": 99990
}
```

**Ответ сервера:**
```json
{
  "status": "duplicate",
  "transaction_id": "TXN789456"  ← возвращаем тот же ID!
}
```

**Итого:** Заказ оплачивается **один раз**! ✅

## ⚖️ Как работает Idempotency-key на сервере?

### Алгоритм обработки запроса:

```python
# Псевдокод (без кода, только концепция)

def handle_payment_request(request):
    idempotency_key = request.headers.get("Idempotency-Key")
    
    # 1. Проверяем: был ли уже такой ключ?
    if idempotency_key in stored_results:
        return stored_results[idempotency_key]  # Возвращаем тот же результат
    
    # 2. Обрабатываем запрос
    result = process_payment(request)
    
    # 3. Сохраняем результат с ключом
    stored_results[idempotency_key] = result
    
    return result
```

### Где хранить Idempotency-key?

| Место хранения | Плюсы | Минусы | Когда использовать |
|----------------|-------|--------|-------------------|
| **Память (Redis)** | Быстро, просто | Данные теряются при перезапуске сервера | Для короткосрочных операций (оплата) |
| **База данных** | Данные не теряются | Медленнее, сложнее | Для важных операций с долгосрочной историей |

## 🎯 Что важно запомнить аналитику

1. **Idempotency-key нужен для POST запросов**  
   > GET и DELETE уже идемпотентны по умолчанию. POST — нет, нужно добавлять ключ.

2. **Ключ должен быть уникальным для каждого пользователя**  
   > Нельзя использовать один ключ для всех пользователей (иначе повторная попытка одного пользователя помешает другому).

3. **Храните ключи с TTL (временем жизни)**  
   > Через час-два ключ можно удалить из памяти, чтобы не занимать место.

4. **Не используйте Idempotency-key для всех запросов**  
   > Только там где это критично (оплата, создание заказов).

## ❓ Типичные вопросы и ответы

### Вопрос 1: Почему GET запросы идемпотентны по умолчанию?

> **Ответ:** GET предназначен только для чтения данных. Чтение не меняет состояние сервера, поэтому многократное выполнение даёт тот же результат.

### Вопрос 2: Что делать если Idempotency-key уже использовался, но операция не завершилась?

> **Ответ:** Нужно хранить результат с ключом даже при ошибках. Если запрос был отклонён → сохраняем `status: "failed"` с этим ключом, чтобы повторная попытка вернула тот же ответ об ошибке.

### Вопрос 3: Как долго нужно хранить Idempotency-key?

> **Ответ:** Обычно 1-24 часа в зависимости от бизнес-процесса.  
> - Для оплаты → 24 часа (пользователь может повторить попытку на следующий день)
> - Для создания заказа → 1 час (обычно пользователь не повторяет сразу)

### Вопрос 2: Объясните Idempotency-key бизнесу.

**Ответ:**
Я бы сказал:
> "Idempotency-key — это как номер заказа в банке. Если вы нажмёте 'Оплатить' дважды из-за сбоя сети, банк проверит этот номер и скажет: 'Этот заказ уже оплачен, не нужно повторять'. Это защищает от двойных оплат."

**Пример из жизни:**
- **Без Idempotency-key:** Вы нажали "Оплатить" дважды → две транзакции в банке ❌
- **С Idempotency-key:** Банк видит что это повтор → одна транзакция ✅

---

### Вопрос 3: Когда НЕ нужно использовать Idempotency-key?

**Ответ:**
Не нужен, когда:
1. Операция не критична (просмотр товара)
2. Пользователь редко повторяет действия (например, добавление в корзину)
3. Есть другие механизмы защиты от дубликатов (уникальные ID заказов)

# 3.9 Проектировать контракты (OAS, SDL, OpenRPC)

---

## 📌 Короткий ответ

> **Контракт API** — это документ, который описывает как работает API: какие есть методы, какие данные принимаются и возвращаются.  
> **OAS (OpenAPI Specification)** — самый популярный стандарт для контрактов REST API.

---

## 💡 Простыми словами

### Что такое контракт?

Представь интернет-магазин:
- **Разработчик бэкенда** пишет код сервера
- **Разработчик фронтенда** пишет код сайта/приложения

**Без контракта:**
- Бэкенд возвращает данные в формате `{"id": 123}`
- Фронтенд ожидает формат `{"product_id": "123"}` (строка вместо числа)
- **Ошибка!** ❌

**С контрактом:**
- Контракт говорит: "API вернёт JSON с полем `id` типа число"
- Бэкенд и фронтенд знают что ожидать → всё работает! ✅

### Основные стандарты контрактов

| Стандарт | Для чего | Популярность |
|----------|----------|--------------|
| **OAS (OpenAPI)** | REST API с JSON | ⭐⭐⭐⭐⭐ (самый популярный) |
| **SDL** | SOAP/WSDL | ⭐⭐ (устаревает) |
| **OpenRPC** | Универсальный (REST, GraphQL, gRPC) | ⭐⭐⭐ (новый стандарт) |

## 🔍 Подробно

### 1. OAS (OpenAPI Specification) — REST API

**Что это:** Стандарт для описания REST API в формате YAML или JSON.

**Пример контракта (OAS):**
```yaml
openapi: 3.0.0
info:
  title: API интернет-магазина
  version: 1.0.0

paths:
  /api/products:
    get:
      summary: Получить список товаров
      responses:
        '200':
          description: Успех
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/Product'

  /api/orders:
    post:
      summary: Создать новый заказ
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateOrderRequest'
      responses:
        '201':
          description: Заказ создан
```

**Плюсы OAS:**
- ✅ Автоматическая генерация документации из кода
- ✅ Генерация клиентских библиотек (SDK)
- ✅ Тестирование API без написания кода (Postman, Swagger UI)
- ✅ Совместная работа бэкенда и фронтенда

**Минусы OAS:**
- ❌ Только для REST API (не GraphQL/gRPC)
- ❌ Сложный формат YAML/JSON

---

### 2. SDL (SOAP Document Language) — SOAP API

**Что это:** Стандарт для описания SOAP-сервисов в формате WSDL.

**Пример контракта (WSDL):**
```xml
<?xml version="1.0"?>
<wsdl:definitions xmlns:wsdl="http://schemas.xmlsoap.org/wsdl/">
  <wsdl:message name="GetOrderStatusRequest">
    <wsdl:part element="tns:getOrderStatus" type="xsd:string"/>
  </wsdl:message>
  
  <wsdl:portType name="OrdersPortType">
    <wsdl:operation name="getOrderStatus">
      <wsdl:input message="tns:GetOrderStatusRequest"/>
      <wsdl:output message="tns:GetOrderStatusResponse"/>
    </wsdl:operation>
  </wsdl:portType>
</wsdl:definitions>
```

**Плюсы SDL:**
- ✅ Чёткие правила для SOAP-сообщений
- ✅ Автоматическая генерация клиентского кода
- ✅ Хорошо подходит для корпоративных систем

**Минусы SDL:**
- ❌ Устаревает (SOAP уступает REST/GraphQL)
- ❌ Сложный XML формат
- ❌ Мало инструментов поддержки

---

### 3. OpenRPC — универсальный стандарт

**Что это:** Новый стандарт для описания любых API (REST, GraphQL, gRPC).

**Пример контракта (OpenRPC):**
```json
{
  "info": {
    "title": "API интернет-магазина",
    "version": "1.0.0"
  },
  "methods": [
    {
      "name": "getProducts",
      "summary": "Получить список товаров",
      "params": [
        {"name": "category", "type": "string"}
      ],
      "result": {
        "type": "array",
        "items": {"type": "object"}
      }
    },
    {
      "name": "createOrder",
      "summary": "Создать новый заказ"
    }
  ]
}
```

**Плюсы OpenRPC:**
- ✅ Универсальный (подходит для REST, GraphQL, gRPC)
- ✅ Простой JSON формат
- ✅ Автоматическая генерация документации и SDK

**Минусы OpenRPC:**
- ❌ Новый стандарт (мало инструментов поддержки)
- ❌ Меньше сообщество по сравнению с OAS

## 🛠 Пример из интернет-магазина

### Сценарий: Создание заказа

#### Без контракта:

**Бэкенд возвращает:**
```json
{
  "id": 12345,
  "status": "created"
}
```

**Фронтенд ожидает:**
```json
{
  "orderId": "12345",
  "message": "Заказ создан"
}
```

**Результат:** Ошибка! ❌ Фронтенд не понимает формат ответа.

---

#### С контрактом (OAS):

**Контракт говорит:**
```yaml
/api/orders:
  post:
    responses:
      '201':
        description: Заказ создан
        content:
          application/json:
            schema:
              type: object
              properties:
                orderId:
                  type: string
                message:
                  type: string
```

**Бэкенд возвращает:**
```json
{
  "orderId": "12345",
  "message": "Заказ создан"
}
```

**Фронтенд получает:** ✅ Всё соответствует контракту!

## ⚖️ Плюсы и минусы проектирования контрактов

### ✅ Плюсы

| Преимущество | Объяснение | Пример из жизни |
|-------------|------------|-----------------|
| **Совместная работа** | Бэкенд и фронтенд работают параллельно | Фронтенд может начать писать код до готовности бэкенда |
| **Документация** | Контракт — это живая документация | Не нужно читать README, контракт показывает всё сразу |
| **Автоматизация** | Генерация SDK и тестов из контракта | Postman может создать коллекцию запросов автоматически |
| **Проверка ошибок** | Ошибки обнаруживаются до запуска | Если бэкенд не соответствует контракту — сборка не проходит |

### ❌ Минусы

| Недостаток | Объяснение | Пример из жизни |
|-----------|------------|-----------------|
| **Дополнительная работа** | Нужно писать и поддерживать контракт | Бэкендер должен обновлять контракт при каждом изменении API |
| **Строгость** | Трудно изменить контракт без согласования | Если нужно добавить поле — нужно согласовать с фронтендом |

## 🎯 Что важно запомнить аналитику

1. **Контракт — это договор между бэкендом и фронтендом**  
   > Бэкенд должен соответствовать контракту, иначе фронтенд сломается.

2. **OAS — стандарт де-факто для REST API**  
   > Большинство современных проектов используют OpenAPI/Swagger.

3. **Контракт живёт в Git**  
   > Контракт должен быть частью репозитория и проверяться при каждом коммите.

4. **Не игнорируйте контракты**  
   > Без них бэкенд и фронтенд будут постоянно конфликтовать.

## ❓ Типичные вопросы и ответы

### Вопрос 1: Что такое OpenAPI?

> **Ответ:** OpenAPI (ранее Swagger) — это стандарт для описания REST API в формате YAML или JSON.  
> Он позволяет автоматически генерировать документацию, тесты и клиентские библиотеки.

### Вопрос 2: В чём разница между OAS и SDL?

> **Ответ:**
> - **OAS** — для REST API с JSON (современный стандарт)
> - **SDL** — для SOAP/WSDL (устаревает)
> 
> **Пример:**
> - Интернет-магазин → OAS (REST + JSON)
> - Банковская система → SDL (SOAP + XML, но устаревает)

### Вопрос 3: Почему контракты важны?

> **Ответ:** Контракты позволяют бэкенду и фронтенду работать параллельно без конфликтов.  
> Бэкенд знает что возвращать, фронтенд знает что ожидать → меньше ошибок при интеграции.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как бы вы спроектировали контракт для API интернет-магазина?

**Ответ:**
Я бы использовал **OAS (OpenAPI)**, потому что это стандарт де-факто для REST API.

**Структура контракта:**
```yaml
info:
  title: API интернет-магазина
  version: 1.0.0

paths:
  /api/products:
    get:
      summary: Получить список товаров
      parameters:
        - name: category
          in: query
          schema: { type: string }
      responses:
        '200':
          description: Успех
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/Product'

  /api/orders:
    post:
      summary: Создать новый заказ
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateOrderRequest'
```

**Что я бы уточнил:**
- Какие поля обязательны при создании ресурса?
- Нужна ли пагинация для списков?
- Как обрабатывать ошибки (какие коды HTTP)?

---

### Вопрос 2: Объясните контракты бизнесу.

**Ответ:**
Я бы сказал:
> "Контракт — это как техническое задание для разработчиков. Он говорит: 'API будет возвращать данные в таком формате, а принимать запросы в таком'. Это помогает избежать ошибок при интеграции."

**Пример из жизни:**
- **Без контракта:** Бэкенд вернул `{"id": 123}`, фронтенд ожидал `{"orderId": "123"}` → ошибка ❌
- **С контрактом:** Оба знают формат заранее → всё работает! ✅

---

### Вопрос 3: Как часто нужно обновлять контракт?

**Ответ:**
Контракт должен обновляться **при каждом изменении API**:
- Добавлено новое поле → обновить контракт
- Изменён формат данных → обновить контракт
- Добавлен новый метод → добавить в контракт

**Важно:** Контракт — это часть репозитория и проверяется при каждом коммите. Если не соответствует → сборка не проходит.

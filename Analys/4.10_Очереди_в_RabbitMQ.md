# 4.10 Очереди в RabbitMQ

_Брокеры сообщений — Kafka и RabbitMQ. Эта тема про очереди именно в RabbitMQ._

📌 **Короткий ответ**

Очередь в RabbitMQ — это контейнер для хранения сообщений между отправителем (producer) и получателем (consumer). Сообщения добавляются в конец очереди, потребляются по одному из начала. Гарантирует порядок внутри одной очереди (FIFO) и не потеряет сообщение пока его кто-то не заберёт.

💡 **Простыми словами**

Представьте почтовый ящик в магазине: курьер кладёт заказ внутрь, а кассир забирает только то, что там есть. Очередь — это такой ящик для сообщений между сервисами. Если сервис занят или offline, сообщение ждёт в очереди, пока не освободится потребитель.

🔍 **Подробно**

> **Что такое очередь (queue)?**
> Очередь — это логический контейнер для хранения сообщений в RabbitMQ. Это аналог классической FIFO-очереди (first in first out) — первый пришедший, первый ушёл.
>
> > **Как работает очередь:**
> > 1. Producer отправляет сообщение → оно попадает в конец очереди
> > 2. Consumer забирает сообщение из начала очереди
> > 3. Пока никто не забрал — сообщение хранится на диске/в памяти брокера
> >
> > **Важно:** Очередь работает только с одним consumer'ом на сообщение (unacknowledged) или с подтверждением (acknowledged).

**Что это такое и зачем нужно:**
- Что это: логический контейнер для хранения сообщений в RabbitMQ, аналог классической очереди FIFO.
- Зачем нужна: развязывает отправителя и получателя по времени; позволяет буферизовать нагрузку; гарантирует доставку пока сообщение не обработано.
- Как работает: producer → очередь → consumer. Сообщения хранятся на диске или в памяти брокера, пока их не заберёт потребитель.

**Новые понятия:**
> **Producer (отправитель)** — сервис, который отправляет сообщения в очередь. Например, сервис заказов отправляет сообщение о новом заказе.
>
> > **Consumer (получатель)** — сервис, который забирает и обрабатывает сообщения из очереди. Например, сервис уведомлений забирает сообщение и отправляет email клиенту.
>
> > **Acknowledgement (подтверждение)** — механизм подтверждения доставки. Consumer должен подтвердить, что сообщение обработано. Если подтверждения нет — RabbitMQ вернёт сообщение в очередь для повторной попытки.

**Где используется:**
- Асинхронное взаимодействие сервисов (заказ → уведомление)
- Отложенная обработка (сообщение ждёт определённое время перед обработкой)
- Буферизация пиковых нагрузок (много заказов одновременно → очередь сглаживает нагрузку)

**Особенности:**
> **FIFO (First In First Out)** — порядок внутри одной очереди строго соблюдается. Первое сообщение, которое пришло, первым будет обработано.
>
> > **TTL (Time To Live)** — время жизни сообщения или всей очереди:
> > - TTL сообщения: если не забрали за это время → удаляется автоматически
> > - TTL очереди: очередь сама удалится через заданное время без сообщений
>
> > **Dead Letter Queue (DLQ)** — специальная очередь для "мертвых" сообщений, которые не смогли обработать ни один consumer (например, из-за ошибок).

**Нюансы:**
- Если очередь переполняется, producer может блокироваться или отбрасывать сообщения (зависит от настроек prefetch и max length).
- Очередь можно ограничить по размеру в сообщениях или памяти — при превышении старые удаляются.
- RabbitMQ поддерживает две модели потребления: **pull** (consumer сам запрашивает) и **push** (RabbitMQ сам отдаёт сообщение consumer'у).

🛠 **Пример из интернет-магазина**

> **Сценарий:** Сервис заказов → Сервис уведомлений
>
> 1. Клиент делает заказ на сайте → сервис заказов создаёт запись в БД и отправляет сообщение в очередь `order.created`
> 2. Сервис уведомлений не работает прямо сейчас (например, ночью) → сообщение ждёт в очереди
> 3. Утром сервис уведомлений запускается → забирает первое сообщение из начала очереди и отправляет email клиенту о новом заказе
> 4. Если заказов много — они будут идти по одному в порядке поступления (FIFO)
>
> **Визуально:**
> ```
> [Сервис заказов] → [Очередь order.created: msg1, msg2, msg3] → [Сервис уведомлений]
>                    ↑                                           ↓
>                (сохраняет пока не заберут)               (забирает по одному из начала)
> ```

⚖️ **Плюсы/минусы**

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Гарантирует порядок внутри очереди (FIFO) | Сообщения могут дублироваться при сбоях (нужна обработка дублей) |
| Развязывает отправителя и получателя по времени | Требует настройки acknowledgement для надёжности |
| Буферизует пиковые нагрузки | При переполнении может блокировать producer |
| Поддерживает TTL и DLQ для отложенной обработки | Очередь работает только с одним consumer'ом на сообщение (в отличие от топика Kafka) |

🎯 **Что важно запомнить аналитику**

> 1. **Очередь хранит сообщения до момента потребления** — пока никто не забрал, они там лежат
> 2. **Внутри очереди порядок FIFO** — первый пришёл, первый ушёл (в отличие от топика Kafka)
> 3. **Очереди работают вместе с exchange и binding** — очередь сама по себе ничего не знает об отправителе/получателе, маршрутизация происходит через exchange
> 4. **Подтверждение доставки (acknowledgement)** — ключевой механизм для гарантии exactly-once или at-least-once

❓ **Типичные вопросы и ответы**

1. **Вопрос:** Чем очередь в RabbitMQ отличается от топика в Kafka?
   → **Ответ:** Очередь хранит одно сообщение за раз (один consumer на сообщение), гарантирует порядок FIFO внутри одной очереди. Топик может иметь несколько consumer'ов на одно сообщение, и порядок между партициями не гарантируется.

2. **Вопрос:** Что такое dead letter queue?
   → **Ответ:** Это специальная очередь для сообщений, которые не смогли обработать ни один consumer (например, из-за ошибок). Такие сообщения перемещаются туда автоматически или вручную.

3. **Вопрос:** Как настроить TTL в очереди RabbitMQ?
   → **Ответ:** Через параметры очереди: `x-message-ttl` — время жизни каждого сообщения; `x-expires` — время жизни всей очереди без сообщений.

🛠 **Практические вопросы для собеседования**

1. **Вопрос:** Клиент сделал заказ, но сервис уведомлений упал. Как гарантировать доставку?
   → **Ответ:** Включить acknowledgement в consumer'е: если обработка не завершилась успешно — RabbitMQ вернёт сообщение в очередь для повторной попытки. Также можно настроить retry с экспоненциальной задержкой и переместить "мертвые" сообщения в DLQ после N попыток.

2. **Вопрос:** Нужно отложить обработку сообщений на 1 час. Как это сделать?
   → **Ответ:** Использовать TTL (Time To Live) для сообщений: задать время жизни = 1 час + время обработки. Или использовать задержку очереди (delayed queue) — сообщения будут доступны для потребления только через заданное время.

3. **Вопрос:** Очередь переполняется, новые заказы не поступают. Что делать?
   → **Ответ:** Увеличить размер очереди (x-max-length), увеличить память брокера, добавить consumer'ов или временно отключить отправку в очередь (перенаправить в DLQ).

4. **Вопрос:** Почему сообщения дублируются при сбоях? Как это избежать?
   → **Ответ:** Дубли возникают из-за того, что RabbitMQ не получил acknowledgement до сбоя consumer'а. Решение: реализовать idempotency на стороне consumer'а (хранить обработанные сообщения в БД с уникальным ключом) или использовать exactly-once семантику через транзакции и outbox pattern.

5. **Вопрос:** Когда использовать pull-модель, а когда push?
   → **Ответ:** Pull — когда consumer сам контролирует скорость потребления (например, при пиковой нагрузке). Push — когда нужно гарантировать доставку даже если consumer не запрашивает (RabbitMQ сам отдаст сообщение).

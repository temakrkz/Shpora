# 4.11 Виды брокеров, push и pull модели

_Брокеры сообщений — Kafka и RabbitMQ. Эта тема про типы моделей потребления._

📌 **Короткий ответ**

Существует два основных типа брокеров: **очереди (queues)** и **топики (topics)**. Очереди работают с одним consumer'ом на сообщение, топики — с несколькими. Push-модель: брокёр сам отдаёт сообщения consumer'у. Pull-модель: consumer сам запрашивает сообщения у брокера.

💡 **Простыми словами**

Представьте два типа почтовых систем:
- **Очередь (queue)** — как почтовый ящик в магазине: письмо кладут внутрь, кассир забирает только то, что там есть (один человек на одно письмо).
- **Топик (topic)** — как рассылка по списку подписчиков: одно и то же письмо отправляется всем подписчикам одновременно (множество людей получают одно сообщение).

**Push vs Pull:**
- **Push** — брокёр сам "проталкивает" сообщения consumer'у, когда те готовы.
- **Pull** — consumer сам идёт к брокеру и спрашивает: "Есть ли новые сообщения?".

🔍 **Подробно**

> **Виды брокеров сообщений:**
> 1. **Очереди (Queues)** — хранят сообщения для одного consumer'а, порядок FIFO гарантируется. Пример: RabbitMQ очереди.
> 2. **Топики (Topics)** — рассылка сообщений множеству consumer'ов, один и тот же message может быть получен несколькими подписчиками. Пример: Kafka топик.

**Что это такое и зачем нужно:**

### Очереди (Queues)
- Что это: контейнер для одного consumer'а на сообщение
- Зачем нужна: когда одному сервису нужно обработать задачу (например, отправить email после заказа)
- Как работает: producer → очередь → один consumer

### Топики (Topics)
- Что это: канал рассылки для множества consumer'ов
- Зачем нужен: когда нужно уведомить нескольких сервисов одновременно (например, сохранить в БД, отправить в аналитику, создать индекс)
- Как работает: producer → топик → N consumer'ов

**Новые понятия:**

> **Push-модель (Publisher-Initiated)**
> - Что это: брокёр сам отдаёт сообщения consumer'у без запроса
> - Зачем нужна: когда нужно гарантировать доставку даже если consumer не запрашивает активно
> - Как работает: consumer подписывается на очередь/топик → брокёр отправляет сообщение как только оно появилось
> - Где используется: RabbitMQ с auto_ack=false, Kafka consumer'ы с polling

> **Pull-модель (Consumer-Initiated)**
> - Что это: consumer сам запрашивает сообщения у брокера по запросу
> - Зачем нужна: когда consumer контролирует скорость потребления и не хочет ждать пассивно
> - Как работает: consumer делает запрос → брокёр отдаёт N сообщений → consumer обрабатывает → запрашивает снова
> - Где используется: Kafka (всегда pull), RabbitMQ с manual_ack

**Где используется:**
- **Очереди**: асинхронные задачи, отложенная обработка, буферизация нагрузки
- **Топики**: события системы, уведомления, логирование, аналитика
- **Push**: когда важна гарантия доставки и не нужно контролировать скорость потребления
- **Pull**: когда consumer должен сам регулировать нагрузку (например, при пиковых запросах)

**Особенности:**

| Характеристика | Очередь (Queue) | Топик (Topic) |
|----------------|-----------------|---------------|
| Количество consumer'ов на сообщение | Один | Несколько |
| Порядок сообщений | FIFO гарантируется | Между партициями не гарантируется |
| Модель потребления | Push или Pull | Только Pull |
| Повторная доставка | Нет (если забрал один) | Да (каждый consumer получает копию) |

**Нюансы:**
- В RabbitMQ можно комбинировать: очередь + multiple consumers через prefetch limit.
- Kafka всегда использует pull-модель — consumer сам делает запрос к брокеру.
- Push может быть "тяжёлым" для consumer'а, если он не готов обрабатывать сообщения быстро.

🛠 **Пример из интернет-магазина**

> **Сценарий 1: Очередь (Queue) — отправка email**
> ```
> [Сервис заказов] → [Очередь order.email] → [Сервис уведомлений]
>                    ↑                         ↓
>              (один consumer на сообщение)   (обрабатывает и удаляет)
> ```
> Клиент сделал заказ → сервис заказов отправляет сообщение в очередь → сервис уведомлений забирает одно сообщение, отправляет email и удаляет из очереди.

> **Сценарий 2: Топик (Topic) — события системы**
> ```
> [Сервис заказов] → [Топик order.events]
>                    ↓       ↓       ↓
>            [Сервис БД] [Аналитика] [Уведомления]
> ```
> Клиент сделал заказ → сервис заказов отправляет событие в топик → три сервиса получают копию события и обрабатывают независимо друг от друга.

⚖️ **Плюсы/минусы**

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Очереди: гарантия порядка FIFO внутри очереди | Очереди: только один consumer на сообщение (нужны дубли для параллельной обработки) |
| Топики: одно событие обрабатывается несколькими сервисами | Топики: порядок между партициями не гарантируется |
| Push: брокёр гарантирует доставку без активного запроса | Push: может перегрузить consumer'ов, если они медленные |
| Pull: consumer контролирует скорость потребления | Pull: требует реализации retry и acknowledgement на стороне consumer'а |

🎯 **Что важно запомнить аналитику**

> 1. **Очередь = один consumer на сообщение** (FIFO)
> 2. **Топик = несколько consumer'ов получают копию сообщения**
> 3. **Push = брокёр сам отдаёт, Pull = consumer сам запрашивает**
> 4. **Kafka всегда pull**, RabbitMQ может быть push или pull

❓ **Типичные вопросы и ответы**

1. **Вопрос:** Чем очередь отличается от топика?
   → **Ответ:** Очередь хранит сообщение для одного consumer'а (FIFO). Топик рассылает копию сообщения всем подписчикам одновременно.

2. **Вопрос:** Когда использовать push-модель, а когда pull?
   → **Ответ:** Push — когда нужна гарантия доставки и не важно, как быстро consumer обрабатывает. Pull — когда consumer должен сам контролировать скорость потребления (например, при пиковой нагрузке).

3. **Вопрос:** Почему Kafka всегда использует pull-модель?
   → **Ответ:** Потому что Kafka топик — это просто набор партиций с сообщениями. Consumer сам запрашивает новые сообщения у брокера, когда готов их обработать. Это даёт полный контроль над скоростью потребления.

🛠 **Практические вопросы для собеседования**

1. **Вопрос:** Нужно уведомить 5 сервисов о новом заказе. Как это сделать?
   → **Ответ:** Использовать топик (topic). Один producer отправляет событие в топик, и все 5 сервисов-подписчики получают копию сообщения независимо друг от друга.

2. **Вопрос:** Consumer не успевает обрабатывать сообщения быстро, очередь переполняется. Что делать?
   → **Ответ:** Переключиться на pull-модель с ограниченным prefetch (consumer сам запрашивает по N сообщений за раз). Или добавить больше consumer'ов для параллельной обработки.

3. **Вопрос:** Почему в Kafka нет push-модели?
   → **Ответ:** Потому что Kafka топик — это просто набор партиций. Consumer сам делает запрос к брокеру и получает сообщения, когда готов их обработать. Это даёт полный контроль над скоростью потребления и предотвращает перегрузку consumer'ов.

4. **Вопрос:** Нужно гарантировать доставку даже если consumer упал. Как сделать?
   → **Ответ:** Использовать acknowledgement (подтверждение доставки). Consumer подтверждает обработку после успешного выполнения. Если подтверждения нет — брокёр вернёт сообщение в очередь для повторной попытки.

5. **Вопрос:** Когда использовать RabbitMQ очереди, а когда Kafka топик?
   → **Ответ:** RabbitMQ очереди — когда одному сервису нужно обработать задачу (например, отправка email). Kafka топик — когда несколько сервисов должны получить копию события одновременно (например, сохранение в БД + отправка в аналитику + создание индекса).

# 4.13 Модели потребления брокеров

_Брокеры сообщений — Kafka и RabbitMQ. Эта тема про то, как consumer'ы получают сообщения._

📌 **Короткий ответ**

Существует две основные модели потребления: **pull (вытягивание)** и **push (проталкивание)**. Pull: consumer сам запрашивает сообщения у брокера. Push: брокёр сам отдаёт сообщения consumer'у без запроса.

💡 **Простыми словами**

Представьте два способа получать посылку:
- **Pull**: вы идёте в пункт выдачи и спрашиваете: "Есть ли моя посылка?". Если есть — забираете, если нет — идите позже.
- **Push**: курьер звонит вам и говорит: "Ваша посылка готова, приходите забирать". Вам не нужно идти к нему — он сам приходит к вам.

🔍 **Подробно**

> **Pull-модель (Consumer-Initiated)**
> - Что это: consumer сам запрашивает сообщения у брокера с определённой частотой или по событию
> - Зачем нужна: consumer контролирует скорость потребления и не перегружается пассивными сообщениями
> - Как работает: consumer делает запрос → брокёр отдаёт N сообщений → consumer обрабатывает → запрашивает снова
> - Где используется: Kafka (всегда pull), RabbitMQ с manual_ack

**Преимущества:**
- Consumer сам регулирует скорость обработки
- Не перегружается, если сообщений больше чем может обработать
- Полный контроль над нагрузкой на систему

**Недостатки:**
- Требует реализации retry и acknowledgement на стороне consumer'а
- Есть задержка между появлением сообщения и его получением (до следующего запроса)

> **Push-модель (Broker-Initiated)**
> - Что это: брокёр сам отдаёт сообщения consumer'у без активного запроса
> - Зачем нужна: гарантировать доставку даже если consumer не запрашивает активно
> - Как работает: consumer подписывается на очередь/топик → брокёр отправляет сообщение как только оно появилось
> - Где используется: RabbitMQ с auto_ack, веб-хуки

**Преимущества:**
- Гарантирует доставку без активного запроса от consumer'а
- Реактивность — сообщения доставляются сразу при появлении
- Не требует реализации polling на стороне consumer'а

**Недостатки:**
- Может перегрузить consumer'ов, если они медленные
- Consumer не контролирует скорость потребления
- Требует надёжного брокера с поддержкой push

**Новые понятия:**

> **Acknowledgement (подтверждение доставки)**
> - Что это: механизм подтверждения обработки сообщения
> - Зачем нужен: гарантировать доставку и избежать дублей при сбоях
> - Как работает: consumer получает сообщение → обрабатывает → отправляет подтверждение брокеру. Если подтверждения нет — брокёр вернёт сообщение для повторной попытки

**Где используется:**
- **Pull**: Kafka (всегда), RabbitMQ с manual_ack
- **Push**: RabbitMQ с auto_ack, веб-хуки, чат-боты

**Особенности:**

| Характеристика | Pull | Push |
|----------------|------|------|
| Инициатор запроса | Consumer | Broker |
| Контроль скорости | Полный у consumer'а | У broker'а |
| Реактивность | Зависит от частоты polling | Мгновенная |
| Нагрузка на сеть | Высокая (много запросов) | Низкая (только при появлении сообщений) |

**Нюансы:**
- Pull всегда даёт consumer'у контроль над скоростью обработки.
- Push может перегрузить consumer'ов, если они не успевают обрабатывать сообщения быстро.
- Комбинация: можно использовать pull с manual_ack для контроля скорости и гарантии доставки.

🛠 **Пример из интернет-магазина**

> **Сценарий 1: Pull — обработка заказов в фоне**
> ```
> [Сервис заказов] → [Очередь order.processed]
>                    ↓
>            [Consumer запрашивает каждые 5 сек]
>                    ↓
>            [Обрабатывает заказы по одному]
> ```
> Consumer запрашивает сообщения каждые 5 секунд и обрабатывает их по одному. Контролирует скорость обработки, не перегружается.

> **Сценарий 2: Push — уведомления о статусе заказа**
> ```
> [Сервис заказов] → [Очередь order.status]
>                    ↓
>            [RabbitMQ сам отправляет клиенту при изменении статуса]
> ```
> Когда статус заказа меняется, RabbitMQ сразу отправляет уведомление клиенту. Клиент не должен запрашивать — ему просто приходит push-уведомление.

⚖️ **Плюсы/минусы**

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Pull: полный контроль над скоростью потребления | Pull: требует реализации retry и acknowledgement |
| Pull: не перегружается пассивными сообщениями | Pull: есть задержка между появлением и получением |
| Push: мгновенная доставка при появлении сообщений | Push: может перегрузить consumer'ов |
| Push: не требует реализации polling | Push: consumer не контролирует скорость обработки |

🎯 **Что важно запомнить аналитику**

> 1. **Pull = consumer сам запрашивает** → контроль скорости, но больше запросов к брокеру
> 2. **Push = broker сам отдаёт** → мгновенная доставка, но риск перегрузки consumer'а
> 3. **Kafka всегда pull**, RabbitMQ может быть push или pull

❓ **Типичные вопросы и ответы**

1. **Вопрос:** Чем pull отличается от push?
   → **Ответ:** Pull — consumer сам запрашивает сообщения у брокера. Push — брокёр сам отдаёт сообщения consumer'у без запроса.

2. **Вопрос:** Когда использовать pull, а когда push?
   → **Ответ:** Pull — когда нужно контролировать скорость обработки (например, фоновая обработка заказов). Push — когда нужна мгновенная доставка и не важно, как быстро consumer обрабатывает (например, уведомления в реальном времени).

3. **Вопрос:** Почему Kafka всегда использует pull-модель?
   → **Ответ:** Потому что Kafka топик — это просто набор партиций с сообщениями. Consumer сам запрашивает новые сообщения у брокера, когда готов их обработать. Это даёт полный контроль над скоростью потребления и предотвращает перегрузку consumer'ов.

🛠 **Практические вопросы для собеседования**

1. **Вопрос:** Consumer не успевает обрабатывать сообщения быстро, очередь переполняется. Как это исправить?
   → **Ответ:** Переключиться на pull-модель с ограниченным prefetch (consumer сам запрашивает по N сообщений за раз). Или добавить больше consumer'ов для параллельной обработки.

2. **Вопрос:** Нужно гарантировать доставку даже если consumer упал. Как сделать?
   → **Ответ:** Использовать acknowledgement (подтверждение доставки). Consumer подтверждает обработку после успешного выполнения. Если подтверждения нет — брокёр вернёт сообщение в очередь для повторной попытки.

3. **Вопрос:** Почему push может перегрузить consumer'ов?
   → **Ответ:** Потому что broker отдаст все сообщения сразу, даже если consumer не готов их обрабатывать. Это может привести к падению consumer'а из-за высокой нагрузки.

4. **Вопрос:** Как реализовать retry при сбоях в pull-модели?
   → **Ответ:** Consumer должен сохранять состояние обработки (например, в БД) и при сбое перезапускаться с последней точки. Также можно использовать exponential backoff — увеличивать время между попытками при повторных сбоях.

5. **Вопрос:** Когда использовать веб-хуки вместо pull/push?
   → **Ответ:** Когда нужно уведомить внешний сервис о событии (например, о новом заказе). Веб-хук — это push-уведомление от вашего сервиса к внешнему API.

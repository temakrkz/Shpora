# 4.14 Когда какой брокер использовать

_Брокеры сообщений — Kafka и RabbitMQ. Эта тема про выбор между Kafka и RabbitMQ._

📌 **Короткий ответ**

Выбор зависит от задачи: **Kafka** — для событийной архитектуры, логирования, аналитики (высокая нагрузка, много consumer'ов). **RabbitMQ** — для точечных задач, очередей, маршрутизации (мало consumer'ов, нужна сложная маршрутизация).

💡 **Простыми словами**

Представьте два типа курьерских служб:
- **Kafka**: как почтовое отделение с огромным сортировочным цехом. Одна посылка может быть доставлена десяткам адресатов одновременно (рассылка), и всё сохраняется на долгие годы для анализа.
- **RabbitMQ**: как курьер, который привозит посылку конкретному человеку. Если человек не дома — посылка возвращается в отделение до следующего раза.

🔍 **Подробно**

> **Apache Kafka**
> - Что это: распределённая система сообщений с топиками и партициями для событийной архитектуры
> - Зачем нужна: высокая нагрузка, много consumer'ов на одно событие, логирование, аналитика в реальном времени
> - Как работает: producer → топик (с партициями) → N consumer'ов получают копию сообщения

**Когда использовать Kafka:**
- Высокая пропускная способность (миллионы сообщений в секунду)
- Много consumer'ов на одно событие (один заказ → БД + аналитика + уведомления + индексация)
- Нужно сохранять историю событий на долгие сроки (логирование, аудит)
- Event-driven архитектура с хореографией сервисов

**Когда НЕ использовать Kafka:**
- Нужна сложная маршрутизация (routing rules)
- Нужно гарантировать порядок между разными consumer'ами
- Мало сообщений в секунду (overkill)

> **RabbitMQ**
> - Что это: брокер сообщений с очередями, exchange и binding для точечных задач
> - Зачем нужна: сложная маршрутизация, очереди с TTL, dead letter queues, подтверждение доставки
> - Как работает: producer → exchange → binding → очередь → один consumer на сообщение

**Когда использовать RabbitMQ:**
- Сложная маршрутизация (routing rules) через типы exchange (direct, fanout, topic, header)
- Очереди с TTL и dead letter queues для отложенной обработки
- Гарантированная доставка с acknowledgement
- Мало consumer'ов на сообщение (один consumer на одно сообщение — очередь)

**Когда НЕ использовать RabbitMQ:**
- Очень высокая нагрузка (миллионы сообщений в секунду)
- Нужно, чтобы один event обрабатывался несколькими сервисами одновременно (топик Kafka лучше)
- Нужна горизонтальная масштабируемость без потери порядка

**Новые понятия:**

> **Exchange (обменник)** — компонент RabbitMQ для маршрутизации сообщений к очередям. Типы: direct, fanout, topic, header.
>
> > **Binding (связь)** — правило связи между exchange и очередью. Определяет, какие сообщения попадают в какую очередь.
>
> > **Prefetch limit** — максимальное количество неопределённых сообщений у consumer'а. Контролирует нагрузку на consumer'а при pull-модели.

**Где используется:**
- **Kafka**: логирование, аналитика в реальном времени, event-driven архитектура с хореографией
- **RabbitMQ**: очереди задач, сложная маршрутизация, dead letter queues, подтверждение доставки

**Особенности:**

| Характеристика | Kafka | RabbitMQ |
|----------------|-------|----------|
| Пропускная способность | Очень высокая (миллионы msg/sec) | Средняя (тысячи msg/sec) |
| Количество consumer'ов на событие | Много (топик рассылает всем) | Один (очередь хранит для одного) |
| Маршрутизация | Простая (только по topic name) | Сложная (через exchange и binding rules) |
| Гарантии доставки | At-least-once, exactly-once с настройками | At-least-once, exactly-once с acknowledgement |
| Сохранение истории | Долгосрочное (месяцы/годы) | Краткосрочное (дни/недели без настройки) |

**Нюансы:**
- Kafka платит за простоту маршрутизации сложностью масштабирования.
- RabbitMQ платит за гибкость маршрутизации меньшим масштабом.
- Можно комбинировать: Kafka для событийной архитектуры + RabbitMQ для очередей задач.

🛠 **Пример из интернет-магазина**

> **Сценарий 1: Kafka — события системы (event-driven)**
> ```
> [Сервис заказов] → [Топик order.events]
>                    ↓       ↓       ↓
>            [Сервис БД] [Аналитика] [Уведомления]
> ```
> Клиент сделал заказ → событие в Kafka топик → три сервиса получают копию и обрабатывают независимо. Высокая нагрузка, много consumer'ов.

> **Сценарий 2: RabbitMQ — очередь задач (очередь)**
> ```
> [Сервис заказов] → [Exchange order.tasks]
>                    ↓
>            [Binding rule: priority=high]
>                    ↓
>            [Очередь high_priority_orders]
>                    ↓
>            [Worker обрабатывает заказы по одному]
> ```
> Клиент сделал заказ → сообщение в очередь с высоким приоритетом → worker забирает и обрабатывает один за другим. Сложная маршрутизация, одна задача на consumer'а.

⚖️ **Плюсы/минусы**

| Плюсы ✅ | Минусы ❌ |
|----------|----------|
| Kafka: высокая пропускная способность | Kafka: сложная настройка и масштабирование |
| Kafka: много consumer'ов на событие | Kafka: простая маршрутизация (только по topic name) |
| RabbitMQ: сложная маршрутизация через exchange | RabbitMQ: меньшая пропускная способность |
| RabbitMQ: очереди с TTL и DLQ | RabbitMQ: один consumer на сообщение (нужны дубли для параллельной обработки) |

🎯 **Что важно запомнить аналитику**

> 1. **Kafka = события системы, логирование, аналитика** → много consumer'ов, высокая нагрузка
> 2. **RabbitMQ = очереди задач, сложная маршрутизация** → один consumer на сообщение, гибкие правила routing
> 3. Можно комбинировать: Kafka для событий + RabbitMQ для очередей

❓ **Типичные вопросы и ответы**

1. **Вопрос:** Когда использовать Kafka вместо RabbitMQ?
   → **Ответ:** Когда нужна высокая нагрузка (миллионы сообщений в секунду), много consumer'ов на одно событие, логирование или аналитика в реальном времени.

2. **Вопрос:** Когда использовать RabbitMQ вместо Kafka?
   → **Ответ:** Когда нужна сложная маршрутизация через exchange и binding rules, очереди с TTL и dead letter queues, подтверждение доставки для точечных задач.

3. **Вопрос:** Можно ли комбинировать Kafka и RabbitMQ?
   → **Ответ:** Да! Kafka для событийной архитектуры (один event → несколько сервисов), RabbitMQ для очередей задач (одна задача → один worker).

🛠 **Практические вопросы для собеседования**

1. **Вопрос:** Нужно сохранить историю всех заказов на 5 лет и анализировать в реальном времени. Какой брокер выбрать?
   → **Ответ:** Kafka. Он предназначен для логирования и аналитики, может хранить данные годами и обрабатывать миллионы событий в секунду.

2. **Вопрос:** Нужно обработать заказы с высоким приоритетом перед обычными. Какой брокер лучше?
   → **Ответ:** RabbitMQ. Можно создать очередь с приоритетом или использовать exchange с routing rules для разделения на high_priority и regular очереди.

3. **Вопрос:** Один заказ должен обновить БД, отправить email, создать индекс в Elasticsearch. Какой подход выбрать?
   → **Ответ:** Kafka топик. Один producer отправляет событие в топик, и три сервиса-подписчика получают копию и обрабатывают независимо друг от друга.

4. **Вопрос:** Нужно гарантировать доставку даже если consumer упал. Как сделать?
   → **Ответ:** Использовать acknowledgement (подтверждение доставки). Consumer подтверждает обработку после успешного выполнения. Если подтверждения нет — брокёр вернёт сообщение в очередь для повторной попытки.

5. **Вопрос:** Почему Kafka не подходит для очередей задач?
   → **Ответ:** Потому что Kafka топик рассылает копию сообщения всем consumer'ам одновременно, а очередь задач должна хранить сообщение для одного consumer'а до момента обработки. RabbitMQ лучше подходит для этого счёта.

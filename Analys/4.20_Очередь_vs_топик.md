# 4.20 Очередь vs топик: в чём разница и когда что применять

> 📌 **Короткий ответ**  
> **Очередь (Queue)** — сообщения должны быть обработаны ровно один раз, есть подтверждение от получателя перед удалением.  
> **Топик (Topic)** — сообщения публикуются для всех подписчиков сразу, повторная обработка не гарантируется.

---

## 💡 Простыми словами

Представьте два сценария доставки заказов в интернет-магазине:

### 📦 Очередь (Queue) — как курьерская служба
Клиент заказал товар → заказ попадает в очередь → курьер забирает его → курьер подтверждает доставку → система удаляет заказ из очереди.  
**Важно:** Если курьер не доставил, заказ остаётся в очереди и будет доставлен позже (или переназначен другому курьеру).

### 📢 Топик (Topic) — как новостная рассылка
Система публикует новость "Новый товар поступил!" → все подписчики получают уведомление сразу.  
**Важно:** Если один пользователь не прочитал, система не будет отправлять уведомление повторно.

---

## 🔍 Подробно

### Очередь (Queue)

**Что это:** Линейная структура данных, где сообщения передаются от одного производителя к одному или нескольким потребителям **последовательно**.

**Как работает:**
1. Producer добавляет сообщение в очередь
2. Consumer забирает сообщение и начинает обработку
3. Consumer подтверждает успешную обработку (acknowledgement)
4. Только после подтверждения сообщение удаляется из очереди
5. Если обработка не удалась — сообщение остаётся в очереди для повторной попытки

**Зачем нужно:** Гарантировать, что каждое сообщение будет обработано **ровно один раз**.

### Топик (Topic)

**Что это:** Распределённая структура данных, где сообщения публикуются и могут быть прочитаны множеством подписчиков **параллельно**.

**Как работает:**
1. Producer публикует сообщение в топик
2. Сообщение сразу доступно всем подписчикам
3. Каждый consumer читает сообщение независимо
4. Нет подтверждения удаления — сообщение остаётся до истечения срока хранения или переполнения

**Зачем нужно:** Рассылать события множеству потребителей без блокировки друг друга.

---

## 🛠 Пример из интернет-магазина

### Сценарий с очередью (Queue)
```
Заказ оформлен → Очередь заказов → Сервис обработки заказов → Подтверждение → Удаление из очереди
```

**Почему очередь:** Если сервис обработки упал, заказ не потеряется — он останется в очереди и будет обработан позже.

### Сценарий с топиком (Topic)
```
Заказ оформлен → Топик "Новые заказы" → Сервис уведомлений + Сервис аналитики + Сервис складской учёты
```

**Почему топик:** Все сервисы получают копию события независимо. Если один сервис упал, другие продолжат работать.

## ⚖️ Плюсы и минусы

### Очередь (Queue)

| ✅ Плюсы | ❌ Минусы |
|----------|-----------|
| Гарантированная доставка одного раза | Только один потребитель может обработать сообщение |
| Повторная обработка при сбоях | Блокировка, если consumer медленный |
| Контроль порядка обработки | Не подходит для широкой рассылки событий |

### Топик (Topic)

| ✅ Плюсы | ❌ Минусы |
|----------|-----------|
| Множество потребителей могут читать одно сообщение | Нет гарантии доставки одному получателю |
| Параллельная обработка без блокировки | Потеря сообщений при сбоях consumer'ов |
| Не зависит от состояния конкретных сервисов | Сложнее отслеживать, кто обработал что |

---

## 🎯 Что важно запомнить аналитику

1. **Выбирайте очередь**, когда важна гарантия обработки каждого события один раз (заказы, платежи, важные уведомления)
2. **Выбирайте топик**, когда нужно рассылать события множеству сервисов без блокировки (аналитика, логирование, кэширование)
3. **Очередь** — это "точка-к-одной или нескольким", **топик** — это "многие ко многим"

## ❓ Типичные вопросы и ответы

### Вопрос: В чём главное отличие очереди от топика?  
**Ответ:** Главное отличие в гарантии доставки. Очередь гарантирует, что сообщение будет обработано ровно один раз (consumer подтверждает получение). Топик не гарантирует доставку конкретному получателю — он просто публикует событие для всех подписчиков.

### Вопрос: Когда использовать очередь, а когда топик?  
**Ответ:** Используйте очередь для критических операций, где потеря данных недопустима (заказы, платежи, обновления профиля). Используйте топик для событийной рассылки, где важно, чтобы несколько сервисов получали информацию параллельно (аналитика, уведомления, логирование).

### Вопрос: Может ли одно сообщение прочитать несколько потребителей в очереди?  
**Ответ:** Нет. В очереди сообщение может быть обработано только одним потребителем до тех пор, пока оно не будет подтверждено удалением или истечёт срок хранения.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Вам нужно реализовать обработку платежей. Какой подход выбрать и почему?  
**Ответ →** Очередь (Queue). Платежи — критически важная операция, где потеря данных недопустима. Если сервис обработки упал, платеж должен остаться в очереди до тех пор, пока не будет обработан успешно.

### Вопрос 2: Нужно уведомить о новом заказе несколько служб (уведомления, аналитика, склад). Что выбрать?  
**Ответ →** Топик (Topic). Все службы должны получить копию события независимо друг от друга. Если одна служба упала, другие продолжат работать.

### Вопрос 3: Как проверить, что очередь работает корректно?  
**Ответ →** Нужно отслеживать метрики: количество сообщений в очереди, время обработки, процент подтверждённых сообщений. Также важно проверять, что сообщения не теряются при сбоях и не обрабатываются дважды.

### Вопрос 4: Что будет, если consumer в очереди упал во время обработки?  
**Ответ →** Сообщение останется в очереди (не будет подтверждено) и будет перенаправлено другому consumer'у или обработано повторно после перезапуска сервиса. Это гарантирует, что сообщение не потеряется.

### Вопрос 5: Как реализовать повторную попытку обработки сообщения?  
**Ответ →** Можно использовать механизм dead-letter queue (DLQ) — очередь для сообщений, которые не удалось обработать после нескольких попыток. Также можно настроить автоматическую повторную отправку с задержкой между попытками.

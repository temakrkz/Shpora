# 4.22 Партиции в Kafka: параллельно или последовательно

> 📌 **Короткий ответ**  
> **Партиция (partition)** — это физическая часть топика, на которую он разбивается для распределения нагрузки. Сообщения внутри одной партиции идут **последовательно**, а разные партиции могут обрабатываться **параллельно**.

---

## 💡 Простыми словами

Представьте, что интернет-магазин получает тысячи заказов в день:

### 📦 Одна партиция — как один конвейер
Все заказы идут по одному конвейеру → каждый работник забирает заказы строго по порядку.  
**Плюс:** Гарантируется порядок обработки.  
**Минус:** Если один конвейер медленный, все остальные ждут.

### 📦 Несколько партиций — как несколько конвейеров
Заказы распределяются между 10 конвейерами → каждый работник забирает заказы только со своего конвейера.  
**Плюс:** Все работники работают параллельно, быстро обрабатывают много заказов.  
**Минус:** Нельзя гарантировать порядок между заказами разных конвейеров (только внутри одного).

---

## 🔍 Подробно

### Что такое партиция?

**Партиция** — это физическая единица хранения и обработки сообщений в Kafka топике. Каждый топик состоит из одной или нескольких партиций.

### Как работают партиции

#### Последовательность внутри партиции
```
Партиция #1:
Сообщение 1 (timestamp=10:00) → обработано
Сообщение 2 (timestamp=10:05) → обработано
Сообщение 3 (timestamp=10:10) → обработано

Внутри одной партиции сообщения идут строго по порядку!
```

#### Параллельность между партициями
```
Топик "orders" состоит из 5 партиций:

Партиция #1: Заказы на электронику (обработка параллельно)
Партиция #2: Заказы на одежду (обработка параллельно)
Партиция #3: Заказы на книги (обработка параллельно)
Партиция #4: Заказы на спорттовары (обработка параллельно)
Партиция #5: Заказы на товары для дома (обработка параллельно)

Каждая партиция обрабатывается независимо от других!
```

### Как распределяются сообщения по партициям?

Kafka использует **partitioning key** — ключ, по которому определяется, в какую партицию попадёт сообщение:

```
Правило: одинаковые partitioning key → одна и та же партиция
Разные partitioning key → разные партиции (возможно)
```

**Пример с заказами:**
```
Partition Key = ID клиента

Заказ от Клиента #100 → Партиция, где хранятся данные Клиента #100
Заказ от Клиента #100 → Та же партиция (гарантия порядка!)
Заказ от Клиента #200 → Другая партиция (если ключи разные)
```

## 🛠 Пример из интернет-магазина

### Сценарий 1: Обработка заказов по клиентам

**Настройка:**
```
Partition Key = ID клиента
Количество партиций = 10
```

**Как работает:**
```
Клиент #100 делает заказ → Партиция #3 (где хранятся данные Клиента #100)
Клиент #100 делает ещё заказ → Та же Партиция #3 (гарантия порядка!)
Клиент #200 делает заказ → Партиция #7 (другой клиент, другая партиция)

Результат:
- Внутри заказа одного клиента порядок гарантирован ✅
- Разные клиенты обрабатываются параллельно ✅
```

### Сценарий 2: Обработка заказов по категориям

**Настройка:**
```
Partition Key = Категория товара (electronics, clothing, books...)
Количество партиций = 5
```

**Как работает:**
```
Заказ на телефон → Партиция "electronics"
Заказ на футболку → Партиция "clothing"
Заказ на книгу → Партиция "books"

Результат:
- Все заказы электроники идут в одну партицию ✅
- Разные категории обрабатываются параллельно ✅
```

### Сценарий 3: Без partitioning key (round-robin)

**Настройка:**
```
Partition Key = null или пустой
Количество партиций = 10
```

**Как работает:**
```
Сообщение #1 → Партиция #1
Сообщение #2 → Партиция #2
...
Сообщение #10 → Партиция #10
Сообщение #11 → Партиция #1 (круговое распределение)

Результат:
- Сообщения распределяются равномерно ✅
- Но порядок между сообщениями НЕ гарантирован ❌
```

## ⚖️ Плюсы и минусы

### Параллельная обработка (несколько партиций)

| ✅ Плюсы | ❌ Минусы |
|----------|-----------|
| Высокая производительность | Порядок сообщений между партициями не гарантируется |
| Масштабируемость | Сложнее отлаживать распределение по партициям |
| Отказоустойчивость (если одна партиция падает, другие работают) | Риск неравномерной нагрузки при плохом выборе ключа |

### Последовательная обработка (одна партиция)

| ✅ Плюсы | ❌ Минусы |
|----------|-----------|
| Гарантированный порядок всех сообщений | Ограниченная производительность |
| Простота отладки и мониторинга | Нет возможности горизонтального масштабирования |
| Предсказуемость обработки | Риск бутылочного горлышка при высокой нагрузке |

---

## 🎯 Что важно запомнить аналитику

1. **Партиции — это баланс между порядком и производительностью:**
   - Больше партиций = выше параллелизм, но сложнее гарантировать порядок
   - Меньше партиций = проще контролировать порядок, но ниже производительность

2. **Partitioning key критически важен:**
   - Хороший ключ обеспечивает равномерное распределение нагрузки
   - Плохой ключ может привести к неравномерной нагрузке (hot partition)

3. **Порядок гарантируется только внутри одной партиции:**
   - Если важно, чтобы все события шли в порядке — используйте одну партицию или один partitioning key для всех событий
   - Если порядок между разными потоками не важен — можно использовать несколько партиций

4. **Количество партиций фиксировано после создания топика:**
   - Увеличить количество партиций можно только при создании нового топика или увеличении существующего (необратимо)
   - Планируйте количество партиций заранее, исходя из ожидаемой нагрузки!

## ❓ Типичные вопросы и ответы

### Вопрос: Почему Kafka использует партиции?  
**Ответ →** Для горизонтального масштабирования. Одна партиция может быть обработана одним consumer'ом, поэтому чем больше партиций — тем больше consumer'ов можно запустить для параллельной обработки.

### Вопрос: Гарантируется ли порядок сообщений между разными партициями?  
**Ответ →** Нет. Порядок гарантируется только внутри одной партиции. Сообщения из разных партиций могут обрабатываться в любом порядке относительно друг друга.

### Вопрос: Как выбрать partitioning key?  
**Ответ →** Ключ должен обеспечивать равномерное распределение нагрузки по партициям. Хорошие примеры: ID пользователя, ID заказа, уникальный идентификатор события. Плохой пример: timestamp (все сообщения одного времени попадут в одну партицию).

### Вопрос: Что будет, если выбрать плохой partitioning key?  
**Ответ →** Может возникнуть "горячая" партиция — одна партиция получает непропорционально много сообщений и становится узким местом системы.

### Вопрос: Можно ли изменить количество партиций после создания топика?  
**Ответ →** Количество партиций можно увеличить (добавить новые), но уменьшить нельзя. Поэтому важно правильно рассчитать нужное количество при создании топика.

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Как обеспечить порядок обработки всех заказов в системе?  
**Ответ →** Использовать одну партицию или один partitioning key (например, ID магазина) для всех заказов. Это гарантирует, что все заказы будут обрабатываться последовательно внутри каждой группы по ключу.

### Вопрос 2: Сколько партиций нужно создать для топика с ожидаемой нагрузкой 10K сообщений в секунду?  
**Ответ →** Зависит от мощности consumer'ов. Если один consumer может обработать 1K сообщений/сек, то нужно минимум 10 партиций (чтобы запустить 10 consumer'ов параллельно). Лучше добавить запас — 12-15 партиций для будущего роста.

### Вопрос 3: Как избежать неравномерной нагрузки при выборе partitioning key?  
**Ответ →** Использовать хорошо распределённый ключ (например, hash от ID пользователя) и проверять метрики распределения после запуска системы. Регулярно мониторить нагрузку на партиции.

### Вопрос 4: Что такое "горячая" партиция и как её избежать?  
**Ответ →** Горячая партиция — это партиция с непропорционально высокой нагрузкой. Избежать можно правильным выбором partitioning key (например, не использовать timestamp) и мониторингом распределения нагрузки.

### Вопрос 5: Как проверить, что партиции работают корректно?  
**Ответ →** Нужно мониторить: количество сообщений в каждой партиции, время обработки, метрики latency. Также важно проверять равномерность распределения по партициям — если одна партиция получает значительно больше сообщений, значит partitioning key выбран неправильно.

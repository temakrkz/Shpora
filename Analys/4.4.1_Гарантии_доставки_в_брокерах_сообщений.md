# 4.4.1 Гарантии доставки в брокерах сообщений

> **Короткий ответ**  
> Гарантии доставки — это уровни надёжности передачи сообщений от отправителя к получателю:  
> - **At-most-once** — сообщение может потеряться (быстрее всего)  
> - **At-least-once** — сообщение гарантированно дойдёт, но может дублироваться  
> - **Exactly-once** — сообщение дойдёт ровно один раз (самое надёжно, сложнее реализовать)

---

## 💡 Простыми словами

Представьте курьера, который доставляет посылки:
- **At-most-once** — курьер бросает посылку в почтовый ящик. Может упасть и потеряться. Но быстро!
- **At-least-once** — курьер звонит получателю, чтобы убедиться, что посылка получена. Если не получил — приедет снова (может быть дубликат).
- **Exactly-once** — курьер доставляет, получает подпись, подтверждает отправителю. Гарантированно один раз.

---

## 🔍 Подробно

### At-most-once (не более одного раза)

**Как работает:**  
Сообщение отправляется и всё. Если что-то пошло не так — потеряется. Нет подтверждения доставки.

**Механизм:**
```
Отправитель → [отправка] → Получатель
              ↓
          Если упало сообщение → теряется навсегда
```

**Когда используется:**
- Когда скорость важнее надёжности
- Когда данные можно потерять без проблем
- Для метрик, логирования, статистики

**Примеры в разных брокерах:**

**Kafka:**
- `acks=0` — не ждёт подтверждения от брокера
- Сообщения могут потеряться при сбое сети

**RabbitMQ:**
- Без подтверждений (manual ack disabled)
- Сообщения доставляются и всё

### At-least-once (хотя бы один раз)

**Как работает:**  
Сообщение гарантированно дойдёт, но может прийти несколько раз. Брокёр требует подтверждения от получателя.

**Механизм:**
```
Отправитель → [отправка] → Брокёр → [доставка] → Получатель
                                              ↓
                                        Подтверждение?
                                          ↓ Нет
                                      Повторная доставка
```

**Когда используется:**
- Когда данные важнее скорости
- Когда можно обработать дубликаты (идемпотентность)
- Для уведомлений, событийных систем

**Примеры в разных брокерах:**

**Kafka:**
- `acks=1` или `acks=all` — ждёт подтверждения от брокера/реплик
- Consumer подтверждает обработку после успешной обработки

**RabbitMQ:**
- Manual ack — потребитель сам подтверждает получение
- Если consumer упал → сообщение возвращается в очередь для повторной доставки

### Exactly-once (ровно один раз)

**Как работает:**  
Сообщение доходит ровно один раз — ни больше, ни меньше. Требует сложной координации и идемпотентности.

**Механизм (упрощённо):**
```
1. Отправитель транзакционно записывает данные + событие
2. Брокёр подтверждает запись события
3. Только после подтверждения — транзакция с данными завершается
4. Получатель проверяет идемпотентность по уникальному ID
5. Если уже обработали → игнорируем дубликат
```

**Когда используется:**
- Когда критична точность данных
- Финансовые операции, счётные системы
- Медицинские записи, юридические документы

## 🛠 Пример из интернет-магазина

### Сценарий: Обработка событий заказов

#### At-most-once (быстро, но рискованно):

```
Система отправляет событие "Заказ создан" в Kafka:
├─ acks=0 (не ждёт подтверждения)
└─ Если Kafka упала → событие потеряется

Последствия:
- Уведомления не уйдут
- Аналитика неполная
- Но заказ уже создан, можно пересчитать метрики
```

**Когда ок:** Отправка аналитики в BI-систему (можно пересчитать из сырых данных)

#### At-least-once (надёжно, с дубликатами):

```
Система отправляет событие "Заказ создан" в Kafka:
├─ acks=all (ждёт подтверждения от всех реплик)
└─ Consumer подтверждает после успешной обработки

Проблема:
- Consumer упал во время отправки email
- Kafka доставила сообщение снова
- Email отправлен дважды! ❌

Решение — идемпотентность:
1. Проверяем, не был ли уже отправлен email для этого order_id
2. Если нет → отправляем
3. Если да → игнорируем дубликат ✅
```

**Когда ок:** Отправка уведомлений о заказах (с идемпотентностью)

#### Exactly-once (максимально надёжно):

```
Система списывает деньги с карты пользователя:
├─ Транзакция в БД + запись события атомарно
└─ Получатель проверяет идемпотентность по order_id

Гарантии:
- Деньги спишутся ровно один раз (не 2000₽ вместо 1000₽)
- Списание не потеряется (не 0₽ вместо 1000₽)
```

**Когда ок:** Финансовые операции, обновление баланса пользователя

## ⚖️ Плюсы/минусы каждого уровня

### At-most-once

**✅ Плюсы:**
- Максимальная скорость
- Минимум ресурсов (нет подтверждений)
- Простая реализация

**❌ Минусы:**
- Данные могут потеряться
- Не подходит для важных операций
- Требует дублирования данных в источнике

### At-least-once

**✅ Плюсы:**
- Данные не теряются
- Можно восстановить упавшие сообщения через retry
- Стандартное поведение большинства систем

**❌ Минусы:**
- Возможны дубликаты → нужна идемпотентность
- Больше ресурсов (подтверждения, retry)
- Сложнее отладка (нужно мониторить дубликаты)

### Exactly-once

**✅ Плюсы:**
- Полная гарантия точности данных
- Идеально для финансовых операций
- Нет дубликатов и потерь

**❌ Минусы:**
- Сложная реализация (транзакции, идемпотентность)
- Медленнее других уровней
- Не все брокеры поддерживают полноценно

---

## 🎯 Что важно запомнить аналитику

1. **At-most-once** — скорость важнее надёжности (метрики, логирование)
2. **At-least-once** — данные важнее скорости (уведомления, события), нужна идемпотентность
3. **Exactly-once** — критичная точность (финансы, счёты), сложная реализация
4. **В большинстве e-commerce систем используется at-least-once + идемпотентность**

## ❓ Типичные вопросы и ответы

### Вопрос: В чём разница между at-least-once и exactly-once?
→ **Ответ:**  
At-least-once гарантирует, что сообщение дойдёт хотя бы один раз, но может прийти несколько раз (дубликаты). Exactly-once гарантирует доставку ровно один раз — ни больше, ни меньше.

### Вопрос: Как реализовать идемпотентность для at-least-once?
→ **Ответ:**  
1. При обработке сообщения проверяем уникальный ID события (order_id, message_id)
2. Если уже обрабатывали это событие → игнорируем или обновляем
3. Храним обработанные ID в Redis или БД

### Вопрос: Почему exactly-once сложно реализовать?
→ **Ответ:**  
Потому что нужно гарантировать атомарность на нескольких уровнях: запись в БД, отправка сообщения брокеру, обработка получателем. Любая ошибка на любом этапе может привести к дубликатам или потерям.

### Вопрос: Когда использовать at-most-once?
→ **Ответ:**  
Когда данные можно потерять без проблем и скорость критична. Например, логирование метрик мониторинга, которые легко пересчитать из сырых данных.

## 🛠 Практические вопросы для собеседования

**Вопрос 1: Как гарантировать exactly-once в Kafka?**
→ **Ответ:**  
Использовать транзакции producer'а и идемпотентность consumer'а:
- Producer записывает данные и событие атомарно (enable.idempotence=true)
- Consumer проверяет уникальные ID событий перед обработкой
- При дубликате — игнорируем или обновляем

**Вопрос 2: Что будет, если использовать at-least-once без идемпотентности?**
→ **Ответ:**  
Получим дубликаты данных. Например, обработка события "создать заказ" дважды создаст два заказа вместо одного. Это критично для финансовых операций.

**Вопрос 3: Как проверить, что система работает at-least-once?**
→ **Ответ:**  
1. Отправить тестовое сообщение несколько раз
2. Проверить, что оно обработано хотя бы один раз
3. Проверить, нет ли дубликатов (для exactly-once)

**Вопрос 4: Почему в e-commerce чаще используют at-least-once вместо exactly-once?**
→ **Ответ:**  
Потому что at-least-once проще реализовать и достаточно надёжно при правильной идемпотентности. Exactly-once слишком сложен для большинства сценариев (кроме финансовых транзакций).

**Вопрос 5: Как обработать дубликат сообщения в at-least-once?**
→ **Ответ:**  
1. Использовать уникальный ID события (order_id, message_id)
2. Перед обработкой проверять, не было ли уже сообщение с таким ID
3. Если было — игнорировать или обновлять данные (в зависимости от бизнес-логики)

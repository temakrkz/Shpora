# 4.5. Паттерны Transactional Inbox / Outbox

> **Короткий ответ**  
> Это паттерны для гарантии доставки сообщений вместе с транзакцией данных:  
> - **Inbox** — сообщение сохраняется в отдельной таблице *после* основной транзакции  
> - **Outbox** — сообщение сохраняется в отдельной таблице *вместе* с основной транзакцией (в одной транзакции)

---

## 💡 Простыми словами

Представьте, что вы делаете заказ в интернет-магазине:
1. Заказ создаётся в базе данных
2. Должна отправиться уведомление о заказе в систему уведомлений

**Проблема:** Если база данных успешно создала заказ, но система уведомлений не получила сообщение — у нас разрыв! Заказ есть, а уведомления нет.

**Решение Outbox:**  
Сохраняем и заказ, и сообщение в одну транзакцию. Либо оба сохранятся, либо ни один. Гарантируем целостность.

**Решение Inbox:**  
Сначала сохраняем заказ. Затем в отдельной транзакции пытаемся сохранить сообщение. Если не получилось — пробуем снова позже (retry).

---

## 🔍 Подробно

### Что такое Outbox Pattern?

**Outbox** — это таблица, где хранятся все сообщения, которые должны быть отправлены брокеру сообщений.

**Как работает:**
1. При создании заказа мы делаем **одну транзакцию**:
   - Вставляем запись в таблицу заказов
   - Вставляем сообщение в таблицу outbox
2. Отдельный процесс (consumer) читает из таблицы outbox и отправляет сообщения брокеру
3. Когда сообщение успешно отправлено — удаляем его из outbox

**Почему это надёжно:**  
Транзакция атомарна. Либо заказ создан + сообщение записано, либо ничего не произошло.

### Что такое Inbox Pattern?

**Inbox** — это таблица, где мы *ждем* сообщения от брокера (или сохраняем их для повторной обработки).

**Как работает:**
1. Создаём заказ в базе данных
2. Отправляем сообщение брокеру (не ждём подтверждения)
3. Брокёр доставляет сообщение сервису уведомлений
4. Сервис уведомлений сохраняет сообщение в inbox и обрабатывает его
5. При ошибках — сообщение остаётся в inbox для повторной обработки

**Почему это надёжно:**  
Сообщение не теряется даже если обработка упала — оно ждёт в inbox.

## 🛠 Пример из интернет-магазина

### Сценарий: Создание заказа с отправкой уведомления

#### Outbox подход:

```
Транзакция 1 (ордер-сервис):
├─ Вставляем заказ в таблицу orders
└─ Вставляем сообщение {"order_id": 123, "event": "OrderCreated"} в таблицу outbox

Фондовый процесс (consumer):
├─ Читает из таблицы outbox
├─ Отправляет сообщение Kafka/RabbitMQ
└─ Удаляет сообщение из outbox (если успешно)
```

**Что происходит:**
- Пользователь нажал "Оформить заказ"
- Система в одной транзакции создала заказ и записала событие в outbox
- Отдельный процесс через 10 секунд прочитал из outbox и отправил уведомление в Kafka
- Если отправка в Kafka упала — сообщение остаётся в outbox и будет переслано позже

#### Inbox подход:

```
Транзакция 1 (ордер-сервис):
├─ Вставляем заказ в таблицу orders
└─ Отправляем сообщение брокеру (не ждём подтверждения)

Брокёр доставляет сообщение:
├─ Сервис уведомлений получает событие
├─ Сохраняет {"order_id": 123, "event": "OrderCreated"} в inbox таблицу notifications
└─ Обрабатывает уведомление (отправляет email/SMS)

Если обработка упала:
└─ Сообщение остаётся в inbox для повторной обработки
```

**Что происходит:**
- Пользователь нажал "Оформить заказ"
- Заказ создан, сообщение отправлено брокеру
- Брокёр доставил сообщение сервису уведомлений
- Сервис сохранил событие в inbox и начал отправка email
- Email не ушёл (ошибка SMTP), но событие осталось в inbox
- Через минуту сервис попробовал снова — на этот раз email ушёл

## ⚖️ Плюсы/минусы

### Outbox Pattern

**✅ Плюсы:**
- **Гарантия доставки** — сообщение не потеряется, если записано в outbox
- **Атомарность** — заказ и событие создаются одновременно или ничего
- **Простота реализации** — нужна только дополнительная таблица
- **Контроль порядка** — можно гарантировать порядок отправки

**❌ Минусы:**
- **Дополнительная таблица** — нужно хранить все события в outbox
- **Отдельный процесс** — нужен consumer для чтения из outbox
- **Задержка** — событие может не уйти сразу (зависит от consumer)
- **Ресурсы** — занимает место в БД до удаления

### Inbox Pattern

**✅ Плюсы:**
- **Гибкость** — можно обрабатывать сообщения асинхронно
- **Повторная обработка** — упавшие сообщения остаются для retry
- **Разделение ответственности** — сервис уведомлений сам управляет своими данными
- **Масштабируемость** — несколько потребителей могут читать из inbox

**❌ Минусы:**
- **Нет гарантии доставки от брокера** — если брокер не доставил, сообщение потеряется
- **Сложнее отслеживать** — нужно мониторить inbox на предмет "зависших" сообщений
- **Двойная транзакционность** — сначала заказ, потом попытка сохранить в inbox

---

## 🎯 Что важно запомнить аналитику

1. **Outbox гарантирует целостность** между данными и событиями в рамках одной транзакции
2. **Inbox даёт гибкость**, но требует доверия к брокеру сообщений
3. **Выбор зависит от требований:**
   - Если критично, чтобы событие не потерялось → Outbox
   - Если важна гибкость обработки → Inbox
4. **Оба подхода требуют отдельного процесса** для доставки/обработки сообщений

## ❓ Типичные вопросы и ответы

### Вопрос: В чём разница между Outbox и Inbox?
→ **Ответ:**  
Outbox — сообщение сохраняется *вместе* с данными в одной транзакции. Inbox — сообщение сохраняется *после* данных, часто с повторными попытками.

### Вопрос: Когда использовать Outbox?
→ **Ответ:**  
Когда критично, чтобы событие не потерялось и оно должно быть создано одновременно с данными (например, создание заказа + событие о создании).

### Вопрос: Когда использовать Inbox?
→ **Ответ:**  
Когда важна гибкость обработки, когда сервис сам управляет своими сообщениями и может делать повторные попытки при ошибках.

### Вопрос: Что если consumer outbox упал?
→ **Ответ:**  
Сообщение остаётся в таблице outbox и будет перепробовано позже (обычно есть retry-логика).

### Вопрос: Как избежать дублирования сообщений из outbox?
→ **Ответ:**  
Идемпотентность — при обработке события проверяем, не обработали ли мы уже это сообщение (например, по order_id).

## 🛠 Практические вопросы для собеседования

**Вопрос 1: Как гарантировать, что событие будет отправлено после создания заказа?**
→ **Ответ:**  
Используем Outbox Pattern. В одной транзакции создаём заказ и записываем сообщение в таблицу outbox. Отдельный consumer читает из outbox и отправляет брокеру.

**Вопрос 2: Что такое дедупликация событий?**
→ **Ответ:**  
Это проверка, не обработали ли мы уже это событие. Например, если два процесса прочитали одно сообщение из outbox — второй должен проигнорировать его (проверить по уникальному ID события).

**Вопрос 3: Как обрабатывать ошибки при отправке событий?**
→ **Ответ:**  
- Для Outbox: оставить сообщение в таблице и запускать consumer повторно (retry)
- Для Inbox: сохранить сообщение в inbox, обработать позже или удалить после успеха

**Вопрос 4: Что такое идемпотентность в контексте событий?**
→ **Ответ:**  
Идемпотентность — это свойство операции, которая при многократном выполнении даёт тот же результат. Например, обработка события "создать заказ" с тем же order_id дважды должна создать только один заказ.

**Вопрос 5: Почему Outbox лучше чем просто отправлять сообщение после транзакции?**
→ **Ответ:**  
Если отправить сообщение *после* транзакции — есть риск, что транзакция упадёт, а сообщение уйдёт. Outbox гарантирует, что либо оба сохранятся, либо ни один.

# 4.6. Partitioning key в Kafka

> **Короткий ответ**  
> Partitioning key — это поле сообщения, по которому Kafka определяет, в какую партицию записать сообщение. От этого зависит порядок доставки и балансировка нагрузки.

---

## 💡 Простыми словами

Представьте, что у вас есть почтовый отдел с несколькими сортировщиками (партиции).  
**Partitioning key** — это адрес на конверте, по которому сортировщик решает: в какую корзину положить письмо.

Если все письма с одним и тем же получателем идут в одну корзину — они придут в порядке написания.  
Но если письма разных получателей могут попасть в разные корзины — порядок между ними не гарантируется.

---

## 🔍 Подробно

### Что такое партиции в Kafka?

Kafka делит тему (topic) на несколько **партиций** для параллельной обработки:
- Каждая партиция — это отдельная очередь сообщений
- Сообщения внутри одной партиции идут **в порядке записи**
- Разные партиции могут обрабатываться разными потребителями одновременно

### Зачем нужен Partitioning key?

Kafka должна решить: в какую партицию записать новое сообщение. Есть два варианта:

#### 1. Без ключа (random partition)
Сообщение попадает в случайную партицию.  
**Проблема:** Все сообщения одного типа разбросаны по разным партициям → нарушается порядок.

#### 2. С Partitioning key
Kafka смотрит на значение ключа и отправляет все сообщения с одинаковым ключом в одну и ту же партицию.  
**Преимущество:** Порядок внутри группы сообщений сохраняется.

### Как работает хеширование?

```
Partition = Hash(Partitioning Key) % Number of Partitions
```

Пример: у нас 4 партиции (0, 1, 2, 3).
- Сообщение с key="user_1" → всегда в партицию 0
- Сообщение с key="user_2" → всегда в партицию 1
- Сообщение с key="order_5" → всегда в партицию 2

Все события для одного пользователя идут в одну партицию → порядок сохраняется.

## 🛠 Пример из интернет-магазина

### Сценарий: Отправка уведомлений о заказах

#### Без Partitioning key (проблема):

```
Тема: order_events (4 партиции)

Поток событий:
├─ Пользователь 1 делает заказ → случайная партиция
├─ Пользователь 2 делает заказ → другая партиция
└─ Пользователь 1 снова делает заказ → ещё одна партиция

Проблема:
- Все события пользователя 1 разбросаны по разным партициям
- Потребитель уведомлений получает их в случайном порядке
- Может прийти уведомление о втором заказе до первого!
```

#### С Partitioning key (решение):

```
Тема: order_events (4 партиции)
Partitioning key = user_id

Поток событий:
├─ Пользователь 1 заказ #100 → user_id=1 → партиция 0
├─ Пользователь 2 заказ #101 → user_id=2 → партиция 1
└─ Пользователь 1 заказ #102 → user_id=1 → партиция 0

Результат:
- Все события пользователя 1 в одной партиции (партиция 0)
- Уведомления приходят в правильном порядке для каждого пользователя
- Разные пользователи могут быть обработаны параллельно
```

### Другой пример: Обновление профиля

```
Тема: user_profile_updates
Partitioning key = user_id

События:
├─ {"user_id": 123, "event": "change_email", "old_email": "a@b.com"} → партиция X
├─ {"user_id": 123, "event": "update_phone", "phone": "+7900..."} → партиция X
└─ {"user_id": 456, "event": "change_email", "old_email": "c@d.com"} → партиция Y

Результат:
- Все изменения профиля пользователя 123 идут в одну партицию
- Профиль всегда актуален после всех изменений
```

## ⚖️ Плюсы/минусы

### ✅ Плюсы Partitioning key

**Гарантия порядка внутри группы:**
- Все события с одним ключом идут в одну партицию
- Потребитель видит их в правильном порядке

**Балансировка нагрузки:**
- Сообщения разных пользователей распределяются по разным партициям
- Несколько потребителей могут работать параллельно

**Эффективность:**
- Не нужно хранить историю всех событий для одного пользователя в одной партиции
- Можно масштабировать количество партиций

### ❌ Минусы Partitioning key

**Проблема с новым пользователем:**
- Если партиций мало, а пользователей много — одна партиция может быть перегружена
- Решение: динамически добавлять партиции или использовать балансировку

**Сложность при изменении количества партиций:**
- При увеличении партиций сообщения могут перераспределяться
- Нужно учитывать это в логике обработки

**Не подходит для агрегатов:**
- Если нужно суммировать данные по всем пользователям — нельзя просто прочитать одну партицию
- Нужно читать все партиции (медленнее)

---

## 🎯 Что важно запомнить аналитику

1. **Partitioning key определяет порядок доставки** — все события с одним ключом идут в одну партицию
2. **Без ключа порядок не гарантируется** — сообщения разбрасываются случайно
3. **Выбор ключа критичен:**
   - `user_id` → порядок событий по пользователю
   - `order_id` → порядок событий по заказу
   - Не использовать `timestamp` или случайные ID
4. **Количество партиций влияет на производительность** — больше партиций = больше параллелизма

## ❓ Типичные вопросы и ответы

### Вопрос: В чём разница между партицией и темой?
→ **Ответ:**  
Тема (topic) — это логическая коллекция сообщений. Партиция (partition) — физическое разделение темы на несколько частей для параллельной обработки. Одна тема может состоять из множества партиций.

### Вопрос: Почему порядок между разными партициями не гарантируется?
→ **Ответ:**  
Каждая партиция обрабатывается независимо другими потребителями. Kafka не синхронизирует порядок между партициями — это было бы слишком медленно и сложно.

### Вопрос: Какой Partitioning key выбрать для событий заказов?
→ **Ответ:**  
`order_id` или `user_id`. Если нужно, чтобы все события одного заказа шли вместе → order_id. Если важно обрабатывать заказы разных пользователей параллельно → user_id.

### Вопрос: Что если партиций мало и нагрузка высокая?
→ **Ответ:**  
Можно увеличить количество партиций в теме (если это позволяет конфигурация Kafka). Но нужно учитывать, что потребители должны уметь работать с большим количеством партиций.

### Вопрос: Можно ли изменить Partitioning key после записи сообщения?
→ **Ответ:**  
Нет. Как только сообщение записано в партицию, его нельзя переместить. Поэтому выбор ключа критичен на этапе производства события.

## 🛠 Практические вопросы для собеседования

**Вопрос 1: Почему важно выбирать правильный Partitioning key?**
→ **Ответ:**  
Потому что он определяет порядок доставки сообщений и балансировку нагрузки. Неправильный ключ может привести к нарушению порядка событий или неравномерной нагрузке на партиции.

**Вопрос 2: Что будет, если не указывать Partitioning key?**
→ **Ответ:**  
Сообщения будут разбрасываться по партициям случайно. Порядок внутри группы связанных событий не гарантируется — это может привести к ошибкам в бизнес-логике.

**Вопрос 3: Как обеспечить порядок событий для разных пользователей одновременно?**
→ **Ответ:**  
Использовать Partitioning key = user_id. Все события одного пользователя будут идти в одну партицию и обрабатываться в порядке записи, а разные пользователи могут быть обработаны параллельно разными потребителями.

**Вопрос 4: Что такое ребалансировка партиций?**
→ **Ответ:**  
Это процесс перераспределения сообщений между брокерами при изменении конфигурации (добавление/удаление брокеров или партиций). Может временно снизить производительность системы.

**Вопрос 5: Как избежать ситуации, когда одна партиция перегружена?**
→ **Ответ:**  
1. Использовать хороший Partitioning key для равномерного распределения
2. Динамически добавлять новые партиции при росте нагрузки
3. Рассмотреть горизонтальное масштабирование (добавление брокеров)

# 4.7. Из чего состоит сообщение в RabbitMQ

> **Короткий ответ**  
> Сообщение в RabbitMQ — это не просто текст, а структурированный объект с полями: тело сообщения, заголовки (headers), свойства (properties) и маршрутизация (routing). Всё это помогает брокеру правильно доставить сообщение нужному получателю.

---

## 💡 Простыми словами

Представьте, что вы отправляете письмо по почте:
- **Тело письма** — само содержание (текст, фото)
- **Обертка с адресом** — куда доставить
- **Отметки на конверте** — важность, тип документа, срок годности
- **Маршрутизатор** — сортировщик почты решает, в какой почтовый ящик положить письмо

RabbitMQ делает то же самое: сообщение + метаданные → брокер понимает, кому и как доставить.

---

## 🔍 Подробно

### Структура сообщения RabbitMQ

Сообщение состоит из 4 основных частей:

#### 1. Тело сообщения (Body)
**Что это:** Основная полезная нагрузка — данные, которые нужно передать.  
**Формат:** Обычно сериализованный JSON или AMQP-формат.  
**Пример:** `{"order_id": 123, "event": "OrderCreated"}`

#### 2. Заголовки (Headers)
**Что это:** Ключ-значение для бизнес-логики сообщения.  
**Для чего:** Фильтрация, маршрутизация, дополнительные данные.  
**Примеры:**
```json
{
  "order_type": "standard",
  "priority": "high",
  "source_system": "ecommerce_platform"
}
```

#### 3. Свойства (Properties) — метаданные RabbitMQ
**Что это:** Технические данные, которые добавляет сам брокер или отправитель.  
**Важные свойства:**
- `delivery_mode` — как долго хранить сообщение (transient/persistent)
- `message_id` — уникальный ID для дедупликации
- `correlation_id` — связывает связанные сообщения (для ответов)
- `reply_to` — куда отправить ответ
- `expiration` — время жизни сообщения

#### 4. Маршрутизация (Routing)
**Что это:** Правила, по которым брокер решает, к какой очереди доставить сообщение.  
**Состоит из:**
- **Exchange** — центральный хаб для маршрутизации
- **Binding key** — паттерн, связывающий exchange с очередью

## 🛠 Пример из интернет-магазина

### Сценарий: Создание заказа с уведомлением

#### Отправка сообщения (Producer):

```
Тело сообщения (Body):
{
  "order_id": 12345,
  "customer_email": "user@example.com",
  "total_amount": 99.99,
  "items_count": 3
}

Заголовки (Headers):
{
  "event_type": "OrderCreated",
  "version": "1.0",
  "priority": "normal"
}

Свойства (Properties):
- delivery_mode: persistent (сохранить на диск)
- message_id: uuid-generated
- correlation_id: order-12345-correlation
- expiration: 86400000 (24 часа в мс)

Маршрутизация:
Exchange: "order_exchange"
Binding key: "orders.*" → очередь "order_notifications"
```

#### Как брокер обрабатывает:

1. **Получает сообщение** от ордер-сервиса
2. **Смотрит на routing key** ("orders.created")
3. **Ищет очереди**, связанные с этим паттерном через binding
4. **Находит очередь** "order_notifications" (binding: "orders.*")
5. **Доставляет сообщение** в эту очередь

#### Получение сообщения (Consumer):

```
Сервис уведомлений читает из очереди "order_notifications":

Получил:
├─ Body: {"order_id": 12345, ...}
├─ Headers: {event_type: "OrderCreated", ...}
└─ Properties: {message_id, correlation_id, ...}

Действия:
1. Проверяет headers.event_type == "OrderCreated"
2. Отправляет email пользователю
3. Если нужно — отправляет ответ с correlation_id
```

## ⚖️ Плюсы/минусы

### ✅ Плюсы структурированных сообщений

**Гибкость:**
- Можно добавлять любые заголовки для бизнес-логики
- Свойства позволяют контролировать доставку на уровне брокера

**Надёжность:**
- `delivery_mode` гарантирует сохранение важных сообщений
- `message_id` позволяет делать дедупликацию

**Связанность:**
- `correlation_id` связывает запрос и ответ в распределённой системе
- Можно отслеживать цепочку событий

### ❌ Минусы

**Сложность:**
- Нужно понимать структуру сообщения для отладки
- Заголовки могут разрастаться со временем

**Производительность:**
- Дополнительные метаданные занимают место в памяти
- При очень больших телах — overhead на сериализацию/десериализацию

---

## 🎯 Что важно запомнить аналитику

1. **Сообщение ≠ только тело** — заголовки и свойства критичны для маршрутизации
2. **Routing key определяет доставку** — это не просто текст, а паттерн для matching с binding
3. **Correlation ID связывает запрос-ответ** — важно для async коммуникации
4. **Delivery mode влияет на надёжность** — persistent сообщения сохраняются на диск

## ❓ Типичные вопросы и ответы

### Вопрос: В чём разница между Headers и Properties?
→ **Ответ:**  
Headers — это бизнес-метаданные, которые задаёт отправитель (например, тип события). Properties — технические метаданные от брокера или отправителя (delivery_mode, message_id, expiration).

### Вопрос: Для чего нужен correlation_id?
→ **Ответ:**  
Он связывает запрос и ответ в асинхронной коммуникации. Когда сервис A отправляет сообщение с correlation_id="X" и ждёт ответа, сервис B ставит это же ID в свой ответ — сервис A понимает, что это ответ на своё сообщение.

### Вопрос: Что такое routing key?
→ **Ответ:**  
Это ключ маршрутизации, который определяет, к каким очередям доставить сообщение через exchange. Exchange сравнивает routing key с binding patterns и выбирает подходящие очереди.

### Вопрос: Почему важно указывать expiration?
→ **Ответ:**  
Сообщения не должны жить вечно. Если обработка упала на несколько дней — устаревшее сообщение может помешать новым операциям. Expiration гарантирует удаление "мёртвых" сообщений.

## 🛠 Практические вопросы для собеседования

**Вопрос 1: Как сделать дедупликацию сообщений в RabbitMQ?**
→ **Ответ:**  
Использовать message_id из properties или свой заголовок. Перед обработкой проверять, не было ли уже сообщение с таким ID (например, через Redis). Если было — игнорировать.

**Вопрос 2: Как связать запрос и ответ в асинхронной системе?**
→ **Ответ:**  
1. Отправитель генерирует correlation_id
2. Ставит его в properties сообщения
3. Получатель ставит это же ID в reply_to (куда отправить ответ)
4. Ответ отправляется с тем же correlation_id

**Вопрос 3: Что такое prefetch count и зачем она нужна?**
→ **Ответ:**  
Prefetch ограничивает количество сообщений, которые потребитель может прочитать одновременно. Это предотвращает ситуацию, когда один медленный потребитель забивает очередь сообщениями для других потребителей.

**Вопрос 4: Когда использовать persistent vs transient delivery mode?**
→ **Ответ:**  
Persistent — для важных сообщений, которые не должны потеряться при перезагрузке брокера (например, заказы). Transient — для временных данных, которые можно потерять без проблем (например, метрики мониторинга).

**Вопрос 5: Как реализовать идемпотентность при обработке сообщений?**
→ **Ответ:**  
1. Использовать message_id или свой уникальный ID события
2. Перед обработкой проверять, не было ли уже сообщение с таким ID
3. Если было — игнорировать или обновлять (в зависимости от бизнес-логики)

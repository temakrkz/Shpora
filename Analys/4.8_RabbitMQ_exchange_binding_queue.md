# 4.8. RabbitMQ: exchange, binding, queue

> **Короткий ответ**  
> Это три ключевых компонента маршрутизации в RabbitMQ:  
> - **Exchange** — центральный хаб, который распределяет сообщения по очередям  
> - **Binding** — правило связи между exchange и очередью (через routing key)  
> - **Queue** — очередь, где хранятся сообщения для потребителей

---

## 💡 Простыми словами

Представьте почтовую систему:
- **Exchange** — сортировочный центр, куда приходят все письма
- **Binding** — правила сортировки (например, "все письма из Москвы → ящик №5")
- **Queue** — конкретные почтовые ящики, где хранятся письма для получения

Письмо попадает в exchange → exchange смотрит на адрес (routing key) → по правилам (binding) отправляет в нужный ящик (queue).

---

## 🔍 Подробно

### Exchange — центральный хаб

**Что это:** Точка входа для всех сообщений. Producer отправляет сообщение в exchange, а не напрямую в queue.

**Почему нужен:**  
Без exchange каждый producer должен знать все очереди → хаос при изменении системы. Exchange абстрагирует маршрутизацию.

**Типы exchange (важно!):**
1. **Direct** — точное совпадение routing key с binding pattern
2. **Fanout** — рассылка всем очередям, к которым связан exchange
3. **Topic** — паттерны с дикими картами (`*`, `#`)
4. **Headers** — фильтрация по заголовкам сообщения

### Binding — правило связи

**Что это:** Связь между exchange и queue через routing key (паттерн).

**Как работает:**  
Когда сообщение приходит в exchange с определённым routing key → exchange проверяет все binding patterns → доставляет сообщение в очереди, где pattern совпадает.

**Примеры паттернов:**
- `"orders.*"` — совпадёт с "orders.created", "orders.updated"
- `"user.#"` — совпадёт с чем угодно после "user."
- `"#"` — всё (для fanout)

### Queue — очередь для потребителей

**Что это:** Место, где хранятся сообщения для consumers.

**Виды очередей:**
1. **Дискретная** — сообщения могут быть доставлены нескольким consumer'ам (работает как пул сообщений)
2. **Конкурентная** — каждое сообщение достаётся только одному consumer'у

## 🛠 Пример из интернет-магазина

### Сценарий: Разные типы уведомлений о заказах

#### Архитектура:

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────┐
│  Order      │     │   Exchange       │     │ Notifications│
│  Service    │────▶│ order_exchange   │◀────│   Service   │
└─────────────┘     └──────────────────┘     └─────────────┘
                          │
              ┌───────────┴───────────┐
              │ Binding patterns      │
              ├───────────────────────┤
              ▼                       ▼
    ┌─────────────────┐      ┌─────────────────┐
    │ Email Queue     │      │ SMS Queue       │
    │ pattern:        │      │ pattern:        │
    │ orders.*.email  │      │ orders.*.sms    │
    └─────────────────┘      └─────────────────┘
```

#### Отправка сообщения (Producer):

```
Сообщение о создании заказа:
- Routing key: "orders.created"
- Body: {"order_id": 123, "email": "user@example.com", "phone": "+7900..."}

Exchange (order_exchange) смотрит на binding patterns:
├─ Binding 1: pattern="orders.*.email", queue="email_queue" → совпадает!
├─ Binding 2: pattern="orders.*.sms", queue="sms_queue"    → не совпадает
└─ Binding 3: pattern="orders.*", queue="order_archive"     → совпадает!

Результат:
- Сообщение доставляется в email_queue (для отправки письма)
- Сообщение доставляется в order_archive (для хранения истории)
```

#### Получение сообщений (Consumers):

```
Email consumer читает из email_queue:
├─ Получил сообщение с routing key "orders.created"
├─ Извлекает email из тела сообщения
└─ Отправляет письмо пользователю

SMS consumer читает из sms_queue:
├─ Очередь пуста (сообщение не попало сюда, потому что binding не совпал)
└─ SMS не отправляется
```

## ⚖️ Плюсы/минусы

### ✅ Плюсы архитектуры Exchange-Binding-Queue

**Гибкость маршрутизации:**
- Одно сообщение может идти в несколько очередей (publish/subscribe)
- Легко добавлять новые потребители без изменения producers

**Разделение ответственности:**
- Producers не знают о consumers — только отправляют в exchange
- Consumers подписываются на нужные события через binding patterns

**Масштабируемость:**
- Можно добавить новых потребителей, просто создав новую очередь и binding

### ❌ Минусы

**Сложность конфигурации:**
- Нужно правильно настроить exchange типы и binding patterns
- Ошибки в паттернах приведут к потере сообщений

**Производительность:**
- Каждый проход через exchange добавляет latency (несколько мс)
- Слишком много binding'ов может замедлить обработку

---

## 🎯 Что важно запомнить аналитику

1. **Exchange — это не очередь!** Exchange только маршрутизирует, хранит сообщения в queue
2. **Binding pattern определяет доставку** — нужно точно понимать, какие события куда попадут
3. **Тип exchange критичен:**
   - Direct → точное совпадение
   - Fanout → всем подряд
   - Topic → паттерны с дикими картами
4. **Одна queue может иметь несколько binding'ов** — но только один exchange

## ❓ Типичные вопросы и ответы

### Вопрос: В чём разница между Direct и Topic exchange?
→ **Ответ:**  
Direct использует точное совпадение (или префикс). Topic поддерживает дикие карты `*` (одна часть паттерна) и `#` (множество частей), что позволяет более гибко фильтровать сообщения.

### Вопрос: Почему не отправлять сообщение напрямую в очередь, а через exchange?
→ **Ответ:**  
1. Прямая отправка связывает producer с consumer — при изменении системы нужно менять код producers
2. Exchange позволяет одному сообщению идти в несколько очередей
3. Exchange абстрагирует сложность маршрутизации

### Вопрос: Что будет, если binding pattern не совпадёт?
→ **Ответ:**  
Сообщение просто потеряется (не будет доставлено ни в одну очередь). Поэтому важно тестировать binding patterns перед продакшном.

### Вопрос: Можно ли связать queue с несколькими exchange'ами?
→ **Ответ:**  
Да, но это редко используется. Обычно одна queue связана с одним exchange через несколько binding'ов.

## 🛠 Практические вопросы для собеседования

**Вопрос 1: Когда использовать Fanout вместо Topic?**
→ **Ответ:**  
Fanout — когда нужно отправить сообщение всем очередям без фильтрации (например, метрики мониторинга). Topic — когда нужна маршрутизация по паттернам (например, события разных типов в разные очереди).

**Вопрос 2: Как реализовать "если событие типа X → только в эту очередь"?**
→ **Ответ:**  
Использовать Direct или Topic exchange с точным binding pattern. Например, binding="orders.created" → queue="created_orders_queue".

**Вопрос 3: Что такое dead letter queue (DLQ) и зачем она нужна?**
→ **Ответ:**  
DLQ — очередь для сообщений, которые не могут быть обработаны (ошибки consumers, истечение времени). Позволяет мониторить проблемы и пересылать сообщения позже.

**Вопрос 4: Как избежать дублирования сообщений при использовании Fanout exchange?**
→ **Ответ:**  
Идемпотентность — перед обработкой проверять, не было ли уже сообщение с таким ID (message_id или свой уникальный ключ).

**Вопрос 5: В чём разница между дискретной и конкурентной очередью?**
→ **Ответ:**  
Дискретная — сообщения могут быть доставлены нескольким consumer'ам (работает как пул). Конкурентная — каждое сообщение достаётся только одному consumer'у (стандартное поведение для большинства очередей).

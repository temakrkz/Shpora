# 4.9. Типы exchange в RabbitMQ

> **Короткий ответ**  
> В RabbitMQ есть 4 типа exchange, каждый для разных сценариев:  
> - **Direct** — точное совпадение routing key (для конкретных событий)  
> - **Fanout** — рассылка всем очередям (для broadcast)  
> - **Topic** — паттерны с фильтрацией (для событийных систем)  
> - **Headers** — фильтрация по заголовкам (редко используется)

---

## 💡 Простыми словами

Представьте почтовую систему:
- **Direct** — как адрес на конверте, письмо идёт только в тот ящик, где совпадает адрес
- **Fanout** — как объявление на доске, все видят информацию
- **Topic** — как рубрикация (новости, спорт, политика) — письмо попадает в нужную категорию
- **Headers** — как метки на пакете ("хрупкое", "приоритетное")

---

## 🔍 Подробно

### 1. Direct Exchange

**Как работает:**  
Сообщение доставляется только в очереди, где binding pattern **точно совпадает** с routing key (или начинается с него).

**Паттерны:**
- `"orders.created"` → совпадёт только с точным ключом
- `"orders.*"` → совпадёт с "orders.created", "orders.updated"
- `"#"` — всё (редко используется)

**Когда использовать:**
✅ Когда нужно отправить событие конкретному получателю  
✅ Для событийных систем с чёткими типами событий  
❌ Не подходит для broadcast или сложной фильтрации

**Пример из интернет-магазина:**

```
Exchange: order_exchange (type: direct)

Binding patterns:
├─ "orders.created" → queue: "created_orders"
├─ "orders.updated" → queue: "updated_orders"
└─ "orders.cancelled" → queue: "cancelled_orders_archive"

Producer отправляет:
- Routing key: "orders.created"
- Результат: только в created_orders (остальные очереди не получат)
```

### 2. Fanout Exchange

**Как работает:**  
Сообщение доставляется **во все очереди**, связанные с этим exchange, независимо от routing key.

**Паттерны:**  
Не используются! Routing key игнорируется.

**Когда использовать:**
✅ Когда нужно отправить одно сообщение всем подписчикам (broadcast)  
✅ Для систем мониторинга и алертингов  
❌ Не подходит для фильтрации по типу события

**Пример из интернет-магазина:**

```
Exchange: metrics_exchange (type: fanout)

Binding patterns:
├─ queue: "frontend_metrics"    (любой pattern, routing key не важен)
├─ queue: "backend_metrics"     (любой pattern)
└─ queue: "analytics_dashboard" (любой pattern)

Producer отправляет метрики производительности:
- Routing key: "ignored" (не используется)
- Результат: все три очереди получают сообщение одновременно
```

**Другой пример — уведомления о статусе заказа:**

```
Exchange: order_status_exchange (type: fanout)

Подписчики:
├─ Email notifications service
├─ SMS notifications service
├─ Mobile app push notifications
└─ Analytics dashboard

Когда заказ создан → все получают уведомление одновременно
```

### 3. Topic Exchange

**Как работает:**  
Сообщение доставляется в очереди, где binding pattern **совпадает с routing key по паттернам**.

**Паттерны (дикие карты):**
- `*` — одна часть паттерна (делититель `.`)
- `#` — ноль или более частей паттерна

**Примеры:**
- `"orders.*"` → совпадёт с "orders.created", "orders.updated", но не "user.orders"
- `"orders.#"` → совпадёт с чем угодно после "orders." (включая "orders.created.v2")
- `"user.*/profile"` → совпадёт только с паттернами типа "user.*.profile"

**Когда использовать:**
✅ Для событийных систем с иерархией типов событий  
✅ Когда нужно гибко фильтровать сообщения  
❌ Сложнее настраивать, чем Direct или Fanout

**Пример из интернет-магазина:**

```
Exchange: event_exchange (type: topic)

Binding patterns:
├─ "orders.*.email" → queue: "order_emails"
├─ "orders.*.sms"   → queue: "order_sms"
├─ "user.*.profile" → queue: "user_profile_updates"
└─ "payment.*"      → queue: "payment_processor"

Producer отправляет разные события:

1. Routing key: "orders.created.email"
   └─ Результат: попадает в order_emails (pattern "orders.*.email" совпал)

2. Routing key: "user.123.profile.updated"
   └─ Результат: попадает в user_profile_updates

3. Routing key: "payment.processed"
   └─ Результат: попадает в payment_processor
```

### 4. Headers Exchange (редко используется)

**Как работает:**  
Сообщение доставляется в очереди, где **заголовки сообщения совпадают с условиями binding**.

**Паттерны:**  
Не routing key, а условия по заголовкам:
- `{"event_type": "OrderCreated"}` → только если header.event_type == "OrderCreated"
- Можно использовать операторы: `=`, `!=`, `>`, `<`

**Когда использовать:**
✅ Когда нужно фильтровать по множеству заголовков одновременно  
❌ Медленнее других типов (нужно сравнивать все заголовки)  
❌ Редко используется в современных системах

**Пример из интернет-магазина:**

```
Exchange: complex_filter_exchange (type: headers)

Binding conditions:
├─ {"event_type": "OrderCreated", "priority": "high"} → queue: "urgent_orders"
├─ {"event_type": "OrderUpdated"}                      → queue: "order_updates"
└─ {"event_type": "PaymentReceived", "amount > 1000"} → queue: "large_payments_audit"

Producer отправляет:
- Headers: {"event_type": "OrderCreated", "priority": "high"}
- Результат: попадает только в urgent_orders (оба условия совпали)
```

## ⚖️ Плюсы/минусы каждого типа

### Direct Exchange

**✅ Плюсы:**
- Простота и предсказуемость
- Хорошая производительность
- Чёткое соответствие между событием и получателем

**❌ Минусы:**
- Не подходит для broadcast
- Требует точного совпадения паттернов

### Fanout Exchange

**✅ Плюсы:**
- Максимальная простота для рассылки
- Высокая производительность (не нужно сравнивать паттерны)

**❌ Минусы:**
- Нельзя фильтровать сообщения
- Все получают всё — может быть избыточно

### Topic Exchange

**✅ Плюсы:**
- Гибкость фильтрации по паттернам
- Идеально для событийных систем
- Можно добавлять новые типы событий без изменения producers

**❌ Минусы:**
- Сложность настройки паттернов
- Больше overhead на сравнение паттернов

### Headers Exchange

**✅ Плюсы:**
- Гибкая фильтрация по множеству заголовков
- Подходит для сложных условий

**❌ Минусы:**
- Медленнее других типов
- Редко используется в современных системах

---

## 🎯 Что важно запомнить аналитику

1. **Direct** — точное совпадение (для конкретных событий)
2. **Fanout** — всем подряд (для broadcast и метрик)
3. **Topic** — паттерны с фильтрацией (для событийных систем) ← самый популярный в e-commerce
4. **Headers** — по заголовкам (редко, но полезно для сложных условий)

## ❓ Типичные вопросы и ответы

### Вопрос: Когда использовать Fanout вместо Topic?
→ **Ответ:**  
Fanout — когда нужно отправить одно сообщение всем подписчикам без фильтрации (например, метрики мониторинга). Topic — когда нужна маршрутизация по типам событий.

### Вопрос: В чём разница между Direct и Topic exchange?
→ **Ответ:**  
Direct использует точное совпадение или префикс. Topic поддерживает дикие карты `*` (одна часть) и `#` (множество частей), что позволяет более гибко фильтровать сообщения по паттернам.

### Вопрос: Почему Headers exchange редко используется?
→ **Ответ:**  
Потому что он медленнее других типов (нужно сравнивать все заголовки с условиями) и сложнее в настройке. В большинстве случаев Topic exchange даёт ту же гибкость, но быстрее.

### Вопрос: Можно ли комбинировать типы exchange?
→ **Ответ:**  
Да, можно использовать несколько exchange'ов для разных целей. Например, Fanout для метрик и Topic для событийных данных. Но это усложняет архитектуру.

## 🛠 Практические вопросы для собеседования

**Вопрос 1: Как реализовать рассылку уведомления всем пользователям о статусе системы?**
→ **Ответ:**  
Использовать Fanout exchange. Создать очереди для разных клиентов/приложений, связать их с fanout exchange. Отправлять сообщение в exchange — все получат его одновременно.

**Вопрос 2: Как разделить события заказов по типу (создание, обновление, отмена)?**
→ **Ответ:**  
Использовать Topic или Direct exchange. Для Topic: binding patterns "orders.created", "orders.updated", "orders.cancelled" → в разные очереди. Для Direct: точное совпадение routing key с pattern.

**Вопрос 3: Когда использовать Headers exchange?**
→ **Ответ:**  
Когда нужно фильтровать по нескольким заголовкам одновременно (например, event_type = "OrderCreated" И priority = "high"). Но лучше сначала попробовать Topic — он быстрее и проще в поддержке.

**Вопрос 4: Как избежать перегрузки Fanout exchange при большом количестве подписчиков?**
→ **Ответ:**  
1. Ограничить количество сообщений через rate limiting на уровне producers
2. Использовать дискретные очереди с prefetch для балансировки нагрузки
3. Рассмотреть Topic вместо Fanout, если нужна фильтрация

**Вопрос 5: В чём разница между routing key и binding pattern?**
→ **Ответ:**  
Routing key — это значение, которое producer передаёт в exchange при отправке сообщения. Binding pattern — это правило (с дикими картами), которое consumer или admin задаёт при создании связи с очередью. Exchange сравнивает routing key с pattern для определения доставки.

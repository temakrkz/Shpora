# 5.2 Событийное взаимодействие: когда используется 📌

> **Короткий ответ**  
> Событийное взаимодействие применяется когда важна асинхронность, независимость сервисов и устойчивость к сбоям — например, для уведомлений, синхронизации данных между системами или обработки фоновых задач.

---

## 💡 Простыми словами

Когда **нужно**:
- Пользователь ждёт мгновенного ответа (не 5-10 секунд)
- Одной операции нужно выполнить несколько последующих (доставка + бонусы + уведомления)
- Сервисы могут работать независимо друг от друга
- Важно не потерять данные при сбоях

Когда **не нужно**:
- Нужна мгновенная реакция всех участников
- Простая операция без зависимостей
- Критично важно знать точно кто и когда выполнит действие

---

## 🔍 Подробно

### Типичные сценарии использования

#### 1. Фоновые задачи (async processing)
**Пример:** После оформления заказа нужно:
- Создать транспортную накладную
- Отправить SMS/Email клиенту
- Начислить бонусы
- Обновить аналитику

**Решение:** Сервис заказов публикует событие `OrderCreated`, остальные сервисы реагируют в своём темпе. Пользователь сразу видит подтверждение!

#### 2. Синхронизация данных между системами
**Пример:** Данные из CRM нужно синхронизировать с:
- Системой учёта
- Аналитической платформой
- Отделом маркетинга

**Решение:** При изменении в CRM публикуется событие `CustomerUpdated`, все системы получают его и обновляют свои данные.

#### 3. Уведомления и оповещения
**Пример:** Когда заказ доставлен нужно уведомить:
- Клиента (SMS, Email, Push)
- Менеджера (для обратной связи)
- Отдел логистики (закрыть дело)

**Решение:** Сервис доставки публикует событие `OrderDelivered`, три сервиса реагируют независимо.

#### 4. Агрегация данных для отчётов
**Пример:** Нужно собрать статистику:
- Продажи за день
- Новые пользователи
- Популярность товаров

**Решение:** Все сервисы публикуют события о своих действиях, аналитический агрегирует их в реальном времени.

---

## 🛠 Пример из интернет-магазина

**Сценарий: Регистрация нового пользователя**

| Шаг | Синхронный подход (проблемно) | Событийный подход (правильно) |
|-----|-------------------------------|-------------------------------|
| 1. Пользователь вводит данные | Ждёт регистрации на сервере | Мгновенная регистрация! |
| 2. Создание профиля | Ждёт ответа от всех сервисов | Публикует событие `UserRegistered` |
| 3. Отправка Welcome Email | Задержка 5-10 сек | Сервис уведомлений реагирует через 1-2 сек |
| 4. Начисление бонусов | Задержка ещё больше | Сервис лояльности реагирует параллельно |
| **Итог** | Пользователь ждёт 10-15 секунд | Мгновенный отклик + фоновые процессы |

## ⚖️ Плюсы/минусы

| ✅ Когда использовать | ❌ Когда НЕ использовать |
|----------------------|-------------------------|
| Нужна высокая скорость ответа пользователю | Все участники должны знать результат мгновенно |
| Есть несколько независимых последующих действий | Простая операция без зависимостей |
| Сервисы могут работать в своём темпе | Критично важно отслеживать кто и когда выполнил действие |
| Нужно обеспечить устойчивость к сбоям | Прямая зависимость между участниками обязательна |

---

## 🎯 Что важно запомнить аналитику

1. **События — это про "что-то произошло"** — не про "сделай что-то"
2. **Асинхронность — ключевое преимущество** — пользователь сразу видит результат, фоновые процессы выполняются позже
3. **Независимость сервисов** — сбой одного не ломает всю цепочку
4. **Нужна инфраструктура** — брокеры сообщений, топик, механизмы гарантий доставки

---

## ❓ Типичные вопросы и ответы

**В: В каких случаях событийное взаимодействие НЕ подходит?**  
О: Когда нужна мгновенная реакция всех участников, когда простая операция без зависимостей, или когда критично точно знать кто и когда выполнил действие.

**В: Можно ли использовать события для простых операций типа "сохранить данные"?**  
О: Лучше нет — это избыточно. Для простых синхронных операций достаточно REST API. События нужны когда есть несколько последующих независимых действий.

**В: Что если сервису нужно знать результат действия другого сервиса?**  
О: Тогда события не подходят — нужен синхронный вызов или паттерн Outbox с проверкой результата.

---

## 🛠 Практические вопросы для собеседования

**В: Приведите пример когда событийное взаимодействие лучше REST API.**  
→ Ответ: Когда нужно выполнить несколько независимых последующих действий (отправка Email, начисление бонусов, обновление аналитики) и не хочется заставлять пользователя ждать.

**В: В чём разница между событием "Заказ создан" и командой "Создай заказ"?**  
→ Ответ: Событие описывает факт что-то уже произошло (пассивно), команда — это приказ сделать что-то (активно). Для создания заказа нужна команда, для уведомления об этом — событие.

**В: Когда стоит отказаться от событийного подхода?**  
→ Ответ: Когда все участники должны знать результат мгновенно, когда простая операция без зависимостей, или когда критично точно отслеживать выполнение каждым сервисом.

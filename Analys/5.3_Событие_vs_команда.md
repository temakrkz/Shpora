# 5.3 Событие vs команда 📌

> **Короткий ответ**  
> **Событие** — это факт что-то уже произошло (пассивно, для уведомления). **Команда** — это приказ сделать что-то (активно, требует выполнения и результата).

---

## 💡 Простыми словами

### Событие = "Что-то случилось!"
Представьте вы звоните другу: "Привет, я купил новый телефон!"  
Вы просто информируете о факте — друг не обязан ничего делать. Он может:
- Просто поблагодарить
- Задать вопрос про характеристики
- Купить себе такой же

**Событие не требует реакции!** Оно просто сообщает что-то произошло.

### Команда = "Пожалуйста, сделай это!"
Вы говорите другу: "Купи мне новый телефон"  
Друг **обязан**:
- Заказать телефон
- Принести вам его
- Подтвердить выполнение

**Команда требует выполнения и результата!**

---

## 🔍 Подробно

### Событие (Event)

**Что это:** Сообщение о произошедшем факте в системе.

**Примеры событий:**
- `OrderCreated` — заказ создан
- `PaymentCompleted` — оплата прошла успешно  
- `UserRegistered` — пользователь зарегистрировался
- `InventoryUpdated` — остатки товара обновлены

**Ключевые особенности:**
1. **Пассивно** — описывает что уже произошло
2. **Не требует немедленной реакции** — консьюмер может реагировать когда готов
3. **Одно событие → много реакций** — на одно событие могут отреагировать несколько сервисов
4. **Без обратной связи** — продаксер не ждёт подтверждения

### Команда (Command)

**Что это:** Запрос на выполнение действия с ожиданием результата.

**Примеры команд:**
- `CreateOrder` — создай заказ
- `UpdateUserProfile` — обновь профиль пользователя
- `DeleteProduct` — удали товар из каталога
- `TransferMoney` — переведи деньги

**Ключевые особенности:**
1. **Активно** — требует выполнения действия
2. **Синхронно или асинхронно с ожиданием результата** — отправитель ждёт подтверждения
3. **Одна команда → один исполнитель** — обычно одна команда обрабатывается одним сервисом
4. **Требует обратной связи** — нужно знать результат (успех/ошибка)

## 🛠 Пример из интернет-магазина

### Сценарий: оформление заказа

| Действие | Тип сообщения | Почему |
|----------|---------------|--------|
| Пользователь нажимает "Оплатить" | **Команда** `CreateOrder` | Нужно создать заказ в системе, ждём подтверждения |
| Сервис заказов создаёт заказ и публикует факт создания | **Событие** `OrderCreated` | Информируем другие сервисы что заказ существует |
| Сервис доставки получает уведомление о новом заказе | **Событие** `OrderCreated` | Просто узнаём, не ждём немедленного действия |
| Сервис лояльности начисляет бонусы за покупку | **Событие** `OrderCreated` | Параллельная реакция на факт создания заказа |

### Визуализация потока:

```
Пользователь → [Команда] → Сервис заказов → "Заказ создан!"
                                    ↓
                          [Событие OrderCreated]
                                    ↓    ↓
                        Сервис доставки  Сервис лояльности
                        (создаёт накладную)   (начисляет бонусы)
```

## ⚖️ Плюсы/минусы

| ✅ События | ❌ Минусы событий | ✅ Команды | ❌ Минусы команд |
|------------|------------------|------------|-----------------|
| Асинхронность — мгновенный отклик пользователю | Нет гарантии выполнения | Синхронность — ждём результат | Ждём ответ (задержка) |
| Независимость сервисов | Сложнее отладить цепочку | Прямая зависимость между участниками | Сбой одного ломает всё |
| Масштабируемость — много консьюмеров | Потенциальные дубли сообщений | Простота отслеживания выполнения | Не подходит для фоновых задач |

---

## 🎯 Что важно запомнить аналитику

1. **Событие = "что-то произошло"** (пассивно, уведомление)
2. **Команда = "сделай это"** (активно, требует выполнения и результата)
3. **Для создания/изменения данных нужны команды** — REST API, gRPC
4. **Для уведомления о изменениях нужны события** — Kafka, RabbitMQ топик

## ❓ Типичные вопросы и ответы

**В: Когда использовать событие а не команду?**  
О: Когда нужно просто уведомить другие сервисы что-то произошло, без требования немедленного действия или ожидания результата.

**В: Можно ли обработать событие как команду?**  
О: Технически да (если добавить ожидание реакции), но это противоречит смыслу — события пассивны по природе.

**В: Чем паттерн Event Sourcing отличается от событийного взаимодействия?**  
О: Event Sourcing хранит все события как источник истины для состояния системы, а событийное взаимодействие — просто способ общения между сервисами.

## 🛠 Практические вопросы для собеседования

**В: В чём разница между событием "Заказ создан" и командой "Создай заказ"?**  
→ Ответ: Событие описывает факт что-то уже произошло (пассивно), команда — это приказ сделать что-то (активно, требует выполнения и результата).

**В: Почему для создания заказа нужна команда а не событие?**  
→ Ответ: Потому что нужно гарантировать выполнение действия и получить подтверждение успеха/ошибки. Событие пассивно и не гарантирует результат.

**В: Можно ли использовать события вместо REST API?**  
→ Ответ: Для простых синхронных операций лучше нет — это избыточно и усложняет архитектуру. События нужны для асинхронного уведомления о изменениях.

# 7.18. Артефакты аналитика и их пользователи

> 📌 **Короткий ответ**  
> Артефакты аналитика — это документы, диаграммы и модели, которые создаёт системный аналитик в процессе работы. У каждого артефакта есть свои пользователи (кто его читает) и цель создания.

---

## 💡 Простыми словами

Представьте, что вы строите дом:
- **Чертежи** — для архитекторов и строителей
- **Паспорт дома** — для будущих жильцов
- **Инструкция по ремонту** — для обслуживающего персонала
- **Рекламный буклет** — для покупателей

Так и в разработке ПО: аналитик создаёт разные документы для разных людей.

---

## 🔍 Подробно

### Что такое артефакты аналитика

**Артефакт** (от лат. artifactum — "созданное человеком") — любой документ, модель, диаграмма или файл, созданный в процессе анализа требований.

### Зачем нужны разные артефакты?

Каждый стейкхолдер (заинтересованная сторона) хочет видеть систему со своей точки зрения:
- **Заказчик** хочет понять "что будем делать"
- **Разработчики** хотят знать "как это реализовать"
- **Тестировщики** хотят проверить "что должно работать"
- **Менеджеры** хотят планировать "когда будет готово"

Поэтому один и тот же функционал описывается разными способами для разных людей.

---

## 📋 Основные артефакты аналитика

### 1. BRD (Business Requirements Document) — Бизнес-требования

**Что это:**  
Документ с бизнес-целями, проблемами и высокоуровневыми требованиями.

**Кто читает:**
- Бизнес-заказчики
- Руководители проектов
- Архитекторы

**Пример из интернет-магазина:**
```
Бизнес-проблема: Пользователи не могут быстро найти нужный товар
Бизнес-цель: Увеличить конверсию поиска с 15% до 25%
Требование: Реализовать умный поиск с фильтрами и автодополнением
```

---

### 2. SRS (Software Requirements Specification) — Спецификация требований ПО

**Что это:**  
Подробное описание функциональных и нефункциональных требований к системе.

**Кто читает:**
- Разработчики
- Тестировщики
- Архитекторы

**Пример из интернет-магазина:**
```
Функциональное требование:
Система должна позволять пользователю фильтровать товары по цене в диапазоне от X до Y рублей.

Нефункциональное требование:
Поиск должен возвращать результаты за не более чем 2 секунды при 100 запросах в секунду.
```

---

### 3. ТЗ (Техническое задание)

**Что это:**  
Документ с детальным описанием функционала, часто на русском языке для заказчиков.

**Кто читает:**
- Заказчик/бизнес
- Разработчики
- Тестировщики

**Пример из интернет-магазина:**
```
Раздел "Поиск товаров":
1. Пользователь вводит запрос в поле поиска
2. Система показывает автодополнение с 5 вариантами
3. При нажатии Enter или выборе варианта — переход к результатам
4. Результаты отображаются в виде списка карточек товара
```

---

### 4. User Stories + Acceptance Criteria

**Что это:**  
Описание функционала с точки зрения пользователя + критерии приёмки.

**Кто читает:**
- Разработчики
- Тестировщики
- Product Owner

**Пример из интернет-магазина:**
```
User Story: Как покупатель, я хочу фильтровать товары по цене, чтобы быстро найти нужный товар в бюджете.

Acceptance Criteria:
1. Есть поле "Цена" с двумя ползунками (мин/макс)
2. При перемещении ползунков список товаров обновляется
3. Фильтр сохраняется при переходе между страницами
4. Если диапазон пустой — показываются все товары
```

---

### 5. BPMN-диаграммы

**Что это:**  
Визуальное описание бизнес-процессов в нотации BPMN.

**Кто читает:**
- Разработчики (логика процессов)
- Бизнес-аналитики
- Тестировщики (сценарии)

**Пример из интернет-магазина:**
```
Процесс "Оформление заказа":
[Пользователь] → [Добавить в корзину] → [Перейти к оформлению] 
→ [Ввести данные доставки] → [Выбрать оплату] → [Подтвердить заказ] 
→ [Создать заказ в БД] → [Отправить уведомление]
```

---

### 6. ER-диаграммы (Entity-Relationship)

**Что это:**  
Модель данных: сущности, их атрибуты и связи между ними.

**Кто читает:**
- Разработчики БД
- Архитекторы
- Тестировщики (структура данных)

**Пример из интернет-магазина:**
```
[Пользователь] ──(создал)── [Заказ] ──(содержит)── [Товар]
  |              |               |
  |            [статус]         [количество]
  └────(имеет)────[Адрес]
```

---

### 7. Use Case диаграммы

**Что это:**  
Визуальное описание сценариев использования системы пользователями.

**Кто читает:**
- Разработчики (функционал)
- Бизнес-заказчики (сценарии)
- Тестировщики (сценарии тестирования)

**Пример из интернет-магазина:**
```
(Пользователь) ──[Поиск товаров]── (Система)
              │
        +-----+-----+
        │           │
  [Найти товары]  [Не найдено]
```

---

### 8. Class Diagrams (Диаграммы классов)

**Что это:**  
Модель объектов системы: классы, их атрибуты и методы.

**Кто читает:**
- Разработчики (структура кода)
- Архитекторы (дизайн)

**Пример из интернет-магазина:**
```
class Product {
  - id: Integer
  - name: String
  - price: Decimal
  + getName(): String
  + getPrice(): Decimal
}

class Order {
  - orderId: Integer
  - userId: Integer
  - totalAmount: Decimal
  + calculateTotal(): Decimal
}
```

---

### 9. API-спецификации (OpenAPI/Swagger)

**Что это:**  
Документация REST/gRPC API: эндпоинты, методы, параметры, ответы.

**Кто читает:**
- Разработчики бэкенда/фронтенда
- Мобильные разработчики
- Тестировщики (API-тесты)

**Пример из интернет-магазина:**
```
GET /api/v1/products/{id}
Response: {
  "id": 123,
  "name": "Телефон",
  "price": 50000
}
```

---

### 10. Wireframes/Mockups (Прототипы)

**Что это:**  
Визуальные макеты интерфейсов (не дизайн, а структура).

**Кто читает:**
- Дизайнеры
- Разработчики фронтенда
- Бизнес-заказчики (подтверждение логики)

**Пример из интернет-магазина:**
```
[Поле поиска] [Кнопка "Найти"]
[Список товаров: фото | название | цена | кнопка "Купить"]
```

## ⚖️ Плюсы и минусы разных артефактов

### Преимущества документирования

✅ **Единый источник правды** — все работают с одними требованиями  
✅ **Снижение рисков** — понятно, что делать до начала разработки  
✅ **Упрощение онбординга** — новые сотрудники быстро вникают  
✅ **База для тестов** — из требований пишутся тест-кейсы  
✅ **Доказательство выполненной работы** — есть документация  

### Риски переизбытка документации

❌ **Много бумаги** — тратить время на написание вместо разработки  
❌ **Устаревание** — документы не обновляются при изменениях  
❌ **Иллюзия понимания** — "есть документ = всё понятно" (часто не так)  
❌ **Разные версии** — кто-то работает с устаревшим документом  

---

## 🎯 Что важно запомнить аналитику

1. **Один артефакт для всех — плохо**  
   Разные люди хотят видеть информацию в разных форматах

2. **Меньше лучше, чем больше**  
   Создавайте только то, что действительно нужно читателям

3. **Живая документация**  
   Обновляйте артефакты при изменениях требований

4. **Визуальное > текстовое**  
   Диаграммы и схемы понятнее длинных описаний

5. **Контекст важнее деталей**  
   Сначала общее (BRD), потом детали (SRS, ТЗ)

## ❓ Типичные вопросы и ответы

### Какие артефакты создаёт системный аналитик?
Основные артефакты: BRD (бизнес-требования), SRS (спецификация требований ПО), ТЗ (техническое задание), User Stories с Acceptance Criteria, BPMN-диаграммы процессов, ER-диаграммы данных, Use Case диаграммы, Class Diagrams, API-спецификации, Wireframes/прототипы.

### Кто читает разные артефакты?
Заказчики — BRD и ТЗ; разработчики — SRS, User Stories, BPMN, ER-диаграммы, API-спеки; тестировщики — все требования для проверки; дизайнеры — Wireframes; менеджеры — BRD и User Stories.

### Зачем нужны разные форматы артефактов?
Потому что каждый стейкхолдер хочет видеть систему со своей точки зрения: бизнесу важно "что", разработчикам — "как", тестировщикам — "что должно работать". Один формат не подходит всем.

### Какой главный артефакт аналитика?
Зависит от проекта, но обычно это комбинация User Stories с Acceptance Criteria (для Agile) или SRS/ТЗ (для waterfall). Главное — чтобы требования были понятны команде и актуальны.

### Что важнее: документация или разговоры со стейкхолдерами?
Разговоры первичны — именно от них берутся требования. Документация фиксирует договорённости, но если в процессе общения что-то изменилось — обновляйте документы.

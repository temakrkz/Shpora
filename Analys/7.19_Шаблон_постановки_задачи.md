# 7.19. Шаблон постановки задачи

> 📌 **Короткий ответ**  
> Шаблон постановки задачи — это структура описания задачи для разработчиков, которая включает: заголовок, описание, контекст, требования (функциональные/нефункциональные), критерии приёмки, ограничения и приложенные материалы.

---

## 💡 Простыми словами

Представьте, что вы заказываете пиццу:
- **Что хотите** — описание задачи
- **Какая начинка** — функциональные требования
- **Сколько времени ждать** — сроки
- **Аллергия на орехи** — ограничения/особенности
- **Фото примера** — приложенные материалы

Так и с задачами для разработчиков: нужно чётко сказать "что, зачем, как, когда".

---

## 🔍 Подробно

### Зачем нужен шаблон?

Без шаблона задачи часто описываются хаотично:
- ❌ "Сделать поиск" (не понятно, какой именно)
- ❌ "Улучшить страницу товара" (что улучшить?)
- ❌ "Исправить баг с оплатой" (какую именно ошибку?)

Шаблон обеспечивает **полноту** и **понятность**.

---

## 📋 Структура шаблона задачи

### 1. Заголовок (Title)

**Что писать:**  
Краткое описание сути задачи в формате "Как [пользователь], я хочу [действие], чтобы [ценность]".

**Плохо:** "Поиск товаров"  
**Хорошо:** "Как покупатель, я хочу фильтровать товары по цене, чтобы быстро найти нужный товар в бюджете"

---

### 2. Описание (Description)

**Что писать:**  
Подробное объяснение задачи своими словами. Что нужно сделать и почему это важно.

**Пример из интернет-магазина:**
```
Сейчас пользователи не могут отфильтровать товары по диапазону цен. 
Это приводит к тому, что им приходится вручную просматривать сотни товаров.
Нужно добавить фильтры "от X до Y рублей" в раздел поиска.
```

---

### 3. Контекст (Context)

**Что писать:**  
- Где это используется в системе
- Какие есть похожие функции
- Что уже реализовано, что нет

**Пример из интернет-магазина:**
```
Контекст:
- Функция поиска уже есть на главной странице
- Есть фильтры по бренду и категории
- Фильтр по цене пока отсутствует
- Аналогичный фильтр есть в мобильном приложении (можно использовать как референс)
```

---

### 4. Требования

#### Функциональные требования

**Что писать:**  
Конкретные действия, которые должна выполнять система. Используйте формулировки "Система должна...".

**Пример из интернет-магазина:**
```
Функциональные требования:
1. Система должна отображать два ползунка для выбора диапазона цен (min/max)
2. При перемещении любого ползунка список товаров должен обновляться без перезагрузки страницы
3. Система должна показывать выбранный диапазон в текстовом виде ("Цена от 5000 до 15000 руб.")
4. Если оба ползунка не заданы — показываются все товары
5. Фильтр должен сохраняться при переходе между страницами (localStorage)
```

#### Нефункциональные требования

**Что писать:**  
Производительность, безопасность, доступность и т.д.

**Пример из интернет-магазина:**
```
Нефункциональные требования:
1. Поиск с фильтрами должен работать за не более чем 2 секунды при 100 запросах в секунду
2. Фильтр должен быть доступен для пользователей с экранированными устройствами (WCAG 2.1 AA)
3. Данные о выбранном фильтре должны храниться локально в браузере пользователя
```

---

### 5. Критерии приёмки (Acceptance Criteria / AC)

**Что писать:**  
Чёткие условия, при которых задача считается выполненной. В формате Given-When-Then или просто списком.

**Пример из интернет-магазина:**
```
AC:
1. GIVEN пользователь на странице поиска WHEN он двигает ползунок цены THEN список товаров обновляется без перезагрузки
2. GIVEN диапазон цен задан WHEN пользователь переходит на другую страницу поиска THEN фильтр сохраняется
3. GIVEN оба ползунка не заданы WHEN пользователь открывает страницу поиска THEN показываются все товары без фильтрации
4. GIVEN выбран диапазон цен WHEN цена товара вне диапазона THEN товар не отображается в результатах поиска
5. GIVEN есть товары с ценой от 0 до 100000 WHEN пользователь выбирает диапазон 5000-15000 THEN показываются только товары в этом диапазоне
```

---

### 6. Ограничения и зависимости (Constraints & Dependencies)

**Что писать:**  
- Технические ограничения
- Зависимости от других задач/команд
- Риски

**Пример из интернет-магазина:**
```
Ограничения:
1. Использовать существующую инфраструктуру поиска, нельзя менять БД
2. Фильтр должен работать на мобильных устройствах
3. Нужно согласовать дизайн с дизайнерами до начала разработки

Зависимости:
1. Ждём API-контактов от команды аналитики (структура данных товаров)
2. Дизайн готов в Figma, ссылка: [ссылка]
```

### 8. Дополнительные разделы (по необходимости)

#### Риски
**Что писать:**  
Возможные проблемы и как их избежать.

**Пример из интернет-магазина:**
```
Риски:
1. API поиска может быть медленным → нужно протестировать нагрузку заранее
2. Пользователи могут не понимать, как работает фильтр → нужна подсказка "перетащите ползунок"
```

#### Вопросы для разработчиков
**Что писать:**  
Неоднозначности, которые нужно прояснить до начала работы.

**Пример из интернет-магазина:**
```
Вопросы:
1. Нужно ли показывать товары с ценой 0 (бесплатные)?
2. Как обрабатывать товары со скидкой — показывать старую или новую цену?
3. Какой формат хранения диапазона в localStorage?
```

#### Вопросы для тестировщиков
**Что писать:**  
На что обратить внимание при тестировании.

**Пример из интернет-магазина:**
```
Для тестирования:
1. Проверить работу фильтра на разных разрешениях экрана
2. Тестировать с товарами, у которых цена не указана (NULL)
3. Проверить сохранение фильтра в кэше браузера
4. Тестировать скорость ответа при большом количестве товаров (>10 000)
```

## ⚖️ Плюсы и минусы шаблона

| Плюсы | Минусы |
|-------|--------|
| ✅ Полнота описания (всё важное учтено) | ❌ Требует времени на заполнение |
| ✅ Понятность для всех участников | ❌ Может стать слишком формальным |
| ✅ Снижение количества вопросов в процессе работы | ❌ Риск "заполнения ради заполнения" |
| ✅ Легче оценивать задачу (есть все данные) | ❌ Нужно соблюдать структуру всегда |

## 🎯 Что важно запомнить аналитику

1. **Заголовок = User Story**  
   Кратко и по делу: "Как [кто], я хочу [что], чтобы [зачем]"

2. **Описание ≠ требования**  
   Описание — это объяснение контекста, требования — конкретные действия системы

3. **AC должны быть проверяемыми**  
   Каждый критерий приёмки должен иметь чёткие условия (Given-When-Then)

4. **Нефункциональные требования не менее важны**  
   Производительность, безопасность, доступность — это тоже требования

5. **Вопросы до начала работы лучше, чем в процессе**  
   Чем больше прояснить до старта — тем меньше переделок

## ❓ Типичные вопросы и ответы

### Что такое шаблон постановки задачи?
Шаблон постановки задачи — это структура описания задачи для разработчиков, которая включает: заголовок, описание, контекст, требования (функциональные/нефункциональные), критерии приёмки, ограничения и приложенные материалы.

### Зачем нужен шаблон?
Без шаблона задачи часто описываются хаотично и неполно. Шаблон обеспечивает полноту и понятность, снижает количество вопросов в процессе работы и помогает правильно оценивать effort.

### Какие разделы обязательны в шаблоне?
Обязательные разделы: заголовок (User Story), описание, функциональные требования, критерии приёмки (AC). Остальные разделы (нефункциональные требования, ограничения, приложения) — по необходимости.

### Что писать в описании задачи?
В описании объясняется контекст задачи своими словами: что нужно сделать и почему это важно. Это помогает разработчикам понять бизнес-цель, даже если они не видят всех требований детально.

### Чем требования отличаются от критериев приёмки?
Требования — это то, что система должна делать (функциональные/нефункциональные). Критерии приёмки — это условия проверки: "если X, то должно быть Y". Требования описывают поведение, AC описывают проверку.

### Что такое Given-When-Then в критериях приёмки?
Это формат написания AC:  
**Given** (Дано) — начальное состояние системы  
**When** (Когда) — действие пользователя или событие  
**Then** (Тогда) — ожидаемый результат/состояние после действия

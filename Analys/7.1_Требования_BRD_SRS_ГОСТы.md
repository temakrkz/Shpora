# 7.1 Требования, BRD, SRS и ГОСТы 📌

> **Короткий ответ**  
> **BRD (Business Requirements Document)** — документ о бизнес-целях проекта. **SRS (Software Requirements Specification)** — техническое описание функциональных требований. **ГОСТ 34** — российский стандарт для ТЗ, устарел.

---

## 💡 Простыми словами

### BRD — Бизнес-требования
**Что это:** Документ о том **ЗАЧЕМ** нужен проект с точки зрения бизнеса.

**Пример из интернет-магазина:**
```
Бизнес-проблема: Клиенты жалуются что не могут найти товары по категориям
Бизнес-цель: Увеличить конверсию в покупку на 15% за счёт улучшения поиска
Ожидаемый результат: +200 заказов в месяц, рост среднего чека
```

**Кто пишет:** Бизнес-аналитик, продукт-менеджер  
**Кто читает:** Заказчик, разработчики (для понимания контекста)

---

### SRS — Технические требования
**Что это:** Документ о том **ЧТО** должна делать система.

**Пример из интернет-магазина:**
```
Функциональное требование:
"Система должна позволять фильтровать товары по категориям, цене и рейтингу"

Критерии приёмки:
1. Пользователь может выбрать категорию "Электроника"
2. Список товаров обновляется мгновенно
3. Можно комбинировать несколько фильтров одновременно
```

**Кто пишет:** Системный аналитик  
**Кто читает:** Разработчики, тестировщики

---

### ГОСТ 19 и ГОСТ 34 — Российские стандарты

**ГОСТ 19 (ГОСТ Р ИСО/МЭК 12207)** — жизненный цикл ПО:
- Описывает этапы разработки от идеи до утилизации
- Не обязателен для следования, но даёт структуру

**ГОСТ 34 (ГОСТ Р 58596.1)** — стандарт для ТЗ:
- Устаревший документ из 2010 года
- Требует огромных объёмов текста
- В современной разработке практически не используется

## 🔍 Подробно

### Жизненный цикл требований

```
Бизнес-требования (BRD)
    ↓ (детализация)
Функциональные требования (SRS)
    ↓ (разбивка на задачи)
Технические задания для разработчиков
    ↓ (проверка)
Критерии приёмки и тест-кейсы
```

### Отличия BRD от SRS

| Аспект | BRD (Бизнес) | SRS (Техническое) |
|--------|--------------|-------------------|
| **Фокус** | Зачем нужен проект? | Что должна делать система? |
| **Язык** | Бизнес-термины, деньги, метрики | Технические термины, функции |
| **Читатели** | Заказчик, стейкхолдеры | Разработчики, тестировщики |
| **Детализация** | Высокоуровневые цели | Детальные критерии приёмки |

## 🛠 Пример из интернет-магазина

### BRD (Бизнес-требования):
```
Проблема: Клиенты уходят с сайта если не могут быстро найти товар
Цель: Увеличить конверсию в покупку на 15% за квартал
Метрики успеха:
- Среднее время поиска товара < 30 секунд
- Конверсия из поиска в покупку +15%
- Количество найденных товаров ↑20%
```

### SRS (Технические требования):
```
Функциональное требование FR-001: Поиск по каталогу

Описание: Система должна позволять искать товары по названию, категории и бренду.

Критерии приёмки:
- Поле поиска должно поддерживать ввод минимум 3 символов
- Результаты должны отображаться не позднее 500мс после ввода
- Поддерживается фильтрация по цене (от/до) и рейтингу
- При вводе "iphone" показывать только товары с этим словом в названии
```

## ⚖️ Плюсы/минусы

| ✅ Преимущества | ❌ Недостатки |
|-----------------|---------------|
| BRD даёт понимание бизнес-контекста | Может быть слишком абстрактным для разработчиков |
| SRS чётко определяет функционал | Может стать устаревшим при изменениях требований |
| ГОСТы дают структуру документации | Устаревшие стандарты не подходят для Agile/гибкой разработки |

---

## 🎯 Что важно запомнить аналитику

1. **BRD = бизнес-цели** (зачем делаем)  
2. **SRS = функционал** (что делает система)  
3. **ГОСТ 34 устарел** — в современной разработке используют User Story и Agile-документы  
4. **Важно связывать требования с метриками успеха**

---

## ❓ Типичные вопросы и ответы

**В: В чём разница между BRD и SRS?**  
О: BRD описывает бизнес-цели и почему нужен проект, SRS — детальные технические требования к функционалу системы.

**В: Нужно ли следовать ГОСТ 34 при написании ТЗ?**  
О: Нет, это устаревший стандарт из 2010 года с огромными требованиями к объёму текста. В современной разработке используют User Story и критерии приёмки в Agile-стиле.

**В: Кто читает BRD а кто SRS?**  
О: BRD читают бизнес-стейкхолдеры (заказчик, инвесторы), SRS — разработчики и тестировщики.

---

## 🛠 Практические вопросы для собеседования

**В: Приведите пример когда BRD был важнее SRS.**  
→ Ответ: Когда нужно обосновать бюджет проекта перед заказчиком — бизнес-метрики из BRD показывают ROI, а технические детали из SRS не интересны.

**В: Почему в Agile не используют большие документы типа SRS?**  
→ Ответ: Потому что требования меняются часто. Вместо статичного документа используют User Story с критериями приёмки которые уточняются в процессе разработки.

**В: Как связать бизнес-требования с техническими?**  
→ Ответ: Через карту требований (Traceability Matrix) — каждое бизнес-требование должно иметь соответствующие функциональные требования и тест-кейсы для проверки.

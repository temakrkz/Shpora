# 7.20. AS-IS и TO-BE

> 📌 **Короткий ответ**  
> **AS-IS** — как сейчас (текущее состояние системы/процесса). **TO-BE** — как должно быть (желаемое будущее состояние). Аналитик сравнивает их, чтобы понять, что именно нужно изменить.

---

## 💡 Простыми словами

Представьте ремонт квартиры:
- **AS-IS**: "У меня старая ванна, плитка отваливается, трубы протекают"
- **TO-BE**: "Хочу новую ванну, красивую плитку, без протечек"
- **Разница**: то, что нужно сделать (заменить ванну, переложить плитку)

Так и в разработке: сравниваем текущее состояние с желаемым, чтобы понять изменения.

---

## 🔍 Подробно

### Что такое AS-IS

**AS-IS** (как есть сейчас) — описание текущего состояния системы или процесса без изменений.

**Зачем нужно:**
- Понять проблемы и боли пользователей
- Выявить узкие места и неэффективности
- Зафиксировать существующие ограничения
- Не потерять контекст при изменениях

**Что описываем:**
- Текущие процессы (как сейчас работают)
- Существующую систему (функционал, ограничения)
- Данные (какие есть, где хранятся)
- Интеграции (с кем общается система)

---

### Что такое TO-BE

**TO-BE** (как должно быть) — описание желаемого будущего состояния после изменений.

**Зачем нужно:**
- Чётко сформулировать цель изменений
- Понять, что именно нужно реализовать
- Оценить effort и риски
- Договориться со стейкхолдерами

**Что описываем:**
- Новые процессы (как будут работать после изменений)
- Новый функционал (что добавим/изменим)
- Изменённые данные (новая структура, новые поля)
- Новые интеграции (с кем будем общаться)

---

## 📊 Сравнение AS-IS и TO-BE

| Аспект | AS-IS (как есть) | TO-BE (как должно быть) |
|--------|------------------|-------------------------|
| **Состояние** | Текущее, реальное | Желаемое, планируемое |
| **Проблемы** | Выявлены из анализа | Решены/улучшены |
| **Функционал** | То, что есть сейчас | Новые функции + улучшения |
| **Данные** | Существующая структура | Новая структура (если нужно) |
| **Интеграции** | Текущие партнёры | Новые/изменённые интеграции |
| **Цель** | Понять контекст | Описать результат изменений |

## 🛠 Пример из интернет-магазина

### Ситуация: Улучшение процесса оформления заказа

#### AS-IS (как сейчас работает)

```
Текущий процесс оформления заказа:
1. Пользователь добавляет товар в корзину
2. Переходит к оформлению
3. Вводит данные доставки вручную (каждый раз)
4. Выбирает способ оплаты
5. Подтверждает заказ
6. Менеджер проверяет заказ вручную через email
7. Создает доставку вручную из CRM

Проблемы:
- Пользователь каждый раз вводит одни и те же данные
- Менеджеры тратят время на ручную проверку
- Нет автоматического уведомления о статусе заказа
```

**Текущая система:**
- Корзина есть, но нет автозаполнения данных
- Данные доставки не сохраняются между сессиями
- Уведомления отправляются email менеджером вручную
- Статусы заказов хранятся в Excel

---

#### TO-BE (как должно работать)

```
Желаемый процесс оформления заказа:
1. Пользователь добавляет товар в корзину
2. Переходит к оформлению
3. Данные доставки автозаполняются из профиля пользователя
4. Выбор способа оплаты (карта, наличные, при получении)
5. Подтверждение заказа одной кнопкой
6. Автоматическое создание задачи для склада
7. Автоматические уведомления: заказ создан → в обработке → доставлен

Решения проблем:
- Автозаполнение данных из профиля
- Сохранение адреса в корзине
- Интеграция с CRM и складом
- Автоматические push/email уведомления
```

**Новая система:**
- Профиль пользователя с адресами доставки
- Корзина сохраняет данные между сессиями
- Интеграция с платежным шлюзом
- Интеграция со складской системой
- Система уведомлений (email/push/SMS)

---

#### Разница AS-IS vs TO-BE

| Что изменилось | AS-IS → TO-BE |
|----------------|---------------|
| **Данные доставки** | Вводятся вручную → автозаполняются из профиля |
| **Проверка заказа** | Ручная проверка менеджером → автоматическая валидация |
| **Уведомления** | Email от менеджера → автоматические push/email/SMS |
| **Статусы заказов** | Excel → автоматическое обновление в системе |
| **Интеграции** | Нет → CRM, склад, платежи, уведомления |

## 📝 Как документировать AS-IS и TO-BE

### Формат сравнения

Используйте таблицу или диаграммы "до/после":

```
┌─────────────────────┬──────────────────────┐
│   AS-IS (сейчас)    │     TO-BE (будет)    │
├─────────────────────┼──────────────────────┤
│ Ввод данных вручную │ Автозаполнение       │
│ Ручная проверка     │ Автоматическая       │
│ Email от менеджера  │ Push/SMS авто        │
│ Excel для статусов  │ База данных          │
└─────────────────────┴──────────────────────┘
```

### BPMN диаграммы

Рисуйте два процесса рядом:
- **Левая колонка**: AS-IS (текущий процесс с "болтами")
- **Правая колонка**: TO-BE (желаемый процесс)

Стрелками покажите переходы.

## ⚖️ Плюсы и минусы подхода

| Плюсы | Минусы |
|-------|--------|
| ✅ Понятно, что именно меняем | ❌ AS-IS может быть неполным (люди забывают нюансы) |
| ✅ Видны все изменения сразу | ❌ TO-BE — это идеализация, не всё реализуемо |
| ✅ Легче оценить effort (разница между ними) | ❌ Стейкхолдеры могут спорить про AS-IS ("а мы так всегда делали") |
| ✅ Снижает риски (понятен контекст) | ❌ Требует времени на анализ текущего состояния |

---

## 🎯 Что важно запомнить аналитику

1. **AS-IS — это факты, TO-BE — это мечты**  
   AS-IS описывает реальность (даже с проблемами), TO-BE — идеальное состояние

2. **Нужно документировать оба состояния**  
   Без AS-IS не понятно, что именно меняется; без TO-BE нет цели изменений

3. **Разница между ними = изменения**  
   Всё, что есть в TO-BE и нет в AS-IS — это новый функционал/изменения

4. **AS-IS помогает найти скрытые проблемы**  
   Часто пользователи не осознают неудобств до анализа текущего процесса

5. **TO-BE должен быть реалистичным**  
   Не все "мечты" из TO-BE можно реализовать сразу — приоритизируйте по MoSCoW

## ❓ Типичные вопросы и ответы

### Что такое AS-IS?
AS-IS (как есть сейчас) — описание текущего состояния системы или процесса без изменений. Помогает понять проблемы, боли пользователей и существующие ограничения.

### Что такое TO-BE?
TO-BE (как должно быть) — описание желаемого будущего состояния после изменений. Описывает цель проекта: новый функционал, процессы, данные.

### Зачем сравнивать AS-IS и TO-BE?
Чтобы понять, что именно нужно изменить. Разница между текущим и желаемым состоянием показывает объём работ, новые функции и улучшения.

### Как документировать AS-IS и TO-BE?
Используйте таблицы сравнения, BPMN-диаграммы (два процесса рядом), или текстовые описания с разделами "Текущее состояние" и "Желаемое состояние".

### Что делать, если стейкхолдеры спорят про AS-IS?
Проводите интервью и наблюдение за реальным процессом. Часто пользователи не осознают неудобств до анализа текущего состояния. Записывайте всё, что видите.

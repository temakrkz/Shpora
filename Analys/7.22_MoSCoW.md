# 7.22. MoSCoW (приоритизация требований)

> 📌 **Короткий ответ**  
> **MoSCoW** — метод приоритизации требований: **M**ust have (обязательно), **S**hould have (желательно), **C**ould have (можно), **W**on't have (не будет в этот раз). Помогает разделить фичи по важности и планировать релизы.

---

## 💡 Простыми словами

Представьте, что вы собираете новый телефон:
- **Must have**: без этого телефон не работает (экран, батарея)
- **Should have**: очень желательно (камера, память)
- **Could have**: было бы круто, но можно и без (чехол в комплекте)
- **Won't have**: точно не сейчас (поддержка 5G — будет в следующем поколении)

Так и с требованиями к продукту: разделяем на "нужно", "хорошо бы" и "будет потом".

---

## 🔍 Подробно

### Что такое MoSCoW

**MoSCoW** — это аббревиатура из 4 категорий приоритизации требований:
- **M**ust have — обязательно
- **S**hould have — желательно  
- **C**ould have — можно (если останется время)
- **W**on't have — не будет в этот релиз

---

### 1. Must Have (Обязательно) 🚨

**Что это:**  
Требования без которых продукт бесполезен или неработоспособен. MVP (минимально жизнеспособный продукт).

**Критерии:**
- Без этого пользователь не сможет достичь цели
- Это критично для бизнеса
- Нарушение = продукт сломан

**Примеры из интернет-магазина:**
```
Must Have:
- Пользователь может добавить товар в корзину
- Корзина сохраняется между сессиями
- Оформление заказа создаёт заказ в БД
- Оплата проходит через платёжный шлюз
- Заказ получает статус "Оплачен"
```

**Если нет Must Have:**  
Продукт не работает или пользователь не достигает цели.

---

### 2. Should Have (Желательно) ✨

**Что это:**  
Важные требования, которые сильно улучшают продукт, но без них он всё ещё usable.

**Критерии:**
- Значительно улучшает пользовательский опыт
- Важно для конкурентоспособности
- Можно отложить на следующий релиз без критичных последствий

**Примеры из интернет-магазина:**
```
Should Have:
- Фильтры по цене, бренду, категории
- Поиск с автодополнением
- Уведомления о статусе заказа (email)
- История заказов в личном кабинете
- Отзывы покупателей на карточке товара
```

**Если нет Should Have:**  
Продукт работает, но хуже, чем мог бы быть. Пользователи могут уйти к конкурентам.

---

### 3. Could Have (Можно) 💡

**Что это:**  
Нnice-to-have фичи — улучшают продукт, но не критичны. Реализуем, если останется время/ресурсы.

**Критерии:**
- Улучшает UX, но не обязательно
- "Было бы круто"
- Можно отложить или убрать без последствий

**Примеры из интернет-магазина:**
```
Could Have:
- Видео-обзоры товаров
- AR-просмотр товара в интерьере
- Персональные рекомендации на основе истории покупок
- Кэшбэк за покупки
- Интеграция с банковскими приложениями
```

**Если нет Could Have:**  
Продукт работает хорошо, просто не так "круто", как мог бы быть.

---

### 4. Won't Have (Не будет) 🚫

**Что это:**  
Требования, которые откладываются на следующий релиз или вообще не реализуются в текущем цикле.

**Важно:**  
Это **не значит "никогда"**. Просто "не сейчас". Нужно зафиксировать, когда будет рассмотрено снова.

**Примеры из интернет-магазина:**
```
Won't Have (в этом релизе):
- Поддержка криптовалют как способа оплаты
- Мультимедийный магазин (видео, музыка)
- AI-ассистент для подбора товаров
- Интеграция с телеграм-ботами

Но: "Будет рассмотрено в следующем квартале" или "Решение откладывается до 2025 года"
```

**Если нет Won't Have:**  
Команда теряет фокус и пытается сделать всё сразу.

---

## 📊 Сравнение категорий MoSCoW

| Категория | Приоритет | Без этого... | Пример из магазина |
|-----------|----------|--------------|---------------------|
| **Must** | 🔴 Критично | Продукт не работает/неusable | Корзина, оформление заказа |
| **Should** | 🟡 Важно | Продукт хуже, чем мог бы быть | Фильтры, уведомления |
| **Could** | 🟢 Желательно | Продукт хороший, но не крутой | Видео-обзоры, рекомендации |
| **Won't** | ⚪ Отложено | Ничего страшного | Криптовалюта, AI-ассистент |

## 🛠 Пример приоритизации для интернет-магазина

### Релиз 1: MVP (первый запуск)

**Must Have:**
```
✅ Регистрация/вход пользователя
✅ Просмотр каталога товаров
✅ Добавление товара в корзину
✅ Оформление заказа с данными доставки
✅ Оплата картой через платёжный шлюз
✅ Создание заказа в БД со статусом "Оплачен"
✅ Email-уведомление о создании заказа
```

**Should Have (если останется время):**
```
⭕ Фильтры по категории товаров
⭕ Поиск по названию товара
⭕ История заказов в личном кабинете
```

**Could Have:**
```
❌ Видео-обзоры товаров
❌ Персональные рекомендации
```

**Won't Have:**
```
🚫 Поддержка криптовалют
🚫 Мобильное приложение (будет позже)
🚫 AI-ассистент
```

---

### Релиз 2: Улучшения UX

**Must Have (новые критичные фичи):**
```
✅ Сохранение данных доставки в профиле пользователя
✅ Автозаполнение адреса при оформлении заказа
✅ Отслеживание статуса заказа на карте
```

**Should Have:**
```
✅ Фильтры по цене, бренду, наличию
✅ Поиск с автодополнением и подсказками
✅ Push-уведомления о статусе заказа
```

**Could Have:**
```
⭕ Видео-обзоры товаров на карточке
⭕ Персональные рекомендации "Вам может понравиться"
```

**Won't Have (переносим с Релиза 1):**
```
🚫 Поддержка криптовалют (решение откладывается)
🚫 AI-ассистент
```

---

### Релиз 3: Улучшения и новые фичи

**Must Have:**
```
✅ Возможность отмены заказа до доставки
✅ Возврат товара в течение 14 дней
```

**Should Have:**
```
✅ Отзывы покупателей на карточке товара
✅ Сравнение товаров (до/после, характеристики)
```

**Could Have:**
```
⭕ Видео-обзоры
⭕ Персональные рекомендации
```

## ⚖️ Плюсы и минусы MoSCoW

| Плюсы | Минусы |
|-------|--------|
| ✅ Простой и понятный метод | ❌ Субъективность (кто решает, что "Must"?) |
| ✅ Помогает планировать релизы | ❌ Риск перекладывания Must в Should ("а вдруг успеем") |
| ✅ Фокусирует команду на главном | ❌ Требует честности от стейкхолдеров |
| ✅ Гибкость (можно менять приоритеты) | ❌ Не учитывает effort (усилия на реализацию) |

---

## 🎯 Что важно запомнить аналитику

1. **Must Have = MVP**  
   Без Must продукт не работает или не достигает бизнес-цели

2. **Won't Have ≠ "Никогда"**  
   Это просто "не сейчас". Нужно зафиксировать, когда будет рассмотрено снова

3. **Приоритизация — это договорённость**  
   MoSCoW — это не мнение аналитика, а согласованное решение со стейкхолдерами

4. **Меняйте приоритеты при изменениях**  
   Если требования изменились — пересмотрите MoSCoW

5. **Учитывайте effort**  
   Иногда "Must" слишком большой — разбивайте на под-истории

## ❓ Типичные вопросы и ответы

### Что такое метод MoSCoW?
MoSCoW — это аббревиатура из 4 категорий приоритизации требований: Must have (обязательно), Should have (желательно), Could have (можно), Won't have (не будет в этот раз). Помогает разделить фичи по важности и планировать релизы.

### В чём разница между Must Have и Should Have?
Must Have — критично, без этого продукт не работает или не достигает цели. Should Have — важно для качества, но без него продукт всё ещё usable. Без Must = сломан; без Should = хуже, чем мог бы быть.

### Что значит Won't Have?
Won't Have — требование откладывается на следующий релиз или вообще не реализуется в текущем цикле. Это **не "никогда"**, просто "не сейчас". Нужно зафиксировать, когда будет рассмотрено снова.

### Кто принимает решение по MoSCoW?
Решение принимают совместно: аналитик предлагает приоритизацию, Product Owner согласовывает со стейкхолдерами (бизнес, разработчики, тесты). Это договорённость всех участников.

### Как часто пересматривать MoSCoW?
При каждом значимом изменении требований, перед планированием нового спринта/релиза, или если появляются новые инсайты от пользователей.

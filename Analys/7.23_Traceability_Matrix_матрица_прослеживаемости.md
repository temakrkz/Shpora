# 7.23 Traceability Matrix (Матрица прослеживаемости) — отслеживание требований

---

## 📌 Короткий ответ

> **Traceability Matrix** — это таблица, которая показывает связь между требованиями к системе и артефактами разработки (тест-кейсами, задачами в Jira, модулями кода). Она позволяет отследить: каждое требование проработано? Каждый тест-кейс проверяет какое-то требование?

---

## 💡 Простыми словами

### Аналогия с интернет-магазином

| Без Traceability Matrix | С Traceability Matrix |
|------------------------|----------------------|
| Есть 100 требований, но не понятно какие проработаны, а какие забыли. Есть 200 тест-кейсов, но не понятно что они проверяют. | Таблица показывает: требование №5 "Кнопка 'Купить' должна быть зелёной" → задача Jira-123 → тест-кейс TC-456. Всё прослеживается! |

### Что такое прослеживаемость?

> **Прослеживаемость** — это возможность отследить путь требования от бизнес-задачи до реализации и проверки.

**Пример:**
```
Бизнес-идея → Требование → Задача в Jira → Код → Тест-кейс → Отчёт о тестировании
```

---

## 🔍 Подробно

### Что такое Traceability Matrix?

Это **таблица**, где строки — это требования, а столбцы — артефакты разработки. Каждая ячейка показывает связь между ними.

**Варианты матриц:**

| Тип | Связывает | Когда используется |
|-----|-----------|-------------------|
| **RTM (Requirement Traceability Matrix)** | Требования ↔ Тест-кейсы | При тестировании, приёмке ПО |
| **Bi-directional RTM** | Требования ↔ Тесты + Код ↔ Тесты | Полный цикл разработки |
| **Linkage Matrix** | Бизнес-требования ↔ Технические требования ↔ Тесты | Для сложных систем с множеством уровней |

### Зачем нужна Traceability Matrix?

#### ✅ Основные цели:

1. **Убедиться, что все требования проработаны**  
   > Если в матрице есть требование без ссылки на тест — значит его не проверили!

2. **Избежать дублирования тестов**  
   > Два тест-кейса проверяют одно и то же требование → можно объединить или удалить один.

3. **Быстро найти, что сломалось при изменении**  
   > Изменили требование №10 → смотрим в матрицу: какие тесты его проверяют? Какие модули затронуты?

4. **Доказать соответствие требованиям**  
   > При аудите или сертификации нужно показать: "Вот требование, вот как мы его реализовали и протестировали".

5. **Управлять изменениями**  
   > Изменили требование → матрица показывает все затронутые артефакты (задачи, тесты).

---

### Как строится Traceability Matrix?

#### Шаг 1: Идентифицируем требования

Каждое требование получает уникальный ID:
```
REQ-001: Пользователь может зарегистрироваться через email
REQ-002: После регистрации пользователь видит личную страницу
REQ-003: Личная страница показывает историю заказов
```

#### Шаг 2: Создаём задачи в Jira

Каждое требование превращается в задачу(s):
```
JIRA-101: Реализовать форму регистрации (из REQ-001)
JIRA-102: Создать страницу личного кабинета (из REQ-002)
JIRA-103: Подключить историю заказов на странице (из REQ-003)
```

#### Шаг 3: Пишем тест-кейсы

Каждый тест проверяет требование:
```
TC-001: Проверка регистрации через email (проверяет REQ-001)
TC-002: Проверка отображения личного кабинета после регистрации (проверяет REQ-002)
TC-003: Проверка отображения истории заказов (проверяет REQ-003)
```

#### Шаг 4: Строим матрицу

| ID требования | Описание требования | Jira задача(s) | Тест-кейс(и) | Статус реализации |
|--------------|---------------------|---------------|-------------|-------------------|
| **REQ-001** | Регистрация через email | JIRA-101, JIRA-104 | TC-001, TC-005 | ✅ Протестировано |
| **REQ-002** | Личная страница после регистрации | JIRA-102 | TC-002, TC-006 | ✅ Протестировано |
| **REQ-003** | История заказов на странице | JIRA-103 | TC-003, TC-007 | ⏳ В работе |

### Пример из интернет-магазина

#### Ситуация: Интернет-магазин "Книжный мир"

**Требования:**
```
REQ-101: Пользователь может добавить книгу в корзину
REQ-102: Корзина сохраняется после выхода из системы
REQ-103: При оформлении заказа товары списываются со склада
REQ-104: Пользователь видит уведомление о статусе заказа
```

**Jira задачи:**
```
JIRA-201: Реализовать добавление в корзину (из REQ-101)
JIRA-202: Сохранять корзину в localStorage/БД (из REQ-102)
JIRA-203: Подключить API склада к оформлению заказа (из REQ-103)
JIRA-204: Отправлять email уведомления о статусе (из REQ-104)
```

**Тест-кейсы:**
```
TC-301: Добавление книги в корзину (проверяет REQ-101)
TC-302: Выход из системы → возврат к корзине (проверяет REQ-102)
TC-303: Оформление заказа → списание со склада (проверяет REQ-103)
TC-304: Получение email уведомления (проверяет REQ-104)
```

#### Матрица прослеживаемости:

| ID требования | Описание | Jira задача(s) | Тест-кейс(и) | Статус | Примечание |
|--------------|----------|---------------|-------------|--------|------------|
| **REQ-101** | Добавить книгу в корзину | JIRA-201 | TC-301, TC-305 | ✅ Passed | 2 теста: добавление и удаление из корзины |
| **REQ-102** | Корзина сохраняется после выхода | JIRA-202 | TC-302 | ✅ Passed | Используется localStorage |
| **REQ-103** | Списание со склада при заказе | JIRA-203 | TC-303, TC-306 | ⚠️ Partially | Тест проходит только для 95% товаров |
| **REQ-104** | Email уведомления о статусе | JIRA-204 | TC-304 | ❌ Failed | Не отправляется при ошибке API |

---

### Виды связей в матрице

#### 1. Один к одному (1:1)
```
Одно требование → Одна задача → Один тест
REQ-101 → JIRA-201 → TC-301
```
**Когда:** Простое, изолированное требование.

#### 2. Один ко многим (1:N)
```
Одно требование → Несколько задач → Несколько тестов
REQ-101 → JIRA-201, JIRA-205, JIRA-206 → TC-301, TC-305, TC-307
```
**Когда:** Требование реализуется несколькими модулями или тестируется с разных сторон.

#### 3. Многие к одному (N:1)
```
Несколько требований → Одна задача → Один тест
REQ-102, REQ-105, REQ-108 → JIRA-207 → TC-308
```
**Когда:** Несколько мелких требований объединены в одну большую задачу.

#### 4. Разрывы (нежелательны!)
```
Требование без задачи: ❌ REQ-109 (забыли проработать)
Задача без требования: ⚠️ JIRA-208 (техническое улучшение, не из требований)
Тест без требования: ❌ TC-309 (проверяет что-то лишнее)
```

### Автоматизация Traceability Matrix

#### В Jira:
Используйте **JQL** и **Link Types**:
```jql
# Найти все задачи, связанные с требованием
project = "IM" AND requirementId in ("REQ-101", "REQ-102")

# Показать статус реализации требования
requirementId = "REQ-103" ORDER BY status ASC
```

#### В тестировании:
- **TestRail**: связывает требования с тест-кейсами
- **Zephyr**: интеграция с Jira, автоматическая генерация матрицы
- **Xray**: встраивается в Jira, показывает покрытие требований

**Пример отчёта в TestRail:**
```
Requirement Coverage Report:
┌─────────────┬──────────────┬─────────────┐
│ Requirement │ Test Cases   │ Coverage    │
├─────────────┼──────────────┼─────────────┤
│ REQ-101     │ TC-301, 305  │ 100% ✅     │
│ REQ-102     │ TC-302       │ 100% ✅     │
│ REQ-103     │ TC-303, 306  │ 85% ⚠️      │
│ REQ-104     │ TC-304       │ 0% ❌       │
└─────────────┴──────────────┴─────────────┘
```

### Когда Traceability Matrix обязательна?

| Ситуация | Нужна ли матрица | Почему |
|----------|------------------|--------|
| **Крупный проект** | ✅ Обязательно | Много требований, нужно отслеживать всё |
| **Аудит/сертификация** | ✅ Обязательно | Нужно доказать соответствие требованиям |
| **Медицинское ПО / Финансы** | ✅ Обязательно | Требования регуляторов (FDA, PCI DSS) |
| **Небольшой стартап** | ⚠️ По желанию | Можно обойтись простыми задачами в Jira |
| **Критичное к безопасности ПО** | ✅ Обязательно | Нужно отследить каждое требование безопасности |

## ⚖️ Плюсы и минусы Traceability Matrix

### ✅ Плюсы

| Преимущество | Объяснение | Пример из жизни |
|-------------|------------|-----------------|
| **Видно, что забыли проработать** | Требование без задачи → сигнал к действию | REQ-110 "Уведомление о доставке" — нет задачи! Нужно создать JIRA-210 |
| **Быстро найти влияние изменений** | Изменил требование → матрица показывает все тесты | Изменил логику оплаты (REQ-105) → нужно перепроверить TC-310, TC-311, TC-312 |
| **Доказательство покрытия** | При аудите: "Вот 100 требований, у всех есть тесты" | Аудитор спрашивает: "А где тест для REQ-107?" → показываем TC-307 |
| **Управление техническим долгом** | Видно старые требования без актуальных тестов | REQ-050 от 2022 года — нет тестов, нужно добавить или удалить |
| **Количественные метрики** | Покрытие требований: "95% протестировано" | Отчёт для менеджера: "Из 100 требований 95 имеют тесты" |

### ❌ Минусы

| Недостаток | Объяснение | Пример из жизни |
|-----------|------------|-----------------|
| **Трудозатраты на ведение** | Нужно постоянно обновлять связи | Забыли добавить TC в матрицу → отчёт некорректен |
| **Может стать бюрократией** | Команда тратит время на заполнение вместо работы | Аналитик 2 часа заполняет матрицу вместо уточнения требований у заказчика |
| **Сложность для простых проектов** | Для MVP это избыточно | Интернет-магазин из 10 функций — матрица не нужна, достаточно задач в Jira |
| **Разрывы связей** | Забыли обновить при изменении требований | Изменил REQ-103 → забыл удалить старый тест TC-306 → путаница |
| **Не показывает качество** | Есть связь, но требование не протестировано правильно | В матрице: REQ-104 → TC-304, но тест написан неправильно и ничего не проверяет |

## 🎯 Что важно запомнить аналитику

### 1. Traceability Matrix — это инструмент контроля качества
> Она помогает убедиться, что **каждое требование проработано**, а **каждый тест проверяет конкретное требование**. Это не бюрократия, а способ избежать ошибок и дублирования.

### 2. Матрица должна быть актуальной
> Если изменили требование — обновите матрицу! Устаревшая матрица бесполезна и вводит в заблуждение.

**Как поддерживать актуальность:**
- При создании задачи → сразу свяжите с требованием
- При изменении требования → обновите все связи
- Перед релизом → проверьте покрытие всех требований

### 3. Не обязательно связывать всё 1:1
> Один тест может проверять несколько мелких требований, одна задача — несколько требований. Главное — прослеживаемость.

**Пример:**
```
REQ-201: Кнопка должна быть синей
REQ-202: При наведении кнопка увеличивается
→ JIRA-305 (реализовать кнопку)
→ TC-401 (проверить цвет и анимацию кнопки)
```

### 4. Используйте автоматизацию там, где это возможно
> В Jira с TestRail/Zephyr/Xray матрица генерируется автоматически. Это экономит время и снижает риск ошибок.

### 5. Матрица — не самоцель
> Цель — **качество ПО**, а не красивая таблица. Если команда тратит больше времени на ведение матрицы, чем на работу → упростите процесс или откажитесь от неё для небольших проектов.

## ❓ Типичные вопросы и ответы

### Вопрос 1: Что такое Traceability Matrix и зачем она нужна?

**Ответ:**
> **Traceability Matrix (RTM)** — это таблица, которая показывает связь между требованиями к системе и артефактами разработки (задачами в Jira, тест-кейсами). Она позволяет отследить: каждое требование проработано? Каждый тест проверяет какое-то требование?

**Зачем нужна:**
1. Убедиться, что все требования реализованы
2. Избежать дублирования тестов
3. Быстро найти влияние изменений
4. Доказать соответствие требованиям (при аудите)
5. Управлять изменениями

---

### Вопрос 2: Как строится Traceability Matrix для интернет-магазина?

**Ответ:**
1. **Идентифицируем требования**: REQ-001, REQ-002...
2. **Создаём задачи в Jira**: JIRA-101 (из REQ-001), JIRA-102 (из REQ-002)...
3. **Пишем тест-кейсы**: TC-001 (проверяет REQ-001), TC-002 (проверяет REQ-002)...
4. **Строим таблицу** со связями:

| ID требования | Описание | Jira задача(s) | Тест-кейс(и) | Статус |
|--------------|----------|---------------|-------------|--------|
| REQ-001 | Регистрация | JIRA-101, JIRA-104 | TC-001, TC-005 | ✅ Passed |

---

### Вопрос 3: Что делать, если требование не протестировано?

**Ответ:**
> В матрице будет видно: требование без тест-кейса. Действия:
1. **Проверьте**: действительно ли требование реализовано? Если да — создайте тест-кейс.
2. **Уточните**: возможно, требование неактуально → удалите его или пометьте как "отменено".
3. **Обновите матрицу**: добавьте новый тест и обновите статус.

**Пример:**
```
REQ-105: Уведомление о доставке
JIRA-205: Реализовать email уведомления ✅
TC-305: Проверка отправки email ❌ (нет!)

Действие: Создать TC-306, проверить отправку, обновить матрицу.
```

---

### Вопрос 4: Как автоматизировать Traceability Matrix в Jira?

**Ответ:**
Используйте плагины для интеграции с тестированием:

1. **Xray**: Встраивается в Jira, автоматически связывает требования и тесты
2. **Zephyr Scale/Cloud**: Генерирует отчёты по покрытию требований
3. **TestRail + Jira**: Экспорт матрицы из TestRail

**Пример Xray:**
```jql
# Найти все требования без тестов
requirementStatus = "Open" AND testCoverage = 0%

# Показать покрытие требований
project = "IM" ORDER BY requirementCoverage ASC
```

### Вопрос 5: Когда Traceability Matrix обязательна, а когда не нужна?

**Ответ:**

| Ситуация | Нужна ли матрица | Почему |
|----------|------------------|--------|
| Крупный проект с сотнями требований | ✅ Обязательно | Без неё невозможно отследить всё |
| Аудит/сертификация (ISO, FDA) | ✅ Обязательно | Требование регуляторов |
| Финансовое ПО / Медицина | ✅ Обязательно | Критично к соответствию требованиям |
| Небольшой стартап (10-20 функций) | ⚠️ По желанию | Можно обойтись задачами в Jira без матрицы |
| MVP для проверки гипотезы | ❌ Не нужна | Главное — быстро, а не документация |

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Бизнес-заказчик просит добавить новую функцию "Быстрый просмотр товара". Как вы отразите это в Traceability Matrix?

**Ответ:**

**Шаг 1: Создаю требование**
```
REQ-206: Пользователь может открыть карточку товара без добавления в корзину (быстрый просмотр)
```

**Шаг 2: Создаю задачу(и) в Jira**
```
JIRA-306: Реализовать модальное окно быстрого просмотра
JIRA-307: Подключить API товаров к модальному окну
JIRA-308: Добавить кнопку "Добавить в корзину" в модальном окне
```

**Шаг 3: Пишу тест-кейсы**
```
TC-406: Открытие модального окна быстрого просмотра (проверяет REQ-206)
TC-407: Закрытие модального окна (проверяет REQ-206)
TC-408: Добавление товара из быстрого просмотра в корзину (связано с REQ-101)
```

**Шаг 4: Обновляю матрицу**

| ID требования | Описание | Jira задача(s) | Тест-кейс(и) | Статус |
|--------------|----------|---------------|-------------|--------|
| **REQ-206** ⭐ | Быстрый просмотр товара | JIRA-306, JIRA-307 | TC-406, TC-407 | ⏳ В работе |

### Вопрос 2: Вы обнаружили в матрице требование без задачи. Что делаете?

**Ответ:**

**Действия:**
1. **Проверяю статус требования**: актуально ли оно? Возможно, заказчик отменил его.
2. **Уточняю у бизнес-заказчика**: действительно ли эта функция нужна?
3. **Если требование актуально → создаю задачу в Jira** и связываю с требованием.
4. **Обновляю матрицу**: добавляю новую задачу и меняю статус на "В работе".

**Пример:**
```
В матрице вижу: REQ-150 "Фильтр по цвету" → нет задачи в Jira

Действия:
1. Спрашиваю у заказчика: "А нужен ли фильтр по цвету?"
2. Заказчик говорит: "Да, нужно!"
3. Создаю JIRA-400: Реализовать фильтр по цвету (из REQ-150)
4. Обновляю матрицу: добавляю JIRA-400 и меняю статус на "В работе"
```

### Вопрос 3: Как вы объясните разработчику, почему нужно обновлять Traceability Matrix при изменении требований?

**Ответ:**

Я бы сказал:

> "Traceability Matrix — это карта изменений. Когда мы меняем требование, матрица показывает нам **все затронутые артефакты**:
> - Какие задачи нужно переделать?
> - Какие тесты нужно перепроверить?
> - Где ещё могут быть последствия?
> 
> Если не обновлять матрицу — мы можем забыть про некоторые тесты или создать дубли. Это приведёт к ошибкам и доработкам после релиза."

**Пример:**
```
Изменили требование:
Было: REQ-103 "При заказе списываются все товары со склада"
Стало: REQ-103 "При заказе списываются только доступные товары (не больше остатка)"

Матрица показывает:
→ JIRA-203 нужно переделать (логика изменилась)
→ TC-303 нужно обновить (проверять не все товары, а доступные)
→ TC-306 тоже затронут (проверка остатков)

Без обновления матрицы мы могли бы забыть про TC-306 и найти баг после релиза!
```

### Вопрос 4: Как автоматизировать Traceability Matrix для большого проекта?

**Ответ:**

Для большого проекта с сотнями требований ручное ведение — это антипаттерн. Использую **автоматизацию**:

#### Инструменты:

1. **Jira + Xray/Zephyr**
   - Требования и тесты создаются в Jira
   - Связи формируются автоматически через Link Types
   - Отчёты генерируются по запросу

2. **TestRail + Jira API**
   - Тест-кейсы в TestRail
   - При создании задачи в Jira → автоматическая связь с требованием
   - Экспорт матрицы один раз перед релизом

3. **Custom solution (если нужно)**
   - Скрипт, который парсит JQL запросы и формирует таблицу
   - Запускается автоматически перед релизом

**Пример Xray:**
```jql
# Один запрос показывает всё покрытие:
project = "IM" AND requirementStatus != "Done" ORDER BY testCoverage ASC
```

### Вопрос 5: Что делать, если тест проверяет несколько требований? Как отразить это в матрице?

**Ответ:**

Это нормальная ситуация! В матрице можно указывать **несколько тестов для одного требования** или **один тест для нескольких требований**.

**Вариант 1: Один тест → несколько требований (рекомендуется)**
```
| ID требования | Описание | Jira задача(s) | Тест-кейс(и) | Статус |
|--------------|----------|---------------|-------------|--------|
| REQ-201 | Кнопка синяя | JIRA-305 | TC-401 | ✅ Passed |
| REQ-202 | При наведении увеличивается | JIRA-305 | TC-401 | ✅ Passed |
```

**Вариант 2: Один требование → несколько тестов (если тестируем с разных сторон)**
```
| ID требования | Описание | Jira задача(s) | Тест-кейс(и) | Статус |
|--------------|----------|---------------|-------------|--------|
| REQ-101 | Добавить в корзину | JIRA-201 | TC-301 (UI), TC-305 (API), TC-307 (БД) | ✅ Passed |

**Важно:** В ячейке можно указывать несколько тестов через запятую или использовать формат массива:
```
TC-301, TC-305, TC-307
или
[TC-301, TC-305, TC-307]
```

### Вопрос 6: Как Traceability Matrix помогает при аудите?

**Ответ:**

При аудите (особенно для критичных систем — медицина, финансы) нужно **доказать соответствие требованиям**. Матрица — идеальный инструмент:

**Что показывает аудитору:**
1. **Все требования реализованы**: "Вот 100 требований, у каждого есть задача и тест"
2. **Нет дублирования**: "Каждый тест проверяет конкретное требование, нет лишнего"
3. **Изменения отслежены**: "Когда меняли REQ-50, мы перепроверили TC-101, TC-102, TC-103"

**Пример отчёта для аудитора:**
```
Requirement Coverage Report:
┌─────────────┬──────────────┬─────────────┬──────────────┐
│ Requirement │ Description  │ Test Cases  │ Coverage     │
├─────────────┼──────────────┼─────────────┤              │
│ REQ-001     | Регистрация  │ TC-001      │ ✅ 100%      │
│ REQ-002     | Личный кабинет│TC-002,006   │ ✅ 100%      │
│ ...         │ ...          │ ...         │ ...          │
│ REQ-100     | Уведомления  │ TC-350      │ ✅ 100%      │
└─────────────┴──────────────┴─────────────┴──────────────┘

Summary:
Total Requirements: 100
Covered: 100 (100%)
Not Covered: 0
```

### Вопрос 7: Какие метрики можно вывести из Traceability Matrix?

**Ответ:**

Из матрицы можно получить несколько полезных метрик:

#### 1. **Coverage Requirements** (покрытие требований)
> Сколько процентов требований имеют тесты?
```
Total Requirements: 100
With Tests: 95
Coverage: 95% ✅
```

#### 2. **Requirements without Tasks** (требования без задач)
> Какие требования забыли проработать?
```
Total Requirements: 100
Without Tasks: 3 ❌
→ REQ-107, REQ-108, REQ-109
```

#### 3. **Duplicate Tests** (дубликаты тестов)
> Сколько тестов проверяют одно и то же требование?
```
TC-401 и TC-402 оба проверяют REQ-201 → дублирование! Нужно объединить или удалить один.
```

#### 4. **Stale Requirements** (устаревшие требования)
> Требования без задач уже давно:
```
REQ-050: Последняя задача была в 2022 году → возможно, требование отменено?
```

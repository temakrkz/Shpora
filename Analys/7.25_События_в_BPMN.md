# 7.25 События в BPMN — триггеры и точки остановки процессов

---

## 📌 Короткий ответ

> **События в BPMN** — это элементы, которые запускают процесс или останавливают его. Есть три типа: **начало** (триггер), **промежуточное** (внутренние события) и **конечное** (завершение). События отвечают на вопрос "Когда происходит действие?".

---

## 💡 Простыми словами

### Аналогия с интернет-магазином

| Тип события | Как работает | Пример из жизни |
|-------------|--------------|-----------------|
| **Начало** | Запускает процесс | Пользователь оформил заказ → начинается обработка |
| **Промежуточное** | Срабатывает внутри процесса | Пришло уведомление от службы доставки → обновить статус |
| **Конечное** | Останавливает процесс | Заказ доставлен → процесс завершен |

### Что такое событие в BPMN?

> **Событие** — это что-то, что происходит в процессе. Оно может:
> - **Запустить** процесс (начальное событие)
> - **Изменить ход** процесса (промежуточное событие)
> - **Завершить** процесс (конечное событие)

---

## 🔍 Подробно

### Три типа событий в BPMN

#### 1. Начальные события (Start Events)

Запускают процесс. Процесс начинается только после срабатывания начального события.

**Виды:**
- **Черная точка (•)** — простое событие, запускается по таймингу или вручную
- **Желтая точка со стрелкой (⬡→)** — таймер (по расписанию)
- **Зелёный круг с волной (🌊)** — сообщение (пришло уведомление)
- **Красная точка с крестом (❌)** — исключение (ошибка, отмена)

**Пример из интернет-магазина:**

```
┌─────────────────────────────┐
│  Начальное событие:          │
│  • Пользователь оформил заказ│
└───────────────────┬──────────┘
                   ▼
         [Начинается обработка заказа]
```

**Детальные примеры:**

| Тип | Визуал | Пример из магазина | Когда используется |
|-----|--------|-------------------|-------------------|
| **Простое** | Черная точка (•) | Пользователь нажал "Оформить заказ" | Ручное действие пользователя |
| **Таймер** | Желтая точка со стрелкой (⬡→) | Ежедневно в 09:00 → проверка заказов | Автоматическое расписание |
| **Сообщение** | Зелёный круг с волной (🌊) | Пришло уведомление от службы доставки | Внешнее событие (сообщение) |
| **Исключение** | Красная точка с крестом (❌) | Пользователь отменил заказ в корзине | Ошибка или отмена |

---

#### 2. Промежуточные события (Intermediate Events)

Срабатывают внутри процесса и могут изменить его ход.

**Виды:**
- **Таймер** — событие по времени
- **Сообщение** — пришло сообщение извне
- **Исключение/Ошибка** — что-то пошло не так
- **Медиатор (Message Intermediate Catch)** — ждёт сообщения
- **Сигнал (Signal Intermediate Catch)** — реагирует на сигнал

**Примеры из интернет-магазина:**

##### Пример 1: Таймерное событие
```
Заказ создан → Параллельный шлюз:
├─ Отправить email клиенту
└─ Создать чек в БД

→ Промежуточное таймерное событие (через 24 часа):
   ├─ Если заказ не оплачен → отменить
   └─ Если оплачен → отправить на склад
```

##### Пример 2: Событие сообщения
```
Заказ создан → Ждём оплаты... 🌊

→ Промежуточное событие "Сообщение":
   ├─ Пришло сообщение "Оплата прошла" → отправка на склад
   └─ Не пришло в течение 3 дней → отмена заказа
```

##### Пример 3: Событие исключения
```
Проверка наличия товара... ❌

→ Промежуточное событие "Исключение":
   ├─ Товар есть → продолжить процесс
   └─ Товара нет → уведомить пользователя, предложить аналоги
```

---

#### 3. Конечные события (End Events)

Завершают процесс. После конечного события процесс больше не продолжается.

**Виды:**
- **Круг с галочкой (✓)** — нормальное завершение
- **Круг с крестом (❌)** — завершение по ошибке/исключению
- **Многоточие (...)** — завершение без результата

**Примеры из интернет-магазина:**

```
Заказ доставлен ✓ → Конечное событие "Успех"
→ Процесс завершен, заказ в статусе "Доставлен"

Ошибка при оплате ❌ → Конечное событие "Исключение"
→ Процесс завершен, заказ отменён с ошибкой
```

**Важные нюансы:**
- После конечного события процесс **не продолжается**
- Можно иметь несколько конечных событий (успех и ошибка)
- Конечное событие может возвращать результат (данные о завершении)

### События в контексте процессов

#### Как события взаимодействуют с другими элементами BPMN:

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Начало     │───►│   Действие   │───►│    Шлюз     │
│ (черная     │     │             │     │             │
│ точка)      │     │             │     │             │
└─────────────┘     └─────────────┘     └──────┬──────┘
                                               ├─ Путь A
                                               ├─ Путь B
                                               └─ Слияние
```

**Событие запускает процесс → Действия выполняются → Результат завершает процесс.**

---

### Специальные события BPMN

#### 1. События-компенсация (Compensation Event)

Используются для отката изменений при ошибке.

**Пример:**
```
Заказ создан → Товар списан со склада ✓

→ Ошибка оплаты ❌ → Компенсационное событие:
   ├─ Вернуть товар на склад
   └─ Отменить заказ
```

#### 2. События-границы (Boundary Events)

Привязаны к конкретному действию и могут прервать его выполнение.

**Пример:**
```
Проверка наличия товара → Граничное событие "Товар есть?"
├─ Да → Продолжить процесс
└─ Нет → Отменить заказ, предложить аналоги
```

### Автоматизация событий в BPMN

#### Как события превращаются в код:

**Пример автоматизации (Camunda/Activiti):**

```java
// Начальное событие "Пользователь оформил заказ"
@StartEvent(id="orderCreated")
public void onOrderCreated(Order order) {
    // Запуск процесса обработки заказа
}

// Промежуточное событие "Таймер — проверка через 24 часа"
@IntermediateCatchEvent(
    condition = "${TODAY == order.createdDate + 1 day}",
    eventDefinitionType = "timer"
)
public void checkOrderStatus(Order order) {
    if (order.isPaid()) {
        sendToWarehouse(order);
    } else {
        cancelOrder(order);
    }
}

// Промежуточное событие "Сообщение — оплата прошла"
@IntermediateCatchEvent(
    condition = "${payment.status == 'PAID'}",
    eventDefinitionType = "message"
)
public void onPaymentReceived(Payment payment) {
    sendToWarehouse(payment.getOrder());
}

// Конечное событие "Заказ доставлен"
@endEvent(id="orderDelivered")
public void orderDelivered(Order order) {
    // Логирование успешного завершения
}
```

### Антипаттерны с событиями

#### ❌ Ошибка 1: Отсутствие начального события

**Плохо:** Процесс начинается без явного триггера.

```
[Начало процесса] → Действие 1 → Действие 2
→ Когда процесс запускается? ❓
```

**Хорошо:** Явное начальное событие с понятным условием.

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Пользователь│───►│  Создать    │───►│  Обработать  │
│ оформил заказ│    │   заказ     │    │   заказ      │
└─────────────┘     └─────────────┘     └─────────────┘
```

---

#### ❌ Ошибка 2: Промежуточное событие без условия

**Плохо:** Событие срабатывает всегда, не проверяя условие.

```
Заказ создан → Промежуточное событие "Проверить оплату"
→ Всегда идёт по одному пути! ❌ (баг!)
```

**Хорошо:** Добавить условие или использовать шлюз.

```
Заказ создан → Промежуточное событие "Проверить оплату"
├─ Оплачено → Отправить на склад
└─ Не оплачено → Уведомить пользователя
```

---

#### ❌ Ошибка 3: Конечное событие без возврата результата

**Плохо:** Процесс завершается, но результат не сохраняется.

```
Заказ доставлен ✓ → Конечное событие
→ Где информация о доставке? ❓
```

**Хорошо:** Добавить выходной поток с результатом.

```
Заказ доставлен ✓ → Конечное событие + Выходные данные:
   ├─ Статус заказа: "Доставлен"
   ├─ Дата доставки: 2026-09-05
   └─ Курьер: Иван Иванов
```

## ⚖️ Плюсы и минусы событий BPMN

### ✅ Плюсы

| Преимущество | Объяснение | Пример из жизни |
|-------------|------------|-----------------|
| **Чёткие триггеры** | Понятно, когда процесс начинается/завершается | "Заказ создан" → начинается обработка |
| **Реактивность** | Процесс реагирует на внешние события (сообщения, ошибки) | Пришло уведомление от доставки → обновить статус |
| **Гибкость** | Можно менять ход процесса в зависимости от событий | Ошибка оплаты → отмена заказа автоматически |
| **Автоматизация** | События можно связывать с кодом для автоматического выполнения | Таймерное событие → ежедневная проверка заказов |

### ❌ Минусы

| Недостаток | Объяснение | Пример из жизни |
|-----------|------------|-----------------|
| **Сложность отладки** | Много событий → трудно понять, где процесс завис | "Процесс остановился на таймере — почему?" |
| **Риск дублирования** | Несколько событий могут сработать одновременно | Таймер + сообщение пришли в одно время → конфликт логики |
| **Зависимость от внешних систем** | Если внешнее событие не приходит, процесс зависнет | Не пришло уведомление от доставки → заказ висит вечно |

## 🎯 Что важно запомнить аналитику

### 1. Событие — это "когда", а не "что"
> **Событие** отвечает на вопрос **"Когда происходит действие?"**, а не **"Что делать?"**. Действия — это отдельные элементы BPMN (задачи, шлюзы).

**Пример:**
- **Событие**: "Пришло сообщение от службы доставки" (когда?)
- **Действие**: "Обновить статус заказа на 'В пути'" (что делать?)

---

### 2. Начальное событие — точка входа в процесс
> Без начального события процесс не запустится! Всегда определяйте чёткий триггер начала процесса.

**Хорошо:**
```
┌─────────────┐     ┌─────────────┐
│ Пользователь│───►│  Создать    │
│ оформил заказ│    │   заказ     │
└─────────────┘     └─────────────┘
```

**Плохо:**
```
[Начало процесса] → Создать заказ
→ Когда процесс запустится? ❓
```

---

### 3. Промежуточные события — точки реакции внутри процесса
> Они позволяют процессу реагировать на изменения во время выполнения. Используйте их для:
- Таймеров (проверка по расписанию)
- Сообщений (реакция на внешние уведомления)
- Ошибок (обработка исключений)

---

### 4. Конечные события — точки выхода из процесса
> После конечного события процесс **не продолжается**. Можно иметь несколько конечных событий для разных сценариев (успех, ошибка).

**Пример:**
```
Заказ доставлен ✓ → Успешное завершение
Ошибка при оплате ❌ → Завершение с ошибкой
```

---

### 5. Граничные события — страховка от ошибок
> Присоединяйте граничные события к задачам, которые могут завершиться неудачно. Это позволяет обработать ошибку и продолжить процесс альтернативным путём.

**Пример:**
```
Проверка наличия товара → Граничное событие "Товар есть?"
├─ Да → Продолжить процесс
└─ Нет → Отменить заказ, предложить аналоги
```

## ❓ Типичные вопросы и ответы

### Вопрос 1: Что такое начальное событие в BPMN?

**Ответ:**
> **Начальное событие** — это элемент BPMN, который запускает процесс. Процесс начинается только после срабатывания начального события. Оно отвечает на вопрос "Когда начинается процесс?".

**Виды начальных событий:**
1. **Простое (черная точка)** — запускается вручную или по расписанию
2. **Таймерное (желтая точка со стрелкой)** — запускается по времени (например, ежедневно в 09:00)
3. **Сообщение (зелёный круг с волной)** — запускается при получении сообщения извне
4. **Исключение (красная точка с крестом)** — запускается при ошибке или отмене

**Пример из интернет-магазина:**
```
┌─────────────┐     ┌─────────────┐
│ Пользователь│───►│  Создать    │
│ оформил заказ│    │   заказ     │
└─────────────┘     └─────────────┘

Начальное событие: "Пользователь нажал 'Оформить заказ'"
```

---

### Вопрос 2: Когда использовать промежуточное событие?

**Ответ:**

Используйте **промежуточные события**, когда процесс должен реагировать на что-то во время выполнения.

**Примеры использования:**
1. **Таймер**: "Проверить заказ через 24 часа"
2. **Сообщение**: "Пришло уведомление от службы доставки — обновить статус"
3. **Исключение**: "Оплата не прошла — отменить заказ"

**Пример из магазина:**
```
Заказ создан → Ждём оплаты... 🌊 (промежуточное событие)

→ Пришло сообщение "Оплата прошла" → Отправка на склад
→ Не пришло в течение 3 дней → Отмена заказа
```

---

### Вопрос 3: В чём разница между промежуточным и граничным событием?

**Ответ:**

| Характеристика | Промежуточное событие | Граничное событие |
|----------------|----------------------|-------------------|
| **Расположение** | На линии процесса | На выходе из задачи |
| **Функция** | Меняет ход всего процесса | Может прервать конкретную задачу |
| **Пример** | Таймер "через 24 часа" | "Товар есть?" после проверки наличия |

**Визуально:**
```
Промежуточное:
Заказ создан → 🌊 (промежуточное) → Проверка оплаты

Граничное:
Проверка товара ──┐
                  ├─ Граничное событие "Товар есть?"
                  │  ├─ Да → Продолжить
                  └─ Нет → Отмена
```

---

### Вопрос 4: Как конечное событие влияет на процесс?

**Ответ:**

**Конечное событие завершает процесс**. После него процесс больше не продолжается. Можно иметь несколько конечных событий для разных сценариев (успех, ошибка).

**Примеры:**
```
Заказ доставлен ✓ → Конечное событие "Успех" → Процесс завершен

Ошибка при оплате ❌ → Конечное событие "Исключение" → Процесс завершен
```

**Важно:** После конечного события можно:
- Сохранить результат (статус, данные)
- Запустить новый процесс (если нужно)
- Но старый процесс **не продолжается**!

---

### Вопрос 5: Как автоматизировать событие в BPMN?

**Ответ:**

События в BPMN можно связывать с кодом через инструменты вроде Camunda, Activiti или Bizagi.

**Пример (Camunda):**

```java
// Начальное событие "Пользователь оформил заказ"
@StartEvent(id="orderCreated")
public void onOrderCreated(Order order) {
    // Запуск процесса обработки заказа
}

// Промежуточное таймерное событие "Проверка через 24 часа"
@IntermediateCatchEvent(
    condition = "${TODAY == order.createdDate + 1 day}",
    eventDefinitionType = "timer"
)
public void checkOrderStatus(Order order) {
    if (order.isPaid()) {
        sendToWarehouse(order);
    } else {
        cancelOrder(order);
    }
}

// Конечное событие "Заказ доставлен"
@endEvent(id="orderDelivered")
public void orderDelivered(Order order) {
    // Логирование успешного завершения
}
```

## 🛠 Практические вопросы для собеседования

### Вопрос 1: Бизнес-заказчик просит "Проверять заказы ежедневно в 09:00". Как это отразить в BPMN?

**Ответ:**

Использую **промежуточное таймерное событие**.

**Логика процесса:**
```
Заказ создан → [Действия по обработке] → Промежуточное таймерное событие (каждый день в 09:00)
├─ Если заказ оплачен и не доставлен → Отправить на доставку
└─ Если заказ не оплачен более 3 дней → Отменить заказ
```

**BPMN диаграмма:**
```
┌─────────────┐     ┌─────────────┐     ┌──────────────────────────┐
│ Пользователь│───►│ Создать     │───►│ Промежуточное таймерное   │
│ оформил заказ│    │   заказ     │    │ событие (каждый день 09:00)│
└─────────────┘     └─────────────┘     └──────────────┬──────────┘
                                                       ├─ Оплачен → Доставка
                                                       └─ Не оплачен → Отмена
```

**Почему таймерное событие:**
- Процесс должен проверять заказы **ежедневно** в фиксированное время
- Это не срабатывает один раз, а повторяется по расписанию
- Нужно проверить статус каждого незавершенного заказа

### Вопрос 2: Заказчик просит "Если пришло уведомление от службы доставки — обновить статус". Какой тип события?

**Ответ:**

Использую **промежуточное событие "Сообщение" (Message Intermediate Event)**.

**Логика процесса:**
```
Заказ создан → Ждём уведомления... 🌊 (промежуточное событие)

→ Пришло сообщение от службы доставки:
   ├─ Статус: "В пути" → Обновить статус заказа на "В пути"
   └─ Статус: "Доставлен" → Отправить клиенту уведомление, завершить процесс
```

**BPMN диаграмма:**
```
┌─────────────┐     ┌─────────────┐     ┌──────────────────────────┐
│ Пользователь│───►│ Создать     │───►│ Промежуточное событие      │
│ оформил заказ│    │   заказ     │    │ "Сообщение" от доставки   │
└─────────────┘     └─────────────┘     └──────────────┬──────────┘
                                                       ├─ В пути → Обновить статус
                                                       └─ Доставлен → Уведомить клиента, завершить
```

**Почему событие "Сообщение":**
- Процесс должен **реагировать на внешнее событие** (уведомление от службы доставки)
- Это не таймер, а реакция на входящее сообщение
- Нужно обновить статус заказа только после получения уведомления

### Вопрос 3: Как обработать ошибку "Товара нет на складе"? Какой тип события?

**Ответ:**

Использую **граничное событие исключения (Exception Boundary Event)**.

**Логика процесса:**
```
Проверка наличия товара → Граничное событие "Товар есть?"
├─ Да → Продолжить процесс, отправить заказ на склад
└─ Нет → Отменить заказ, предложить аналоги пользователю
```

**BPMN диаграмма:**
```
┌─────────────┐     ┌─────────────┐
│ Создать     │───►│ Проверка    │───┬─ Да → Продолжить процесс
│   заказ     │    │  наличия    │   │
└─────────────┘     └──────┬──────┘   │
                           │          │
                    Граничное событие "Товар есть?"
                           │
                           ├─ Нет → Отменить заказ, предложить аналоги
```

**Почему граничное событие:**
- Ошибка может произойти **в процессе выполнения задачи** (проверка наличия)
- Нужно обработать ошибку и продолжить процесс альтернативным путём
- Граничное событие привязано к конкретной задаче, а не ко всему процессу

### Вопрос 4: Как вы объясните заказчику разницу между начальным и промежуточным событием?

**Ответ:**

Я бы сказал:

> "Представьте, что мы в магазине:
> 
> **Начальное событие** — это как открытие магазина. Процесс начинается только когда магазин открыт (например, пользователь нажал 'Оформить заказ').
> 
> **Промежуточное событие** — это как звонок от курьера во время работы магазина. Магазин уже работает, но что-то произошло (пришло уведомление), и нам нужно реагировать."

**Примеры:**
```
Начальное событие: "Пользователь оформил заказ" → Начинаем обработку

Промежуточное событие: 
→ "Пришло сообщение от доставки" → Обновить статус
→ "Таймер сработал через 24 часа" → Проверить заказ
→ "Ошибка оплаты" → Отменить заказ
```

### Вопрос 5: Как вы тестируете BPMN процесс с событиями?

**Ответ:**

Тестирую **все возможные пути** через события:

#### Для начальных событий:
1. Проверяю, что процесс запускается только после срабатывания начального события
2. Тестирую разные типы начальных событий (простое, таймерное, сообщение)

**Пример:**
```
Начальное событие "Пользователь оформил заказ":
✓ Тест 1: Пользователь нажал кнопку → процесс запустился
✓ Тест 2: Таймер сработал в 09:00 → процесс запустился автоматически
✓ Тест 3: Пришло сообщение от API → процесс запустился через webhook
```

#### Для промежуточных событий:
1. Проверяю, что событие срабатывает при правильном условии
2. Проверяю все возможные пути после события (успех/ошибка)
3. Проверяю таймеры — срабатывают ли они в нужное время

**Пример:**
```
Промежуточное событие "Проверить через 24 часа":
✓ Тест 1: Заказ создан в 09:00 → проверка в 09:00 следующего дня
✓ Тест 2: Заказ оплачен → идёт по пути "Отправка на склад"
✓ Тест 3: Заказ не оплачен → идёт по пути "Отмена"
```

#### Для конечных событий:
1. Проверяю, что процесс завершается после каждого возможного конечного события
2. Проверяю, что результат сохраняется (статус заказа и т.д.)
3. Проверяю, что процесс не продолжается после завершения

**Пример:**
```
Конечное событие "Заказ доставлен":
✓ Тест 1: Процесс завершается
✓ Тест 2: Статус заказа обновлён на "Доставлен"
✓ Тест 3: Клиент получил уведомление
✓ Тест 4: Процесс не продолжается дальше
```

### Вопрос 6: Как автоматизировать проверку заказов по таймеру?

**Ответ:**

Использую **промежуточное таймерное событие** с расписанием.

**BPMN диаграмма:**
```
┌─────────────┐     ┌─────────────┐     ┌──────────────────────────┐
│ Пользователь│───►│ Создать     │───►│ Промежуточное таймерное   │
│ оформил заказ│    │   заказ     │    │ событие (каждый день 09:00)│
└─────────────┘     └─────────────┘     └──────────────┬──────────┘
                                                       ├─ Оплачен → Отправить на доставку
                                                       └─ Не оплачен → Отменить заказ
```

**Автоматизация (Camunda):**

```java
// Промежуточное таймерное событие "Проверка заказов каждый день в 09:00"
@IntermediateCatchEvent(
    condition = "${TODAY == order.createdDate + N days}",
    eventDefinitionType = "timer",
    cronExpression = "0 0 9 * * ?" // Ежедневно в 09:00
)
public void checkOrdersDaily() {
    List<Order> orders = findUnprocessedOrders();
    
    for (Order order : orders) {
        if (order.isPaid()) {
            sendToWarehouse(order);
        } else if (!order.isCancelled()) {
            cancelOrder(order, "Не оплачен более 3 дней");
        }
    }
}
```

**Преимущества:**
- Автоматическая проверка без участия человека
- Можно настроить расписание (ежедневно, еженедельно и т.д.)
- Процесс реагирует на изменения статуса заказов

### Вопрос 7: Какие метрики можно вывести из BPMN процесса с событиями?

**Ответ:**

Из BPMN процессов с событиями можно получить несколько полезных метрик:

#### 1. **Покрытие событий (Event Coverage)**
> Сколько процентов всех возможных путей через события протестировано?
```
Всего путей через события: 8
Протестировано: 6
Coverage: 75% ✅
```

#### 2. **Частота срабатывания событий**
> Как часто срабатывают промежуточные события (таймеры, сообщения)?
```
Таймерное событие "Проверка заказов": 365 раз в год
Сообщение от доставки: ~1000 раз в месяц
→ Нужно оптимизировать частоту проверок?
```

#### 3. **Время ожидания между событиями**
> Сколько времени процесс ждёт между начальным и промежуточными событиями?
```
Начальное событие → Промежуточное таймерное: 24 часа
→ Слишком долго? Можно уменьшить до 12 часов?
```

#### 4. **Точки отказа (Failure Points)**
> Где процесс может завершиться ошибкой?
```
Конечные события "Ошибка": 3 точки
→ Нужно добавить больше граничных событий для обработки ошибок?
```

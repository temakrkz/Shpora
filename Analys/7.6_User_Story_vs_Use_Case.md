# 7.6 User Story vs Use Case: когда что 📌

> **Короткий ответ**  
> **User Story** — краткое описание функции от лица пользователя ("Как роль, я хочу действие чтобы получить ценность"). Используется в Agile/Scrum для планирования спринтов.  
> **Use Case** — детальное сценарий использования системы с разными вариантами развития событий. Используется для проектирования системы и тестирования.

---

## 💡 Простыми словами

Представьте что вы заказываете пиццу:

**User Story (кратко):**
> "Как голодный человек, я хочу заказать пиццу через приложение чтобы не ходить в магазин"

Это — пожелание от пользователя. Короткое, без деталей.

---

**Use Case (подробно):**
```
Сценарий: Заказ пиццы через приложение

Начало: Пользователь открыл приложение

Основной сценарий:
1. Пользователь выбирает пиццу в меню
2. Приложение показывает доступные размеры и начинки
3. Пользователь выбирает размер "М", добавляет сыр
4. Вводит адрес доставки
5. Выбирает способ оплаты (карта)
6. Вводит данные карты
7. Нажимает "Оформить заказ"
8. Система подтверждает заказ, показывает номер заказа

Конец: Заказ успешно оформлен
```

Это — подробный сценарий того как система работает. Показывает все шаги и варианты развития событий.

---

## 🔍 Подробно

### User Story (Пользовательская история) 📖

**Что это:** Краткое описание функции или фичи от лица пользователя в формате:
> "Как [роль], я хочу [действие] чтобы [получить ценность]"

**Как работает:**
- Пишется на высоком уровне без технических деталей
- Описывает что нужно сделать, а не как именно
- Используется для планирования работы команды (спринтов в Scrum)
- Детали раскрываются позже через обсуждения и уточнения

**Зачем нужно:**
- Быстро описать фичу на понятном всем языке
- Сфокусироваться на ценности для пользователя, а не на реализации
- Легко приоритизировать (что важнее сделать)
- Подходит для гибких методологий где требования могут меняться

**Структура User Story:**
```
Как [роль/пользователь], 
я хочу [действие/функцию], 
чтобы [получить ценность/результат]
```

**Принципы хорошего User Story (INVEST):**
- **I**ndependent — независимая от других фич
- **N**egotiable — обсуждаемая с командой
- **V**aluable — имеет ценность для пользователя
- **E**stimable — можно оценить сколько времени займёт
- **S**mall — достаточно маленькая чтобы сделать за один спринт
- **T**estable — можно проверить на соответствие требованиям

**Когда использовать:**
✅ В Agile/Scrum методологиях  
✅ Для планирования спринтов и бэклога продукта  
✅ Когда нужно быстро описать фичу без деталей  
✅ Когда требования могут меняться в процессе разработки  
❌ Для детального проектирования системы  
❌ Для тестирования (нужны более конкретные критерии)

**Примеры User Story из интернет-магазина:**

> **User Story 1: Поиск товаров**
> Как покупатель, я хочу искать товары по названию чтобы быстро найти нужный товар.

> **User Story 2: Корзина**
> Как покупатель, я хочу добавлять товары в корзину чтобы не оформлять заказ сразу и сравнить несколько товаров.

> **User Story 3: Оплата картой**
> Как покупатель, я хочу оплачивать заказ банковской картой чтобы быстро оформить покупку без визита в банк.

### Use Case (Сценарий использования) 📋

**Что это:** Подробное описание сценария взаимодействия пользователя с системой для достижения конкретной цели. Содержит основные и альтернативные варианты развития событий.

**Как работает:**
- Описывает пошагово как система реагирует на действия пользователя
- Учитывает разные варианты развития событий (что если пользователь ошибся?)
- Может включать роли, предпосылки, постусловия
- Используется для проектирования системы и тестирования

**Зачем нужно:**
- Детально описать поведение системы
- Увидеть все возможные сценарии использования
- На основе Use Cases писать тесты (тестирование по сценариям)
- Понять как система должна реагировать на ошибки и исключения

**Структура Use Case:**
```
Название Use Case: [Действие пользователя]

Роли: [кто использует систему]

Предпосылки: [что должно быть до начала сценария]

Основной сценарий (Happy Path):
1. Шаг 1 → Система реагирует X
2. Шаг 2 → Система реагирует Y
...

Альтернативные сценарии (Alt.):
Alt. 1: Если [условие], то [действие]
Alt. 2: Если пользователь вводит неверный пароль, система показывает ошибку

Постусловия: [что должно быть после завершения сценария]
```

**Когда использовать:**
✅ Для детального проектирования системы  
✅ Для написания тестов (тестирование по сценариям)  
✅ Когда нужно учесть все варианты развития событий  
✅ В документации для разработчиков и тестировщиков  
❌ Для быстрого планирования работы команды  
❌ Когда требования очень быстро меняются

**Пример Use Case из интернет-магазина:**

> **Use Case: Оформление заказа с оплатой картой**
> 
> **Роль:** Покупатель (клиент)
> 
> **Предпосылки:**
> - Пользователь авторизован в системе
> - В корзине есть выбранные товары
> 
> **Основной сценарий:**
> 1. Пользователь нажимает кнопку "Оформить заказ"
> 2. Система показывает страницу оформления заказа
> 3. Пользователь вводит адрес доставки
> 4. Система проверяет адрес, показывает доступные способы доставки
> 5. Пользователь выбирает способ доставки (курьером)
> 6. Система рассчитывает итоговую сумму заказа
> 7. Пользователь нажимает "Перейти к оплате"
> 8. Система открывает форму оплаты картой
> 9. Пользователь вводит данные карты (номер, срок действия, CVV)
> 10. Система проверяет данные карты
> 11. Банк подтверждает операцию
> 12. Система создаёт заказ и показывает номер заказа
> 
> **Альтернативные сценарии:**
> 
> Alt. 1: Если пользователь вводит неверный адрес доставки, система показывает сообщение "Неверный формат адреса"
> 
> Alt. 2: Если способ доставки недоступен для выбранного адреса, система предлагает альтернативные способы
> 
> Alt. 3: Если данные карты неверны, система показывает ошибку и запрашивает повторный ввод
> 
> Alt. 4: Если банк отклоняет операцию, система показывает сообщение "Оплата не прошла" и предлагает другой способ оплаты
> 
> **Постусловия:**
> - Заказ создан в системе с номером заказа
> - Сумма списана со счета пользователя
> - Пользователь получил уведомление о заказе

## ⚖️ Сравнение User Story vs Use Case

| Аспект | User Story | Use Case |
|--------|------------|----------|
| **Цель** | Описать фичу для планирования работы | Детально описать поведение системы |
| **Детальность** | Кратко, без деталей реализации | Подробно, все варианты развития событий |
| **Фокус** | Ценность для пользователя | Взаимодействие с системой |
| **Использование** | Планирование спринтов (Agile) | Проектирование и тестирование системы |
| **Гибкость** | Легко меняется при новых идеях | Менее гибкий, требует изменений |
| **Структура** | Формат "Как... я хочу... чтобы..." | Шаги + альтернативные сценарии |
| **Для кого** | Команда разработки (все роли) | Разработчики и тестировщики |

---

## 🎯 Что важно запомнить аналитику

1. **User Story — это не требование!** Это пожелание от пользователя, детали раскрываются позже через обсуждения
2. **Use Case — это сценарий**, он показывает как система должна работать в разных ситуациях
3. **Используйте оба подхода** в зависимости от этапа:
   - Планирование → User Story (быстро описать фичу)
   - Проектирование/тестирование → Use Case (детально описать поведение)
4. **User Story должен быть INVEST-совместимым** — иначе его сложно оценить и реализовать

## ❓ Типичные вопросы и ответы

**В: В чём главное отличие User Story от Use Case?**  
→ Ответ: User Story — это краткое описание фичи от лица пользователя для планирования работы ("что нужно сделать"). Use Case — это подробный сценарий взаимодействия с системой, показывающий все шаги и варианты развития событий ("как система должна работать").

**В: Когда использовать User Story а когда Use Case?**  
→ Ответ: User Story использую на этапе планирования в Agile/Scrum для описания фич и приоритизации. Use Case использую на этапе проектирования системы и тестирования для детального описания поведения во всех возможных ситуациях.

**В: Можно ли использовать только User Story без Use Case?**  
→ Ответ: Да, в Agile часто используют только User Story с детальными критериями приёмки (Acceptance Criteria). Use Case нужен когда важно учесть все варианты развития событий или когда система сложная.

## 🛠 Практические вопросы для собеседования

**В: Приведите пример User Story из вашего опыта.**  
→ Ответ: "Как покупатель, я хочу фильтровать товары по цене чтобы быстро найти товары в своём бюджете." Эта User Story была добавлена в бэклог продукта и реализована за один спринт. После этого мы обсудили детали с командой и написали критерии приёмки (фильтр должен показывать товары от 100 до 500 рублей, сортировать по возрастанию/убыванию цены).

**В: Как вы пишете хорошие User Story?**  
→ Ответ: Следую принципу INVEST — фича должна быть независимой, обсуждаемой, ценной для пользователя, оцениваемой, маленькой (влезать в один спринт) и тестируемой. Также всегда добавляю критерии приёмки (Acceptance Criteria) которые показывают что именно должно работать после реализации.

**В: Как вы подходите к написанию Use Case?**  
→ Ответ: Сначала определяю цель сценария и роли пользователя. Затем описываю предпосылки (что должно быть до начала). Пишу основной сценарий (happy path) — идеальный вариант когда всё идёт по плану. Добавляю альтернативные сценарии для ошибок, исключений и разных вариантов поведения пользователя. В конце определяю постусловия (что должно быть после завершения).

**В: Как вы проверяете что User Story понят команде?**  
→ Ответ: Провожу демо-сессию где показываю прототип или mockup фичи, обсуждаю детали с разработчиками и тестировщиками. Также использую критерии приёмки (Acceptance Criteria) как чек-лист для проверки готовности фичи.

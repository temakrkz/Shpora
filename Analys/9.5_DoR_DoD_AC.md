# 9.5 DoR, DoD, AC — определения готовности задач в Agile/Scrum

---

## 📌 Короткий ответ

> **DoR (Definition of Ready)** — задача готова к работе: есть описание, макеты, нет открытых вопросов.  
> **DoD (Definition of Done)** — задача полностью завершена: код написан, покрыт тестами, прошёл ревью, выложен в продакшен.  
> **AC (Acceptance Criteria)** — условия приёмки конкретной задачи: конкретные требования к результату работы.

---

## 💡 Простыми словами

### Аналогия с интернет-магазином

| Понятие | Что это значит | Пример из жизни |
|---------|----------------|-----------------|
| **DoR** | "Можно брать в работу" | Задача описана, есть макеты, нет вопросов — можно начинать писать код |
| **DoD** | "Полностью готово" | Код написан, протестирован, проверен коллегами, выложен на сервер |
| **AC** | "Условия, при которых считаем сделанным" | При оплате картой списывается сумма и приходит чек — вот что значит "сделано" для этой задачи |

### Что это такое?

> Это три определения готовности, которые помогают команде понимать: когда задачу можно брать в работу (DoR), когда она считается выполненной (DoD) и какие именно условия должны быть выполнены (AC).

**Пример из жизни:**
- **До работы**: "Нужна кнопка 'Купить'" — недостаточно информации ❌ (нет DoR)
- **В работе**: "Кнопка нарисована, код написан" — в процессе ✅
- **После работы**: "Кнопка работает, тесты пройдены, выложено на сервер" — готово! ✅✅

## 🔍 Подробно

### DoR (Definition of Ready) — задача готова к работе

> **DoR** — это чек-лист готовности задачи к началу разработки. Если задача не соответствует DoR — её нельзя брать в работу.

#### Что входит в DoR?

1. **Чёткое описание задачи**
   - Понятно, что нужно сделать
   - Есть User Story или техническое задание

2. **Необходимые материалы**
   - Макеты/прототипы интерфейсов (если есть фронтенд)
   - API-спецификация (если есть бэкенд)
   - Документация по интеграциям

3. **Нет открытых вопросов**
   - Все требования понятны команде
   - Нет двусмысленностей
   - Вопросы решены или зафиксированы в бэклоге

4. **Оценка задачи**
   - Команда оценила задачу (story points или часы)
   - Понятна сложность и риски

5. **Приоритет**
   - Задача имеет приоритет в спринте
   - Понятно, почему она важна сейчас

#### Пример DoR из интернет-магазина:

```
Задача: "Добавить кнопку 'Купить'"

DoR (проверка перед началом работы):
✅ Описание задачи понятно: "при нажатии товар добавляется в корзину"
✅ Есть макет кнопки с дизайном
✅ API корзины готов и документирован
✅ Команда оценила задачу: 3 story points
✅ Приоритет высокий — в текущем спринте

→ Задача готова к работе! Можно брать в работу. ✅
```

### DoD (Definition of Done) — задача полностью завершена

> **DoD** — это чек-лист готовности задачи к сдаче. Если задача не соответствует DoD — она считается незавершённой, даже если код написан.

#### Что входит в DoD?

1. **Код написан и закоммичен**
   - Код проверен на синтаксические ошибки
   - Зафиксирован в репозитории (commit)

2. **Тесты написаны и проходят**
   - Unit-тесты для нового кода
   - Тесты покрытия граничных случаев
   - Все тесты зелёные (проходят успешно)

3. **Код проверен коллегами (Code Review)**
   - Другой разработчик проверил код
   - Внесены исправления по замечаниям

4. **Задача протестирована**
   - Функциональное тестирование пройдено
   - E2E-сценарии работают корректно
   - Нет критических ошибок

5. **Документация обновлена**
   - API-документация актуализирована (если есть изменения)
   - Коммит-сообщения понятные и информативные

6. **Выложено в окружение**
   - Код развёрнут на тестовом сервере
   - Готов к проверке заказчиком

7. **Нет открытых блокирующих задач**
   - Все зависимости от других задач решены
   - Нет задач, которые могут сломать эту задачу

#### Пример DoD из интернет-магазина:

```
Задача: "Добавить кнопку 'Купить'"

DoD (проверка перед сдачей):
✅ Код написан и закоммичен в репозиторий
✅ Написаны unit-тесты для кнопки (3 теста) — все проходят ✅
✅ Проведён Code Review коллегой — замечания исправлены ✅
✅ Тестировщик проверил функциональность — работает корректно ✅
✅ API-документация обновлена с описанием новой функции ✅
✅ Код выложен на тестовый сервер ✅

→ Задача полностью завершена! Можно сдавать. ✅✅
```

### AC (Acceptance Criteria) — условия приёмки задачи

> **AC** — это конкретные требования к результату работы. Это **'чек-лист того, что должно быть сделано'**, чтобы задача считалась выполненной с точки зрения бизнеса.

#### Что входит в AC?

1. **Функциональные требования**
   - Что именно должна делать функция
   - Какие действия пользователь может совершать

2. **Бизнес-правила**
   - Условия, при которых функция работает корректно
   - Исключения и особые случаи

3. **Нефункциональные требования**
   - Производительность (время отклика)
   - Безопасность (валидация данных)

4. **Интеграционные требования**
   - Как функция взаимодействует с другими системами
   - Какие данные передаются между системами

#### Пример AC из интернет-магазина:

```
Задача: "Добавить кнопку 'Купить'"

AC (условия приёмки):
1. При нажатии кнопки товар добавляется в корзину ✅
2. Счётчик корзины увеличивается на 1 ✅
3. Показывается сообщение "Товар добавлен в корзину" ✅
4. Если товара нет в наличии — показывается ошибка "Нет в наличии" ✅
5. Время отклика < 2 секунды ✅
6. Данные корректно сохраняются в БД ✅

→ Задача выполнена, если все AC выполнены! ✅✅
```

### Связь DoR → Работа → DoD → AC

```
DoR (до работы)     →      В работе       →      DoD (после работы)
"Можно брать"        →    "Идёт работа"   →  "Готово сдать"
                     ↓              ↓            ↓
Описание задачи      Код пишется      Тесты проходят
Макеты готовы        Коммитятся       Code Review
Нет вопросов         Протестируется   Выложено в продакшен
```

### Где используется?

| Понятие | Когда применяется | Кто определяет |
|---------|-------------------|----------------|
| **DoR** | Перед началом работы над задачей | Команда совместно с аналитиком |
| **DoD** | После завершения работы над задачей | Команда (разработчики, тестировщики) |
| **AC** | При постановке задачи | Аналитик/бизнес-заказчик |

### Особенности DoR, DoD и AC

✅ **Это командные чек-листы**  
> DoR и DoD определяются командой совместно. Это не правила одного человека, а договорённость всей команды.

✅ **AC — конкретные условия задачи**  
> AC описывает именно эту задачу, а не общие принципы работы системы.

✅ **DoR предотвращает проблемы на старте**  
> Если задача не соответствует DoR — её нельзя брать в работу. Это экономит время и ресурсы.

✅ **DoD обеспечивает качество**  
> Задача считается выполненной только если она прошла все этапы проверки.

## ⚖️ Плюсы и минусы

### ✅ Плюсы

| Преимущество | Объяснение | Пример из жизни |
|-------------|------------|-----------------|
| **Единое понимание готовности** | Все знают, что значит "готово" | Разработчик не сдает задачу без тестов — это часть DoD |
| **Предотвращение недоделок** | Задачи не уходят в бэклог незавершёнными | Задача "Добавить кнопку" считается выполненной только после Code Review и тестов |
| **Снижение количества багов** | Все проверки зафиксированы заранее | Тесты написаны до начала работы — меньше ошибок в продакшене |
| **Прозрачность процесса** | Понятно, на каком этапе задача | Задача в работе → есть код, но нет тестов. Это нормально! |

### ❌ Минусы

| Недостаток | Объяснение | Пример из жизни |
|-----------|------------|-----------------|
| **Дополнительная бюрократия** | Нужно заполнять чек-листы | На каждый коммит нужно писать понятное сообщение — это время |
| **Может замедлить работу** | Нужно выполнить все условия DoD | Тесты пишутся параллельно с кодом — это может занять больше времени |
| **Не всегда гибко** | Жёсткие правила могут мешать | В экстренной ситуации нужно выложить код, но тестов ещё нет |

## 🎯 Что важно запомнить аналитику

### 1. DoR — это **'можно брать в работу'**

> Если задача не соответствует DoR — её нельзя начинать делать. Это экономит время и ресурсы команды.

**Что я бы делал:**
- Перед постановкой задачи проверяю: есть ли макеты, API-документация, нет ли вопросов?
- Если чего-то не хватает — возвращаю задачу в бэклог на доработку
- Не даю команде брать задачи без DoR

### 2. DoD — это **'полностью готово'**

> Задача считается выполненной только если она прошла все этапы проверки: код, тесты, ревью, выкладка.

**Что я бы делал:**
- Создаю чек-лист DoD вместе с командой
- Убеждаюсь, что каждый разработчик понимает, что входит в DoD
- При приёмке проверяю соответствие DoD

### 3. AC — это **'условия, при которых считаем сделанным'**

> AC описывает конкретные требования к результату работы. Без чётких AC невозможно понять, выполнена ли задача.

**Что я бы делал:**
- Превращаю User Story в конкретные AC
- Убеждаюсь, что AC проверяемы (не "должно быть удобно", а "время отклика < 2 сек")
- Согласовываю AC с бизнесом перед началом работы

### 4. DoR и DoD — командные чек-листы

> Это не правила одного человека, а договорённость всей команды. Все должны понимать и соблюдать их.

**Что я бы делал:**
- Провожу встречу по созданию/обновлению DoR и DoD
- Убеждаюсь, что каждый разработчик понимает эти чек-листы
- Регулярно пересматриваю чек-листы (они могут меняться со временем)

## ❓ Типичные вопросы и ответы

### Вопрос 1: Чем DoR отличается от DoD?

**Ответ:**

| Аспект | DoR (Definition of Ready) | DoD (Definition of Done) |
|--------|---------------------------|--------------------------|
| **Когда применяется** | Перед началом работы над задачей | После завершения работы над задачей |
| **Что проверяет** | Готовность задачи к работе | Полноту выполнения задачи |
| **Пример из интернет-магазина** | "Есть макет кнопки, API готов" → можно брать в работу | "Код написан, тесты пройдены, выложено на сервер" → задача завершена |

**Пример из жизни:**
- **DoR**: Задача описана, есть макеты, нет вопросов — можно начинать писать код ✅
- **DoD**: Код написан, протестирован, проверен коллегами, выложен на сервер — задача завершена ✅✅

---

### Вопрос 2: Что такое AC?

**Ответ:**

> **AC (Acceptance Criteria)** — условия приёмки конкретной задачи. Это конкретные требования к результату работы, которые должны быть выполнены, чтобы задача считалась выполненной с точки зрения бизнеса.

**Пример из интернет-магазина:**
```
Задача: "Добавить кнопку 'Купить'"

AC (условия приёмки):
1. При нажатии кнопки товар добавляется в корзину ✅
2. Счётчик корзины увеличивается на 1 ✅
3. Показывается сообщение "Товар добавлен в корзину" ✅
4. Если товара нет в наличии — показывается ошибка "Нет в наличии" ✅

→ Задача выполнена, если все AC выполнены! ✅✅
```

**Важно:** AC должны быть **конкретными и проверяемыми**. Не "должно работать быстро", а "время отклика < 2 секунды".

---

### Вопрос 3: Кто определяет DoD?

**Ответ:**

> **DoD определяется командой совместно.** Это не правило одного человека, а договорённость всей команды.

**Что я бы делал:**
1. Провёл бы встречу с разработчиками и тестировщиками
2. Обсудил бы, какие этапы обязательны для каждой задачи
3. Создал бы чек-лист DoD на основе договорённости
4. Убедился бы, что каждый разработчик понимает эти правила

**Пример DoD команды:**
```
DoD нашей команды:
✅ Код написан и закоммичен в репозиторий
✅ Написаны unit-тесты (минимум 80% покрытия) — все проходят
✅ Проведён Code Review коллегой — замечания исправлены
✅ Функциональное тестирование пройдено
✅ API-документация актуализирована (если есть изменения)
✅ Код выложен на тестовый сервер
```

---

### Вопрос 4: Какие проблемы возникают при отсутствии DoR и DoD?

**Ответ:**

1. **Непонимание готовности задачи**
   - Разработчик думает, что задача готова, а заказчик — нет
   - Пример: разработчик написал код, но не тесты → заказчик считает задачу незавершённой

2. **Дополнительная работа после сдачи**
   - Задача сдана без тестов → нужно дописывать тесты
   - Это отнимает время и ресурсы

3. **Регрессия (сломанные функции)**
   - Новая функция сломала старую, но никто не заметил
   - Пример: изменение в API сломало отображение товаров

4. **Потеря времени на уточнения**
   - Задача не соответствует DoR → нужно возвращать её на доработку
   - Это сдвигает сроки и раздражает команду

### Вопрос 1: Как бы ты подготовил DoD для команды, которая начинает проект интернет-магазина?

**Ответ:**

Я бы провёл встречу с командой (разработчики, тестировщики, аналитики) и создал чек-лист на основе договорённости:

```
DoD для проекта "Интернет-магазин":

1. Код и репозиторий:
   ✅ Код написан и закоммичен в репозиторий
   ✅ Коммит-сообщения понятные и информативные (что сделано, почему)
   
2. Тестирование:
   ✅ Написаны unit-тесты для нового кода — покрытие > 80%
   ✅ Все тесты проходят успешно (зелёные)
   ✅ Проведено функциональное тестирование по AC
   ✅ E2E-сценарии работают корректно
   
3. Code Review:
   ✅ Код проверен коллегой (минимум один ревью)
   ✅ Замечания исправлены, ревью пройдено
   
4. Документация:
   ✅ API-документация актуализирована (если есть изменения в API)
   ✅ README обновлён с описанием изменений
   
5. Развёртывание:
   ✅ Код выложен на тестовый сервер
   ✅ Тесты проходят в окружении (не только локально)
   
6. Интеграции:
   ✅ Все интеграционные тесты пройдены (платёжный шлюз, уведомления и т.д.)
   ✅ Нет ошибок при взаимодействии с внешними сервисами

→ Задача считается выполненной только если все пункты выполнены! ✅✅
```

**Что я бы уточнил у команды:**
1. Какое минимальное покрытие тестами (80%, 90%?)
2. Обязательно ли E2E-тестирование для каждой задачи?
3. Кто проводит Code Review и как часто?
4. Нужно ли обновлять документацию для каждой задачи или только для крупных изменений?

### Вопрос 2: Задача в спринте не соответствует DoR — что ты сделаешь?

**Ответ:**

Я бы **не дал команде брать эту задачу в работу**:

1. **Объяснил бы, почему задача не готова**
   - "Нет макета кнопки — разработчики не знают, как она должна выглядеть"
   - "API ещё не документирован — бэкенд не может начать работу"

2. **Предложил бы варианты решения:**
   ```
   Вариант 1: Вернуть задачу в бэклог на доработку
     → Сначала подготовить макеты и API-документацию
     → Затем снова оценить DoR
   
   Вариант 2: Разделить задачу на части
     → Бэкенд может начать работу без макета (API готов)
     → Фронтенд ждёт макетов — задача в бэклог
   
   Вариант 3: Упростить задачу до минимально жизнеспособной версии (MVP)
     → Сделать базовую кнопку без дизайна
     → Добавить дизайн позже
   ```

3. **Убедился бы, что все вопросы решены**
   - "Есть ли у вас ещё вопросы по задаче?"
   - "Что нужно подготовить дополнительно?"

4. **Проверил бы DoR перед началом работы**
   - После доработки снова проверил чек-лист DoR
   - Только после этого дал команду брать задачу в работу

### Вопрос 3: Как бы ты объяснил разработчику, почему задача считается незавершённой без тестов?

**Ответ:**

Я бы сказал:

> "Представь, что мы строим дом для клиента.
>
> **Код — это стены дома**. Без стен дом не стоит.
> **Тесты — это проверка качества строительства**:
> - Стены ровные ✅
> - Окна открываются ✅
> - Электрика работает ✅
>
> Если мы сдадим дом без проверки, клиент может обнаружить проблемы:
> - Окно заклинило → нужно переделывать
> - Электрика не работает → нужно перекладывать провода
>
> **DoD — это правила сдачи дома**: стены должны быть, окна должны открываться, электрика должна работать. Без этого дом считается незавершённым."

**Пример из интернет-магазина:**
```
Задача: "Добавить кнопку 'Купить'"

Без тестов:
→ Кнопка работает у разработчика локально ✅
→ Но что если в продакшене она не работает? ❓
→ Что если при нажатии сломается корзина? ❓
→ Что если данные не сохранятся в БД? ❓

С тестами:
→ Мы знаем, что кнопка работает корректно во всех сценариях ✅✅
→ Если что-то сломается — мы это обнаружим до релиза ✅✅
```

---

### Вопрос 4: Как бы ты поступил, если команда хочет упростить DoD для скорости?

**Ответ:**

Я бы **не согласился на необоснованное упрощение**:

1. **Выяснил бы причины предложения**
   - "Почему вы хотите убрать тесты из DoD?"
   - "Что именно замедляет процесс сейчас?"

2. **Объяснил бы риски:**
   ```
   Риск 1: Баги в продакшене
     → Без тестов мы не знаем, работает ли код корректно
     
   Риск 2: Дополнительные затраты на исправление
     → Исправление бага в продакшене стоит в 10 раз дороже, чем до релиза
     
   Риск 3: Потеря доверия заказчиков
     → Много багов → клиенты не доверяют системе
   ```

3. **Предложил бы альтернативы:**
   - "Можно ли упростить процесс Code Review (например, сократить время с 2 дней до 1 дня)?"
   - "Можно ли автоматизировать некоторые проверки (CI/CD)?"
   - "Можно ли изменить приоритеты: тесты пишутся параллельно с кодом, а не после?"

4. **Предложил бы пилотное упрощение:**
   - "Давайте попробуем убрать одно условие из DoD на один спринт"
   - "Посмотрим, что произойдёт: сколько багов попадёт в продакшен?"
   - "Если всё хорошо — можно рассмотреть постоянное изменение"

5. **Привлёк бы бизнес-заказчика:**
   - "Как вы относитесь к упрощению DoD? Сколько багов допустимо в продакшене?"
   - "Что для вас важнее: скорость разработки или качество продукта?"
